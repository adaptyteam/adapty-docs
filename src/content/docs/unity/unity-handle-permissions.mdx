A [flow](adapty-flow-builder) can ask users for a system permission with the **Request permission** action. For example, a flow can ask for push notifications on an onboarding screen that explains them, or for camera access before a feature that scans documents. The Adapty SDK doesn't show the system permission dialog itself. It passes the permission request to an `IAdaptyUISystemRequestsHandler` implementation in your app. Your app shows the dialog and passes the result back to the flow. The flow then continues.

## Before you start

You need:

- **Adapty Unity SDK 4.1.0 or later**: Earlier versions don't have the `IAdaptyUISystemRequestsHandler` interface with this signature. On Android, the version depends on the entry point of the app:
  - **UnityPlayerActivity**: Use 4.1.0 or later.
  - **GameActivity**, the default for new Unity 6 projects: Use 4.3.0-beta.1 or later, which requires Unity 6. With 4.1.x, the Adapty SDK doesn't call your handler in such an app.
- **A flow with the Request permission action**: In the Flow & Paywall Builder, add the **Request permission** action to an element's **On Tap** or **On Screen Appear** trigger. In the action, select the permission in the **Permission** field. Add the actions for each result. The default **After response** action is **Navigate Next**. For the action settings, see [Request permission](onboarding-actions#request-permission).
- **For notifications on iOS**: The [Mobile Notifications](https://docs.unity3d.com/Packages/com.unity.mobile.notifications@latest) package, which the handler in this guide uses to show the iOS dialog. In **Project Settings > Mobile Notifications > iOS**, turn off **Request Authorization on App Launch**, so that the dialog appears when the flow asks for it.
- **The declarations of the permissions that your handler requests**: On iOS, a purpose string: the text in `Info.plist` that tells users why your app needs the permission. On Android, a permission in the Android manifest. See [Declare the permissions](#declare-the-permissions).
- **For notifications on Android**: A target API level of 33 or higher in **Player Settings**. Only apps that target Android 13 or later choose when the notification permission dialog appears.
- **Native plugins**: On Android, the handler requests permissions through a small Java library in `Assets/Plugins/Android`. On iOS, most permissions need an Objective-C plugin file. This guide includes the Java library and the plugin for location while using the app.

:::note
**If your handler already requests push notifications**: For `respond(false, null)`, the flow runs the **After response** actions. To have the flow run the **When denied** actions for users who decline, call `respond(false, "denied")`. To request other permissions, add their cases to the handler.
:::

## How the flow requests a permission

1. The flow reaches the **Request permission** action: the user taps the element, or the screen appears.
2. The Adapty SDK calls the `FlowViewDidAskPermission` method of your handler with the permission selected in the action, such as `push` or `camera`.
3. Your app requests the permission from the OS and calls the `respond` callback once with the result.

<FlowPermissionAnswers />

The flow waits on the screen until your app calls the `respond` callback. If your app never calls it, the flow stays on the screen. If the user already granted or declined the permission, the OS shows no dialog and returns the permission state to your app at once. Your app then calls the `respond` callback, and the flow runs the actions for the result right away. If those actions leave the screen, the user sees the screen that requests the permission only for a moment.

The flow sends one permission request at a time. [The trigger of the action](onboarding-actions#request-permission) decides how often the flow sends the request. Your handler can receive the same permission again, for example on each tap: call the `respond` callback with the result that matches the current permission state.

## Implement the handler

:::warning
**Request only the permissions that your app declares, and call `respond(false, "unsupported")` for any other permission.** For most permissions, iOS terminates the app when the app requests a permission whose purpose string is missing from `Info.plist`. A flow author can add a request for any permission at any time, and the flow also reaches app versions released before the request was added.
:::

To pass the results of permission requests to the flow, implement the `IAdaptyUISystemRequestsHandler` interface. The handler in `FlowSystemRequestsHandler.cs` requests push notifications and camera access. For every other permission, it calls `respond(false, "unsupported")` without a dialog:

```csharp showLineNumbers title="FlowSystemRequestsHandler.cs"
using System;
using System.Collections.Generic;
using AdaptySDK;
using UnityEngine;

public partial class FlowSystemRequestsHandler : MonoBehaviour, IAdaptyUISystemRequestsHandler
{
    public void FlowViewDidAskPermission(
        AdaptyUIFlowView view,
        string permission,
        IReadOnlyDictionary<string, string> customArgs,
        Action<bool, string> respond
    ) {
        try
        {
            switch (permission)
            {
                case "push": RequestPush(respond); return;
                case "camera": RequestCamera(respond); return;
                // Add a case for each permission that your app requests.
                default:
                    // A permission this app version doesn't request: pass the result without a dialog.
                    respond(false, "unsupported");
                    return;
            }
        }
        catch (Exception e)
        {
            // Without a result, the flow stays on the screen.
            Debug.LogException(e);
            respond(false, null);
        }
    }

    public void FlowViewDidRequestAppReview(AdaptyUIFlowView view)
    {
        // Shows the native store review prompt, as the SDK does without a handler.
        AdaptyUI.RequestAppReview(null);
    }
}
```

The handler calls the `RequestPush()` and `RequestCamera()` methods: copy them, and the shared methods that they call, from [Code for each permission](#code-for-each-permission). To request another permission, add its case to the `switch` statement, and write the method that the case calls. The class is `partial`, so the code of each permission is a separate file.

The `FlowViewDidAskPermission` method receives:

- **`view`**: The flow view that sent the request.
- **`permission`**: The permission selected in the action, as a string from the **Value** column in [Declare the permissions](#declare-the-permissions).
- **`customArgs`**: Custom arguments of the request. The **Request permission** action sends none, so the value is `null`.
- **`respond`**: The callback that passes the result to the flow.

To pass the result to the flow:

1. In the `FlowViewDidAskPermission` method, show the system dialog.
2. Call the `respond` callback with `true` if the user granted the permission, and `false` otherwise.
3. To have the flow run the **When denied** actions, pass `"denied"`, `"restricted"`, or `"permanently_denied"` as the second argument of the `respond` callback. For example, `respond(false, "permanently_denied")`. With `null` as the second argument, the flow runs the **After response** actions.

<FlowPermissionStrings />

With `true`, pass the string as the second argument too. For example, `respond(true, "limited")`.

Call the `respond` callback exactly once for each permission request. The Adapty SDK ignores a second call and prints a warning to the Unity console. The `respond` callback is safe to call from any thread. On Android in 4.1.x, call it on Unity's main thread: from another thread, the result reaches the flow only after the flow closes.

If the `FlowViewDidAskPermission` method throws before it calls the `respond` callback, the Adapty SDK logs the exception and passes no result to the flow, so the flow stays on the screen. Catch exceptions and call `respond(false, null)`, as `FlowSystemRequestsHandler.cs` does.

The `IAdaptyUISystemRequestsHandler` interface also requires the `FlowViewDidRequestAppReview` method. With a handler registered, the Adapty SDK doesn't request a store review on its own, so call `AdaptyUI.RequestAppReview(null)` in it to keep the native review prompt, as in the example.

## Register the handler

:::warning
**Without a handler, the flow stops at the permission request.** If your app registers no handler, the Adapty SDK passes no result to the flow, on iOS and on Android, and the Unity console shows the warning `System requests handler is not set`. The flow stays on the screen that sent the request and doesn't run the **When allowed**, **When denied**, or **After response** actions.
:::

To send the permission requests from all flows to your handler, register it with the `Adapty.SetSystemRequestsHandler()` method before you present a flow. Register it in the same place as the [flows events listener](unity-handle-paywall-actions#set-up-the-flows-events-listener). Attach the handler to a GameObject that lives as long as your app, and add these methods to the handler class:

```csharp showLineNumbers title="Unity"
void Awake()
{
    DontDestroyOnLoad(gameObject);
    Adapty.SetSystemRequestsHandler(this);
}

void OnDestroy()
{
    Adapty.SetSystemRequestsHandler(null);
}
```

The `Adapty.SetSystemRequestsHandler()` method keeps one handler for every flow in the app. A second call replaces the first handler, and `null` removes it.

## Test the permission request

iOS shows most permission dialogs only once per app install. Android stops showing a permission dialog after the user grants the permission or declines it twice. To see the dialog again while you test the flow, delete the app from the device and install it again. Then open the flow and reach the **Request permission** action.

- **The screen stays, and no dialog appears**: Your app passed no result to the flow. Make sure that your app registers the handler before it presents the flow.
- **On Android, the flow moves on without a dialog**: Make sure that the manifest declares the permission. For notifications, the app must also target API level 33 or higher.
- **On Android, the dialog appears, but the flow stays after the user grants or declines the permission**: Make sure that the app requests the permission with the `FlowPermissions` plugin, and that a minified build has its keep rules.

## Code for each permission

This section has the code for push notifications, camera access, and location while using the app. The code of each permission is a C# file and, where iOS needs it, a native plugin file.

The code for other permissions follows the same patterns. To request another permission, look up its Unity API or plugin in [Unity APIs and plugins for each permission](#unity-apis-and-plugins-for-each-permission). Then write its code like [Camera](#camera) for a Unity API, or like [Location while using the app](#location_when_use) for a native plugin. For what to request and which result to pass, see System permissions on [iOS](ios-system-permissions) and [Android](android-system-permissions).

### Add the shared methods

The code of each permission uses shared methods. Add them once:

- **On Android**: The `RequestAndroid()` method requests runtime permissions with a small Java plugin. When the user doesn't grant access, the method selects the string by the [rules for every permission](android-system-permissions#rules-for-every-permission). It calls the `shouldShowRequestPermissionRationale()` method before and after the permission request. It also keeps a flag in a `SharedPreferences` file for each permission that the app requested before.
- **On iOS**: Unity has no API for most permissions, so a [native plugin](https://docs.unity.com/en-us/engine/current/manual/platform-specific/iphone/ios-developing/plugins-for-ios/ios-native-plugin-call) requests them. The plugin of each permission is an Objective-C or Swift file in `Assets/Plugins/iOS`, which Unity adds to the Xcode project. The C# file of each permission calls its plugin function with the `[DllImport("__Internal")]` attribute, and the `RequestNative()` method passes the result to the flow, with the string from the plugin callback. The plugins use iOS 15 APIs: set **Target minimum iOS Version** in **Player Settings > iOS > Other Settings** to 15.0 or later.

With the string `denied` or `permanently_denied`, the flow runs the **When denied** actions. The two strings only differ in the `outcome` property of the `flow_permission_answered` event. The `RequestAndroid()` method tells them apart with the `shouldShowRequestPermissionRationale()` method. Its flags matter in one case. When the user closes the first dialog without a choice, the `RequestAndroid()` method passes a not-granted result without a string. The flow then runs the **After response** actions, not the **When denied** actions.

```csharp showLineNumbers title="FlowSystemRequestsHandler.Helpers.cs"
using System;
using System.Collections;
using System.Collections.Generic;
using UnityEngine;
#if UNITY_ANDROID
using UnityEngine.Android;
#endif

public partial class FlowSystemRequestsHandler
{
#if UNITY_IOS
    // The callback of every native function in Assets/Plugins/iOS.
    public delegate void NativePermissionCallback(int requestId, string status);

    static readonly Dictionary<int, Action<bool, string>> nativeRequests = new Dictionary<int, Action<bool, string>>();
    static int lastNativeRequestId;

    // Calls a native request function and passes the result with its string to the flow.
    static void RequestNative(Action<int, NativePermissionCallback> nativeRequest, Action<bool, string> respond)
    {
        int requestId;
        lock (nativeRequests)
        {
            requestId = ++lastNativeRequestId;
            nativeRequests[requestId] = respond;
        }
        nativeRequest(requestId, OnNativeAnswer);
    }

    [AOT.MonoPInvokeCallback(typeof(NativePermissionCallback))]
    static void OnNativeAnswer(int requestId, string status)
    {
        Action<bool, string> respond;
        lock (nativeRequests)
        {
            if (!nativeRequests.TryGetValue(requestId, out respond)) return;
            nativeRequests.Remove(requestId);
        }
        respond(status == "granted" || status == "limited" || status == "provisional", status);
    }

    // Runs a coroutine that passes the result of a request. If the coroutine throws, passes the result without a string.
    static IEnumerator AnswerOnException(IEnumerator routine, Action<bool, string> respond)
    {
        while (true)
        {
            object current;
            try
            {
                if (!routine.MoveNext()) yield break;
                current = routine.Current;
            }
            catch (Exception e)
            {
                Debug.LogException(e);
                respond(false, null);
                yield break;
            }
            yield return current;
        }
    }
#endif

#if UNITY_ANDROID
    // The Java plugin in Assets/Plugins/Android/FlowPermissions.androidlib.
    const string FlowPermissionsPlugin = "com.example.flowpermissions.FlowPermissions";

    // Starts tracking the activity on screen, so that a request goes to the flow's activity.
    [RuntimeInitializeOnLoadMethod]
    static void StartFlowPermissionsPlugin()
    {
        if (Application.platform != RuntimePlatform.Android) return;
        using (var plugin = new AndroidJavaClass(FlowPermissionsPlugin))
        using (var activity = AndroidActivity())
            plugin.CallStatic("start", activity);
    }

    static int AndroidSdkInt()
    {
        using (var version = new AndroidJavaClass("android.os.Build$VERSION"))
            return version.GetStatic<int>("SDK_INT");
    }

    static AndroidJavaObject AndroidActivity()
    {
        using (var player = new AndroidJavaClass("com.unity3d.player.UnityPlayer"))
            return player.GetStatic<AndroidJavaObject>("currentActivity");
    }

    static bool AndroidHasFeature(string feature)
    {
        using (var activity = AndroidActivity())
        using (var packageManager = activity.Call<AndroidJavaObject>("getPackageManager"))
            return packageManager.Call<bool>("hasSystemFeature", feature);
    }

    // Requests one permission: granted when the user allows it.
    static void RequestAndroid(string permission, Action<bool, string> respond)
    {
        RequestAndroid(
            new[] { permission },
            () => Permission.HasUserAuthorizedPermission(permission) ? "granted" : null,
            respond);
    }

    // Requests several permissions in one dialog. currentStatus returns "granted" or "limited"
    // for access, "denied" for a refusal, or null for no access: then the rationale rules decide.
    static void RequestAndroid(string[] permissions, Func<string> currentStatus, Action<bool, string> respond)
    {
        if (currentStatus() == "granted")
        {
            respond(true, "granted");
            return;
        }
        var rationaleBefore = ShouldShowRationale(permissions);
        var requestedBefore = MarkRequested(permissions);
        var callback = new PermissionResultCallback(outcome =>
        {
            try
            {
                var status = currentStatus();
                if (status == "granted" || status == "limited") respond(true, status);
                else if (status != null) respond(false, status);
                // No activity on screen could show the dialog.
                else if (outcome == "failed") respond(false, null);
                // A rationale before or after the request: the user declined the dialog.
                else if (rationaleBefore || ShouldShowRationale(permissions)) respond(false, "denied");
                // Android returned no result: the user closed the dialog without a choice.
                else if (outcome == "dismissed") respond(false, null);
                // No rationale before or after a repeated request: Android showed no dialog.
                else if (requestedBefore) respond(false, "permanently_denied");
                // No rationale before or after the first request: the user closed the dialog.
                else respond(false, null);
            }
            catch (Exception e)
            {
                Debug.LogException(e);
                respond(false, null);
            }
        });
        using (var plugin = new AndroidJavaClass(FlowPermissionsPlugin))
            plugin.CallStatic("request", permissions, callback);
    }

    static bool ShouldShowRationale(string[] permissions)
    {
        using (var plugin = new AndroidJavaClass(FlowPermissionsPlugin))
            return plugin.CallStatic<bool>("shouldShowRationale", new object[] { permissions });
    }

    // The plugin calls it when a request ends: on Unity's main thread with UnityPlayerActivity,
    // and on the Android main thread with GameActivity.
    class PermissionResultCallback : AndroidJavaProxy
    {
        readonly Action<string> onOutcome;

        public PermissionResultCallback(Action<string> onOutcome)
            : base(FlowPermissionsPlugin + "$Callback")
        {
            this.onOutcome = onOutcome;
        }

        [UnityEngine.Scripting.Preserve]
        public void onResult(string outcome) => onOutcome(outcome);
    }

    // Returns whether the app requested any of the permissions before, and remembers this request.
    static bool MarkRequested(string[] permissions)
    {
        using (var activity = AndroidActivity())
        using (var preferences = activity.Call<AndroidJavaObject>("getSharedPreferences", "flow_permissions", 0))
        using (var editor = preferences.Call<AndroidJavaObject>("edit"))
        {
            var requestedBefore = false;
            foreach (var permission in permissions)
            {
                requestedBefore |= preferences.Call<bool>("getBoolean", permission, false);
                editor.Call<AndroidJavaObject>("putBoolean", permission, true).Dispose();
            }
            editor.Call("apply");
            return requestedBefore;
        }
    }
#endif
}
```

:::warning
**On Android, request permissions with the `FlowPermissions` Java plugin, not with the `Permission.RequestUserPermissions()` method.** Otherwise Android reports the user's choice to your handler only after the flow closes, and the flow stays on the screen.
:::

On Android, a flow is a separate activity. The `Permission.RequestUserPermissions()` method requests from the Unity activity behind the flow, and Android reports the user's choice only when that activity returns to the screen. The `FlowPermissions` plugin requests from the activity on screen.

Create the folder `Assets/Plugins/Android/FlowPermissions.androidlib`, which Unity builds as an Android library. Put these files in it:

- **`AndroidManifest.xml`**: The permissions that your handler requests. The Gradle build merges them into the manifest of the app:

  ```xml title="Assets/Plugins/Android/FlowPermissions.androidlib/AndroidManifest.xml"
  <manifest xmlns:android="http://schemas.android.com/apk/res/android">
      <!-- One line for each permission that your handler requests. -->
      <uses-permission android:name="android.permission.POST_NOTIFICATIONS" />
      <uses-permission android:name="android.permission.CAMERA" />
  </manifest>
  ```

- **`project.properties`**: One line, `android.library=true`.
- **`build.gradle`**:


C# calls the plugin and the `NotificationManagerCompat` class only through JNI. When **Minify** is on for a build, R8 removes code that Java doesn't call, so add these keep rules to `proguard-rules.pro` in the same folder:

```text showLineNumbers title="Assets/Plugins/Android/FlowPermissions.androidlib/proguard-rules.pro"
# C# reaches these classes only through JNI, so R8 can't see that they are used.
# If you change the package of the plugin, change it here too.
-keep class com.example.flowpermissions.FlowPermissions {
    public static <methods>;
}
-keep interface com.example.flowpermissions.FlowPermissions$Callback {
    <methods>;
}
# Push notifications on Android 12 and earlier.
-keep class androidx.core.app.NotificationManagerCompat {
    public static androidx.core.app.NotificationManagerCompat from(android.content.Context);
    public boolean areNotificationsEnabled();
}
```

Then add the plugin class in `src/main/java/com/example/flowpermissions` of the same folder. If you change its package, change it in `proguard-rules.pro` and in the `FlowPermissionsPlugin` constant in the C# code too.

```java showLineNumbers title="Assets/Plugins/Android/FlowPermissions.androidlib/src/main/java/com/example/flowpermissions/FlowPermissions.java"
package com.example.flowpermissions;

import android.app.Activity;
import android.app.Application;
import android.os.Bundle;
import android.os.Handler;
import android.os.Looper;

import androidx.activity.ComponentActivity;
import androidx.activity.result.ActivityResultLauncher;
import androidx.activity.result.contract.ActivityResultContracts;

import java.util.Map;
import java.util.concurrent.atomic.AtomicInteger;
import java.util.concurrent.atomic.AtomicReference;

// Requests runtime permissions from the activity on screen. With a flow on screen,
// that is the flow's activity, not the Unity activity behind it.
public final class FlowPermissions {
    public interface Callback {
        // "answered", "dismissed" when the user closed the dialog without a choice,
        // or "failed" when no activity on screen can request permissions.
        void onResult(String outcome);
    }

    private static final AtomicInteger lastRequestId = new AtomicInteger();
    private static volatile Activity resumedActivity;
    private static boolean started;

    // Call once, before a flow opens.
    public static synchronized void start(Activity activity) {
        if (started) return;
        started = true;
        resumedActivity = activity;
        activity.getApplication().registerActivityLifecycleCallbacks(new Application.ActivityLifecycleCallbacks() {
            @Override public void onActivityResumed(Activity a) { resumedActivity = a; }
            @Override public void onActivityDestroyed(Activity a) { if (resumedActivity == a) resumedActivity = null; }
            @Override public void onActivityCreated(Activity a, Bundle state) {}
            @Override public void onActivityStarted(Activity a) {}
            @Override public void onActivityPaused(Activity a) {}
            @Override public void onActivityStopped(Activity a) {}
            @Override public void onActivitySaveInstanceState(Activity a, Bundle state) {}
        });
    }

    public static boolean shouldShowRationale(String[] permissions) {
        Activity activity = resumedActivity;
        if (activity == null) return false;
        for (String permission : permissions) {
            if (activity.shouldShowRequestPermissionRationale(permission)) return true;
        }
        return false;
    }

    // Calls back through the Looper of the calling thread. With UnityPlayerActivity, that is Unity's
    // main thread. With GameActivity, Unity's main thread has no Looper: the callback runs on the
    // Android main thread.
    public static void request(String[] permissions, Callback callback) {
        Looper callerLooper = Looper.myLooper();
        Handler caller = new Handler(callerLooper != null ? callerLooper : Looper.getMainLooper());
        new Handler(Looper.getMainLooper()).post(() -> {
            Activity activity = resumedActivity;
            if (!(activity instanceof ComponentActivity)) {
                caller.post(() -> callback.onResult("failed"));
                return;
            }
            String key = "flow_permissions_" + lastRequestId.incrementAndGet();
            AtomicReference<ActivityResultLauncher<String[]>> launcher = new AtomicReference<>();
            launcher.set(((ComponentActivity) activity).getActivityResultRegistry().register(
                key,
                new ActivityResultContracts.RequestMultiplePermissions(),
                (Map<String, Boolean> result) -> {
                    launcher.get().unregister();
                    // Android returns no results for a dialog closed without a choice.
                    String outcome = result.isEmpty() ? "dismissed" : "answered";
                    caller.post(() -> callback.onResult(outcome));
                }));
            launcher.get().launch(permissions);
        });
    }
}
```

The Objective-C files of the plugins import this header:

```objectivec showLineNumbers title="Assets/Plugins/iOS/FlowPermissions.h"
#import <Foundation/Foundation.h>

// The C# callback: the request ID and the string to pass with the result, or NULL for no string.
typedef void (*FlowPermissionCallback)(int requestId, const char *status);

// Calls the C# callback on the iOS main thread, which is Unity's main thread on iOS.
static inline void FlowPermissionAnswer(FlowPermissionCallback callback, int requestId, const char *status) {
    dispatch_async(dispatch_get_main_queue(), ^{
        callback(requestId, status);
    });
}
```

### Push notifications \{#push\}

Declare the `POST_NOTIFICATIONS` permission on Android. iOS needs no key in `Info.plist`. See System permissions on [iOS](ios-system-permissions#push) and [Android](android-system-permissions#push).

```csharp showLineNumbers title="FlowSystemRequestsHandler.Push.cs"
using System;
using System.Collections;
using UnityEngine;
#if UNITY_IOS
using Unity.Notifications.iOS;
#endif

public partial class FlowSystemRequestsHandler
{
    void RequestPush(Action<bool, string> respond)
    {
#if UNITY_IOS
        StartCoroutine(AnswerOnException(RequestPushOnIOS(respond), respond));
#elif UNITY_ANDROID
        if (AndroidSdkInt() < 33)
        {
            // Android 12 and earlier show no dialog: pass the result from the notification settings.
            using (var activity = AndroidActivity())
            using (var compat = new AndroidJavaClass("androidx.core.app.NotificationManagerCompat"))
            using (var manager = compat.CallStatic<AndroidJavaObject>("from", activity))
            {
                var enabled = manager.Call<bool>("areNotificationsEnabled");
                respond(enabled, enabled ? "granted" : "permanently_denied");
            }
            return;
        }
        RequestAndroid("android.permission.POST_NOTIFICATIONS", respond);
#else
        respond(false, "unsupported");
#endif
    }

#if UNITY_IOS
    IEnumerator RequestPushOnIOS(Action<bool, string> respond)
    {
        switch (iOSNotificationCenter.GetNotificationSettings().AuthorizationStatus)
        {
            case AuthorizationStatus.Authorized:
            case AuthorizationStatus.Ephemeral:
                respond(true, "granted");
                yield break;
            case AuthorizationStatus.Provisional:
                respond(true, "provisional");
                yield break;
            case AuthorizationStatus.Denied:
                // The user declined earlier: iOS shows no alert.
                respond(false, "permanently_denied");
                yield break;
        }

        var options = AuthorizationOption.Alert | AuthorizationOption.Badge | AuthorizationOption.Sound;
        using (var request = new AuthorizationRequest(options, false))
        {
            while (!request.IsFinished)
            {
                yield return null;
            }
            if (!string.IsNullOrEmpty(request.Error)) respond(false, null);
            else respond(request.Granted, request.Granted ? "granted" : "denied");
        }
    }
#endif
}
```

- On iOS, the code uses the [Mobile Notifications](https://docs.unity3d.com/Packages/com.unity.mobile.notifications@latest) package. The package reads the notification settings when the app becomes active, and the `GetNotificationSettings()` method returns that copy. If the user changed the setting in Settings shortly before the request, the copy can be stale, and the code then passes `denied` for a refusal that the user gave before.
- On Android, the code requests the `POST_NOTIFICATIONS` permission with the `FlowPermissions` plugin. The `PermissionRequest` class of Mobile Notifications calls the `Permission.RequestUserPermission()` method, which requests from the Unity activity behind the flow.
- With a granted notification permission, your app can show notifications. To receive push notifications, register the device with your push provider, as your app does outside flows.

### Camera \{#camera\}

Declare the `NSCameraUsageDescription` key on iOS in **Player Settings > iOS > Other Settings > Camera Usage Description**, and the `CAMERA` permission on Android. See System permissions on [iOS](ios-system-permissions#camera) and [Android](android-system-permissions#camera).

```csharp showLineNumbers title="FlowSystemRequestsHandler.Camera.cs"
using System;
using System.Collections;
using UnityEngine;
#if UNITY_ANDROID
using UnityEngine.Android;
#endif

public partial class FlowSystemRequestsHandler
{
    void RequestCamera(Action<bool, string> respond)
    {
#if UNITY_IOS
        StartCoroutine(AnswerOnException(RequestCameraOnIOS(respond), respond));
#elif UNITY_ANDROID
        if (!AndroidHasFeature("android.hardware.camera.any"))
        {
            respond(false, "unsupported");
            return;
        }
        RequestAndroid(Permission.Camera, respond);
#else
        respond(false, "unsupported");
#endif
    }

#if UNITY_IOS
    IEnumerator RequestCameraOnIOS(Action<bool, string> respond)
    {
        if (Application.HasUserAuthorization(UserAuthorization.WebCam))
        {
            respond(true, "granted");
            yield break;
        }
        yield return Application.RequestUserAuthorization(UserAuthorization.WebCam);
        // Unity reports only yes or no: an earlier refusal and a restriction also arrive as "denied".
        var granted = Application.HasUserAuthorization(UserAuthorization.WebCam);
        respond(granted, granted ? "granted" : "denied");
    }
#endif
}
```

- **Differs from System permissions**: On iOS, the `Application.HasUserAuthorization()` method reports only whether the user granted access, so the code never passes `permanently_denied` or `restricted` there. To pass them, call the `AVCaptureDevice.authorizationStatus(for:)` method in a native plugin, as the code for [location while using the app](#location_when_use) does.

### Location while using the app \{#location_when_use\}

Declare the `NSLocationWhenInUseUsageDescription` key on iOS, and the `ACCESS_COARSE_LOCATION` and `ACCESS_FINE_LOCATION` permissions on Android. See System permissions on [iOS](ios-system-permissions#location_when_use) and [Android](android-system-permissions#location_when_use).

```csharp showLineNumbers title="FlowSystemRequestsHandler.LocationWhenInUse.cs"
#endif
    }
```

```objectivec showLineNumbers title="Assets/Plugins/iOS/FlowPermissionLocationWhenInUse.m"
#import <CoreLocation/CoreLocation.h>
#import "FlowPermissions.h"

@interface FlowLocationWhenInUseRequest : NSObject <CLLocationManagerDelegate>
@property (nonatomic) CLLocationManager *manager;
@property (nonatomic) FlowPermissionCallback callback;
@property (nonatomic) int requestId;
@end

static FlowLocationWhenInUseRequest *activeRequest; // keeps the manager alive until the request finishes

@implementation FlowLocationWhenInUseRequest
- (void)locationManagerDidChangeAuthorization:(CLLocationManager *)manager {
    switch (manager.authorizationStatus) {
        case kCLAuthorizationStatusNotDetermined: return; // iOS also calls this when it creates the manager
        case kCLAuthorizationStatusAuthorizedWhenInUse:
        case kCLAuthorizationStatusAuthorizedAlways: [self finish:"granted"]; return;
        case kCLAuthorizationStatusRestricted: [self finish:"restricted"]; return;
        case kCLAuthorizationStatusDenied: [self finish:"denied"]; return;
    }
}

- (void)finish:(const char *)status {
    if (activeRequest != self) return;
    activeRequest = nil;
    self.manager.delegate = nil;
    FlowPermissionAnswer(self.callback, self.requestId, status);
}
@end

void FlowPermissions_requestLocationWhenInUse(int requestId, FlowPermissionCallback callback) {
    dispatch_async(dispatch_get_main_queue(), ^{
        FlowLocationWhenInUseRequest *request = [FlowLocationWhenInUseRequest new];
        request.manager = [CLLocationManager new];
        switch (request.manager.authorizationStatus) {
            case kCLAuthorizationStatusAuthorizedWhenInUse:
            case kCLAuthorizationStatusAuthorizedAlways: FlowPermissionAnswer(callback, requestId, "granted"); return;
            // Includes Location Services turned off: iOS shows no alert.
            case kCLAuthorizationStatusDenied: FlowPermissionAnswer(callback, requestId, "permanently_denied"); return;
            case kCLAuthorizationStatusRestricted: FlowPermissionAnswer(callback, requestId, "restricted"); return;
            case kCLAuthorizationStatusNotDetermined: break;
        }
        request.callback = callback;
        request.requestId = requestId;
        request.manager.delegate = request;
        activeRequest = request;
        [request.manager requestWhenInUseAuthorization];
        // Without NSLocationWhenInUseUsageDescription, iOS never calls the delegate.
        dispatch_after(dispatch_time(DISPATCH_TIME_NOW, 50 * NSEC_PER_SEC), dispatch_get_main_queue(), ^{
            [request finish:NULL];
        });
    });
}
```
