A [flow](adapty-flow-builder) can ask users to allow push notifications with the **Request permission** action. Use it to ask at the moment the user sees why notifications matter, for example on an onboarding screen about reminders.

The Adapty SDK doesn't show the system dialog itself. It passes the request to your app, your app shows the dialog and returns the user's answer, and then the flow continues. This guide shows how to answer the request in Unity.

## Before you start

You need:

- **Adapty Unity SDK 4.1.0 or later**: The `IAdaptyUISystemRequestsHandler` signature in this guide ships in version 4.1.0.
- **A flow with the Request permission action**: In the Flow Builder, add the **Request permission** action to an **On Tap** or **On Screen Appear** interaction. Push notifications are the only permission the action can request.
- **For Android**: The `android.permission.POST_NOTIFICATIONS` permission declared in your Android manifest. Android 13 and later shows the dialog only for a declared permission.
- **For iOS**: The [Mobile Notifications](https://docs.unity3d.com/Packages/com.unity.mobile.notifications@latest) package, which the handler in this guide uses to show the iOS dialog.

:::warning
Register the handler before you present a flow that requests a permission. Without a handler, the SDK sends the flow no answer: the flow stays on that screen and doesn't run its **After response** actions.
:::

## How a flow requests a permission

1. The user taps an element with the **Request permission** action, or opens a screen that has the action on **On Screen Appear**.
2. The SDK calls `FlowViewDidAskPermission` in your handler with the permission `push`.
3. Your app shows the system dialog and calls `respond` once with the user's answer.
4. The flow runs the actions in the **After response** section. It runs the same actions whether the user allowed notifications or not.

If the OS doesn't show the dialog again, for example because the user has allowed notifications before, your app gets the answer at once. The flow then moves on right away, and a screen that requests the permission on **On Screen Appear** only flashes.

With **On Screen Appear**, the flow doesn't send the request again when the user comes back to the screen with a back action. With **On Tap**, the flow sends the request on every tap.

## Implement the handler

To answer permission requests, implement the `IAdaptyUISystemRequestsHandler` interface and register it with `Adapty.SetSystemRequestsHandler()`. Register it early in your app's lifecycle, in the same place where you register the [flows events listener](unity-handle-paywall-actions#set-up-the-flows-events-listener).

```csharp showLineNumbers title="Unity"
using System;
using System.Collections;
using System.Collections.Generic;
using AdaptySDK;
using UnityEngine;
#if UNITY_ANDROID
using UnityEngine.Android;
#endif
#if UNITY_IOS
using Unity.Notifications.iOS;
#endif

public class FlowSystemRequestsHandler : MonoBehaviour, IAdaptyUISystemRequestsHandler
{
    void Start()
    {
        Adapty.SetSystemRequestsHandler(this);
    }

    public void FlowViewDidAskPermission(
        AdaptyUIFlowView view,
        string permission,
        IReadOnlyDictionary<string, string> customArgs,
        Action<bool, string> respond
    ) {
        if (permission != "push") {
            // Answer every request, or the flow waits on this screen.
            respond(false, null);
            return;
        }

#if UNITY_IOS
        StartCoroutine(RequestPushOnIOS(respond));
#elif UNITY_ANDROID
        RequestPushOnAndroid(respond);
#else
        respond(false, null);
#endif
    }

    public void FlowViewDidRequestAppReview(AdaptyUIFlowView view)
    {
        // Shows the native store review prompt, as the SDK does without a handler.
        AdaptyUI.RequestAppReview(null);
    }

#if UNITY_IOS
    private IEnumerator RequestPushOnIOS(Action<bool, string> respond)
    {
        var options = AuthorizationOption.Alert | AuthorizationOption.Badge | AuthorizationOption.Sound;

        // true also registers the app with APNs: the token is in request.DeviceToken.
        using (var request = new AuthorizationRequest(options, true))
        {
            while (!request.IsFinished) {
                yield return null;
            }
            respond(request.Granted, null);
        }
    }
#endif

#if UNITY_ANDROID
    private void RequestPushOnAndroid(Action<bool, string> respond)
    {
        const string postNotifications = "android.permission.POST_NOTIFICATIONS";

        // Android 12 and earlier has no runtime permission for notifications.
        using (var version = new AndroidJavaClass("android.os.Build$VERSION"))
        {
            if (version.GetStatic<int>("SDK_INT") < 33) {
                respond(true, null);
                return;
            }
        }

        if (Permission.HasUserAuthorizedPermission(postNotifications)) {
            respond(true, null);
            return;
        }

        var callbacks = new PermissionCallbacks();
        callbacks.PermissionGranted += _ => respond(true, null);
        callbacks.PermissionDenied += _ => respond(false, null);
#if UNITY_6000_0_OR_NEWER
        callbacks.PermissionRequestDismissed += _ => respond(false, null);
#else
        callbacks.PermissionDeniedAndDontAskAgain += _ => respond(false, null);
#endif
        Permission.RequestUserPermission(postNotifications, callbacks);
    }
#endif
}
```

`FlowViewDidAskPermission` receives:

- **`view`**: The flow view that sent the request.
- **`permission`**: The permission the flow requests. For push notifications, the value is `push`.
- **`customArgs`**: Custom arguments for the request. Flows from the Flow Builder have none, so the value is `null`.
- **`respond`**: The callback that returns the answer to the flow. Pass `true` if the user allowed the permission and `false` otherwise. The second argument is an optional detail string, and `null` is a valid value.

Call `respond` exactly once for each request. The SDK ignores a second call and prints a warning to the Unity console. You can call `respond` from any thread, including an OS permission callback, because the SDK sends the answer from the Unity main thread.

`IAdaptyUISystemRequestsHandler` also requires `FlowViewDidRequestAppReview`. With a handler registered, the SDK doesn't request a store review on its own, so call `AdaptyUI.RequestAppReview` in this method to keep the native review prompt.

`Adapty.SetSystemRequestsHandler()` keeps one handler for every flow in the app. A second call replaces the first handler, and `null` removes it.

:::note
The handler only returns the user's answer to the flow. Sending the device token to your push provider after the user allows notifications stays your app's job.
:::

## Test the permission request

After the user answers the notification dialog, iOS doesn't show it again. Android stops showing it once the user allows notifications or denies them twice. To see the dialog again while you test the flow, reinstall the app or reset its notification permission in the device settings.
