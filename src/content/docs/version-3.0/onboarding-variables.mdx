Variables let you display dynamic content in your flows — product pricing, offer details, and other data that updates based on each user's context. Use them to control element visibility and personalize screen content.

To open the Variable management view, click <Inline id="variables.svg" alt="Variables" /> in the left panel. The view includes three tabs:

- **[Custom](#custom-variables)**: In-flow variables and [custom tags](flow-custom-tags) — variables you can set from your app.
- **[Product](#product-variables)**: Built-in variables that pull localized product and offer data from the store.
- **[Element](#element-variables)**: Variables of elements on the canvas, such as a quiz answer or whether a toggle is on.

## Custom variables

### Create a custom variable

1. Open the <Inline id="variables.svg" alt="Variables" /> Variables panel in the flow builder.
2. Add a new variable — click <Inline id="plus.svg" alt="Plus" />.
3. Configure the variable **Name**.
4. (Optional) To distinguish between different variables, fill in the **Description** field. When you hover over the variable's name in the builder, you'll see the description.
5. Select the **Value Type**: **String**, **Number**, **Boolean**, **Array**, **Date**, or **Formula**. You can only insert a variable into a text element if its type is String, Number, Date, or Formula.
   - **Date**: A calendar day, such as a trial start date. Enter the Initial value as `DD.MM.YYYY`, or pick it in the calendar. In the **Date format** dropdown, select how text elements show the date. See [Formulas](flow-formulas#show-a-date-in-a-text-element).
   - **Formula**: A number or a date that the flow calculates from answers, other variables, and product prices. A formula always depends on other values, so it has no Initial value. Enter the formula in the **Expression** field instead. See [Formulas](flow-formulas).

   <ZoomImage id="flow-variable-value-type.webp" width="300px" alt="The Value Type dropdown with the String, Number, Boolean, Array, Date, and Formula types" />

6. In the **Initial value** field, enter the value the variable holds when the flow starts. For a Date variable, the Initial value is optional. A Formula has no Initial value.
7. (Optional, **String** variables only) To set the variable's value from your app's code, select the **Value comes from outside the app** checkbox. This action is irreversible and locks in the **Value Type**. The variable becomes a [custom tag](flow-custom-tags) — your app needs to set its value when you load the flow. If no value is passed, the users see its initial value as a fallback.
8. Click **Create variable**.

Variables are flow-specific. To use a variable in another flow, create it there too.

When you delete a custom variable that conditions use, the builder asks first. A dialog, such as **Delete “user.goal”?**, lists the conditions that use the variable. If you click **Delete**, these conditions break, and you can't publish the flow until you fix them: pick an existing variable in each condition, or remove the condition.

:::tip
Use dots in names to group related variables — for example, `user.score` or `user.goal`.
:::

<ZoomImage id="create-variable.webp" width="500px" alt="Creating a custom variable" />

### Update a variable via an interaction

:::link
See the [Actions](onboarding-actions) article for more details.
:::

You can update a variable value at runtime by adding a **Set variable** action to any element.

1. Select an element on the canvas.
2. In the **Interactions** tab, click **Add trigger**.
3. Select **On tap** and click **Add action**. From the **Action type** dropdown, select **Set variable**.
4. Click **Add variable**. Select the variable and set the new value.

:::tip
For example, you can assign a different value to `user.goal` based on which quiz answer a user selects, then use that variable to navigate them to a different screen.
:::

<ZoomImage id="update-custom-variable.webp" width="500px" alt="Updating a variable via an interaction" />

## Product variables

Product variables pull localized data directly from the app stores. Use them in text fields to display localized prices, titles, and offer details — or in conditions, to show or hide content based on offer eligibility. When you insert a variable for a specific product, the builder adds that product to the screen's list in the [**Products** panel](paywall-product-block#add-products-to-a-screen).

| Variable | Description | Example |
| :--- | :--- | :--- |
| `prod_title` | Localized title of the product | Premium Subscription |
| `prod_price` | Localized price for one billing period | $9.99 |
| `prod_price_per_day` | Subscription price converted to one day. Empty for non-subscriptions. | $0.33 |
| `prod_price_per_week` | Subscription price converted to one week. Empty for non-subscriptions. | $2.33 |
| `prod_price_per_month` | Subscription price converted to one month. Empty for non-subscriptions. | $9.99 |
| `prod_price_per_year` | Subscription price converted to one year. Empty for non-subscriptions. | $119.88 |
| `prod_billing_price` | Localized price of one payment. Differs from `prod_price` only for the [12-month commitment plan](#12-month-commitment-plan). | $9.99 |
| `prod_billing_period` | Localized period of one payment. Differs from the subscription period only for the 12-month commitment plan. Empty for non-subscriptions. | 1 month |
| `offer_price` | Localized price of an intro or promo offer. Empty if the user is not eligible for any offer. | $0.99 |
| `offer_billing_period` | Localized billing period of an offer. Same as `offer_full_duration` for trial and pay-upfront offers. Empty if the user is not eligible. | 1 week |
| `offer_full_duration` | Localized full duration of an offer. Empty if the user is not eligible. | 1 month |
| `offer_price_per_day`, `offer_price_per_week`, `offer_price_per_month`, `offer_price_per_year` | Offer price converted to one day, week, month, or year. A pay-up-front offer's price is spread over its full duration, and a free trial returns a zero price. Empty if the user is not eligible. | $4.24 (`offer_price_per_month`) |
| `intro_price` | Localized price of the first paid phase of an offer. Differs from `offer_price` only for an offer that starts with a free trial. Empty if the offer has no paid phase. See [Free trial followed by an intro price](#free-trial-followed-by-an-intro-price). | $2.99 |
| `intro_billing_period` | Localized billing period of the first paid phase of an offer. Empty if the offer has no paid phase. | 1 month |
| `intro_full_duration` | Localized full duration of the first paid phase of an offer. Empty if the offer has no paid phase. | 3 months |
| `is_free_trial` | Returns `true` if the user is eligible for an offer with a free trial. | true |
| `is_pay_up_front` | Returns `true` if the user is eligible for a pay-up-front offer. | true |
| `is_pay_as_you_go` | Returns `true` if the user is eligible for a pay-as-you-go offer. | true |
| `has_intro_price` | Returns `true` if the user is eligible for an offer with a paid phase: a pay-as-you-go or pay-up-front price. | true |
| `is_monthly_plan` | Returns `true` if the user buys the product under the 12-month commitment plan. | true |

The `prod_price_per_*` variables convert the price from the product's billing period into the period you ask for. The conversion uses fixed period lengths, not calendar dates:

- 1 week = 7 days
- 1 month = 30 days
- 1 year = 12 months, 52 weeks, or 365 days

For a $59.99 monthly subscription, `prod_price_per_week` returns $14.00: $59.99 × 7 ÷ 30 = $13.9977, rounded for display. A month is 30 / 7 ≈ 4.2857 weeks, so multiplying the weekly value by 4 doesn't return the original price.

:::tip
Use `is_free_trial`, `is_pay_up_front`, and `is_pay_as_you_go` with conditional visibility to show or hide elements based on the offer a user is eligible for. For example, show a free-trial timeline only when `is_free_trial` is `true`.
:::

Offer variable values depend on the offer type the user is eligible for. To illustrate, take a weekly subscription called "Premium Subscription" at $5, with three possible offers:

- **Pay As You Go**: First 3 weeks for $3 (billed weekly), then $5/week.
- **Pay Up Front**: First 3 weeks for $8 (billed immediately), then $5/week.
- **Free Trial**: First week free, then $5/week.

In this example, `prod_title` returns "Premium Subscription" and `prod_price` returns $5. The offer variable values depend on which offer the user is eligible for:

| Variable | Pay As You Go | Pay Upfront | Free Trial |
| :--- | :--- | :--- | :--- |
| `offer_price` | $3 | $8 | $0 |
| `offer_billing_period` | 1 week | 3 weeks | 1 week |
| `offer_full_duration` | 3 weeks | 3 weeks | 1 week |

For Pay Upfront and Free Trial offers, `offer_billing_period` and `offer_full_duration` return the same value. For Pay As You Go, they differ because the billing period is one week but the full duration is three weeks.

All of these values come from the store, so the builder preview resolves only some of them: offer values stay unresolved on the canvas, and `is_free_trial`, `is_pay_up_front`, `is_pay_as_you_go`, and `has_intro_price` follow the offer you selected on the product card. See [Preview products and offers](paywall-device-compatibility-preview#preview-products-and-offers) to preview each offer type while you build.

:::note
To learn more about offers and how to configure them, see [Offers](offers).
:::

### Free trial followed by an intro price

A [Google Play offer](google-play-offers) can have two phases: a free trial, and then a discounted price. The `offer_*` variables read the first phase of the offer, so for this offer they describe the free trial. The `intro_*` variables read the first paid phase, so they describe the discounted price.

For example, take a $9.99 monthly subscription with a Google Play offer: the first week free, then $2.99/month for 3 months. For a user eligible for this offer, the variables return:

| Variable | Value |
| :--- | :--- |
| `offer_price` | $0 |
| `offer_full_duration` | 1 week |
| `intro_price` | $2.99 |
| `intro_billing_period` | 1 month |
| `intro_full_duration` | 3 months |
| `is_free_trial` | `true` |
| `has_intro_price` | `true` |

An App Store offer has one phase. For a paid App Store offer, the `intro_*` variables return the same values as the `offer_*` variables. For an App Store free trial, the `intro_*` variables are empty and `has_intro_price` is `false`.

To show the discounted price only to users who get it, put the text with the `intro_*` variables in an element that is [visible](onboarding-element-visibility) only when `has_intro_price` is `true`. Users without a paid phase in their offer then don't see a sentence with empty values.

:::important
For a Google Play offer that starts with a free trial, the `intro_*` variables require Adapty Android SDK v4.4.2 or later, React Native SDK v4.4.0 or later, or Flutter SDK v4.4.1 or later. Other SDK versions pass only the first phase of the offer to the flow, so the `intro_*` variables are empty and `has_intro_price` is `false`. An offer without a free trial has one paid phase, and the `intro_*` variables return its values on every SDK version.
:::

### 12-month commitment plan

With a [12-month commitment plan](set-up-12-month-commitment), subscribers pay for a yearly product in 12 monthly payments. Apple requires the paywall to show both the monthly payment and the yearly total before the purchase. To display both, insert `prod_billing_price` and `prod_billing_period` for the monthly payment, and `prod_price` for the yearly total. For example: "$9.99 per 1 month for 12 months, $119.88 in total".

The values depend on whether the user can buy the commitment plan:

| Variable | Commitment plan applies | Commitment plan doesn't apply, or upfront plan |
| :--- | :--- | :--- |
| `prod_billing_price` | $9.99 | Same as `prod_price` |
| `prod_billing_period` | 1 month | 1 year |
| `prod_price` | $119.88 | $99.99 |
| `is_monthly_plan` | `true` | `false` |

Users who [can't buy the commitment plan](set-up-12-month-commitment#4-add-to-a-flow-or-custom-paywall) buy the upfront plan — for example, on Apple devices earlier than iOS 26.4, or in countries where you don't offer the plan.

:::important
`prod_billing_price` and `prod_billing_period` require Adapty SDK v4.3.1 or later on iOS, or v4.3.0 or later on React Native, Flutter, Unity, or Capacitor. On earlier SDK versions, text with these variables shows `prod_price` and the subscription period instead. For a commitment-plan purchase on Adapty iOS SDK v4.3.0, that's the yearly total and "1 year".
:::

## Element variables

Element variables capture the user's choices — what they selected in quizzes, which tab they are on, and whether a toggle is on.

Element variable types depend on the group:
- **Single choice**: Single choice quizzes, tabs, and toggles:
    - `selectedOptionId`: Element ID to use in conditions
    - `selectedOptionTitle`: Element title to use in dynamic text
- **Multi-choice**: Multi-choice quizzes:
    - `selectedOptionIds`: Element IDs to use in conditions
    - `selectedOptionTitles`: Element titles to use in dynamic text
- **Toggle**: Elements that switch between on and off:
    - `isActive`: Boolean value
- **Product**: Product cards:
    - `selectedProduct`: The selected product, to use in conditions

Common use cases include:
- Displaying different content based on whether the trial toggle is enabled.
- [Navigating users to different screens](onboarding-navigation-branching) based on their quiz answers

## Use variables in text

To insert a variable into a text element:

1. Select a text element on the canvas.
2. In the **Design** tab, find the **Content** field and write your text.
3. Click <Inline id="variables.svg" alt="Variables" /> in the field.
4. Select a variable. On the **Product** tab, products already listed in the **Products** panel come first. The rest of your catalog follows under **Other products**.

:::tip
You can also use variables in other elements:
- Use variables in links and alerts to make them dynamic
- Create dynamic conditions based on variables. For example, the condition can be `if experience.current > experience.target, navigate to...`
:::

<ZoomImage id="insert-var.webp" width="500px" alt="Inserting a variable into a text element" />

### Style variables

You can't apply rich text formatting to a variable on its own. Selecting a variable in the **Content** field and applying bold, italic, underline, strikethrough, or a color change has no effect.

Rich text settings apply only to the whole text block. To style the text, use the **Typography** section of the **Design** tab, or apply a saved [text style](onboarding-text#set-up-text-styles).

### Reuse content across screens

Some content repeats across your flow — a button label like "Continue", a recurring call to action, or a disclaimer shown on several screens. The same applies to longer text, such as a feature description reused across multiple screens. Instead of typing this content into each element, store it in a custom variable. This helps when you navigate different users to different screens but want consistent wording across them.

1. [Create a custom variable](#create-a-custom-variable) of type String and set its initial value to the text you want to reuse. For example, name it `button.navigation` and set the value to `Continue`.
   <ZoomImage id="reuse-create-variable.webp" width="500px" alt="Creating a custom variable with its initial value set to the reusable text" />
2. Insert this variable into the **Content** field of each element where the text should appear.

To change the text everywhere, update the variable's initial value once. Every element that uses the variable updates automatically, so you don't edit each screen by hand.

<ZoomImage id="reuse-insert-variable.webp" width="500px" alt="The same custom variable inserted into the Content field across multiple elements" />

Custom variable values cannot be localized: the variable shows the same value in every locale. To translate the reused text, in the [**Localizations** panel](add-paywall-locale-in-adapty-paywall-builder#translate-strings-manually), replace the variable with the translation in each row that contains it.
