A migration from RevenueCat has six steps. The [Adapty CLI](developer-cli) does the second and third for you: it rebuilds your RevenueCat catalog in Adapty and can have your coding agent replace the RevenueCat SDK in your app.

1. [Learn the core differences](#learn-the-core-differences).
2. [Move your catalog to Adapty](#move-your-catalog-to-adapty) with the CLI.
3. [Replace the RevenueCat SDK](#replace-the-revenuecat-sdk) with your coding agent.
4. [Switch App Store server notifications to Adapty](#switch-app-store-server-notifications-to-adapty).
5. [Test and release a new version of your app](#test-and-release-a-new-version-of-your-app).
6. (Optional) [Import your transaction history](#optional-import-your-transaction-history).

:::info
Your subscribers will migrate automatically

All users who have ever activated a subscription will instantly move to Adapty as soon as they open a new version of your app with Adapty SDK. The subscription status validation and premium access will be restored automatically.
:::

Before you push a new version of your app with Adapty SDK, make sure to check our [release сhecklist](release-checklist).

## Learn the core differences

Adapty and RevenueCat SDKs are similarly designed. The biggest difference is the network usage and the speed: Adapty SDK is designed to provide you with information on demand as fast as possible when you ask for it. For example, when requesting a paywall, you get the [remote config](customize-paywall-with-remote-config) first to pre-build your onboarding or paywall and then request products in a dedicated request.

Naming is slightly different:

| RevenueCat  | Adapty          |
| :---------- | :-------------- |
| Package     | Product         |
| Offering    | Paywall         |
| Paywall     | Paywall Builder |
| Entitlement | Access level    |

Adapty has a concept of [placement](placements). It's a logical place inside your app where the user can make a purchase. In most cases, you have one or two placements:

- Onboarding (because 80% of all purchases take place there);
- General (you show it in settings or inside the app after the onboarding).

## Move your catalog to Adapty

The CLI reads your RevenueCat project and creates a new Adapty app with the same catalog: access levels from entitlements, products from packages, and a paywall and a placement for each offering.

:::tip
A coding agent can run these commands for you. [Install the Adapty CLI and log in](developer-cli-quickstart), then ask the agent to migrate your RevenueCat catalog to Adapty.
:::

### Before you start

- Install the Adapty CLI and log in. See the [CLI quickstart](developer-cli-quickstart) and [Authentication](developer-cli-authentication).
- In RevenueCat, [create a secret API key (v2)](#create-a-revenuecat-secret-api-key) for the project you migrate.
- Check the stores. The CLI migrates App Store and Google Play apps only.

### Create a RevenueCat secret API key

Adapty reads your RevenueCat catalog with a secret API key of the project you migrate. Secret keys in RevenueCat belong to one project, so create the key in that project.

1. To open the key list, in the RevenueCat dashboard, open the project, then go to **API keys**.
2. To create the key, click **New secret API key**.
3. To set up the key, enter a name, for example `Adapty migration`, and choose **V2** in **API version**.
4. To let Adapty read the catalog, set **Project configuration permissions** to **Read only**. Adapty needs no other permissions.
5. To create the key, click **Generate**, then copy it.

:::warning
Use a secret API key, not a public one. A public app-specific key can't read the project configuration.
:::

<ZoomImage id="rc-api-key.webp" width="600px" alt="RevenueCat secret API key form with API version V2 and Project configuration permissions set to Read only" />

When the migration asks for the key, paste it into the Adapty Dashboard page that opens.

### Run the catalog migration

1. To start the migration, create it with the name of the new Adapty app:

   ```bash
   adapty migrations create --name "My App"
   ```

   The CLI saves the migration as current, so the next commands don't need a migration ID.

2. To connect RevenueCat, run `enter_rc_key`. It opens a page in the Adapty Dashboard: paste the secret API key there. The key goes to Adapty directly and never passes through the CLI.

   ```bash
   adapty migrations run enter_rc_key
   ```

3. To choose the RevenueCat apps to migrate, list them, then send their IDs. Choose the apps of one product, usually one per platform: together they become a single Adapty app.

   ```bash
   adapty migrations show apps
   ```

   ```bash
   adapty migrations run resolve_app_mapping --input '{"rc_app_ids":["app1a2b3c","app4d5e6f"]}'
   ```

4. To review the mapping Adapty suggests, show it. Rows with the status `needs_decision` are the ones Adapty couldn't map on its own.

   ```bash
   adapty migrations show mapping
   ```

   Send one decision for each of those rows: `create` migrates the row, `none` leaves it out. If no row needs a decision, send an empty list. Run `adapty migrations status --json` to see every field a decision accepts.

   ```bash
   adapty migrations run resolve_mapping --input '{"decisions":[{"key":"ROW_KEY","action":"none"}]}' --yes
   ```

   :::warning
   Decisions are final. When every row has a decision, Adapty creates the catalog, and you can't change the mapping after that.
   :::

5. To follow the catalog creation, wait for the migration to change state:

   ```bash
   adapty migrations status --wait --timeout 5m
   ```

   Adapty creates access levels, products, paywalls, and placements, in that order. If some of them fail, the status names each failure and the reason. Fix the cause, then run `adapty migrations run retry_catalog_apply`. Entities that already exist stay as they are.

6. To let the new app validate purchases, connect it to the stores in the Adapty Dashboard: [App Store](initial_ios) and [Google Play](initial-android).

For the full list of migration commands and flags, see the [CLI reference](developer-cli-reference#migrations).

### How RevenueCat entities map to Adapty

- An entitlement identifier becomes the access level ID, so `customerInfo.entitlements["premium"]` becomes `profile.accessLevels["premium"]`.
- A product that grants no entitlement grants the `premium` access level.
- An offering identifier becomes the placement ID.
- Offering metadata becomes the paywall's [remote config](customize-paywall-with-remote-config), up to 256 KB.

### What the catalog migration leaves out

- **Offerings with a Paywall Editor paywall**: Adapty can't import a RevenueCat Paywall Editor paywall, so these offerings get no paywall and no placement. Their placement IDs stay free: create a flow or a paywall with the same ID yourself.
- Offerings without products.
- Apps in stores other than App Store and Google Play.
- **Integrations**: Set them up in Adapty as described in [Migrate integrations to Adapty](migrate-integrations-to-adapty).

## Replace the RevenueCat SDK

A coding agent replaces the RevenueCat SDK with the Adapty SDK in your app code, using the `adapty-integration` skill. The CLI can run the agent for you, or you can run the skill yourself in any coding agent.

### With the CLI

The CLI runs Claude Code or Codex on your app's code with the catalog the migration created, so the code uses the exact access level IDs and placement IDs from Adapty.

Before you start:

- Install Claude Code or Codex.
- Open a terminal in the root of your app's git repository, and commit or stash your changes. The CLI refuses to run on uncommitted changes, so the migration stays one reviewable diff.

1. To choose how your app shows paywalls, run one of these:

   - To keep your paywall screens in the app code:

     ```bash
     adapty migrations run choose_paywall_ui --input '{"paywall_ui":"native"}'
     ```

   - To show paywalls as flows from the Flow & Paywall Builder, rebuilt from your current screens (`rebuild`) or designed from scratch around the same products (`new`):

     ```bash
     adapty migrations run choose_paywall_ui --input '{"paywall_ui":"flow_builder","flow_design":"rebuild"}'
     ```

2. To migrate the code, run:

   ```bash
   adapty migrations run migrate_code
   ```

   The CLI installs the Adapty skills into your agent, switches to a branch named `adapty-migrate`, and runs the agent there. The agent commits nothing.

3. To finish the code migration, review the changes on the `adapty-migrate` branch, then work through `ADAPTY_SETUP.md` in the root of your project. It lists what the agent left to you, for example flows to publish before their paywalls show, and integrations to set up.

### With the adapty-integration skill

Use the skill directly to work with a coding agent other than Claude Code or Codex, or to answer the agent's questions as it works instead of letting it run on its own.

1. To give your agent the skill, install it for your tool as described in [SDK integration skill](adapty-sdk-integration-skill).
2. To start the migration, open your app's project in the agent and ask:

   ```text
   Migrate this app from RevenueCat to Adapty with the adapty-integration skill. Use my existing Adapty app "My App".
   ```

   The skill detects your platform and the RevenueCat SDK from the project files, so the prompt needs neither.
3. To finish the code migration, review the agent's changes, then work through `ADAPTY_SETUP.md` in the root of your project.

### Close the migration

When the code uses Adapty, mark the migration as complete:

```bash
adapty migrations close --outcome finish --yes
```

## (Optional) Import your transaction history

The import fills [profiles](profiles-crm) and [charts](charts) with the payment history of your users. It doesn't affect anyone's access.

:::warning
Don't rush the historical data import

You should wait for at least a week after the release with the SDK before doing historical data import. During that time we will get all the info about purchase prices from the SDK, so the data you import will be more relevant.
:::

The CLI offers two ways to import the history, both for the app your catalog migration created. To see them, run `adapty migrations list`.

### With a RevenueCat Cloud Export

RevenueCat delivers a daily export into a bucket Adapty prepares for your app, and Adapty imports every file it receives.

1. To start the import, create the migration with the ID of your Adapty app:

   ```bash
   adapty migrations create --flow transactions --app APP_ID
   ```

2. To connect the export, run `setup_export`. It opens a page in the Adapty Dashboard.

   ```bash
   adapty migrations run setup_export
   ```

   In RevenueCat, open the **Scheduled Data Exports** settings, choose **IAM Role (ARN)** as the credential type, and paste the **External ID** RevenueCat shows into the Adapty page.

3. To finish the export settings in RevenueCat, show the bucket, region, and role ARN Adapty prepared, then enter them in RevenueCat:

   ```bash
   adapty migrations show export-config
   ```

   Turn on **Receive new and updated transactions only**. Otherwise, RevenueCat exports the whole history every day, and Adapty imports every file.

RevenueCat can take up to 24 hours to deliver the first file, and Adapty looks for new files in the bucket every hour. The migration finishes on its own a week after the last file RevenueCat delivers. The Customer User ID of each imported profile is `rc_last_seen_app_user_id_alias`.

### Through support

Use this way if your RevenueCat plan has no Cloud Export: RevenueCat support sends you the export, and Adapty support imports it.

1. To start the import, create the migration with the ID of your Adapty app:

   ```bash
   adapty migrations create --flow transactions_support --app APP_ID
   ```

2. To get the two messages to send, show the guide:

   ```bash
   adapty migrations show support-guide
   ```

3. Send the first message to RevenueCat support. When RevenueCat sends the files, forward them to Adapty support with the second message. Attach the files exactly as RevenueCat sent them: opening, re-saving, or merging them changes the column format the import expects.

### What the import brings over

The following data will imported to Adapty for every transaction:

| Parameter                     | Description                                                  |
| ----------------------------- | ------------------------------------------------------------ |
| user_id                       | Customer User ID, the main identifier of your user in Adapty and your system. |
| apple_original_transaction_id | For subscription chains, this is the original transaction's purchase date, linked by `store_original_transaction_id`. |
| google_product_id             | The product ID in the Google Play Store.                     |
| google_purchase_token         | A unique identifier provided by Google Play for each transaction, required for validation. |
| country                       | The country of the user.                                     |
| created_at                    | The date and time of the user creation.                      |
| subscription_expiration_date  | The date and time when the subscription expires.             |
| email                         | The end user's email.                                        |
| phone_number                  | The end user's phone number.                                 |
| idfa                          | The Identifier for Advertisers (IDFA), assigned by Apple to a user's device. |
| idfv                          | The Identifier for Vendors (IDFV), a code assigned to all apps by one developer and shared across those apps on a device. |
| advertising_id                | A unique identifier provided by the Android OS that advertisers may use for tracking. |
| attribution_channel           | The marketing channel name.                                  |
| attribution_campaign          | The marketing campaign name.                                 |
| attribution_ad_group          | The attribution ad group.                                    |
| attribution_ad_set            | The attribution ad set.                                      |
| attribution_creative          | The attribution creative keyword.                            |

In addition, integration identifiers for the following integrations will be imported: Amplitude, Mixpanel, AppsFlyer, Adjust, and FacebookAds.

### What doesn't come across

- Every transaction is re-validated with the store during import, so rows the store no longer recognizes are dropped.
- Rows without a real store transaction ID — for example, RevenueCat promotional or manually granted entitlements — import as profiles without transactions. To restore such users' access, grant them an access level with the [server-side API](api-adapty/operations/grantAccessLevel).
- Refund and billing-issue history isn't carried over verbatim: a refund keeps only its cancellation date, and a subscription's billing-issue state is recorded as of the import, not with the historical dates.

## FAQ

### I successfully installed Adapty SDK and released a new app version with it. What will happen to my legacy subscribers who did not update to a version with Adapty SDK?

Most users charge their phones overnight, it's when the App Store usually auto-updates all their apps, so it shouldn't be a problem. There may still be a small number of paid subscribers who did not upgrade, but they will still have access to the premium content. You don't need to worry about it and force them to update.

### Do I need to export my historical data from RevenueCat as quickly as possible, or will I lose it?

You don't need to make it super fast; make a release with Adapty SDK first, and then import your history. We will restore the history of your users' payments and fill in [profiles](profiles-crm) and [charts](charts).

### I use MMP (AppsFlyer, Adjust, etc.) and analytics (Mixpanel, Amplitude, etc.). How do I make sure that everything will work?

You first need to pass us the IDs of such 3rd party services via our SDK that you want us to send data to. Read the guide for [attribution integration](attribution-integration) and for [analytics integration](analytics-integration). For historical data and legacy users, **make sure you pass us those IDs from the data you exported from RevenueCat.**
