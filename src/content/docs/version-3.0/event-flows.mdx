A single user action often generates several Adapty events. For example, a new subscription triggers **Subscription started** and **Access level updated**. The diagrams below show which events Adapty sends, and in what order, when a customer buys, renews, cancels, or changes a subscription. To see which events your users trigger, open the [Event Feed](event-feed).

## Rules and limitations

- **Timing.** The App Store renews a subscription up to 24 hours before the billing period ends, so **Subscription renewed** and **Trial converted** can arrive early. The diagrams draw the charge and the start of the period together.
- **Order.** If a single action triggers multiple events, they can arrive in any order. The diagrams draw them in one order, and your [Event Feed](event-feed) may list them in another.
- **Coverage.** Adapty learns about a purchase, a renewal, or a cancellation from a store notification, the Adapty SDK in your app, or the [Server-side API](getting-started-with-server-side-api). The diagrams show the events that these changes trigger. [Synthetic events](events#synthetic-events) don't appear: Adapty sends them on a timer, and the delay differs per integration, so they have no fixed place in a sequence.
- **Integration limitations.** Not all integrations receive all events.
  - To forward an event, [enable it](events#event-list) in integration settings.
  - The **Access level updated** event only reaches your [webhooks](webhook).
  - To view all events from the past two weeks, open the [Event Feed](event-feed).
  - Events that [can't be linked to any user](how-profiles-work#transactions-without-profiles) don't appear in the Event Feed and never reach real-time integrations, such as the webhook. You can include them in [Google Cloud Storage](google-cloud-storage) and [Amazon S3](s3-exports) exports if you turn on **Include events without profile**.

## Subscription lifecycle

### Initial purchase

When a customer starts a new subscription without a trial, Adapty sends:

- **Subscription started**
- **Access level updated** to grant access

What counts as a new subscription depends on the store:

- For App Store subscriptions, all of a customer's purchases in one subscription group belong to the same subscription, even after it expires. So Adapty only sends **Subscription started** for the first purchase in the group.
- For Google Play and web purchases, each new purchase starts a new subscription. So Adapty sends **Subscription started** for each of them, including a repurchase after the old subscription expires.

[Repurchase after expiry](#repurchase-after-expiry) lists the events for a repurchase.

At each renewal, Adapty sends:

- **Subscription renewed** to start a new subscription period
- **Access level updated** to extend access for another period

If a renewal payment fails, the [billing issue sequence](#billing-issues) begins. If the user turns off auto-renewal, the [cancellation sequence](#subscription-cancellation) begins.

### Subscription cancellation

When a user turns off auto-renewal, Adapty sends:

- **Subscription renewal canceled** to mark that the subscription won't renew
- **Access level updated** to mark that access won't renew

The user keeps access until the end of the current period. When it ends, Adapty sends **Subscription expired (churned)**. If a refund is issued before then, Adapty sends the [refund events](#refunds) instead.

- Adapty sends **Subscription renewed** for each remaining monthly payment.

For web purchases, you can cancel the subscription immediately: the user loses access right away, not at the end of the paid period. In this case, Adapty creates these events at the same time:

- **Subscription renewal canceled**
- **Subscription expired (churned)**
- **Access level updated** to remove the user’s access

### Refunds

When a refund is issued, Adapty sends:

- **Subscription refunded**. Its [revenue properties](webhook-event-types-and-fields#event-properties) hold the refunded amount (negative).
- **Access level updated** to revoke access

Whether Adapty sends **Subscription expired (churned)** depends on when the refund comes:

- Before the subscription expires: Adapty sends **Subscription refunded** instead of **Subscription expired (churned)**.
- After the subscription expires, for example after an immediate cancellation: Adapty sends **Subscription refunded** in addition to the earlier **Subscription expired (churned)**.

<ZoomImage id="Subscription_Cancellation_Flow_with_a_Refund.webp" width="700px" alt="Events for a cancellation with a refund" />

Some refunds only cover part of a payment:

- When an App Store subscriber upgrades, Apple refunds the unused part of the old subscription. [Immediate product changes](#immediate-product-change) lists the events.
- If you refund a Google Play payment for a billing period that's already over, Adapty doesn't record the refund. There's no event, and the payment keeps its full amount.
- If you refund the payment for the ongoing billing period, Google revokes the subscription, and Adapty sends **Subscription expired (churned)** with `cancellation_reason` = `refund`. {/* Inferred from code, no test. Confirm with devs. */}
- If you partially refund a Stripe payment, Adapty [doesn't record the refund](stripe#refunds). There's no event, and the payment keeps its full amount in Adapty analytics.
- If you partially refund a Paddle payment, Adapty sends a **Subscription refunded** event for each partial refund. The event's revenue properties hold the refunded amount (negative).

After a partial refund, the user's access depends on the store:

- For App Store subscriptions, you can't refund a payment yourself: customers request refunds from Apple. If you use Adapty's [Refund Saver](refund-saver), it can suggest that Apple refund only the unused part of the billing period. When Apple grants a refund, full or prorated, it revokes the refunded payment, so the user loses access.
- For Google Play subscriptions, if you refund the payment for the ongoing billing period, Google [revokes the subscription](https://support.google.com/googleplay/android-developer/answer/2741495), and the user loses access right away. If you refund a payment for a billing period that's already over, the refund doesn't affect the current subscription status.
- For web purchases, a partial refund only returns money. The subscription keeps running, so the user keeps access, and Adapty sends no **Access level updated**. Adapty can't cancel the subscription for you: cancel it manually in the [Stripe](https://docs.stripe.com/billing/subscriptions/cancel) or [Paddle](https://developer.paddle.com/build/subscriptions/cancel-subscriptions) dashboard, or automate the cancellation through their APIs. In the Stripe Dashboard, you can cancel and refund in one step.

If you revoke the access level through the [Server-side API](api-adapty/operations/revokeAccessLevel), billing continues, and the next renewal restores access.

### Repurchase after expiry

If a subscription expires and the user later subscribes again, the event depends on what they buy:

- An App Store product from a subscription group the user subscribed to before: Adapty sends **Subscription renewed**, even if the duration differs. The purchase keeps the old `original_transaction_id`.
- An App Store product from another group: Adapty sends **Subscription started**, even if the product unlocks the same access level.
- Any Google Play or web purchase: Adapty sends **Subscription started**.

Adapty also sends **Access level updated** to grant access again.

<ZoomImage id="Subscription_Rejoin_Flow.webp" width="700px" alt="Events for a repurchase after expiry" />

### Subscription pause (Google Play only)

A Google Play subscriber can pause a subscription. The pause starts when the current billing period ends, so the user keeps access until then.

1. When the pause starts, Adapty sends:
   - **Subscription paused (Android only)**
   - **Access level updated** to revoke access
2. When the subscription resumes, Adapty sends:
   - **Subscription renewed**
   - **Access level updated** to restore access

The renewal keeps the subscription's `original_transaction_id`.

<ZoomImage id="Subscription_Paused_Flow.webp" width="700px" alt="Events for a subscription pause" />

## Trials

### Trial that leads to conversion

When a user starts a trial, Adapty sends:

- **Trial started**
- **Access level updated** to grant access for the trial period

When the trial ends and the store charges the user for the first period, Adapty sends:

- **Trial converted**
- **Access level updated** to extend access for the subscription period

<ZoomImage id="Trial_Flow_with_Successful_Conversion.webp" width="700px" alt="Events for a trial that converts to a subscription" />

### Trial that leads to a cancellation

When a user turns off auto-renewal before the trial ends, Adapty sends:

- **Trial renewal canceled** to mark that the trial won't convert
- **Access level updated** to mark that access won't renew

The user keeps access until the trial ends. When it ends, Adapty sends **Trial expired**.

<ZoomImage id="Trial_Flow_without_Successful_Conversion.webp" width="700px" alt="Events for a canceled trial" />

### Purchase after an expired trial

If a trial expires and the user later subscribes, the event depends on what they buy:

- An App Store product from the trial's subscription group: Adapty sends **Trial converted**, even if the duration differs. The purchase keeps the trial's `original_transaction_id`.
- An App Store product from another group: Adapty sends **Subscription started**, even if the product unlocks the same access level.
- Any Google Play or web purchase: Adapty sends **Subscription started**.

Adapty also sends **Access level updated** to grant access again.

<ZoomImage id="Subscription_Reactivation_Flow_after_Expired_Trial.webp" width="700px" alt="Events for a purchase after an expired trial" />

## Product changes

A product change switches an active subscription to another product: an upgrade, a downgrade, or a crossgrade within the same subscription group. For App Store subscriptions, a purchase from another group starts a second, separate subscription.

When a product change takes effect, Adapty sends one or more **Access level updated** events:

- If the old and the new product unlock the same access level, Adapty sends one event: the access level now comes from the new product, with a new expiration date.
- If the products unlock different access levels, Adapty sends two: one that removes the old access level, and one that grants the new one.

### Immediate product change

A product change can take effect immediately, before the current period ends. This is typical for upgrades. In this case, the following events fire at the moment of the change:

- For App Store subscriptions:
  - Apple refunds the unused part of the old subscription. The old subscription triggers the **Subscription refunded** event with `cancellation_reason` = `upgraded`. The event's [revenue properties](webhook-event-types-and-fields#event-properties) hold the refunded amount (negative). Adapty sends no **Subscription expired (churned)** event for the old subscription.
  - The new product **does not** count as a new subscription. The first payment triggers **Subscription renewed** instead, or **Trial converted** if the old product was in a trial.
- For Stripe subscriptions, the event sequence is the same — but without an actual refund. Instead, with prorations on, Stripe applies the value of the unused time to the customer's future invoices.
- For Google Play subscriptions:
  - The old purchase triggers the **Subscription renewal canceled** event.
  - The old purchase triggers the **Subscription expired (churned)** event with `cancellation_reason` = `upgraded`. Adapty sends no **Subscription refunded** event.
  - The new product triggers a new subscription, and, with its first payment, a **Subscription started** event. The active [replacement mode](https://developer.android.com/google/play/billing/subscriptions#replacement-modes) determines the event's revenue.

<ZoomImage id="Immediate_Product_Change_Flow_Upgrade.webp" width="700px" alt="Events for an immediate product change" />

### Product change at the next renewal

A product change takes effect at the next renewal in these cases:

- For App Store subscriptions: a downgrade, or a crossgrade to a subscription of the same level with a different duration.
- For Google Play subscriptions: a change with the `DEFERRED` [replacement mode](https://developer.android.com/google/play/billing/subscriptions#replacement-modes).

For App Store subscriptions, scheduling the change triggers no events, not even **Access level updated**: auto-renewal stays on, and only the product of the next renewal changes. The change takes effect at the renewal. Then Adapty sends **Access level updated**, and **Subscription renewed** for the new product's first payment. It sends no **Subscription expired (churned)** for the old one.

For Stripe subscriptions, an upgrade and a downgrade trigger the same events.

## Billing issues

When a renewal or trial conversion payment fails, the store keeps retrying the payment. The events Adapty sends depend on whether a grace period applies.

### With a grace period

When the payment fails, Adapty sends:

- **Billing issue detected**
- **Entered grace period**
- **Access level updated** to extend access until the grace period ends

For App Store and Google Play subscriptions, the store can still collect the payment for up to 60 days after it fails. The grace period is the start of this recovery window. After the grace period ends, the user has no access until the payment succeeds.

The billing issue ends in one of three ways:

- The payment succeeds before the grace period ends: Adapty sends **Subscription renewed** or **Trial converted**, and **Access level updated** to extend access. The user keeps access without a gap.
- The payment succeeds after the grace period ends, but before the end of the recovery window: Adapty sends the same events, and the user regains access.
- The recovery window ends without a payment: Adapty sends **Subscription expired (churned)** or **Trial expired** with `cancellation_reason` = `billing_error`.

<ZoomImage id="Billing_Issue_Outcome_Flow_with_Grace_Period.webp" width="700px" alt="Events for a billing issue with a grace period" />

### Without a grace period

When the payment fails, the user loses access right away, and Adapty sends:

- **Billing issue detected**
- **Access level updated** to revoke access

For App Store and Google Play subscriptions, the store can still collect the payment during a recovery window of up to 60 days after it fails. The billing issue ends in one of two ways:

- The payment succeeds before the end of the recovery window: Adapty sends **Subscription renewed** or **Trial converted**, and **Access level updated** to restore access.
- The recovery window ends without a payment: Adapty sends **Subscription expired (churned)** or **Trial expired** with `cancellation_reason` = `billing_error`.

<ZoomImage id="Billing_Issue_Outcome_Flow_without_Grace_Period.webp" width="700px" alt="Events for a billing issue without a grace period" />

## Sharing paid access between profiles

When a second profile claims a purchase that another profile made, the [Sharing paid access between user accounts](sharing-paid-access-between-user-accounts) setting controls which profiles have access. The events Adapty sends depend on that setting.

:::note
For Apple Family Sharing transactions (`in_app_ownership_type=FAMILY_SHARED`), Adapty only sends **Access level updated** to family members. Subscription events, such as **Subscription started** and **Subscription renewed**, only reach the purchaser. [Apple Family Sharing](apple-family-sharing) lists all the events.
:::

:::note
If a user restores purchases on a profile that already has the access level, Adapty sends no events.
:::

This table shows which events fire when a second profile claims a purchase. The subsections below show the access properties of each event.

| Event | Enabled (default) | Transfer access to new user | Disabled |
| --- | --- | --- | --- |
| New profile: **Access level updated** (`is_active=true`) | Fires | Fires | Does not fire |
| Old profile: **Access level updated** (`is_active=false`) | Does not fire — both profiles keep access | Fires when the new identified device propagates the transaction | Does not fire — the original profile keeps access |
| `profiles_sharing_access_level` property on the new event | Lists the other profiles that share the access level | `null` | Not applicable — no event fires |

In every mode, transactional events, such as **Subscription renewed** and **Subscription refunded**, only appear on the [parent profile](how-profiles-work#parent-and-inheritor-profiles): the first profile that recorded the purchase. Adapty sends **Access level updated** for every profile with an access change. A claim records no new transaction, so it triggers no **Subscription started**.

To compare what each mode guarantees, read the [practical reference](sharing-paid-access-between-user-accounts#practical-reference).

### Shared access between profiles (Enabled)

With the **Enabled (default)** mode, all profiles that use the same store account share the access level. When a new profile claims the purchase, the old profile keeps access, and Adapty sends one event: **Access level updated**, to grant access to the new profile.

<ZoomImage id="Share_Access_Between_Users_Flow.webp" width="700px" alt="Events for shared access" />

The access properties of this event look like this:

- **User B: Access level updated**, sent when User B logs in and receives access:

  ```json showLineNumbers
  {
    "profile_id": "00000000-0000-0000-0000-000000000001",
    "customer_user_id": "UserB",
    "event_properties": {
      "profile_has_access_level": true
    },
    "profiles_sharing_access_level": [
      {
        "profile_id": "00000000-0000-0000-0000-000000000000",
        "customer_user_id": "UserA"
      }
    ]
  }
  ```

### Access moves to the new profile (Transfer access to new user)

With the **Transfer access to new user** mode, only one profile has the access level at a time. When a new profile claims the purchase, Adapty sends two **Access level updated** events:

1. One that revokes the old profile's access
2. One that grants access to the new profile

<ZoomImage id="Transfer_Access_to_New_User_Flow.webp" width="700px" alt="Events for an access transfer" />

The access properties of these events look like this:

- **User A: Access level updated**, sent when User A buys a subscription:

  ```json showLineNumbers
  {
    "profile_id": "00000000-0000-0000-0000-000000000000",
    "customer_user_id": "UserA",
    "event_properties": {
      "profile_has_access_level": true
    },
    "profiles_sharing_access_level": null
  }
  ```

- **User A: Access level updated**, sent when User B logs in after the app is reinstalled, and Adapty revokes User A's access:

  ```json showLineNumbers
  {
    "profile_id": "00000000-0000-0000-0000-000000000000",
    "customer_user_id": "UserA",
    "event_properties": {
      "profile_has_access_level": false,
      "cancellation_reason": "adapty_revoked"
    },
    "profiles_sharing_access_level": [
      {
        "profile_id": "00000000-0000-0000-0000-000000000001",
        "customer_user_id": "UserB"
      }
    ]
  }
  ```

- **User B: Access level updated**, sent when User B receives access:

  ```json showLineNumbers
  {
    "profile_id": "00000000-0000-0000-0000-000000000001",
    "customer_user_id": "UserB",
    "event_properties": {
      "profile_has_access_level": true
    },
    "profiles_sharing_access_level": null
  }
  ```

### Access stays with the purchaser (Sharing access disabled)

With the **Disabled** mode, Adapty ties the purchase to the Customer User ID that was active when the user bought it. When any other profile claims the purchase, that profile receives no access, and Adapty sends no events.

Adapty only ties purchases when they are credited to a profile with a Customer User ID. If the purchaser had no Customer User ID, a new profile that claims the purchase receives access, and Adapty sends **Access level updated** for it.
