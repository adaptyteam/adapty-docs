With the Adapty Mail API, you can send user profiles, purchases, subscription changes, and custom events to Adapty Mail directly from your server. Use the API to:

- Add subscribers when you don't have a base in Adapty Mail yet.
- Reuse the subscriber base from your other apps.
- Feed Adapty Mail server-to-server, with your backend as the source of truth.
- Start and stop email sequences on events from your app, such as a completed onboarding.

:::note
**API or SDK?** Most apps send data to Adapty Mail through the [Adapty SDK](mail-collect-emails): Adapty forwards profiles, emails, and subscription events for them. Choose the API when your app has no Adapty SDK, when the data already lives on your server, or when you import subscribers from another source. You can also use the API alongside another entry point, for example to report [custom events](#report-events-from-your-app) if your app runs the Adapty SDK. Adapty Mail matches people by email address. Two sources reporting the same address land on one profile; two different addresses create separate profiles, even when `customer_user_id` is identical.
:::

## Before you start

:::important
Finish setting up Adapty Mail before you send data — that means a campaign, segments (if you need them), a web paywall, and a launched flow. Profiles you send before you launch the flow don't enter it until their next [entry event](mail-purposes#entry-rules-events-and-conditions-that-activate-a-purpose), such as a purchase, a subscription change, or a profile update. Follow [Get started with Adapty Mail](mail-get-started) first, then return here.
:::

You also need your API key and base URL:

- **Secret API key**: In Adapty Mail, go to **Settings** > **Project** and copy the **Secret key**. The key is project-specific, so the API knows which project the data belongs to.
- **Base URL**: All requests go to `https://api-mail.adapty.io`.
- **Authentication**: Send the key in the **Authorization** header as `Bearer {your_secret_api_key}`.

:::important
Get explicit consent before you collect emails and send them to Adapty Mail. You are responsible for compliance with GDPR, CAN-SPAM, and similar regulations in your markets.
:::

## Send user profiles

A profile carries the user's email and attributes. To create or update one, send a POST request to `/api/v1/profile/save/`.

Three fields are required:
- A stable `external_profile_id` that your app or backend owns
- The `email` Adapty Mail delivers campaigns to
- `external_created_at` — the user creation time, which you can use in segments

:::important
Always send a stable `external_profile_id`, never an anonymous or per-install value. Adapty Mail uses it to link emails, clicks, and purchases to one profile.
:::

If the same person also reaches Adapty Mail through another [entry point](mail-entry-points), send `customer_user_id` — the same user ID that source sends. For the Adapty SDK that's the value you pass to `Adapty.identify()`; FunnelFox sends the one it holds. It doesn't decide which profile they land on; the email address does that. What it adds is a second way to find the profile: a purchase or subscription change you report with `customer_user_id` resolves without an email, and a deletion can name it instead of the address.

If the user declined marketing email, send `"email_consent": false`. Adapty Mail then sends them no marketing email and no [double opt-in](mail-double-opt-in) request; other transactional emails still reach them. Omit the field when you don't have an answer: a profile without one receives marketing email.

```bash
curl --request POST \
  --url 'https://api-mail.adapty.io/api/v1/profile/save/' \
  --header 'Authorization: Bearer {your_secret_api_key}' \
  --header 'Content-Type: application/json' \
  --data '{
    "external_profile_id": "user_12345",
    "external_created_at": "2026-06-01T10:30:00Z",
    "email": "jane@example.com",
    "country": "US",
    "custom_attributes": {
      "signup_source": "referral"
    }
  }'
```

:::note
`country` and `store_country` take a two-letter [ISO 3166-1 alpha-2](https://en.wikipedia.org/wiki/ISO_3166-1_alpha-2) code — `US`, not `USA` or `United States`. Any other value is rejected.
:::

`device_info` describes the user's device. The object is optional, but `platform` must be present whenever you send it.

| Field | Optional | Segment filter | Notes |
| --- | --- | --- | --- |
| `platform` | No | Yes | |
| `device` | Yes | Yes | The device model. |
| `os` | Yes | Yes | |
| `locale` | Yes | Yes | Adapty Mail uses it to decide which translation of a [localized campaign](mail-localization#select-languages) to send. A user with no locale receives the emails in English. |
| `app_version` | Yes | Yes | Compared in version order, so `1.10.0` ranks above `1.9.0`. |
| `timezone` | Yes | No | Sets when the user receives email. Without it, Adapty Mail treats them as UTC, so the 08:00–21:00 send window follows UTC rather than their own day. |

See the [Save profile](api-mail/operations/saveProfile) reference for every available field.

A save that changes an existing profile counts as a **Profile updated** event. This event can start the **Never purchased** [purpose](mail-purposes), unless you remove it from the entry rule of that purpose.

## Report purchases and subscription changes

:::note
Of the eight [purposes](mail-purposes) every project starts with, **Never purchased** by default only needs a profile with an email. The other standard marketing purposes need you to report purchases and subscription changes.
:::

Report purchases, renewals, cancellations, and other subscription changes as you handle them. Adapty Mail uses them to place each profile in the right flow and to attribute revenue.

To record a transaction event (one purchase or subscription change), send a POST request to `/api/v1/profile/transaction-event/save/`. Use the same `external_profile_id` you sent with the profile so Adapty Mail links the event to the right user.

```bash
curl --request POST \
  --url 'https://api-mail.adapty.io/api/v1/profile/transaction-event/save/' \
  --header 'Authorization: Bearer {your_secret_api_key}' \
  --header 'Content-Type: application/json' \
  --data '{
    "event_type": "subscription_started",
    "event_id": "evt_abc123",
    "event_datetime": "2026-06-10T14:20:05Z",
    "external_profile_id": "user_12345",
    "store": "app_store",
    "store_product_id": "premium_monthly",
    "store_transaction_id": "1000000123456789",
    "store_original_transaction_id": "1000000123456789",
    "purchased_at": "2026-06-10T14:20:00Z",
    "originally_purchased_at": "2026-06-10T14:20:00Z",
    "price_usd": "9.99"
  }'
```

See the [Save transaction event](api-mail/operations/saveTransactionEvent) reference for every available field.

You can send a transaction event before the profile exists. Adapty Mail keeps the event unattached, then links it to the profile on the next save that includes the same `external_profile_id`.

### Event types and the purposes they start by default

Send the `event_type` that matches what happened. Adapty Mail derives the state of the profile from its event history. Segments and purpose conditions filter profiles by that state. By default, each event can also start the [purposes](mail-purposes) the table lists for it, unless you edit their entry rules.

| `event_type` | Send it when | Starts by default |
| --- | --- | --- |
| `subscription_started` | A user starts a new subscription. | App activation and Cancellation page |
| `subscription_renewed` | A subscription auto-renews. | Nothing |
| `subscription_renewal_reactivated` | A user turns auto-renew back on. | Nothing |
| `non_subscription_purchase` | A user makes a one-time purchase. | App activation and Cancellation page |
| `subscription_renewal_cancelled` | A user turns off auto-renew (still active until expiry). | Renewal cancelled |
| `billing_issue_detected` | A renewal payment fails. | Billing issue |
| `entered_grace_period` | Payment fails but the user is still in a grace period. | Billing issue |
| `subscription_expired` | A subscription lapses and access ends. | Expired |
| `subscription_refunded` | A subscription purchase is refunded. | Refunded |
| `non_subscription_purchase_refunded` | A one-time purchase is refunded. | Nothing |

By default, `non_subscription_purchase` also ends a **Never purchased**, **Renewal cancelled**, **Expired**, **Billing issue**, or **Refunded** sequence. To change this, edit the [exit rules](mail-purposes#exit-rules) of these five purposes.

### Add payment details for receipts

To send [purchase receipts](mail-email-data#email-a-receipt-after-each-purchase), or other emails that show payment details, add the `payment_context` object to the transaction event. Adapty Mail doesn't read these details from `price_usd` or `store_product_id`. Purchases that the Adapty SDK reports come without payment details. An email that shows the amount or the product only [goes out](mail-email-data#emails-held-back-for-missing-data) for a purchase with `payment_context`.

The `payment_context` object has the following fields:

| Field | Required | Notes |
| --- | --- | --- |
| `amount` | Yes | The amount charged, tax included, such as `9.99`. For a free trial start, send `0`. |
| `currency` | Yes | The currency of `amount`, as a three-letter [ISO 4217](https://en.wikipedia.org/wiki/ISO_4217) code, such as `USD`. |
| `tax_amount` | No | The tax included in `amount`. |
| `method.type` | Yes | The payment method: `card`, `apple_pay`, `google_pay`, `paypal`, `pix`, or `other`. |
| `method.brand` | For `card` | The card brand: `visa`, `mastercard`, `amex`, `discover`, `jcb`, `unionpay`, or `other`. |
| `method.last4` | For `card` | The last four digits of the card number. |
| `product_name` | Yes | The product name for emails, such as `Premium, 1 month`. |

For `apple_pay` and `google_pay`, `method.brand` and `method.last4` are optional. Send them so that emails include the card in the wallet.

Send `payment_context` with the first request for a transaction. When you send the same transaction again, Adapty Mail adds a missing `payment_context`, but never replaces or clears a stored one.

## Report events from your app

You can report anything that happens in your app as a [custom event](mail-purposes#event-triggers-from-your-app), such as a completed onboarding. Use custom events to:

- Start an email sequence, as an entry event of a purpose.
- Stop an email sequence early, as an event in the [exit rule](mail-purposes#exit-rules) of its purpose.
- Show the data of an event in emails, with [custom event placeholders](mail-email-data#custom-event-placeholders).
- Filter users in [segments](mail-segments#available-filter-fields) and purpose conditions by the events they had.

Send purchases and subscription changes as [transaction events](#report-purchases-and-subscription-changes), not as custom events. Store facts about the user in the `custom_attributes` of the [profile](#send-user-profiles).

An event name has up to 64 characters: lowercase letters, digits, and underscores, with a letter first. You can't give a custom event a name that Adapty Mail uses for its own events, such as `subscription_started`. Before your server sends a custom event, type its name under **Custom** in the **Entry rule** or **Exit rule** field of a purpose. Purpose rules only apply to events that Adapty Mail receives after you add the name.

To record a custom event, send a POST request to `/api/v1/profile/custom-event/save/`.

```bash
curl --request POST \
  --url 'https://api-mail.adapty.io/api/v1/profile/custom-event/save/' \
  --header 'Authorization: Bearer {your_secret_api_key}' \
  --header 'Content-Type: application/json' \
  --data '{
    "event_type": "onboarding_completed",
    "event_id": "evt_def456",
    "event_datetime": "2026-06-12T18:45:00Z",
    "external_profile_id": "user_12345",
    "payload": {
      "goal": "Sleep better",
      "steps_completed": "6"
    }
  }'
```

Four fields are required:

- `event_type`: The event name, exactly as typed in the purpose.
- `event_id`: A unique ID for each occurrence, up to 128 characters. Adapty Mail ignores an ID it already has, so retries are safe.
- `event_datetime`: When the event happened, in UTC.
- `external_profile_id`: The `external_profile_id` you sent with the profile.

To show data from the event in emails, send up to 50 string fields in the `payload` object. Each value has up to 1,000 characters. Use the field names that the purpose lists under **Payload fields**. They follow the same character rules as event names. Each field appears in emails through its [custom event placeholder](mail-email-data#custom-event-placeholders), such as `{{ custom_event.goal }}`.

The [Save custom event](api-mail/operations/saveCustomEvent) reference describes every field and the response codes.

You can send a custom event before the profile exists. Adapty Mail links the event to the profile on its next save, and the user can match a purpose at that point.

The [journey](mail-profiles#the-activity-journey) of a profile doesn't list custom events. To verify that a custom event starts a sequence, send it for a test profile. Then look for the first email in the journey of the test profile.

## Delete a profile

To fulfil a right-to-erasure request, send the profile's identifiers to `/api/v1/profile/delete/`. Adapty Mail erases the profile's personal data and cancels its scheduled emails.

```bash
curl --request POST \
  --url 'https://api-mail.adapty.io/api/v1/profile/delete/' \
  --header 'Authorization: Bearer {your_secret_api_key}' \
  --header 'Content-Type: application/json' \
  --data '{
    "external_profile_id": "user_12345"
  }'
```

Identify the profile by `external_profile_id`, `customer_user_id`, or `email` — send at least one. Adapty Mail clears the stored data, but it doesn't block the address: if a source sends it again, a new profile appears with no history. To keep someone out for good, stop the source from sending their data.

A delete request that times out leaves you unsure whether it landed, so you send it again. That second call is safe when you identify the profile by `external_profile_id` or `customer_user_id` — it succeeds and changes nothing. A second call carrying only `email` returns `404`, because the first deletion cleared the address it would have matched. The [Delete profile](api-mail/operations/deleteProfile) reference describes the response codes.
