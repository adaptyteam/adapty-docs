Enable the Google Cloud Storage integration to securely store [subscription events](events) and [paywall visit data](paywall-metrics) in one central location: your Google Cloud Storage bucket.

Every day at 4AM UTC, Adapty will upload .csv files with the previous day's data to your buckets. You can choose whether you want to receive **event** data, **paywall visit** data, or **both**. You can also export this data [manually](#manual-data-export) at any time, for any time period.

To set up the integration, [generate a bucket access key](#create-google-cloud-storage-credentials) in your Google Cloud console, and [add it to your Adapty settings](#set-up-google-cloud-storage-integration).

## Upload schedule and duration

Adapty uploads data to Google Cloud Storage every 24 hours, at 04\:00 UTC.

The files contain data for events created during the previous calendar day (UTC). The file uploaded on March 8th will contain all the events created on March 7th, from 00\:00\:00 to 23\:59\:59 UTC.

The process may take up to several hours, depending on the total number of files in the queue, as well as the amount of data you personally requested. If Adapty includes historical data with your first upload, it will take longer than the subsequent daily uploads.

## Set up Google Cloud storage integration

You need to have a valid Google Cloud service account key with **write access**. To generate it, follow the steps in the [create credentials](#create-google-cloud-storage-credentials) section.

:::warning
You can use different buckets and credentials for events, paywall visits, and virtual currency transactions. When you save the settings, Adapty verifies the credentials of each export that is on. If any set is invalid, Adapty doesn't save the settings of any tab. See [Troubleshooting](#troubleshooting).
:::

Go to [**Integrations** -> **Google Cloud Storage**](https://app.adapty.io/integrations/google-cloud-storage), and open the necessary tab (**Events** or **Paywall visits**). Enable the integration.

Upload the file with your **Google Cloud service account key**. Specify the target **bucket** and **folder**. Save your changes.

## Create Google Cloud Storage credentials

This guide will help you create the necessary credentials in your Google Cloud Platform Console.

In order for Adapty to upload raw data reports to your designated bucket, the service account's key is required, as well as write access to the corresponding bucket. By providing the service account's key and granting write access to the bucket, you allow Adapty to securely and efficiently transfer the raw data reports from its platform to your storage environment.

:::warning
Please note that we only support Service Account HMAC key authorization, means it's essential to ensure that your Service Account HMAC key has the "Storage Object Viewer", "Storage Legacy Bucket Writer" and "Storage Object Creator" roles added to it to enable proper access to Google Cloud Storage.
:::

## Virtual currency transactions

The virtual currency export sends each change of a [virtual currency](virtual-currencies) balance to your Google Cloud Storage bucket. Use it to load the full history of credits, spends, expiries, and refunds into your own data warehouse.

This export is separate from the events and paywall visits exports. It has its own switch and credentials, and its own bucket and folder settings.

### Turn on the export

1. Go to [**Integrations** -> **Google Cloud Storage**](https://app.adapty.io/integrations/google-cloud-storage) and open the **Virtual currency** tab.
2. Turn on **Export virtual currency transactions to Google Cloud Storage**.
3. Upload the file with your [Google Cloud service account key](#create-google-cloud-storage-credentials), and specify the bucket and the folder. The fields are the same as on the **Paywall visits** tab.

To export the virtual currency transactions of past days, use [manual data export](#manual-data-export).

### File and schedule

Every day, Adapty uploads 1 file with the virtual currency transactions of the previous calendar day in UTC. A transaction belongs to the day of its `created_at` time in UTC.

The file name is `<app_id>_virtual_currency_<date>.csv`, where `<date>` is 1 day after the day of the transactions, in `YYYY-MM-DD` format. For example, the file `<app_id>_virtual_currency_2026-03-08.csv` contains the transactions of March 7, 2026. Each export has its own file name. Keep each export in its own folder, so that a table or loader that reads a whole folder gets only one type of file. If the exports share a folder, select the files of this export by name: `<app_id>_virtual_currency_*.csv`.

The file is a UTF-8 `.csv` file with a header row. For a day with no transactions, the file has only the header row.

Each row is one balance change of one currency. A transaction that changes 2 currencies, such as an exchange of gold for gems, gives 2 rows with the same `vc_transaction_id`. Sandbox transactions are in the file too, with `is_sandbox` set to `true`.

When you save the settings, Adapty verifies the credentials of each export that is on. If the virtual currency credentials are invalid, Adapty doesn't save the settings. The **Save** button saves the settings of all tabs, so Adapty doesn't save your changes on the other tabs either.

The virtual currency export uses its own credentials. If its daily upload fails, the events and paywall visits uploads of the app still run.

### Join with the events table

The virtual currency file has no prices. To get the price of a purchase that credited a currency, join the credit row with the events table:

- Match **store_transaction_id** with **transaction_id** of the events table.
- Match **store** too, but only for `app_store`, `play_store`, `stripe`, and `paddle`. For `adapty` and custom stores, the events table has an empty **store**.

This example query assumes that you loaded the virtual currency files into the `vc_transactions` table and the events files into the `events` table:

```sql title="SQL"
SELECT
  vc.vc_transaction_id,
  vc.created_at,
  vc.profile_id,
  vc.currency_code,
  vc.amount,
  e.event_type,
  e.product_id,
  e.revenue_usd,
  e.currency,
  e.revenue_local
FROM vc_transactions AS vc
LEFT JOIN events AS e
  ON e.transaction_id = vc.store_transaction_id
  AND (
    e.store = vc.store
    OR vc.store NOT IN ('app_store', 'play_store', 'stripe', 'paddle')
  )
  AND e.event_type IN (
    'subscription_initial_purchase',
    'subscription_started',
    'subscription_renewed',
    'trial_started',
    'trial_converted',
    'non_subscription_purchase'
  )
WHERE vc.amount > 0
  AND COALESCE(vc.store_transaction_id, '') <> '';
```

The query lists the default event names. A subscription start is `subscription_initial_purchase` in an integration created since mid-September 2025, and `subscription_started` in an earlier one. If you changed the event names in the events export settings, use your names in the query.

A credit row has no matching event if the events export is off, if the events export settings exclude or rename the event type of the purchase, or if **Exclude historical events** excludes the event.

One purchase can credit more than one currency. Each currency gets its own credit row, and all these rows join the same event. To sum revenue, count each **store_transaction_id** once.

### Limitations

- **No prices or refund amounts**: The virtual currency file has no purchase price and no refund amount. To get the price, [join the credit row with the events table](#join-with-the-events-table).
- **Don't add up credits from the two files**: The **virtual_currency_credits** column of the [events](#events) file and the credit rows of the virtual currency file show the same purchase credits. To count credits, use one of them, not both. Their totals can differ: the events file has only the credits of purchases, and only for the events that its settings export, while the virtual currency file has every balance change, including grants through the API and manual adjustments in the dashboard.
- **No link between a spend and its credits**: The file doesn't show which credits a spend used, for example, purchased or granted credits.
- **Refund rows show only the credits taken back**: A refund row shows the credits that Adapty took back from the balance. Its **amount** can be smaller than the credits that the purchase granted, for example, when the user spent part of them. If no credits were left, the file has no refund row.
- **No refund row for a subscription upgrade**: A refund that comes from a subscription upgrade takes back no credits. The file has no refund row for it.

## Troubleshooting

When you save the settings, Adapty verifies the key of each export that is on. If one key is invalid, Adapty doesn't save the settings of any tab and shows an error.

Each export uploads its files with its own key, so an expired key stops only the uploads of that export. To keep the uploads running, replace your keys before they expire. If several tabs use the same key, replace it on each of them: **Events**, **Paywall visits**, and **Virtual currency**.
