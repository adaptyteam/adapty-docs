A [flow](adapty-flow-builder) can ask users for a system permission with the **Request permission** action. For example, it can ask for push notifications on an onboarding screen that explains them, or for camera access before a feature that scans documents. The Adapty SDK doesn't show the system permission dialog itself. It passes the permission request to the `onRequestPermission` handler in your app. Your app shows the dialog and passes the result to the flow, which then continues.

## Before you start

You need:

- **Adapty React Native SDK 4.0.0 or later**: Earlier versions don't have the `onRequestPermission` handler.
- **A flow with the Request permission action**: In the Flow & Paywall Builder, add the **Request permission** action to the **On Tap** or **On Screen Appear** trigger of an element. In the action, select the permission in the **Permission** field. Add the actions for each result. The default **After response** action is **Navigate Next**. For the action settings, see [Request permission](onboarding-actions#request-permission).
- **A library that shows the permission dialogs**: The code in this guide uses [react-native-permissions](https://github.com/zoontek/react-native-permissions) 5.x. To set it up, follow its [setup guide](https://github.com/zoontek/react-native-permissions#setup). On iOS, list each permission that your handler requests, such as `Notifications` and `Camera`, in the `setup_permissions` call of your `ios/Podfile`. Any other library that shows the dialogs works too, for example `expo-notifications` in an Expo app.
- **A key-value storage for Android**: To tell a new refusal from an earlier one on Android, the handler saves which permissions it requested. The code uses [AsyncStorage](https://github.com/react-native-async-storage/async-storage). Any other storage that keeps its values between app launches works too.
- **The declarations of the permissions that your handler requests**: On iOS, a purpose string: the text in `Info.plist` that tells users why your app needs the permission. On Android, a permission in the Android manifest. See [Declare the permissions](#declare-the-permissions).
- **For push notifications on Android, the `targetSdk` property set to 33 or higher**: Only apps that target Android 13 or later choose when the notification permission dialog appears.

:::warning
**On Android with React Native SDK before 4.3.0, show a flow that requests permissions with the `AdaptyFlowView` component.** In these versions, a flow presented with the `view.present()` method waits on the screen after the permission dialog. Your handler only passes the result after the flow closes.
:::

:::note
**If your handler already requests push notifications**: It keeps working. When the handler resolves with `{ status: 'denied' }`, the flow runs the **After response** actions. To have the flow run the **When denied** actions, also set the `detail` property to `'denied'`, `'restricted'`, or `'permanently_denied'`. To request other permissions, add their cases to the handler.
:::

## How the flow requests a permission

1. The flow reaches the **Request permission** action: the user taps the element, or the screen appears.
2. The Adapty SDK calls your `onRequestPermission` handler with the permission selected in the action, such as `push` or `camera`.
3. Your app shows the system dialog. The promise of your handler resolves to an object with the result in the `status` property and a string in the `detail` property. For example: `{ status: 'denied', detail: 'permanently_denied' }`.

<FlowPermissionAnswers />

The flow waits on the screen until your handler's promise resolves. If the promise never resolves, the flow stays on the screen. If the OS shows no dialog, for example because the user already granted the permission, your handler passes the result at once. The flow then runs the actions for the result right away. If those actions leave the screen, the user sees the screen that requests the permission only for a moment.

The flow sends your handler one permission request at a time. [The trigger of the action](onboarding-actions#request-permission) decides how often the flow sends the request. Your handler can receive the same permission again, for example on each tap. Each time, pass the result for what the OS currently reports.

## Implement the handler

:::warning
**Request only the permissions that your app declares. For any other permission, resolve the promise of the handler with `{ status: 'denied', detail: 'unsupported' }`.** For most permissions, iOS terminates the app when the app requests a permission whose purpose string is missing from `Info.plist`. A flow author can add a request for any permission at any time, and the flow also reaches app versions released before the request was added.
:::

The `onRequestPermission` handler is asynchronous, unlike the other flow handlers. It returns a promise that resolves to an object with the result. The following handler requests push notifications and camera access, and passes `unsupported` for every other permission, without a dialog. The imports cover every function in this guide:

```typescript showLineNumbers title="permissions.ts"
import AsyncStorage from '@react-native-async-storage/async-storage';
import { Platform } from 'react-native';
import {
  PERMISSIONS,
  RESULTS,
  check,
  checkNotifications,
  request,
  requestMultiple,
  requestNotifications,
  type Permission,
  type PermissionStatus,
  type Rationale,
} from 'react-native-permissions';
import type { FlowEventHandlers, FlowPermissionResponse } from 'react-native-adapty';

export const onRequestPermission: FlowEventHandlers['onRequestPermission'] = async (permission) => {
  switch (permission) {
    case 'push':
      return requestPush();
    case 'camera':
      return requestCamera();
    // Add a case for each permission that your app requests.
    default:
      // A permission that this app version doesn't request: pass the result without a dialog.
      return { status: 'denied', detail: 'unsupported' };
  }
};
```

To request another permission, add a case for it, and a function that requests it. For the function, start from [Code for each permission](#code-for-each-permission). A permission without a case needs no setup in react-native-permissions and no declarations.

The functions use these helpers, which turn each permission status that react-native-permissions returns into the result and the string from System permissions on [iOS](ios-system-permissions) and [Android](android-system-permissions):

- **iOS**: Every refusal comes back from react-native-permissions as `RESULTS.BLOCKED`, also right after the alert. So the `requestIOS()` function reads the current authorization status with the `check()` function first: `BLOCKED` before the request passes `permanently_denied`, and `BLOCKED` after the alert passes `denied`.
- **Android**: The `answerAndroid()` helper reads whether Android shows a rationale before the request, and saves a flag for each dialog that it requested. After the request, react-native-permissions returns `RESULTS.DENIED` when Android shows a rationale, and `RESULTS.BLOCKED` when it doesn't.

With `denied` or `permanently_denied`, the flow runs the **When denied** actions. The two strings only differ in the `outcome` property of [`flow_permission_answered`](#track-permission-requests-in-analytics). The `answerAndroid()` function tells them apart with the rationale and its AsyncStorage flags. Compared with code that passes `denied` for every refusal, the `answerAndroid()` function only changes the actions that the flow runs in one case. If the user closes the first dialog without a choice, the `answerAndroid()` function returns `{ status: 'denied' }`, and the flow runs the **After response** actions.

```typescript showLineNumbers title="permissions.ts"
// iOS: the result for a status read before the request (`before`) or after the alert.
function iosAnswer(status: PermissionStatus, before: boolean): FlowPermissionResponse {
  switch (status) {
    case RESULTS.GRANTED:
      return { status: 'granted', detail: 'granted' };
    case RESULTS.LIMITED:
      return { status: 'granted', detail: 'limited' };
    case RESULTS.BLOCKED:
      return { status: 'denied', detail: before ? 'permanently_denied' : 'denied' };
    case RESULTS.UNAVAILABLE:
      // Also restricted access: react-native-permissions doesn't report it apart.
      return { status: 'denied', detail: 'unsupported' };
    default:
      // DENIED: still not determined after the request, so the user made no choice.
      return { status: 'denied' };
  }
}

// iOS: shows the alert only while the permission isn't determined (DENIED).
async function requestIOS(permission: Permission): Promise<FlowPermissionResponse> {
  const before = await check(permission);
  if (before !== RESULTS.DENIED) return iosAnswer(before, true);
  return iosAnswer(await request(permission), false);
}

// Android: tells a refusal in the dialog from one without a dialog by the rationale.
async function answerAndroid(
  key: string,
  run: (rationale: Rationale) => Promise<PermissionStatus>,
): Promise<FlowPermissionResponse> {
  const flag = `flowPermissionRequested:${key}`;
  const requestedBefore = (await AsyncStorage.getItem(flag)) !== null;
  let rationaleBefore = false;
  // react-native-permissions calls the callback only when Android shows a rationale.
  const status = await run(async () => {
    rationaleBefore = true;
    return true;
  });
  await AsyncStorage.setItem(flag, '1');
  switch (status) {
    case RESULTS.GRANTED:
      return { status: 'granted', detail: 'granted' };
    case RESULTS.LIMITED:
      return { status: 'granted', detail: 'limited' };
    case RESULTS.UNAVAILABLE:
      // The permission doesn't exist on this Android version.
      return { status: 'denied', detail: 'unsupported' };
    case RESULTS.DENIED:
      // A rationale after the request: the user declined the dialog.
      return { status: 'denied', detail: 'denied' };
    default:
      // BLOCKED: no rationale after the request.
      if (rationaleBefore) return { status: 'denied', detail: 'denied' };
      // Requested before, and no rationale: Android showed no dialog.
      if (requestedBefore) return { status: 'denied', detail: 'permanently_denied' };
      // The first request, and no rationale: the user closed the dialog without a choice.
      return { status: 'denied' };
  }
}

// Android: requests one permission.
function requestAndroid(permission: Permission): Promise<FlowPermissionResponse> {
  return answerAndroid(permission, (rationale) => request(permission, rationale));
}
```

The `onRequestPermission` handler receives:

- **`permission`**: The permission selected in the action, as a string from the **Value** column in [Declare the permissions](#declare-the-permissions).
- **`customArgs`**: Custom arguments of the request. The **Request permission** action sends none, so the object is empty.

To pass the result to the flow:

1. In the `onRequestPermission` handler, show the system dialog.
2. Resolve the promise of the handler with an object. Set its `status` property to `'granted'` if the user granted the permission, and to `'denied'` otherwise.
3. To have the flow run the **When denied** actions, also set the `detail` property to `'denied'`, `'restricted'`, or `'permanently_denied'`. For example, `{ status: 'denied', detail: 'permanently_denied' }`. Without the `detail` property, the flow runs the **After response** actions.

<FlowPermissionStrings />

On iOS, if the `status` property holds any value other than `'granted'` or `'denied'`, the flow receives no result and stays on the screen.

When your handler throws an error or its promise rejects, the Adapty SDK passes `denied` without a string. The flow then runs the **After response** actions.

## Register the handler

:::warning
**Without an `onRequestPermission` handler, the user is never asked.** On a flow view without the handler, the Adapty SDK passes `denied` without a dialog and without a string, and writes a warning to its log. The flow runs the **After response** actions right away. The `outcome` property of [`flow_permission_answered`](#track-permission-requests-in-analytics) then reports `no_status`.
:::

Set the handler on every flow view your app creates, before the view appears.

## Declare the permissions

For each permission that your handler requests, add these declarations to `ios/<YourApp>/Info.plist` on iOS and to `android/app/src/main/AndroidManifest.xml` on Android:

For example, an app that copies only the `requestPush()` and `requestCamera()` functions adds the `NSCameraUsageDescription` key to `Info.plist` on iOS. On Android, the app declares these permissions:

```xml title="android/app/src/main/AndroidManifest.xml"
<uses-permission android:name="android.permission.POST_NOTIFICATIONS" />
<uses-permission android:name="android.permission.CAMERA" />
```

For what each permission shows users, the OS versions it needs, and the result to pass for what the OS reports, see System permissions on [iOS](ios-system-permissions) and [Android](android-system-permissions).

## Test the permission request

iOS shows most permission dialogs only once per app install. Android stops showing a permission dialog after the user grants the permission or declines it twice. To see the dialog again while you test the flow:

1. Delete the app from the device, and install it again.
2. Open the flow, and reach the **Request permission** action.

On Android, to reset the permission and the AsyncStorage flags of the `answerAndroid()` function together, clear the app data with `adb shell pm clear <package>`.

If the flow moves on without a dialog, make sure that:

- The flow view has the `onRequestPermission` handler.
- The app declares the permission on both platforms, and lists it in the `setup_permissions` call on iOS.
- For notifications on Android, the app targets Android 13 or later.

## Code for each permission

Each function in this section requests one permission and returns the result for the flow. Add it to `permissions.ts`, with the handler and the helpers. The setup line of each permission names its declarations, and the name to list in the `setup_permissions` call of your `ios/Podfile`.

Functions for the other permissions follow one of two patterns. The `requestCamera()` function makes a direct request. The `requestLocationWhenInUse()` function stops waiting after a timeout, because iOS might never call back. For what to request and which result to pass for each permission, see System permissions on [iOS](ios-system-permissions) and [Android](android-system-permissions).

On iOS, react-native-permissions reports restricted access as `RESULTS.UNAVAILABLE`, so every function passes `unsupported` instead of `restricted`. The flow then runs the **After response** actions instead of the **When denied** actions.

### Push notifications \{#push\}

Add the `POST_NOTIFICATIONS` permission to the Android manifest. List `Notifications` in the `setup_permissions` call of your Podfile. See System permissions on [iOS](ios-system-permissions#push) and [Android](android-system-permissions#push).

```typescript showLineNumbers title="permissions.ts"
async function requestPush(): Promise<FlowPermissionResponse> {
  if (Platform.OS === 'ios') {
    const before = await checkNotifications();
    const decided = before.status !== RESULTS.DENIED;
    const { status, settings } = decided
      ? before
      : await requestNotifications(['alert', 'badge', 'sound']);
    // react-native-permissions reports provisional authorization as GRANTED.
    if (status === RESULTS.GRANTED && settings.provisional) {
      return { status: 'granted', detail: 'provisional' };
    }
    // LIMITED is the ephemeral authorization of an App Clip.
    if (status === RESULTS.LIMITED) return { status: 'granted', detail: 'granted' };
    return iosAnswer(status, decided);
  }
  if (Platform.OS === 'android' && Platform.Version < 33) {
    // Android 12 and earlier show no dialog: notifications are on unless the user turned them off.
    const { status } = await checkNotifications();
    return status === RESULTS.GRANTED
      ? { status: 'granted', detail: 'granted' }
      : { status: 'denied', detail: 'permanently_denied' };
  }
  return answerAndroid('android.permission.POST_NOTIFICATIONS', async (rationale) => {
    const { status } = await requestNotifications([], rationale);
    return status;
  });
}
```

- With a granted notification permission, your app can show notifications. To receive push notifications, register the device with your push provider, as your app does outside flows.

### Location while using the app \{#location_when_use\}

Add the `NSLocationWhenInUseUsageDescription` key to `Info.plist`. Add the `ACCESS_COARSE_LOCATION` and `ACCESS_FINE_LOCATION` permissions to the Android manifest. List `LocationWhenInUse` in the `setup_permissions` call of your Podfile. See System permissions on [iOS](ios-system-permissions#location_when_use) and [Android](android-system-permissions#location_when_use).

```typescript showLineNumbers title="permissions.ts"
async function requestLocationWhenInUse(): Promise<FlowPermissionResponse> {
  if (Platform.OS === 'ios') {
    const before = await check(PERMISSIONS.IOS.LOCATION_WHEN_IN_USE);
    if (before !== RESULTS.DENIED) return iosAnswer(before, true);
    // iOS may never call back, for example in the background: wait at most 50 seconds,
    // so the flow gets the result before it reports flow_permission_unanswered at 60 seconds.
    await Promise.race([
      request(PERMISSIONS.IOS.LOCATION_WHEN_IN_USE),
      new Promise<void>((resolve) => setTimeout(resolve, 50_000)),
    ]);
    return iosAnswer(await check(PERMISSIONS.IOS.LOCATION_WHEN_IN_USE), false);
  }
  const { ACCESS_COARSE_LOCATION, ACCESS_FINE_LOCATION } = PERMISSIONS.ANDROID;
  // One flag for every request that shows the location dialog.
  return answerAndroid('location', async () => {
    // Request both: some Android 12 releases ignore a request for fine location alone.
    const result = await requestMultiple([ACCESS_FINE_LOCATION, ACCESS_COARSE_LOCATION]);
    // Approximate location is enough to grant the permission.
    return result[ACCESS_COARSE_LOCATION];
  });
}
```

- **Differs from System permissions**: On Android, a second refusal in the dialog passes `permanently_denied` instead of `denied`, because the `requestMultiple()` function takes no rationale callback. With either string, the flow runs the **When denied** actions.

### Camera \{#camera\}

Add the `NSCameraUsageDescription` key to `Info.plist`, and the `CAMERA` permission to the Android manifest. List `Camera` in the `setup_permissions` call of your Podfile. See System permissions on [iOS](ios-system-permissions#camera) and [Android](android-system-permissions#camera).

```typescript showLineNumbers title="permissions.ts"
async function requestCamera(): Promise<FlowPermissionResponse> {
  if (Platform.OS === 'ios') return requestIOS(PERMISSIONS.IOS.CAMERA);
  return requestAndroid(PERMISSIONS.ANDROID.CAMERA);
}
```

- **Differs from System permissions**: On Android, react-native-permissions doesn't read the `FEATURE_CAMERA_ANY` system feature, so on a device without a camera the function shows the dialog instead of passing `unsupported`.
