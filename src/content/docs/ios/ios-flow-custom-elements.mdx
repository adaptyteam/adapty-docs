When a screen with a [custom element](flow-custom-elements) opens, the Adapty SDK passes the element's Type and ID to a resolver in your app code. The resolver returns one of the following:

- **The view that matches the Type and ID**: Users see the native SwiftUI view, such as a Lottie animation, an interactive chart, or a camera preview.
- **No view**: Users see the fallback, which is the content inside the custom element in the Flow & Paywall Builder.

If the user has an outdated version of your app — one that doesn't have the resolver at all — the flow displays the fallback. Therefore, you can publish the flow before you release the app.

## Before you start

You need:

- **Adapty iOS SDK 4.4 or later**: Earlier versions show the fallback for every custom element.
- **A native iOS app**: The resolver API for cross-platform frameworks is coming soon.
- **A naming scheme for custom elements**: Give each native view a Type, such as `lottie_animation`. Use only lowercase letters, numbers, and underscores in Types. To distinguish between custom elements of the same Type, give each one an ID, such as `welcome_wave`. The Types and IDs in your code must match the ones in the [Flow & Paywall Builder](flow-custom-elements#add-and-configure).

## Create views for custom elements

For each Type, create a native SwiftUI view, or reuse one from your app. The following view of the `lottie_animation` Type plays a Lottie animation:

```swift showLineNumbers title="Swift"
import Lottie
import SwiftUI

struct LottieElementView: View {
    let animation: LottieAnimation?

    var body: some View {
        LottieView(animation: animation)
            .resizable()
            .looping()
    }
}
```

### View requirements and best practices

- **Sizing**:
  - **Padding and alignment**: Make sure the native view fits the container you allocated for it in the Flow & Paywall builder, minus the padding. If the view doesn't take up the entire area, its placement will be determined by container's alignment setting.
  - **Hug height**: If the height of the custom element is set to **Hug**, a view that stretches to fill the available space (like a map) will collapse. Give the custom element a [**Fixed** height](flow-custom-elements#add-and-configure) instead.
- **Flow actions**: The native view can't trigger flow actions, such as a transition to the next screen. Keep navigation buttons, purchase buttons, and other buttons with flow actions outside the custom element.
- **Navigation handling**: When the user moves to the next screen, it triggers the view's  `onDisappear` modifier. Use it to terminate everything you may need — such as camera sessions or other processes. When the user comes back, the SDK calls the resolver again, and SwiftUI resets the state of the view.
- **UIKit views**: Wrap them in `UIViewRepresentable`.

## Write a resolver to match custom elements and views

To write a resolver, make a type conform to the `AdaptyUICustomElementsResolver` protocol, and implement the `view(forType:id:context:)` method.

For the `lottie_animation` Type, the following resolver returns `LottieElementView`. The ID names the animation file in the app bundle, such as `welcome_wave`:

```swift showLineNumbers title="Swift"
import AdaptyUIBuilder
import Lottie
import SwiftUI

struct CustomElementsResolver: AdaptyUICustomElementsResolver {
    func view(
        forType type: String,
        id: String,
        context: AdaptyUICustomElementContext
    ) -> AnyView? {
        switch type {
        case "lottie_animation":
            // the ID names the animation file, such as welcome_wave.json
            return AnyView(LottieElementView(animation: .named(id)))
        default:
            return nil
        }
    }
}
```

In the `default` case, return `nil`, so that users see the fallback. For example, you can [add a custom element with a new Type](flow-custom-elements#what-changes-require-an-app-release) after you release the app.

The resolver has the following requirements:

- **Network data and players**: Keep network data and players in the state of the [native view](#create-views-for-custom-elements), not in the resolver. The SDK calls the resolver many times while the screen is open, such as when products load or a purchase starts. Code in the resolver runs again on each call, so network requests repeat and players start over. SwiftUI keeps the state of the native view between calls, so the data loads once and the players keep playing.
- **One native view per Type**: Some native views change while the screen is open, for example, when their data loads or when the user taps them. Implement this logic in the view `body` itself, not in the resolver. If the resolver returns a different view for the Type, SwiftUI resets the state of the view.
- **App data**: Store the data that your app already has, such as a [daily streak](#display-user-specific-data-such-as-a-daily-streak), in properties of the resolver. Pass the data to the native view when the resolver creates it. Don't use environment objects for this data: with the UIKit [flow controller](ios-present-paywalls#present-flows-and-paywalls-in-uikit), the native view doesn't receive the SwiftUI environment of your app.

:::tip
The simpler, more limited alternative to the resolver approach is to pass a `[String: AdaptyUICustomElementBuilder]` dictionary with Type keys. It demands less code, but you cannot [set conditions for fallback content](#set-conditions-for-fallback-content).
:::

### Set conditions for fallback content

Some situations may cause your native view to malform, and display an empty area:

- Nothing to visualize — the necessary animation file or data file is missing.
- Nothing to process — the user skipped a quiz question, and the data is incomplete.
- Access prohibited — a denied permission prevents the view from accessing a resource.

Return `nil` to show users the [fallback content](flow-custom-elements#set-fallback-content) instead:

```swift showLineNumbers title="Swift" {3-5}
switch type {
case "lottie_animation":
    guard let animation = LottieAnimation.named(id) else {
        return nil // no file for this ID: show the fallback
    }
    return AnyView(LottieElementView(animation: animation))
default:
    return nil
}
```

For a permission, return `nil` only when the user denied it. If the user hasn't answered the permission request yet, return the native view instead of `nil`, and [ask for the permission inside it](#write-a-resolver-to-match-custom-elements-and-views), such as location access for a map. The native view can display the map as soon as the user grants access, while the fallback stays until the SDK calls the resolver again.

## Pass the resolver to the SDK

### Display the same views to all users

To display the same native views to all users, set an app-wide resolver. Call `AdaptyUI.setCustomElementsResolver(_:)` once, before you present a flow, such as at app launch:

```swift showLineNumbers title="Swift"
AdaptyUI.setCustomElementsResolver(CustomElementsResolver())
```

### Display user-specific data, such as a daily streak

To display user-specific data, such as a daily streak, write a resolver that stores the data in its properties.

A resolver that you attach to a flow replaces the app-wide resolver in that flow. To keep the app-wide views, call the app-wide resolver for the Types and IDs that you don't match:

```swift showLineNumbers title="Swift"
struct StreakResolver: AdaptyUICustomElementsResolver {
    let streakProgress: AnimationProgressTime // from 0 to 1

    func view(
        forType type: String,
        id: String,
        context: AdaptyUICustomElementContext
    ) -> AnyView? {
        if type == "lottie_animation", id == "streak_ring" {
            return AnyView(
                LottieView(animation: .named(id))
                    .resizable()
                    .playing(.fromProgress(0, toProgress: streakProgress, loopMode: .playOnce))
            )
        }
        // other Types and IDs: the views of the app-wide resolver
        return CustomElementsResolver().view(forType: type, id: id, context: context)
    }
}
```

Attach the resolver to the flow when you fetch its configuration:

```swift showLineNumbers title="Swift"
do {
    let flowConfiguration = try await AdaptyUI.getFlowConfiguration(
        forFlow: flow,
        customElementsResolver: StreakResolver(streakProgress: streakProgress)
    )
    // present the flow
} catch {
    // handle the error
}
```

## Test on a device

The builder canvas shows the fallback, never the native view. An error in the native view can crash the app. Before you release the app, test every screen that has a custom element on a device:

1. To see the latest published version of each flow instead of a cached one, register the device as a [test device](test-devices).
2. On the device, run a build that includes the resolver. Open each screen that has a custom element, and verify that the native view appears and fits the custom element. If the view scrolls or responds to drags, test these gestures.
3. If the fallback appears instead of the native view, find this warning in the Xcode console: `custom element <type>:<id> is not served by a resolver`. Then verify that:
   - The Type and ID in the warning match the ones in your code, letter for letter.
   - Your app has the file, data, or permission that the view needs.
   - Your app sets the resolver before it presents the flow.
   - A [resolver for this flow](#display-user-specific-data-such-as-a-daily-streak), if you pass one, returns a view for the Type and ID.

   If the warning doesn't appear, verify that the app uses Adapty iOS SDK 4.4 or later, and that [`Adapty.logLevel`](sdk-installation-ios#logging) isn't `.error`.
4. To see the fallback, return `nil` for the Type, and open the screen again.
