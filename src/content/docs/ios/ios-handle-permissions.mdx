A [flow](adapty-flow-builder) can ask users for a system permission with the **Request permission** action, for example push notifications on an onboarding screen that explains what the notifications are for, or camera access before a feature that scans documents. The Adapty SDK doesn't show the system permission dialog itself. It passes the request to an `AdaptySystemRequestsHandler` in your app. Your app shows the dialog and returns the user's answer, and the flow continues.

## Before you start

You need:

- **Adapty iOS SDK 4.0.0 or later**: Earlier versions don't have `AdaptySystemRequestsHandler`.
- **A flow with the Request permission action**: In the Flow & Paywall Builder, add the **Request permission** action to an element's **On Tap** or **On Screen Appear** trigger. In the action, select the permission in the **Permission** field, and add the actions to run after the user answers to its outcome sections, such as **Navigate Next** in **After response**. For the action settings, see [Request permission](onboarding-actions#request-permission).
- **A purpose string in `Info.plist` for each permission that your handler requests**: See [Declare the permissions](#declare-the-permissions).

## How the flow requests a permission

1. The flow reaches the **Request permission** action: the user taps the element, or the screen appears.
2. The Adapty SDK calls `handlePermission(_:withCustomArgs:)` on your handler with the permission selected in the action, such as `.push` or `.camera`.
3. Your app requests the permission from iOS and returns `.granted` or `.denied` with a status.
4. The flow runs the actions of one outcome section.

<FlowPermissionAnswers />

The flow waits on the screen until your app returns the answer. If your app never answers, the flow stays on the screen. If iOS doesn't show the dialog, for example because the user already answered it, your app gets the answer at once, and the flow runs the outcome actions right away. If those actions leave the screen, the user sees the screen that requests the permission only for a moment.

With **On Screen Appear**, the flow doesn't send the request again when the user comes back to the screen with a **Navigate back** action, unless every outcome section of the action is empty. With **On Tap**, each tap sends a new request. The flow sends one permission request at a time: while a request waits for your answer, a tap on an element that requests a permission does nothing.

## Implement the handler

:::warning
**Request only the permissions that your app declares, and answer `.denied("unsupported")` for any other permission.** For most permissions, iOS terminates the app when the app requests a permission whose purpose string is missing from `Info.plist`. A flow author can add a request for any permission at any time, and the flow also reaches app versions released before the request was added.
:::

To answer permission requests, create a class that conforms to `AdaptySystemRequestsHandler` and implement `handlePermission(_:withCustomArgs:)`. In this example, the handler requests push notifications and camera access, and answers every other permission as unsupported without a dialog:

```swift showLineNumbers title="Swift"
import AdaptyUI
import AVFoundation
import UserNotifications

@MainActor
final class FlowPermissionHandler: AdaptySystemRequestsHandler {
    func handlePermission(
        _ permission: AdaptyPermission,
        withCustomArgs customArgs: [String: String]?
    ) async -> AdaptyPermissionResult {
        switch permission {
        case .push:
            return await requestNotifications()
        case .camera:
            return await requestCamera()
        default:
            // A permission this app version doesn't request: answer without a dialog.
            return .denied("unsupported")
        }
    }

    private func requestNotifications() async -> AdaptyPermissionResult {
        do {
            let granted = try await UNUserNotificationCenter.current()
                .requestAuthorization(options: [.alert, .badge, .sound])
            return granted ? .granted("granted") : .denied("denied")
        } catch {
            // Not an answer from the user: the flow runs After response.
            return .denied(nil)
        }
    }

    private func requestCamera() async -> AdaptyPermissionResult {
        switch AVCaptureDevice.authorizationStatus(for: .video) {
        case .authorized:
            return .granted("granted")
        case .denied:
            return .denied("denied")
        case .restricted:
            return .denied("restricted")
        case .notDetermined:
            let granted = await AVCaptureDevice.requestAccess(for: .video)
            return granted ? .granted("granted") : .denied("denied")
        @unknown default:
            return .denied(nil)
        }
    }
}
```

`handlePermission(_:withCustomArgs:)` receives:

- **`permission`**: The permission selected in the action. `AdaptyPermission` has a case for each permission in [Declare the permissions](#declare-the-permissions). A value that the Adapty SDK doesn't know arrives as `.custom(String)`.
- **`customArgs`**: Custom arguments of the request. The **Request permission** action sends none, so the value is `nil`.

`.granted` and `.denied` take the status as a string, such as `.granted("granted")` or `.denied("permanently_denied")`.

A granted notification permission lets your app show notifications. To receive push notifications, register the device with APNs and send the device token to your push provider, as your app does outside flows.

`AdaptySystemRequestsHandler` also declares `handleAppReviewRequest()`. Its default implementation shows the App Store review prompt, so you don't need to implement it.

## Declare the permissions

iOS asks the user for a permission only when the app explains why it needs it. For each permission that your handler requests, add its purpose string to `Info.plist`:

| Permission in the builder | `AdaptyPermission` | `Info.plist` key |
|:--------------------------|:-------------------|:-----------------|
| Push notifications | `.push` | None. To receive push notifications, the app needs the Push Notifications capability. |
| App tracking (ATT) | `.tracking` | `NSUserTrackingUsageDescription` |
| Location while using the app | `.locationWhenInUse` | `NSLocationWhenInUseUsageDescription` |
| Location always | `.locationAlways` | `NSLocationAlwaysAndWhenInUseUsageDescription` and `NSLocationWhenInUseUsageDescription` |
| Precise location | `.locationFullAccuracy` | `NSLocationTemporaryUsageDescriptionDictionary` |
| Camera | `.camera` | `NSCameraUsageDescription` |
| Microphone | `.microphone` | `NSMicrophoneUsageDescription` |
| Photos | `.photos` | `NSPhotoLibraryUsageDescription` |
| Media library | `.mediaLibrary` | `NSAppleMusicUsageDescription` |
| Apple Music | `.music` | `NSAppleMusicUsageDescription` |
| Speech recognition | `.speech` | `NSSpeechRecognitionUsageDescription` |
| Contacts | `.contacts` | `NSContactsUsageDescription` |
| Calendar | `.calendar` | `NSCalendarsFullAccessUsageDescription`, and `NSCalendarsUsageDescription` before iOS 17 |
| Reminders | `.reminders` | `NSRemindersFullAccessUsageDescription`, and `NSRemindersUsageDescription` before iOS 17 |
| Health data | `.health` | `NSHealthShareUsageDescription`, and `NSHealthUpdateUsageDescription` to write health data |
| Motion & Fitness | `.motion` | `NSMotionUsageDescription` |
| Bluetooth | `.bluetooth` | `NSBluetoothAlwaysUsageDescription` |
| Local network | `.localNetwork` | `NSLocalNetworkUsageDescription` |
| HomeKit | `.homekit` | `NSHomeKitUsageDescription` |
| Focus status | `.focusStatus` | `NSFocusStatusUsageDescription` |
| Siri | `.siri` | `NSSiriUsageDescription` |

For example, the handler in [Implement the handler](#implement-the-handler) requests camera access, so the app declares this key:

```xml title="Info.plist"
<key>NSCameraUsageDescription</key>
<string>Scan documents with the camera.</string>
```

Health data, HomeKit, and Siri also need their capability in Xcode.

For `.health`, iOS doesn't tell your app whether the user allowed it to read health data, so your app decides which answer to report.

## Pass the handler to the flow configuration

:::warning
**Without a handler, the flow stops at the permission request.** If you don't pass `systemRequestsHandler`, iOS shows no dialog. The flow stays on the screen that sent the request and doesn't run the outcome actions.
:::

To send the flow's permission requests to your handler, pass the handler in the `systemRequestsHandler` parameter of `AdaptyUI.getFlowConfiguration`:

```swift showLineNumbers title="Swift"
let flowConfiguration = try await AdaptyUI.getFlowConfiguration(
    forFlow: flow,
    systemRequestsHandler: FlowPermissionHandler()
)
```

The flow configuration keeps a strong reference to the handler, so you don't need to store one. Both SwiftUI and UIKit present the flow from this configuration, so the handler works with either. For details, see [Display flows & paywalls](ios-present-paywalls).

## Test the permission request

iOS shows each permission dialog only once per app install. To see the dialog again while you test the flow, delete the app from the device and install it again. Then open the flow and reach the **Request permission** action. If the screen stays and no dialog appears, the flow got no answer: make sure that you pass `systemRequestsHandler` to `AdaptyUI.getFlowConfiguration`.

To see which outcome section ran, read the flow's analytics events in the `didReceiveAnalyticEvent` callback. For where to implement it, see [Handle flow & paywall events](ios-handling-events).
