A [flow](adapty-flow-builder) can ask users for a system permission with the **Request permission** action. For example, an onboarding screen can explain push notifications and then ask for them, or a flow can ask for camera access before a feature that scans documents. The Adapty SDK doesn't show the system permission dialog itself. It sends the permission request to a handler in your app: a class that conforms to the `AdaptySystemRequestsHandler` protocol. Your app shows the dialog and passes the result to the flow. The flow then continues.

## Before you start

You need:

- **Adapty iOS SDK 4.0.0 or later**: Earlier versions don't have the `AdaptySystemRequestsHandler` protocol.
- **A flow with the Request permission action**: In the Flow & Paywall Builder, add the **Request permission** action to an element's **On Tap** or **On Screen Appear** trigger. In the action, select the permission in the **Permission** field. Add the actions for each result. The default **After response** action is **Navigate Next**. For the action settings, see [Request permission](onboarding-actions#request-permission).
- **A purpose string for each permission that your handler requests**: The text in `Info.plist` that tells users why your app needs the permission. See [Declare the permissions](#declare-the-permissions).

:::note
**If your app already has a handler for push notifications**: The handler keeps working. For its not-granted results, the flow runs the **After response** actions. To have the flow run the **When denied** actions, pass the argument `"denied"`, `"restricted"`, or `"permanently_denied"` to `.denied`. For example, `.denied("denied")`. To request other permissions, add their cases to the handler.
:::

## How the flow requests a permission

1. The flow reaches the **Request permission** action: the user taps the element, or the screen appears.
2. The Adapty SDK calls the `handlePermission(_:withCustomArgs:)` method of your handler with the permission selected in the action: an [`AdaptyPermission`](#declare-the-permissions) enum case, such as `.push` or `.camera`.
3. Your app requests the permission from iOS and returns `.granted` or `.denied`.

<FlowPermissionAnswers />

The flow waits on the screen until your app passes the result. If your app never passes a result, the flow stays on the screen. If the user already granted or declined the permission, iOS shows no dialog and returns the authorization status to your app at once. Your app then passes the result, and the flow runs the actions for that result right away. If those actions leave the screen, the user sees the screen that requests the permission only for a moment.

The flow sends your app one permission request at a time. [The trigger of the action](onboarding-actions#request-permission) determines how often the flow sends the request. Your handler can receive the same permission again, for example on each tap. Each time, return the result that matches the current authorization status.

## Implement the handler

:::warning
**Request only the permissions that your app declares, and return `.denied("unsupported")` for any other permission.** For most permissions, iOS terminates the app when the app requests a permission whose purpose string is missing from `Info.plist`. A flow author can add a request for any permission at any time, and the flow also reaches app versions released before the request was added.
:::

To handle permission requests, create a class that conforms to the `AdaptySystemRequestsHandler` protocol, and implement its `handlePermission(_:withCustomArgs:)` method. This handler requests push notifications and camera access. For every other permission, it returns `.denied("unsupported")` without a dialog:

```swift showLineNumbers title="Swift"
import AdaptyUI
import AdaptyUIBuilder

@MainActor
final class FlowPermissionHandler: AdaptySystemRequestsHandler {
    func handlePermission(
        _ permission: AdaptyPermission,
        withCustomArgs customArgs: [String: String]?
    ) async -> AdaptyPermissionResult {
        switch permission {
        case .push: return await requestPush()
        case .camera: return await requestCamera()
        // Add a case for each permission that your app requests.
        default:
            // A permission this app version doesn't request, or a value
            // the Adapty SDK doesn't know (.custom): pass the result without a dialog.
            return .denied("unsupported")
        }
    }
}
```

The handler calls the `requestPush()` and `requestCamera()` functions: copy them from [Code for each permission](#code-for-each-permission). To request another permission, add its case to the `switch` statement, and write the function that the case calls.

The `handlePermission(_:withCustomArgs:)` method receives:

- **`permission`**: The permission selected in the action. The `AdaptyPermission` enum has a case for each permission in [Declare the permissions](#declare-the-permissions). A value that the Adapty SDK doesn't know arrives as the `.custom(String)` enum case.
- **`customArgs`**: Custom arguments of the request. The **Request permission** action sends none, so the value is `nil`.

To pass the result to the flow:

1. In the `handlePermission(_:withCustomArgs:)` method, show the system dialog.
2. Return `.granted` if the user granted the permission, and `.denied` otherwise.
3. To have the flow run the **When denied** actions, pass the argument `"denied"`, `"restricted"`, or `"permanently_denied"` to `.denied`. For example, `.denied("permanently_denied")`. Without this argument, the flow runs the **After response** actions.

<FlowPermissionStrings />

The `.granted` and `.denied` enum cases take the string as an optional `String` argument. For example, `.granted("limited")`. With `.denied(nil)`, your app passes a not-granted result without a string, and the flow runs the **After response** actions.

The `AdaptySystemRequestsHandler` protocol also declares the `handleAppReviewRequest()` method. Its default implementation shows the App Store review prompt, so you don't need to implement it.

## Pass the handler to the flow configuration

:::warning
**Without a handler, the flow stops at the permission request.** If you don't pass a handler in the `systemRequestsHandler` parameter, your app shows no dialog. The flow stays on the screen that sent the request and doesn't run the **When allowed**, **When denied**, or **After response** actions.
:::

To send the flow's permission requests to your handler, pass the handler in the `systemRequestsHandler` parameter of the `AdaptyUI.getFlowConfiguration` method. In SDK 4.5 and later, this method requires the `preferredLocales` parameter: [pass the user's languages](localizations-and-locale-codes#pass-the-users-languages-to-the-sdk) there. Before 4.5, leave out the `preferredLocales` parameter:

```swift showLineNumbers title="Swift"
do {
    let flowConfiguration = try await AdaptyUI.getFlowConfiguration(
        forFlow: flow,
        preferredLocales: Locale.preferredLanguages,
        systemRequestsHandler: FlowPermissionHandler()
    )
    // present the flow with flowConfiguration
} catch {
    // handle the error
}
```

The flow configuration keeps a strong reference to the handler, so you don't need to store one. Both SwiftUI and UIKit present the flow from this configuration, so the handler works with either. For details, see [Display flows & paywalls](ios-present-paywalls).

## Declare the permissions

For each permission that your handler requests, add its purpose string to `Info.plist`. iOS shows this text in the permission alert. The table lists the keys and capabilities of each permission:

| Permission in the builder | `AdaptyPermission` | `Info.plist` keys and capabilities |
|:--------------------------|:-------------------|:-----------------------------------|
| [Push notifications](ios-system-permissions#push) | `.push` | None. The app only needs the Push Notifications capability to receive push notifications |
| [App tracking (ATT)](ios-system-permissions#tracking) | `.tracking` | `NSUserTrackingUsageDescription` |
| [Location while using the app](ios-system-permissions#location_when_use) | `.locationWhenInUse` | `NSLocationWhenInUseUsageDescription` |
| [Location always](ios-system-permissions#location_always) | `.locationAlways` | `NSLocationWhenInUseUsageDescription` and `NSLocationAlwaysAndWhenInUseUsageDescription` |
| [Precise location](ios-system-permissions#location_full_accuracy) | `.locationFullAccuracy` | `NSLocationWhenInUseUsageDescription` and `NSLocationTemporaryUsageDescriptionDictionary` |
| [Camera](ios-system-permissions#camera) | `.camera` | `NSCameraUsageDescription` |
| [Microphone](ios-system-permissions#microphone) | `.microphone` | `NSMicrophoneUsageDescription` |
| [Photos](ios-system-permissions#photos) | `.photos` | `NSPhotoLibraryUsageDescription`, or `NSPhotoLibraryAddUsageDescription` if the app only adds photos |
| [Media library](ios-system-permissions#media_library) | `.mediaLibrary` | `NSAppleMusicUsageDescription` |
| [Apple Music](ios-system-permissions#music) | `.music` | `NSAppleMusicUsageDescription` |
| [Speech recognition](ios-system-permissions#speech) | `.speech` | `NSSpeechRecognitionUsageDescription`, and `NSMicrophoneUsageDescription` for live audio |
| [Contacts](ios-system-permissions#contacts) | `.contacts` | `NSContactsUsageDescription` |
| [Calendar](ios-system-permissions#calendar) | `.calendar` | `NSCalendarsFullAccessUsageDescription` or `NSCalendarsWriteOnlyAccessUsageDescription`, and `NSCalendarsUsageDescription` before iOS 17 |
| [Reminders](ios-system-permissions#reminders) | `.reminders` | `NSRemindersFullAccessUsageDescription`, and `NSRemindersUsageDescription` before iOS 17 |
| [Health data](ios-system-permissions#health) | `.health` | `NSHealthShareUsageDescription` to read and `NSHealthUpdateUsageDescription` to write, and the HealthKit capability |
| [Motion & Fitness](ios-system-permissions#motion) | `.motion` | `NSMotionUsageDescription` |
| [Bluetooth](ios-system-permissions#bluetooth) | `.bluetooth` | `NSBluetoothAlwaysUsageDescription` |
| [Local network](ios-system-permissions#local_network) | `.localNetwork` | `NSLocalNetworkUsageDescription`, and `NSBonjourServices` for Bonjour |
| [HomeKit](ios-system-permissions#homekit) | `.homekit` | `NSHomeKitUsageDescription`, and the HomeKit capability |
| [Focus status](ios-system-permissions#focus_status) | `.focusStatus` | `NSFocusStatusUsageDescription`, and the Communication Notifications capability to read the status |
| [Siri](ios-system-permissions#siri) | `.siri` | `NSSiriUsageDescription`, and the Siri capability |

For example, an app that requests camera access with the code in [Camera](#camera) declares this key:

```xml title="Info.plist"
<key>NSCameraUsageDescription</key>
<string>Scan documents with the camera.</string>
```

[System permissions](ios-system-permissions) describes what users see for each permission, and which iOS versions and capabilities the permission needs. For each authorization status, the article lists the result to pass.

## Test the permission request

iOS shows most permission dialogs only once per app install. To see the dialog again while you test the flow, delete the app and install it again, or open **Settings > General > Transfer or Reset iPhone > Reset > Reset Location & Privacy**, which resets every app. Deleting the app doesn't reset every permission: for example, iOS can keep Bluetooth access after a reinstall. To see the first alert of every permission, install a build with a new bundle ID. Then open the flow and reach the **Request permission** action. If the screen stays and no dialog appears, the flow received no result: make sure that you pass your handler to the `AdaptyUI.getFlowConfiguration` method, in its `systemRequestsHandler` parameter.

## Track permission requests in analytics

To see how many users grant or decline each permission that a flow requests, read the permission events in the `didReceiveAnalyticEvent` callback. For where to implement it, see [Handle flow & paywall events](ios-handling-events).

## Code for each permission

Each function in this section requests one permission and returns the result for the flow. It compiles with the handler from [Implement the handler](#implement-the-handler) after you add its case to the `switch` statement. Where iOS can leave a request without a callback, the function stops waiting after 50 seconds or less: after 60 seconds without a result, the flow reports the `flow_permission_unanswered` event.

This section has functions for push notifications, camera access, and location while using the app. To request another permission, write its function in the pattern that fits its iOS API. For a direct request, follow the [camera function](#camera). For a request with a delegate callback, follow the [location function](#location_when_use). For what to request and which result to pass for each authorization status, see [System permissions](ios-system-permissions).

### Push notifications \{#push\}

Push notifications need no key in `Info.plist`. See [System permissions](ios-system-permissions#push).

```swift showLineNumbers title="Swift"
import AdaptyUI
import AdaptyUIBuilder
import UserNotifications

extension FlowPermissionHandler {
    func requestPush() async -> AdaptyPermissionResult {
        let center = UNUserNotificationCenter.current()
        switch await center.notificationSettings().authorizationStatus {
        case .authorized, .ephemeral:
            return .granted("granted")
        case .provisional:
            return .granted("provisional")
        case .denied:
            // The user declined earlier: iOS shows no alert.
            return .denied("permanently_denied")
        case .notDetermined:
            break
        @unknown default:
            return .denied(nil)
        }
        do {
            let granted = try await center.requestAuthorization(options: [.alert, .badge, .sound])
            return granted ? .granted("granted") : .denied("denied")
        } catch {
            // Not a choice of the user: the flow runs After response.
            return .denied(nil)
        }
    }
}
```

- With a granted notification permission, your app can show notifications. To receive push notifications, register the device with APNs and send the device token to your push provider, as your app does outside flows.

### Camera \{#camera\}

Add the `NSCameraUsageDescription` key to `Info.plist`. See [System permissions](ios-system-permissions#camera).

```swift showLineNumbers title="Swift"
import AdaptyUI
import AdaptyUIBuilder
import AVFoundation

extension FlowPermissionHandler {
    func requestCamera() async -> AdaptyPermissionResult {
        switch AVCaptureDevice.authorizationStatus(for: .video) {
        case .authorized:
            return .granted("granted")
        case .denied:
            // The user declined earlier: iOS shows no alert.
            return .denied("permanently_denied")
        case .restricted:
            return .denied("restricted")
        case .notDetermined:
            let granted = await AVCaptureDevice.requestAccess(for: .video)
            return granted ? .granted("granted") : .denied("denied")
        @unknown default:
            return .denied(nil)
        }
    }
}
```

### Location while using the app \{#location_when_use\}

Add the `NSLocationWhenInUseUsageDescription` key to `Info.plist`. See [System permissions](ios-system-permissions#location_when_use).

```swift showLineNumbers title="Swift"
import AdaptyUI
import AdaptyUIBuilder
import CoreLocation

extension FlowPermissionHandler {
    func requestLocationWhenInUse() async -> AdaptyPermissionResult {
        let request = LocationWhenInUseRequest()
        switch request.manager.authorizationStatus {
        case .authorizedWhenInUse, .authorizedAlways:
            return .granted("granted")
        case .denied:
            // The user declined earlier, or Location Services are off: iOS shows no alert.
            return .denied("permanently_denied")
        case .restricted:
            return .denied("restricted")
        case .notDetermined:
            break
        @unknown default:
            return .denied(nil)
        }
        switch await request.run() {
        case .authorizedWhenInUse, .authorizedAlways:
            // Also after Allow Once. To report approximate location, pass "limited"
            // when request.manager.accuracyAuthorization is .reducedAccuracy.
            return .granted("granted")
        case .denied:
            return .denied("denied")
        case .restricted:
            return .denied("restricted")
        default:
            // No decision before the timeout, for example without the purpose string.
            return .denied(nil)
        }
    }
}

@MainActor
private final class LocationWhenInUseRequest: NSObject, @preconcurrency CLLocationManagerDelegate {
    let manager = CLLocationManager()
    private var continuation: CheckedContinuation<CLAuthorizationStatus, Never>?

    func run() async -> CLAuthorizationStatus {
        await withCheckedContinuation { continuation in
            self.continuation = continuation
            manager.delegate = self
            manager.requestWhenInUseAuthorization()
            Task { @MainActor [weak self] in
                try? await Task.sleep(nanoseconds: 50 * NSEC_PER_SEC)
                self?.finish()
            }
        }
    }

    func locationManagerDidChangeAuthorization(_ manager: CLLocationManager) {
        // iOS also calls this method when it creates the manager, with .notDetermined.
        guard manager.authorizationStatus != .notDetermined else { return }
        finish()
    }

    private func finish() {
        continuation?.resume(returning: manager.authorizationStatus)
        continuation = nil
    }
}
```
