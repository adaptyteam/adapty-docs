A [flow](adapty-flow-builder) can ask users for a system permission with the **Request permission** action. For example, an onboarding screen can explain what push notifications are for and then ask for them, or a flow can ask for camera access before a feature that scans documents. The Adapty SDK doesn't show the system permission dialog itself. It passes the request to the `onShowRequestPermission` method of your flow event listener. Your app shows the dialog and passes the result to the flow, which then continues.

## Before you start

You need:

- **Adapty Android SDK 4.0.0 or later**: Earlier versions don't have the `onShowRequestPermission` method.
- **A flow with the Request permission action**: In the Flow & Paywall Builder, add the **Request permission** action to an element's **On Tap** or **On Screen Appear** trigger. In the action, select the permission in the **Permission** field. Add the actions for each result. The default **After response** action is **Navigate Next**. For the action settings, see [Request permission](onboarding-actions#request-permission).
- **A manifest permission for each permission that your listener requests**: See [Declare the permissions](#declare-the-permissions).
- **For push notifications, the `targetSdk` property set to 33 or higher**: Only apps that target Android 13 or later choose when the notification permission dialog appears.

:::note
**If your app already requests push notifications for flows**: Your override of the `onShowRequestPermission` method keeps working. To have the flow run the **When denied** actions, pass `"denied"`, `"restricted"`, or `"permanently_denied"` as the second argument of the `callback` parameter. For example, `callback(false, "denied")`. Without this argument, the flow runs the **After response** actions. To request other permissions, add their cases to the override.
:::

## How the flow requests a permission

1. The flow reaches the **Request permission** action: the user taps the element, or the screen appears.
2. The Adapty SDK calls the `onShowRequestPermission` method on the event listener of the flow view, with the `permission` parameter set to the permission selected in the action.
3. Your app requests the permission from Android and calls the `callback` parameter with the result.

<FlowPermissionAnswers />

The flow waits on the screen until your app calls the `callback` parameter. If your app never calls it, the flow stays on the screen. If Android doesn't show the dialog, your app receives the permission state at once, and the flow runs the actions for the result right away. If those actions leave the screen, the user sees the screen that requests the permission only for a moment. Android doesn't show the dialog in these cases:

- **Notifications on Android 12 and earlier**: Notifications need no runtime permission, so there is no dialog to show.
- **The user granted the permission before**: The permission is already granted.
- **The user declined the permission twice**: Android stops showing the dialog for that permission and denies each new request.

The flow sends your app one permission request at a time. [The trigger of the action](onboarding-actions#request-permission) determines how often the flow sends the request. Your listener can receive the same permission again, for example on each tap: pass the result that matches the current permission state.

## Override onShowRequestPermission

:::warning
**The default listener never asks the user.** The `AdaptyFlowDefaultEventListener` class passes `false` without a string for every permission request, and shows no dialog. If your listener extends the `AdaptyFlowDefaultEventListener` class and doesn't override the `onShowRequestPermission` method, the flow runs the **After response** actions right away.
:::

To show the system dialogs that a flow requests, override the `onShowRequestPermission` method in your event listener. Request only the permissions that your app declares. A flow author can add a request for any permission at any time, and app versions released before that change also get the request. For every other permission, call the `callback` parameter with `false` and the string `"unsupported"`, without a dialog.

In this example, the activity that shows the flow has a listener that requests push notifications and camera access. A small helper class, `RuntimePermissionRequester`, registers one launcher for the system dialog, and the permission functions in [Code for each permission](#code-for-each-permission) share it:

```kotlin showLineNumbers title="Kotlin"
import android.content.Context
import android.content.pm.PackageManager
import androidx.activity.ComponentActivity
import androidx.activity.result.contract.ActivityResultContracts
import androidx.core.app.ActivityCompat
import androidx.core.content.ContextCompat
import androidx.core.content.edit
import com.adapty.ui.listeners.AdaptyFlowDefaultEventListener
import com.adapty.ui.listeners.AdaptyFlowEventListener.PermissionCallback

class FlowActivity : ComponentActivity() {

    // Create the requester with the activity: it registers its launcher before the activity starts.
    private val requester = RuntimePermissionRequester(this)

    private val eventListener = object : AdaptyFlowDefaultEventListener() {
        override fun onShowRequestPermission(
            permission: String?,
            customArgs: Map<String, String>?,
            callback: PermissionCallback,
            context: Context,
        ) {
            try {
                when (permission) {
                    "push" -> requestPush(requester, callback)
                    "camera" -> requestCamera(requester, callback)
                    // Add a case for each permission that your app requests.
                    // A permission that this app version doesn't request: pass the result without a dialog.
                    else -> callback(false, "unsupported")
                }
            } catch (e: Exception) {
                callback(false, null)
            }
        }
    }

    // Pass eventListener to the flow view.
}

/** Shows the system dialog for runtime permissions, and tells a refusal in the dialog from one without a dialog. */
class RuntimePermissionRequester(val activity: ComponentActivity) {

    // Android can't tell whether the app requested a permission before, so the app keeps a flag.
    // Lazy: the activity has no context yet when it creates its properties.
    private val requestedPermissions by lazy { activity.getSharedPreferences("flow_permissions", Context.MODE_PRIVATE) }
    private var permissions = emptyArray<String>()
    private var rationaleBefore = false
    private var requestedBefore = false
    private var onResult: ((String?) -> Unit)? = null

    private val launcher =
        activity.registerForActivityResult(ActivityResultContracts.RequestMultiplePermissions()) {
            val onResult = onResult ?: return@registerForActivityResult
            this.onResult = null
            val rationaleAfter = permissions.any { ActivityCompat.shouldShowRequestPermissionRationale(activity, it) }
            val refusal = when {
                // The user declined the dialog.
                rationaleBefore || rationaleAfter -> "denied"
                // No rationale before a repeated request: Android showed no dialog.
                requestedBefore -> "permanently_denied"
                // The user closed the dialog without a choice: the flow runs After response.
                else -> null
            }
            onResult(refusal)
        }

    fun isGranted(permission: String) =
        ContextCompat.checkSelfPermission(activity, permission) == PackageManager.PERMISSION_GRANTED

    /** Shows the dialog, then calls [onResult] with the string to pass if the user granted nothing. */
    fun request(permissions: Array<String>, onResult: (refusal: String?) -> Unit) {
        this.permissions = permissions
        rationaleBefore = permissions.any { ActivityCompat.shouldShowRequestPermissionRationale(activity, it) }
        requestedBefore = permissions.any { requestedPermissions.getBoolean(it, false) }
        requestedPermissions.edit { permissions.forEach { putBoolean(it, true) } }
        // A request from another flow that still waits gets a result without a string.
        this.onResult?.invoke(null)
        this.onResult = onResult
        launcher.launch(permissions)
    }

    /** Requests permissions that the user grants together, and passes the result to the flow. */
    fun requestAll(permissions: Array<String>, callback: PermissionCallback) {
        if (permissions.all(::isGranted)) return callback(true, "granted")
        request(permissions) { refusal ->
            if (permissions.all(::isGranted)) callback(true, "granted") else callback(false, refusal)
        }
    }
}
```

The listener calls the `requestPush()` and `requestCamera()` functions: copy them from [Code for each permission](#code-for-each-permission). To request another permission, add its case to the `when` expression, and write the function that the case calls.

The `onShowRequestPermission` method receives:

- **`permission`**: The permission selected in the action, as a string from the **Value** column in [Declare the permissions](#declare-the-permissions).
- **`customArgs`**: Custom arguments of the request. The **Request permission** action sends none, so the value is `null`.
- **`callback`**: The callback that passes the result to the flow. Its parameters are `granted` and `detailResult`.
- **`context`**: A UI context of the flow view.

To pass the result to the flow:

1. In the `onShowRequestPermission` method, show the system dialog.
2. Call the `callback` parameter with `true` if the user granted the permission, and `false` otherwise.
3. To have the flow run the **When denied** actions, pass `"denied"`, `"restricted"`, or `"permanently_denied"` as the second argument of the `callback` parameter. For example, `callback(false, "permanently_denied")`. Without this argument, the flow runs the **After response** actions.

<FlowPermissionStrings />

Call the `callback` parameter once for every request. The Adapty SDK doesn't catch exceptions from the `onShowRequestPermission` method, so the example catches them and calls `callback(false, null)`.

The `RuntimePermissionRequester` class passes the following strings with a not-granted result:

- **The user declined the permission in the dialog**: `denied`.
- **Android showed no dialog after an earlier refusal**: `permanently_denied`.
- **The user closed the dialog without a choice**: No string. The flow runs the **After response** actions.

With `denied` or `permanently_denied`, the flow runs the **When denied** actions. The two strings only differ in the `outcome` property of the [`flow_permission_answered` event](#track-permission-requests-in-analytics).

To find out which case applies, the helper calls the `shouldShowRequestPermissionRationale()` method before and after the dialog, and keeps a flag for each permission that the app requested before. For the rule that tells these cases apart, see [System permissions](android-system-permissions#rules-for-every-permission).

The helper keeps its flags in the `flow_permissions` shared preferences file. After Android Auto Backup restores these flags on a new installation, the helper passes `permanently_denied` for a first dialog closed without a choice. To keep the flags out of a new installation, exclude `flow_permissions.xml` from backups, as [Android backup rules](sdk-installation-android#android-backup-rules-auto-backup-configuration) describes. Add one line for the file to each rules file:

- In the `full-backup-content` file, for Android 11 and earlier: `<exclude domain="sharedpref" path="flow_permissions.xml"/>`.
- In the `data-extraction-rules` file, for Android 12 and later: the same line in both the `cloud-backup` and `device-transfer` elements.

In Jetpack Compose, create a `RuntimePermissionRequester` instance as a property of the activity that calls the `setContent` function, and pass the requester to the composable that creates the event listener.

Android can recreate the activity while the dialog is open, for example on rotation. The new `RuntimePermissionRequester` instance then has no pending callback, and the flow receives no result.

## Pass the listener to the flow

The Adapty SDK sends permission requests to the event listener of the flow view. When you create the view, pass the listener with your override in the `eventListener` parameter. The `AdaptyUI.getFlowView()` method, the `AdaptyFlowView.showFlow()` method, and the `AdaptyFlowScreen()` composable function have this parameter. See [Display flows & paywalls](android-present-paywalls) for these calls, and [Handle flow & paywall events](android-handling-events) for the other listener methods.

## Declare the permissions

Android shows a permission dialog only for a permission that the app declares in its manifest. For each permission that your listener requests, add its `<uses-permission>` element to `AndroidManifest.xml`:

| Permission in the builder | Value | Manifest permission |
|:--------------------------|:------|:--------------------|
| [Push notifications](android-system-permissions#push) | `push` | `POST_NOTIFICATIONS`, Android 13 and later |
| [Location while using the app](android-system-permissions#location_when_use) | `location_when_use` | `ACCESS_COARSE_LOCATION`, and `ACCESS_FINE_LOCATION` for precise location |
| [Location always](android-system-permissions#location_always) | `location_always` | `ACCESS_BACKGROUND_LOCATION`, Android 10 and later, with the foreground location permissions |
| [Precise location](android-system-permissions#location_full_accuracy) | `location_full_accuracy` | `ACCESS_FINE_LOCATION` and `ACCESS_COARSE_LOCATION` |
| [Camera](android-system-permissions#camera) | `camera` | `CAMERA` |
| [Microphone](android-system-permissions#microphone) | `microphone` | `RECORD_AUDIO` |
| [Photos](android-system-permissions#photos) | `photos` | `READ_MEDIA_IMAGES` and `READ_MEDIA_VIDEO`, Android 13 and later. `READ_MEDIA_VISUAL_USER_SELECTED`, Android 14 and later. `READ_EXTERNAL_STORAGE`, Android 12 and earlier |
| [Media library](android-system-permissions#media_library) | `media_library` | `READ_MEDIA_AUDIO`, Android 13 and later. `READ_EXTERNAL_STORAGE`, Android 12 and earlier |
| [Speech recognition](android-system-permissions#speech) | `speech` | `RECORD_AUDIO` |
| [Contacts](android-system-permissions#contacts) | `contacts` | `READ_CONTACTS`, and `WRITE_CONTACTS` to write contacts |
| [Calendar](android-system-permissions#calendar) | `calendar` | `READ_CALENDAR`, and `WRITE_CALENDAR` to add events |
| [Health data](android-system-permissions#health) | `health` | Health Connect permissions for each data type, such as `android.permission.health.READ_STEPS`, requested with the Health Connect contract, not with `RequestPermission` |
| [Motion & Fitness](android-system-permissions#motion) | `motion` | `ACTIVITY_RECOGNITION`, Android 10 and later |
| [Bluetooth](android-system-permissions#bluetooth) | `bluetooth` | `BLUETOOTH_SCAN` and `BLUETOOTH_CONNECT`, and `BLUETOOTH_ADVERTISE` to advertise, Android 12 and later, for apps that target Android 12 or higher. `ACCESS_FINE_LOCATION`, `BLUETOOTH`, and `BLUETOOTH_ADMIN` up to Android 11 |
| [Local network](android-system-permissions#local_network) | `local_network` | `ACCESS_LOCAL_NETWORK`, Android 17 and later, for apps that target Android 17 or higher |

For example, an app that requests notifications and camera access declares these permissions:

```xml title="AndroidManifest.xml"
<uses-permission android:name="android.permission.POST_NOTIFICATIONS" />
<uses-permission android:name="android.permission.CAMERA" />
```

Android has no permission for the other values: `tracking`, `music`, `reminders`, `homekit`, `focus_status`, and `siri`. For these values, call the `callback` parameter with `false` and the string `"unsupported"`. For what each permission shows users, the Android versions it needs, and the result to pass for each permission state, see [System permissions](android-system-permissions).

## Test the permission request

To test a notification request, use a device with Android 13 or later: earlier versions show no notification dialog. Android stops showing a permission dialog after the user grants the permission or declines it twice. To see the dialog again while you test the flow, clear the app data with `adb shell pm clear <package>`. This command resets the permission and the flags of the `RuntimePermissionRequester` class together. Then open the flow and reach the **Request permission** action. If the flow moves on without a dialog, make sure that your listener overrides the `onShowRequestPermission` method with a case for the permission, and that the app declares the manifest permission. For notifications, also make sure that the `targetSdk` property meets the requirement in [Before you start](#before-you-start).

## Track permission requests in analytics

To see how many users grant or decline each permission that a flow requests, read the permission events in the [`onAnalyticEvent`](android-handling-events#analytics-events) method of your listener.

## Code for each permission

Each function in this section requests one permission and passes the result to the flow. The functions that show a runtime dialog use the `RuntimePermissionRequester` class from [Override onShowRequestPermission](#override-onshowrequestpermission).

To request another permission, write its function. For a request where every permission must be granted, follow the [camera function](#camera). For a request where one of several permissions is enough, follow the [location function](#location_when_use). For what to request and which result to pass for each permission state, see [System permissions](android-system-permissions).

### Push notifications \{#push\}

Add the `POST_NOTIFICATIONS` permission to `AndroidManifest.xml`. See [System permissions](android-system-permissions#push).

```kotlin showLineNumbers title="Kotlin"
import android.Manifest
import android.os.Build
import androidx.core.app.NotificationManagerCompat
import com.adapty.ui.listeners.AdaptyFlowEventListener.PermissionCallback

fun requestPush(requester: RuntimePermissionRequester, callback: PermissionCallback) {
    if (Build.VERSION.SDK_INT < Build.VERSION_CODES.TIRAMISU) {
        // Android 12 and earlier show no dialog: the user turns notifications off in the settings.
        val enabled = NotificationManagerCompat.from(requester.activity).areNotificationsEnabled()
        callback(enabled, if (enabled) "granted" else "permanently_denied")
        return
    }
    requester.requestAll(arrayOf(Manifest.permission.POST_NOTIFICATIONS), callback)
}
```

- With a granted notification permission, your app can show notifications. To receive push notifications, register the device with your push provider, such as Firebase Cloud Messaging, as your app does outside flows.

### Camera \{#camera\}

Add the `CAMERA` permission to `AndroidManifest.xml`. See [System permissions](android-system-permissions#camera).

```kotlin showLineNumbers title="Kotlin"
import android.Manifest
import android.content.pm.PackageManager
import com.adapty.ui.listeners.AdaptyFlowEventListener.PermissionCallback

fun requestCamera(requester: RuntimePermissionRequester, callback: PermissionCallback) {
    if (!requester.activity.packageManager.hasSystemFeature(PackageManager.FEATURE_CAMERA_ANY)) {
        return callback(false, "unsupported")
    }
    requester.requestAll(arrayOf(Manifest.permission.CAMERA), callback)
}
```

- Google Play installs an app with the `CAMERA` permission only on devices with a back camera, unless the app declares `<uses-feature android:name="android.hardware.camera" android:required="false" />`.

### Location while using the app \{#location_when_use\}

Add the `ACCESS_COARSE_LOCATION` permission to `AndroidManifest.xml`, and the `ACCESS_FINE_LOCATION` permission for precise location. See [System permissions](android-system-permissions#location_when_use).

```kotlin showLineNumbers title="Kotlin"
import android.Manifest
import com.adapty.ui.listeners.AdaptyFlowEventListener.PermissionCallback

fun requestLocationWhenInUse(requester: RuntimePermissionRequester, callback: PermissionCallback) {
    // Request both: some Android 12 releases ignore a request for ACCESS_FINE_LOCATION alone.
    val permissions = arrayOf(Manifest.permission.ACCESS_FINE_LOCATION, Manifest.permission.ACCESS_COARSE_LOCATION)
    // Precise or approximate location. To report approximate location in analytics, pass "limited" for it.
    if (permissions.any(requester::isGranted)) return callback(true, "granted")
    requester.request(permissions) { refusal ->
        if (permissions.any(requester::isGranted)) callback(true, "granted") else callback(false, refusal)
    }
}
```
