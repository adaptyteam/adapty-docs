The **Request permission** action of a flow asks your app for a system permission, such as push notifications, location, or camera access. This page lists every permission that the action can request. For each permission, it describes what users see, what your app declares on iOS and Android, and which answer your app passes for each result of the system request. Use it when you add the action to a flow, and when you write the code that answers the request.

To answer the requests in your app, see the guide for [iOS](ios-handle-permissions), [Android](android-handle-permissions), [React Native](react-native-handle-permissions), [Flutter](flutter-handle-permissions), [Unity](unity-handle-permissions), [Kotlin Multiplatform](kmp-handle-permissions), or [Capacitor](capacitor-handle-permissions).

:::tip
To add the request to a flow, see [Request permission](onboarding-actions#request-permission).
:::

## Rules for every permission

- **Link only what you request**: Link only the frameworks of the permissions that your app requests, and answer the others as `unsupported` without a call to the OS. Apple notes that [libraries and SDKs can reference APIs that require a purpose string](https://developer.apple.com/documentation/uikit/requesting-access-to-protected-resources).
- **Read the current status before you request**: For most permissions, the OS shows the dialog once, and later requests return the stored answer without a dialog. Some iOS requests never call back when the status is already decided. [`CLLocationManager.requestWhenInUseAuthorization()`](https://developer.apple.com/documentation/corelocation/cllocationmanager/requestwheninuseauthorization()) does nothing and doesn't call the delegate when the status isn't `.notDetermined`. After the first call to [`requestAlwaysAuthorization()`](https://developer.apple.com/documentation/corelocation/cllocationmanager/requestalwaysauthorization()), further calls have no effect. Read the status first, and answer at once when it's decided.
- **Wait for indirect requests with a timeout**: iOS has no request method for **Bluetooth**, **Motion & Fitness**, **Local network**, and **HomeKit**. The alert appears when the app first uses the framework, and the result arrives in a delegate method or a query handler, or not at all. Wrap the wait in a timeout shorter than 60 seconds, then answer from the current status, or without a status. After 60 seconds without an answer, the flow reports `flow_permission_unanswered`.
- **Tell a new refusal from an earlier one**: iOS keeps every refusal until the user changes it in Settings. On iOS, pass `denied` when the user declined the alert of this request, and `permanently_denied` when iOS showed no alert because the user declined earlier. On Android 11 and later, the OS stops showing the dialog after the user denies a permission twice. On Android, `shouldShowRequestPermissionRationale()` also returns `false` after a dialog that the user closed without a choice. So read it before and after the request, and keep a flag for each permission that your app requested before. Apply the cases in this order:
  1. **A rationale before or after the request**: The user declined the dialog. Pass `denied`.
  2. **No rationale before or after the request, and the app requested the permission before**: Android showed no dialog. Pass `permanently_denied`.
  3. **No rationale before or after the first request, and no grant**: The user closed the dialog without a choice. Answer without a status, so the flow runs **After response**.

  On later requests, Android can't tell a dialog closed without a choice from a refusal without a dialog, for example after an **Only this time** grant expires. Such a request follows the second case and passes `permanently_denied`.
- **Request from the activity on screen**: On Android, request the permission from the activity that is on screen while the flow is shown. Android delivers a permission result only to a resumed activity. When the flow has its own activity, a request from the activity behind it gets its result only after the flow closes.
- **Read the status at every request**: Some grants expire. **Allow Once** on iOS and **Only this time** on Android last while the app is in use. Temporary full accuracy on iOS expires on its own. For apps that target Android 11 or higher, Android resets the permissions of an app that the user hasn't used for a few months. Don't store an answer for a later request.
- **Explain the permission, and add a way past it**: Put the request on the **On Tap** trigger of a button on a screen that explains the permission. Add another way off that screen, such as a **Skip** button that runs **Navigate Next**. Without it, the builder warns you: an app version that doesn't answer the request leaves the user on the screen. Apple's [Human Interface Guidelines](https://developer.apple.com/design/human-interface-guidelines/privacy) recommend a screen with only one button, such as **Continue**, that opens the system alert. Use that design only when every app version that sees the flow answers the request.
- **Let the user go on after a refusal**: [App Review Guideline 5.1.2(i)](https://developer.apple.com/app-store/review/guidelines/#data-use-and-sharing) doesn't allow an app to require system functionality, such as push notifications, location services, or tracking, to use the app. Add a way forward to **When denied**, such as **Navigate Next**. A **When denied** section that leaves the user without a way forward risks rejection. Guideline 5.1.1(iv) also asks apps to respect the user's permission settings and not to manipulate, trick, or force users to consent.
- **Reset the answers when you test**: To see a dialog again on iOS, delete the app, or open **Settings > General > Transfer or Reset iPhone > Reset > Reset Location & Privacy**, which resets every app. Deleting the app doesn't reset every permission: Bluetooth access, for example, can survive a reinstall of the same bundle ID. To see the first alert again, use a build with a new bundle ID. On Android, delete the app, or clear its data with `adb shell pm clear <package>`. Clearing the data also resets the flags that your app keeps for earlier requests. `adb shell pm revoke` and `pm clear-permission-flags` reset only the permission, so the app's flags then report an earlier request. Don't install the test build with `adb install -g`: it grants every runtime permission, so no dialog appears.

## Notifications and tracking

### Push notifications \{#push\}

- **What the user sees**: On iOS, an alert that asks to allow notifications. On Android 13 and later, a dialog with **Allow** and **Don't allow**. The user can also swipe the Android dialog away, which leaves the permission unchanged. Android 12 and earlier show no dialog: notifications are on unless the user turns them off in the system settings.
- **Platforms**: iOS and Android.
- **iOS setup**: No `Info.plist` key. Request the permission with `UNUserNotificationCenter.requestAuthorization(options:)`. To receive remote push notifications, the app also needs the Push Notifications capability and registers with APNs. The permission itself doesn't need them.
- **Android setup**: `<uses-permission android:name="android.permission.POST_NOTIFICATIONS" />`, a runtime permission on Android 13 (API 33) and later. Only apps that target API 33 or higher decide when the dialog appears. For an app that targets API 32 or lower, Android shows the dialog when the app starts an activity after it creates its first notification channel. After one **Don't allow**, Android doesn't show it to such an app again until the app is reinstalled. On Android 12 and earlier, answer from `NotificationManagerCompat.areNotificationsEnabled()` without a dialog.

Answer the request from the notification authorization status:

| OS | Native result | Answer | Section | `outcome` |
|:---|:--------------|:-------|:--------|:----------|
| iOS | `.notDetermined`, then the user allows | Granted, `granted` | **When allowed** | `granted` |
| iOS | `.notDetermined`, then the user declines | Not granted, `denied` | **When denied** | `denied` |
| iOS | `.denied` before the request | Not granted, `permanently_denied` | **When denied** | `permanently_denied` |
| iOS | `.authorized`, or `.ephemeral` in an App Clip | Granted, `granted` | **When allowed** | `granted` |
| iOS | `.provisional`, after a request with the `.provisional` option | Granted, `provisional` | **When allowed** | `provisional` |
| iOS | `requestAuthorization(options:)` throws an error | Not granted, no status | **After response** | `no_status` |
| Android 13+ | Granted | Granted, `granted` | **When allowed** | `granted` |
| Android 13+ | Denied in the dialog | Not granted, `denied` | **When denied** | `denied` |
| Android 13+ | Denied, and Android showed no dialog | Not granted, `permanently_denied` | **When denied** | `permanently_denied` |
| Android 13+ | The user swiped the dialog away on the first request | Not granted, no status | **After response** | `no_status` |
| Android 12 and earlier | Notifications are on | Granted, `granted` | **When allowed** | `granted` |
| Android 12 and earlier | Notifications are off | Not granted, `permanently_denied` | **When denied** | `permanently_denied` |

- **Limitations**:
  - iOS shows the alert once: later requests return the first answer. With the `.provisional` option, iOS grants quiet notifications without an alert, so the flow runs **When allowed** right away and the user sees no dialog. Request `.provisional` only if the flow expects that.
  - On Android 13 and later, the user can block notifications for the app in the settings while `POST_NOTIFICATIONS` stays granted. `areNotificationsEnabled()` then returns `false`. If the flow needs visible notifications, answer from `areNotificationsEnabled()`.
- **Cross-platform notes**: The `provisional` status exists only on iOS.

### App tracking (ATT) \{#tracking\}

- **What the user sees**: On iOS, the App Tracking Transparency alert with your purpose string. In France, Germany, Italy, Poland, and Romania, iOS shows a full-page sheet instead of the alert. iOS shows nothing and returns the current status when tracking is restricted, or when the user turned off **Allow Apps to Request to Track** in Settings. iOS also shows nothing when another request waits for an answer, the request comes from an app extension, or the app isn't active.
- **Platforms**: iOS only. Android has no such permission: answer `unsupported`, and the flow runs **After response**.
- **iOS setup**: `NSUserTrackingUsageDescription`. An app that uses the AppTrackingTransparency framework without this key crashes. For the full-page sheet, you can add `NSUserTrackingMarkdownUsageDescription`. Request the permission with `ATTrackingManager.requestTrackingAuthorization()`.
- **Android setup**: None: answer `unsupported` without a dialog. The advertising ID on Android uses the install-time permission `com.google.android.gms.permission.AD_ID`, which asks the user nothing. Don't report `granted` because the app has an advertising ID.

Answer the request from the tracking authorization status:

| OS | Native result | Answer | Section | `outcome` |
|:---|:--------------|:-------|:--------|:----------|
| iOS | `.notDetermined`, then the user allows | Granted, `granted` | **When allowed** | `granted` |
| iOS | `.notDetermined`, then the user declines | Not granted, `denied` | **When denied** | `denied` |
| iOS | `.denied` before the request. In the EU, less than a year after the user's answer | Not granted, `permanently_denied` | **When denied** | `permanently_denied` |
| iOS | `.restricted` | Not granted, `restricted` | **When denied** | `restricted` |
| iOS | `.authorized` | Granted, `granted` | **When allowed** | `granted` |
| iOS | `.notDetermined` after the request: iOS closed the prompt without a decision, the app wasn't active, or another request waited for an answer | Not granted, no status | **After response** | `no_status` |
| Android | Any request | Not granted, `unsupported` | **After response** | `unsupported` |

- **Limitations**:
  - iOS shows the alert only while the app is active. With **On Screen Appear** on the first screen after launch, the request can arrive before the app is active. Before the request, read `UIApplication.shared.applicationState`. Only if it isn't `.active`, wait for `UIApplication.didBecomeActiveNotification`: an app that is already active never receives it.
  - In the EU, iOS lets the app ask again a year after the user's answer, whether the user allowed tracking or not. This doesn't apply when the user turned tracking off in Settings. Store the date of the answer, and after a year, request again instead of answering `permanently_denied`. See [`requestTrackingAuthorization`](https://developer.apple.com/documentation/apptrackingtransparency/attrackingmanager/requesttrackingauthorization(completionhandler:)).
  - [App Review Guideline 5.1.2(i)](https://developer.apple.com/app-store/review/guidelines/#data-use-and-sharing) requires the ATT permission for tracking. The app can't require tracking for access to features or for rewards.
  - A screen before the ATT alert must not offer an incentive, imitate the system alert, show an image of it, or annotate the screen behind it. Apple's [Human Interface Guidelines](https://developer.apple.com/design/human-interface-guidelines/privacy#Tracking-requests) say that App Review rejects such screens.
  - After the user answers, send the ATT status to Adapty. See [Deal with ATT](ios-deal-with-att).

## Location

### Location while using the app \{#location_when_use\}

- **What the user sees**: On iOS, an alert with **Allow Once**, **Allow While Using App**, and **Don't Allow**, and a **Precise** switch. On Android 12 and later, a dialog with a choice of **Precise** or **Approximate**, and the buttons **While using the app**, **Only this time**, and **Don't allow**. If the app requests only `ACCESS_COARSE_LOCATION`, the Android dialog offers only approximate location.
- **Platforms**: iOS and Android.
- **iOS setup**: `NSLocationWhenInUseUsageDescription`. Request the permission with `CLLocationManager.requestWhenInUseAuthorization()`. The status arrives in `locationManagerDidChangeAuthorization(_:)`. iOS also calls this method when the app creates the `CLLocationManager`, with the current status. Ignore `.notDetermined`, and answer only after a status change that follows the request. The app must be in the foreground to show the alert.
- **Android setup**: `ACCESS_COARSE_LOCATION`, and `ACCESS_FINE_LOCATION` for precise location. Request both permissions together: some Android 12 releases ignore a request for `ACCESS_FINE_LOCATION` alone.

Answer the request from the location authorization status:

| OS | Native result | Answer | Section | `outcome` |
|:---|:--------------|:-------|:--------|:----------|
| iOS | `.notDetermined`, then **Allow While Using App** or **Allow Once** | Granted, `granted` | **When allowed** | `granted` |
| iOS | `.notDetermined`, then **Don't Allow** | Not granted, `denied` | **When denied** | `denied` |
| iOS | Still `.notDetermined` after the request, or no answer before the app's timeout | Not granted, no status | **After response** | `no_status` |
| iOS | `.denied` before the request, including Location Services turned off and Airplane mode | Not granted, `permanently_denied` | **When denied** | `permanently_denied` |
| iOS | `.restricted` | Not granted, `restricted` | **When denied** | `restricted` |
| iOS | `.authorizedWhenInUse` or `.authorizedAlways` | Granted, `granted` | **When allowed** | `granted` |
| Android | Precise or approximate location granted | Granted, `granted` | **When allowed** | `granted` |
| Android | Denied in the dialog | Not granted, `denied` | **When denied** | `denied` |
| Android | Denied, and Android showed no dialog | Not granted, `permanently_denied` | **When denied** | `permanently_denied` |

To report approximate location in analytics, pass `limited` with the granted answer instead of `granted`. The flow still runs **When allowed**.

- **Limitations**:
  - If the status isn't `.notDetermined`, [`requestWhenInUseAuthorization()`](https://developer.apple.com/documentation/corelocation/cllocationmanager/requestwheninuseauthorization()) does nothing and doesn't call the delegate. If `NSLocationWhenInUseUsageDescription` is missing, [the request fails at once](https://developer.apple.com/documentation/corelocation/requesting-authorization-to-use-location-services). A handler that waits for a status change in these cases never answers, and the flow stays on the screen. Read `authorizationStatus` first, answer at once when it isn't `.notDetermined`, and wrap the wait in a timeout.
  - **Allow Once** on iOS and **Only this time** on Android grant access while the app is in use. On iOS, the status then returns to `.notDetermined`, so the alert appears again later.
  - When the user changes precise location to approximate, in the dialog or in the Android settings, Android restarts the app process.
- **Cross-platform notes**: On Android, request this permission before **Location always** and **Precise location**: both need location access while the app is in use first. On iOS, **Location always** can also start from `.notDetermined`, with two alerts.

### Location always \{#location_always\}

- **What the user sees**: Two steps on both OSes.
  - **iOS, no answer yet**: The alert for location while using the app. **Allow While Using App** grants provisional Always access. iOS asks the second question, **Keep Only While Using** or **Change to Always Allow**, later, typically while the app isn't running.
  - **iOS, location while using the app already granted**: The upgrade alert, with **Keep Only While Using** and **Change to Always Allow**, at once. After **Allow Once**, or after an earlier Always request, iOS ignores the request and shows nothing.
  - **Android 10**: The dialog includes **Allow all the time**.
  - **Android 11 and later**: For apps that target Android 11 or higher, the dialog has no **Allow all the time** option. The user turns on background location on a settings page.
- **Platforms**: iOS and Android. Android 9 and earlier grant background location together with foreground location.
- **iOS setup**: `NSLocationWhenInUseUsageDescription` and `NSLocationAlwaysAndWhenInUseUsageDescription`. Request the permission with `CLLocationManager.requestAlwaysAuthorization()`. Location updates in the background also need the Background Modes capability. The permission itself doesn't need it.
- **Android setup**: `ACCESS_BACKGROUND_LOCATION`, from Android 10 (API 29), in addition to `ACCESS_COARSE_LOCATION` and `ACCESS_FINE_LOCATION`. Request foreground location first, then background location in a separate request. For apps that target Android 11 or higher, a request for foreground and background location together grants neither. Google Play restricts background location to an app's core features.

Answer the request from the location authorization status:

| OS | Native result | Answer | Section | `outcome` |
|:---|:--------------|:-------|:--------|:----------|
| iOS | `.notDetermined`, then **Allow While Using App** in the first alert: `.authorizedAlways`, provisional Always access | Granted, `provisional` | **When allowed** | `provisional` |
| iOS | `.notDetermined`, then **Allow Once** in the first alert: `.authorizedWhenInUse`, temporary access | Granted, `provisional` | **When allowed** | `provisional` |
| iOS | `.notDetermined`, then **Don't Allow** | Not granted, `denied` | **When denied** | `denied` |
| iOS | Still `.notDetermined` after the request, or no answer before the app's timeout | Not granted, no status | **After response** | `no_status` |
| iOS | `.authorizedWhenInUse`, the upgrade alert appears, then **Change to Always Allow** | Granted, `granted` | **When allowed** | `granted` |
| iOS | `.authorizedWhenInUse`, the upgrade alert appears, then **Keep Only While Using** | Not granted, `denied` | **When denied** | `denied` |
| iOS | `.authorizedWhenInUse`, and no alert appears: after **Allow Once**, or after an earlier Always request | Not granted, `permanently_denied` | **When denied** | `permanently_denied` |
| iOS | `.authorizedAlways` | Granted, `granted` | **When allowed** | `granted` |
| iOS | `.denied` | Not granted, `permanently_denied` | **When denied** | `permanently_denied` |
| iOS | `.restricted` | Not granted, `restricted` | **When denied** | `restricted` |
| Android 10+ | Foreground location not granted in its request | As for **Location while using the app**: `denied`, `permanently_denied`, or no status | **When denied**, or **After response** without a status | As the status |
| Android 10+ | Background location granted | Granted, `granted` | **When allowed** | `granted` |
| Android 10+ | Background location not granted when the user comes back, or Android showed no settings page | Not granted, `denied` | **When denied** | `denied` |
| Android 9 and earlier | Foreground location granted | Granted, `granted` | **When allowed** | `granted` |

- **Limitations**:
  - iOS may show no alert, so don't wait for the app to become active. After the request, wait a short time for the alert. If no alert appears, answer from the status at once. If the alert appears, answer when the app becomes active again: **Keep Only While Using** doesn't call the delegate, because the status doesn't change. Never wait longer than 60 seconds.
  - iOS accepts one Always request per install: later calls have no effect. iOS has no API that tells whether the app asked before, so the app saves its own flag after the first request.
  - In the first alert, **Allow While Using App** reports `.authorizedAlways` for provisional Always access, and **Allow Once** reports `.authorizedWhenInUse`. Both answer `provisional`. On a later request, provisional Always access reads as `.authorizedAlways` and answers `granted`. After **Allow Once**, the access is temporary, and iOS ignores later Always requests, so a later request answers `permanently_denied`. With provisional Always access, the user can choose **Keep Only While Using** later, outside the flow.
  - On Android 11 and later, the user leaves the app for the settings page. Read the permission state when the user comes back to the app, and answer then.
- **Cross-platform notes**: Android needs foreground location first, so request **Location while using the app** on an earlier screen. On iOS, the request can also start from `.notDetermined`.

### Precise location \{#location_full_accuracy\}

- **What the user sees**: On iOS, after the user turned off **Precise** in the location alert, an alert that asks for precise location once. It shows the text of your purpose key and the buttons **Allow Once** and **Don't Allow**. On Android 12 and later, after the user chose approximate location, a dialog offers precise location, precise location only this time, or approximate location. If the user chose **Only this time** with approximate location, the Android dialog offers only this time or keeping approximate location.
- **Platforms**: iOS and Android. On Android 11 and earlier, the dialog has no choice of approximate location: an app that requests `ACCESS_FINE_LOCATION` gets precise location.
- **iOS setup**: `NSLocationWhenInUseUsageDescription` and `NSLocationTemporaryUsageDescriptionDictionary`. Each key of the dictionary is a purpose key, and its value is the text of the alert. Request the permission with `CLLocationManager.requestTemporaryFullAccuracyAuthorization(withPurposeKey:)`. The flow sends no purpose key, so the app code passes one of its own keys.
- **Android setup**: `ACCESS_COARSE_LOCATION` and `ACCESS_FINE_LOCATION`. When only approximate location is granted, request both permissions again.

```xml title="Info.plist"
<key>NSLocationTemporaryUsageDescriptionDictionary</key>
<dict>
    <key>StoreFinder</key>
    <string>Find the store closest to you.</string>
</dict>
```

Answer the request from the location accuracy:

| OS | Native result | Answer | Section | `outcome` |
|:---|:--------------|:-------|:--------|:----------|
| iOS | Location `.notDetermined`, then the user allows location with **Precise** on | Granted, `granted` | **When allowed** | `granted` |
| iOS | Location `.notDetermined`, then the user denies location access | Not granted, `denied` | **When denied** | `denied` |
| iOS | Still `.notDetermined` after the request, or no answer before the app's timeout | Not granted, no status | **After response** | `no_status` |
| iOS | `accuracyAuthorization` is `.fullAccuracy` before the request | Granted, `granted` | **When allowed** | `granted` |
| iOS | `.reducedAccuracy` before, `.fullAccuracy` after the request | Granted, `granted` | **When allowed** | `granted` |
| iOS | The request completes without an error, and `accuracyAuthorization` is still `.reducedAccuracy`: the user declined | Not granted, `denied` | **When denied** | `denied` |
| iOS | The request fails with `promptDeclined`: iOS didn't show the alert | Not granted, no status | **After response** | `no_status` |
| iOS | Location access `.denied` | Not granted, `permanently_denied` | **When denied** | `permanently_denied` |
| iOS | Location access `.restricted` | Not granted, `restricted` | **When denied** | `restricted` |
| Android 12+ | `ACCESS_FINE_LOCATION` granted, including **Only this time** | Granted, `granted` | **When allowed** | `granted` |
| Android 12+ | Only `ACCESS_COARSE_LOCATION` granted after the request | Not granted, `denied` | **When denied** | `denied` |
| Android 12+ | No location access, denied in the dialog | Not granted, `denied` | **When denied** | `denied` |
| Android 12+ | No location access, and Android showed no dialog | Not granted, `permanently_denied` | **When denied** | `permanently_denied` |
| Android 11 and earlier | `ACCESS_FINE_LOCATION` granted | Granted, `granted` | **When allowed** | `granted` |

- **Limitations**:
  - The iOS request needs location access while the app is in use. With location `.notDetermined`, request **Location while using the app** first: its alert has a **Precise** switch. If the user turns it off, continue with the request for precise location.
  - When the user answers the alert, the request completes without an error. Read `accuracyAuthorization` after it. The `promptDeclined` error means that iOS didn't show the alert. iOS doesn't show it when the purpose key is missing from the dictionary, the app already has precise location, or the app is in the background.
  - Precise location from this request is temporary: it expires on its own, and iOS postpones the expiration while the app is in use. The alert can appear again in a later session. Precise location that the user chose in the location alert or in Settings doesn't expire.
- **Cross-platform notes**: Both OSes can grant precise location for a limited time: iOS with this request, and Android with **Only this time**.

## Camera and media

### Camera \{#camera\}

- **What the user sees**: On iOS, an alert with your purpose string. On Android 11 and later, a dialog with **While using the app**, **Only this time**, and **Don't allow**.
- **Platforms**: iOS and Android.
- **iOS setup**: `NSCameraUsageDescription`. Without it, a request for camera access raises an exception, and iOS terminates the app. Request the permission with `AVCaptureDevice.requestAccess(for: .video)`.
- **Android setup**: `CAMERA`, a runtime permission. `CAMERA` implies the required features `android.hardware.camera` and `android.hardware.camera.autofocus`, so Google Play doesn't offer the app to devices without a back camera. To install the app on such devices, declare `<uses-feature android:name="android.hardware.camera" android:required="false" />`.

Answer the request from the camera authorization status:

| OS | Native result | Answer | Section | `outcome` |
|:---|:--------------|:-------|:--------|:----------|
| iOS | `.notDetermined`, then the user allows | Granted, `granted` | **When allowed** | `granted` |
| iOS | `.notDetermined`, then the user declines | Not granted, `denied` | **When denied** | `denied` |
| iOS | `.denied` before the request | Not granted, `permanently_denied` | **When denied** | `permanently_denied` |
| iOS | `.restricted` | Not granted, `restricted` | **When denied** | `restricted` |
| iOS | `.authorized` | Granted, `granted` | **When allowed** | `granted` |
| Android | Granted, including **Only this time** | Granted, `granted` | **When allowed** | `granted` |
| Android | Denied in the dialog | Not granted, `denied` | **When denied** | `denied` |
| Android | Denied, and Android showed no dialog | Not granted, `permanently_denied` | **When denied** | `permanently_denied` |
| Android | The device has no camera: `FEATURE_CAMERA_ANY` is missing | Not granted, `unsupported` | **After response** | `unsupported` |

- **Limitations**: Until the user allows camera access, iOS gives the app black frames. **Only this time** on Android expires shortly after the app goes to the background.

### Microphone \{#microphone\}

- **What the user sees**: On iOS, an alert with your purpose string. On Android 11 and later, a dialog with **While using the app**, **Only this time**, and **Don't allow**.
- **Platforms**: iOS and Android.
- **iOS setup**: `NSMicrophoneUsageDescription`. Without it, the app exits when it tries to use the microphone. Request the permission with `AVCaptureDevice.requestAccess(for: .audio)`, or with `AVAudioApplication.requestRecordPermission()` on iOS 17 and later.
- **Android setup**: `RECORD_AUDIO`, a runtime permission.

Answer the request from the microphone authorization status:

| OS | Native result | Answer | Section | `outcome` |
|:---|:--------------|:-------|:--------|:----------|
| iOS | `.notDetermined`, then the user allows | Granted, `granted` | **When allowed** | `granted` |
| iOS | `.notDetermined`, then the user declines | Not granted, `denied` | **When denied** | `denied` |
| iOS | `.denied` before the request | Not granted, `permanently_denied` | **When denied** | `permanently_denied` |
| iOS | `.restricted` | Not granted, `restricted` | **When denied** | `restricted` |

### Photos \{#photos\}

- **What the user sees**: On iOS, an alert that offers limited access, full access, or no access. On Android 14 and later, a dialog that offers limited access, full access, or no access. Limited access opens a system picker where the user selects photos and videos. On Android 13, the dialog has no selection option.
- **Platforms**: iOS and Android.
- **iOS setup**: `NSPhotoLibraryUsageDescription`, and request the permission with `PHPhotoLibrary.requestAuthorization(for: .readWrite)`. If the app only adds photos, declare `NSPhotoLibraryAddUsageDescription` and request `PHPhotoLibrary.requestAuthorization(for: .addOnly)` instead: add-only access has no limited state. - **Android setup**: Request `READ_MEDIA_IMAGES` and `READ_MEDIA_VIDEO` together on Android 13 and later, with `READ_MEDIA_VISUAL_USER_SELECTED` on Android 14 and later. On Android 12 and earlier, request `READ_EXTERNAL_STORAGE`. Declare all four permissions:

```xml title="AndroidManifest.xml"
<uses-permission android:name="android.permission.READ_EXTERNAL_STORAGE" android:maxSdkVersion="32" />
<uses-permission android:name="android.permission.READ_MEDIA_IMAGES" />
<uses-permission android:name="android.permission.READ_MEDIA_VIDEO" />
<uses-permission android:name="android.permission.READ_MEDIA_VISUAL_USER_SELECTED" />
```

| OS | Native result | Answer | Section | `outcome` |
|:---|:--------------|:-------|:--------|:----------|
| iOS | `.authorized` | Granted, `granted` | **When allowed** | `granted` |
| iOS | `.limited`: the user selected some photos | Granted, `limited` | **When allowed** | `limited` |
| iOS | `.notDetermined`, then the user declines | Not granted, `denied` | **When denied** | `denied` |
| iOS | `.denied` before the request | Not granted, `permanently_denied` | **When denied** | `permanently_denied` |
| iOS | `.restricted` | Not granted, `restricted` | **When denied** | `restricted` |
| Android 13+ | `READ_MEDIA_IMAGES` or `READ_MEDIA_VIDEO` granted | Granted, `granted` | **When allowed** | `granted` |
| Android 14+ | Only `READ_MEDIA_VISUAL_USER_SELECTED` granted | Granted, `limited` | **When allowed** | `limited` |
| Android 12 and earlier | `READ_EXTERNAL_STORAGE` granted | Granted, `granted` | **When allowed** | `granted` |

| Android | Nothing granted, and Android showed no dialog | Not granted, `permanently_denied` | **When denied** | `permanently_denied` |

- **Limitations**:
  - Google Play restricts `READ_MEDIA_IMAGES` and `READ_MEDIA_VIDEO` to [use cases in its policy](https://developer.android.com/training/data-storage/shared/media). Other apps use the Android photo picker, which needs no permission.

In an app that targets Android 14 or higher and doesn't declare it, Android reports `READ_MEDIA_IMAGES` and `READ_MEDIA_VIDEO` as granted after the user selects some photos. ### Health data \{#health\}

- **What the user sees**: On iOS, the Health access sheet for the data types that the app requests. On Android, the Health Connect permissions screen, with an entry for each data type.
- **Platforms**: iOS and Android. On Android, the app requests Health Connect permissions, not a runtime permission.
- **iOS setup**:
  - The HealthKit capability.
  - `NSHealthShareUsageDescription` to read health data, and `NSHealthUpdateUsageDescription` to write it. Without these keys, the app crashes when it requests access.

Before the request, `getRequestStatusForAuthorization(toShare:read:)` tells whether iOS will show the sheet.

  - The Health Connect client library, `androidx.health.connect:connect-client`.

On Android 14 and later, an `<activity-alias>` for the `android.intent.action.VIEW_PERMISSION_USAGE` action, with the `android.intent.category.HEALTH_PERMISSIONS` category and `android:permission="android.permission.START_VIEW_PERMISSION_USAGE"`.

Health Connect needs Android 9 (API 28) or later. Android 14 and later include it. On Android 13 and earlier, the user needs the Health Connect app from Google Play: when `getSdkStatus()` returns `SDK_UNAVAILABLE_PROVIDER_UPDATE_REQUIRED`, the app can send the user to Google Play.

| Android 12+ | All requested permissions granted | Granted, `granted` | **When allowed** | `granted` |
| Android 12+ | Denied in the dialog | Not granted, `denied` | **When denied** | `denied` |
| Android 12+ | Denied, and Android showed no dialog | Not granted, `permanently_denied` | **When denied** | `permanently_denied` |
| Android 11 and earlier, or target below API 31 | Answer from `ACCESS_FINE_LOCATION`, as for **Location while using the app**. Approximate location isn't enough for scans on Android 10 and 11 | As for location | As for location | As for location |

- **Limitations**:
  - Wait for `centralManagerDidUpdateState(_:)` with a timeout, then answer from `CBManager.authorization`.
  - A Bluetooth adapter that is turned off isn't a refusal. Answer from the permission only.
  - With `neverForLocation`, Android filters some BLE beacons out of scan results.
  - On Android 11 and earlier, the user sees a location dialog after a flow screen about Bluetooth. Mention location on that screen.
- **Cross-platform notes**: On Android, Bluetooth is in the **Nearby devices** group, which the user turns on and off as one in the settings.

### Local network \{#local_network\}

- **What the user sees**: On iOS, an alert with your purpose string the first time the app accesses the local network. On Android 17 and later, a runtime permission dialog for apps that target Android 17.
- **Platforms**: iOS and Android. An app that targets Android 16 or lower, and any app on Android 16 and earlier, accesses the local network with the `INTERNET` permission and no dialog.
- **iOS setup**: `NSLocalNetworkUsageDescription`. For each Bonjour service type the app browses or advertises, an entry in `NSBonjourServices`, such as `_myservice._tcp`. Multicast and broadcast also need the `com.apple.developer.networking.multicast` entitlement, which Apple must approve. iOS has no request method and no status API. A local network operation shows the alert, such as a Bonjour browse or a connection to a device on the network.
- **Android setup**: `ACCESS_LOCAL_NETWORK`, only when the app targets Android 17 (API 37) or higher. If the app targets a lower API level, don't declare or request it. `NEARBY_WIFI_DEVICES` is a different permission.

Answer the request from the result of a local network operation on iOS, and from the permission state on Android:

| OS | Native result | Answer | Section | `outcome` |
|:---|:--------------|:-------|:--------|:----------|
| iOS | An outgoing operation that needs local network access succeeds, such as a Bonjour browse or an outgoing TCP connection | Granted, `granted` | **When allowed** | `granted` |
| iOS | The operation fails, or gets no result before the app's timeout | Not granted, no status | **After response** | `no_status` |
| iOS | The app has no local network feature | Not granted, `unsupported` | **After response** | `unsupported` |
| Android | The app targets Android 16 or lower, or the device runs Android 16 or earlier: access comes with `INTERNET` | Granted, `granted` | **When allowed** | `granted` |
| Android 17+ | The app targets Android 17 or higher, and the permission is granted | Granted, `granted` | **When allowed** | `granted` |
| Android 17+ | The app targets Android 17 or higher, denied in the dialog | Not granted, `denied` | **When denied** | `denied` |
| Android 17+ | The app targets Android 17 or higher, denied, and Android showed no dialog | Not granted, `permanently_denied` | **When denied** | `permanently_denied` |

- **Limitations**:
  - On iOS, your app learns nothing when the user declines. The flow stays on the screen until your app's timeout expires, then runs **After response** with the `outcome` `no_status`. **When denied** never runs for this permission on iOS, only on Android 17 and later. Keep the timeout short, such as 20 seconds. Never wait 60 seconds or more: at 60 seconds without an answer, the flow reports `flow_permission_unanswered`.
  - iOS doesn't report the local network status. iOS can deny the operation that shows the alert before the user answers, so a failed operation doesn't mean a refusal. Put the next step of the flow in **After response**.
  - In the background, iOS denies a local network operation without an alert and doesn't store the result. The alert appears at the next operation in the foreground.
  - The iOS Simulator doesn't apply local network privacy. Test on a device.
  - On Android 17, `ACCESS_LOCAL_NETWORK` is in the **Nearby devices** group. If the user granted another permission of the group, such as Bluetooth, Android shows no dialog for the local network. Android can also let the app ask again after an earlier refusal.
  - On Android 17, system pickers, such as `NsdManager` with `FLAG_SHOW_PICKER` and the Output Switcher, give the app access to the device that the user picks without this permission. See [Local network permission](https://developer.android.com/privacy-and-security/local-network-permission).
- **Cross-platform notes**: Only Android reports a refusal, so a flow that also runs on iOS needs the next step in **After response**.

### HomeKit \{#homekit\}

- **What the user sees**: On iOS, an alert with your purpose string the first time the app uses HomeKit.
- **Platforms**: iOS only. Android has no such permission: answer `unsupported`, and the flow runs **After response**.
- **iOS setup**: The HomeKit capability, and `NSHomeKitUsageDescription`. Without the key, the app crashes the first time it uses HomeKit. iOS has no request method: creating an `HMHomeManager` shows the alert. The status arrives in `homeManager(_:didUpdate:)`, and `HMHomeManager.authorizationStatus` returns it. Keep one `HMHomeManager` for the life of the app.
- **Android setup**: None: answer `unsupported` without a dialog.

The HomeKit status is a set of flags. Answer the request from them:

| OS | Native result | Answer | Section | `outcome` |
|:---|:--------------|:-------|:--------|:----------|
| iOS | `.authorized` is set | Granted, `granted` | **When allowed** | `granted` |
| iOS | `.determined` without `.authorized`, after the alert | Not granted, `denied` | **When denied** | `denied` |
| iOS | `.determined` without `.authorized`, before the request | Not granted, `permanently_denied` | **When denied** | `permanently_denied` |
| iOS | `.determined` isn't set when the timeout ends | Not granted, no status | **After response** | `no_status` |
| Android | Any request | Not granted, `unsupported` | **After response** | `unsupported` |

- **Limitations**: A refusal from an earlier launch calls no delegate method: a new `HMHomeManager` already has the decided status. Read `authorizationStatus` right after you create the manager, and again while you wait for the answer, with a timeout. Apple defines the `.restricted` flag as "The app doesn't have access to home data", not as a device policy, so don't pass `restricted` for it.

### Focus status \{#focus_status\}

- **What the user sees**: On iOS, an alert with your purpose string that asks to share the Focus status.
- **Platforms**: iOS only. Android has no such permission: answer `unsupported`, and the flow runs **After response**.
- **iOS setup**: `NSFocusStatusUsageDescription`: add it before the app uses `INFocusStatusCenter`. Request the permission with `INFocusStatusCenter.default.requestAuthorization()`. To read the Focus status after the user allows it, the app also needs notification authorization and the Communication Notifications capability.
- **Android setup**: None: answer `unsupported` without a dialog. Android apps read the Do Not Disturb mode without a permission.

Answer the request from the Focus status authorization status:

| OS | Native result | Answer | Section | `outcome` |
|:---|:--------------|:-------|:--------|:----------|
| iOS | `.notDetermined`, then the user allows | Granted, `granted` | **When allowed** | `granted` |
| iOS | `.notDetermined`, then the user declines | Not granted, `denied` | **When denied** | `denied` |
| iOS | `.notDetermined` after the request: the user chose neither | Not granted, no status | **After response** | `no_status` |
| iOS | `.denied` before the request | Not granted, `permanently_denied` | **When denied** | `permanently_denied` |
| iOS | `.restricted` | Not granted, `restricted` | **When denied** | `restricted` |
| iOS | `.authorized` | Granted, `granted` | **When allowed** | `granted` |
| Android | Any request | Not granted, `unsupported` | **After response** | `unsupported` |

### Siri \{#siri\}

- **What the user sees**: On iOS, an alert with your purpose string that asks to use Siri with the app.
- **Platforms**: iOS only. Android has no such permission: answer `unsupported`, and the flow runs **After response**.
- **iOS setup**: The Siri capability, and `NSSiriUsageDescription`. Request the permission with `INPreferences.requestSiriAuthorization(_:)`. Apple requires the Siri capability for the authorization to succeed. In an app without the capability, answer `unsupported` without a call to `INPreferences`.
- **Android setup**: None: answer `unsupported` without a dialog.

Answer the request from the Siri authorization status:

| OS | Native result | Answer | Section | `outcome` |
|:---|:--------------|:-------|:--------|:----------|
| iOS | `.notDetermined`, then the user allows | Granted, `granted` | **When allowed** | `granted` |
| iOS | `.notDetermined`, then the user declines | Not granted, `denied` | **When denied** | `denied` |
| iOS | `.denied` before the request | Not granted, `permanently_denied` | **When denied** | `permanently_denied` |
| iOS | `.restricted` | Not granted, `restricted` | **When denied** | `restricted` |
| iOS | `.authorized` | Granted, `granted` | **When allowed** | `granted` |
| Android | Any request | Not granted, `unsupported` | **After response** | `unsupported` |

- **Limitations**:
  - An app that only supports actions in the Shortcuts app doesn't need this permission.
  - Siri or Maps can ask the user for this permission on the app's behalf, the first time the user uses one of the app's intents. The status can then be decided before the flow asks.
