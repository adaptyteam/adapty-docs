To ask users for a system permission, add the **Request permission** action to a screen of your flow. For example:

- Ask users to turn on push notifications on the last onboarding screen.
- Ask for location access before users look for nearby stores.
- Ask for camera access before users scan a document.

Your app shows the system dialog and passes the result to the flow. The flow then runs the **When allowed**, **When denied**, or **After response** actions for that result. For example, users who decline location access can enter their city on the next screen. You can change the screen with the request, and the screens after it, without an app release. The dialog itself only appears in app versions that request the permission in their code.

## Before you start

Make sure that:

- Your app has a <InlineTooltip tooltip="permission handler">[iOS](ios-handle-permissions), [Android](android-handle-permissions), [React Native](react-native-handle-permissions), [Flutter](flutter-handle-permissions), [Unity](unity-handle-permissions), [Kotlin Multiplatform](kmp-handle-permissions), and [Capacitor](capacitor-handle-permissions)</InlineTooltip>. It requests the permission that you select in the flow. For any other permission, your app passes a not-granted result without a dialog, and the flow runs the **After response** actions.
- The flow only reaches app versions that request the permission. A published flow reaches every app version, but versions without the permission handler never show the dialog. To exclude them, add an [audience](audience) built from a [segment](segments) on **App version (current)**.

If an app version without the permission handler shows the flow, the Adapty SDK in the app determines what happens:

- **iOS, Unity, and Kotlin Multiplatform SDKs, and Flutter SDK before 4.4.1**: Users see no dialog, and the flow stays on the screen.
- **Android, React Native, and Capacitor SDKs, and Flutter SDK 4.4.1 and later**: Users see no dialog, and the flow runs the **After response** actions.

## Permissions you can request

The **Permission** dropdown lists the following permissions. The table shows what users see on each OS, and what to plan for in the flow:

| Permission | iOS | Android | In the flow |
|:-----------|:----|:--------|:------------|
| Push notifications | Alert | Dialog on Android 13 and later | If your app requests provisional authorization on iOS, users see no alert, and the flow runs the **When allowed** actions at once. |
| App tracking (ATT) | Alert | No such permission | On Android, the flow runs the **After response** actions. |
| Location while using the app | Alert with a **Precise** switch | Dialog where users select precise or approximate location | For approximate location, the flow runs the **When allowed** actions too. |
| Location always | Location alert, or an upgrade alert if users already granted **Location while using the app** | Dialog on Android 10. Settings page on Android 11 and later | On Android, request **Location while using the app** on an earlier screen, so that users see one step per screen. On iOS, after **Allow Once**, the flow runs the **When denied** actions. |
| Precise location | Alert that asks for precise location | Dialog where users select precise location or keep approximate location | — |
| Camera | Alert | Dialog | On Android devices without a camera, the flow runs the **After response** actions. |
| Microphone | Alert | Dialog | — |
| Photos | Alert where users select full or limited access | Dialog. On Android 14 and later, users can select limited access | For limited access, the flow runs the **When allowed** actions too. |
| Media library | Alert | Dialog | On iOS, **Media library** and **Apple Music** share one alert. After users grant or decline one of them, iOS shows no alert for the other. |
| Apple Music | Alert | No such permission | On Android, the flow runs the **After response** actions. On iOS, this permission shares one alert with **Media library**. |
| Speech recognition | Alert | The microphone dialog | On iOS, speech recognition of live audio needs **Microphone** too. Request it on another screen, unless your app requests both. |
| Contacts | Alert. On iOS 18 and later, users select all or some contacts | Dialog | For access to some contacts, the flow runs the **When allowed** actions too. |
| Calendar | Alert for full access or for adding events only | Dialog | For access to add events only, the flow runs the **When allowed** actions too. |
| Reminders | Alert | No such permission | On Android, the flow runs the **After response** actions. |
| Health data | Health access sheet | Health Connect permissions screen | On iOS, when your app only requests read access, the flow runs the **After response** actions: iOS doesn't report whether users granted read access. |
| Motion & Fitness | Alert at the first access to motion data | Dialog on Android 10 and later | On Android 9 and earlier, users see no dialog, and the flow runs the **When allowed** actions. |
| Bluetooth | Alert | **Nearby devices** dialog on Android 12 and later. Location dialog on Android 11 and earlier | — |
| Local network | Alert at the first access to the local network | Dialog on Android 17 and later, for apps that target Android 17 or higher | On iOS, the flow never runs the **When denied** actions: iOS doesn't tell your app when users decline. The flow waits for the timeout in your app, then runs the **After response** actions. |
| HomeKit | Alert | No such permission | On Android, the flow runs the **After response** actions. |
| Focus status | Alert | No such permission | On Android, the flow runs the **After response** actions. |
| Siri | Alert | No such permission | On Android, the flow runs the **After response** actions. |

To skip the screen about an iOS-only permission on Android, [only show it on iOS](onboarding-actions#show-a-screen-on-one-platform-only).

## Add the request to a screen

To give users a reason before the system dialog appears, add the request to a screen that explains the permission:

1. Select the button that should show the system dialog, such as **Continue**.
2. [Add an **On Tap** trigger](onboarding-actions#set-up-interactions) with the **Request permission** action to the button.
3. From the **Permission** dropdown, select the permission. The **Your app must handle this request** warning then lists what your app declares for it: the `Info.plist` keys, the Xcode capabilities, and the Android manifest permissions.

If an earlier screen already explained the permission, add the request to the **On Screen Appear** trigger of the next screen instead.

On the screen with the request:

- Label the button **Continue** or **Next**, not **Allow**.
- On iOS, keep the button with the request as the only way off the screen. The [Human Interface Guidelines](https://developer.apple.com/design/human-interface-guidelines/privacy) advise against a close, cancel, or skip option before the system alert.
- On Android, add a **Skip** button that runs **Navigate Next**, and [only show it on Android](onboarding-element-visibility#show-an-element-on-one-platform-only). The Android [permission guidelines](https://developer.android.com/training/permissions/requesting) ask for a way to cancel a screen that explains a permission.
- Add one **Request permission** action per screen: the flow [sends one permission request at a time](onboarding-actions#request-permission).

When the request is the only way off a screen, the Flow & Paywall Builder and the publish dialog warn you. With the audience from [Before you start](#before-you-start) in place, you can publish the flow anyway. Every app version that shows the flow then passes the result of the permission request.

Apple and Google set more rules for some permissions:

- **App tracking (ATT)**: A screen before the ATT alert must not offer an incentive, imitate the system alert, show an image of it, or annotate the screen behind it. Apple's [Human Interface Guidelines](https://developer.apple.com/design/human-interface-guidelines/privacy#Tracking-requests) say that App Review rejects such screens. [App Review Guideline 5.1.2(i)](https://developer.apple.com/app-store/review/guidelines/#data-use-and-sharing) requires the ATT permission for tracking. The app can't require tracking for access to features or for rewards.
- **Location always**: On Android, Google Play requires a prominent disclosure right before the request. Put it on the screen with the **Location always** request. The disclosure says that the app collects location data for a named feature, even when the app is closed or not in use. See [Access to device location in the background](https://support.google.com/googleplay/android-developer/answer/9799150).
- **Bluetooth**: On Android 11 and earlier, users see a location dialog. Mention location on the screen with the request.

## Add actions for each result

<FlowPermissionAnswers />

Use **When denied** for a path without the permission. For example, let users enter their city instead of location access, or show a button that [opens the system settings](onboarding-actions#what-you-can-do-with-custom-actions). When your app passes `restricted`, the flow runs the **When denied** actions too: a device policy, such as parental controls, blocks the permission. Under such a policy, users can't grant the permission in the system settings.

The flow never runs the **When denied** actions in the following cases:

- The OS has no such permission, such as **App tracking (ATT)** on Android.
- The OS doesn't report a refusal, such as iOS for **Local network** or for read access to **Health data**.
- The app version passes a not-granted result without `denied`, `restricted`, or `permanently_denied`.

In these cases, the flow runs the **After response** actions. Keep a navigation action there. The default **After response** action is **Navigate Next**.

To add an action for a result:

1. Select the element with the **Request permission** action.
2. Click the **Request permission** action.
3. For **When allowed**, **When denied**, or **After response**, click <Inline id="plus.svg" alt="Add action" />.
4. From the **Action** dropdown, select the action to run instead of **Do nothing**.

You can't add **Purchase**, **Restore purchases**, or another **Request permission** action to **When allowed**, **When denied**, and **After response**.

To let users go on after a refusal, end the **When denied** actions with a way forward, such as **Navigate Next**. With no **When denied** actions, the flow runs the **After response** actions instead. [App Review Guideline 5.1.2(i)](https://developer.apple.com/app-store/review/guidelines/#data-use-and-sharing) doesn't allow an app to require system functionality, such as push notifications, location services, or tracking, to use the app. Guideline 5.1.1(iv) asks apps to respect the user's permission settings, and not to manipulate, trick, or force users to consent.

When the OS shows no dialog, for example because the user already granted the permission, your app passes the result at once. The flow then runs the actions for that result. If those actions leave the screen, users only see the screen for a moment.

To count how many users grant a permission on each screen, track the permission events in the <InlineTooltip tooltip="flow analytics of your app">[iOS](ios-handling-events#analytics-events), [Android](android-handling-events#analytics-events), [React Native](react-native-handling-events-1#analytics-events), [Flutter](flutter-handling-events#analytics-events), [Unity](unity-handling-events#analytics-events), [Kotlin Multiplatform](kmp-handling-events#analytics-events), and [Capacitor](capacitor-handling-events#analytics-events)</InlineTooltip>.
