The **Request permission** action of a flow asks your app for a system permission, such as push notifications, location, or camera access. This page lists every permission that the action can request. For each permission, it describes what users see, what your app declares on iOS and Android, and which answer your app passes for each result of the system request. Use it when you add the action to a flow, and when you write the code that answers the request.

To answer the requests in your app, see the guide for [iOS](ios-handle-permissions), [Android](android-handle-permissions), [React Native](react-native-handle-permissions), [Flutter](flutter-handle-permissions), [Unity](unity-handle-permissions), [Kotlin Multiplatform](kmp-handle-permissions), or [Capacitor](capacitor-handle-permissions).

:::tip
To add the request to a flow, see [Request permission](onboarding-actions#request-permission).
:::

## Rules for every permission

- **Request only what the app declares and links**: Answer `unsupported` for any other permission, without a call to the OS. Link only the frameworks of the permissions that your app requests. Apple notes that libraries can reference APIs that require a purpose string, so a linked framework needs its purpose string even when your app answers its permission as unsupported.
- **Read the current status before you request**: For most permissions, the OS shows the dialog once, and later requests return the stored answer without a dialog. Some iOS requests never call back when the status is already decided, and the flow then stays on the screen. Read the status first, and answer at once when it's decided.
- **Wait for indirect requests with a timeout**: iOS has no request method for **Bluetooth**, **Motion & Fitness**, **Local network**, and **HomeKit**. The alert appears when the app first uses the framework, and the result arrives in a delegate method or not at all. Wrap the wait in a timeout, then answer from the current status, or without a status.
- **Tell a new refusal from an earlier one**: iOS keeps every refusal until the user changes it in Settings. Pass `denied` when the user declined the dialog of this request, and `permanently_denied` when iOS showed no dialog because the user declined earlier. On Android 11 and later, the OS stops showing the dialog after the user denies a permission twice. After a refusal, call `shouldShowRequestPermissionRationale()`. Pass `denied` if it returns `true`, and `permanently_denied` if it returns `false`.
- **Read the status at every request**: Some grants expire. **Allow Once** on iOS and **Only this time** on Android last while the app is in use. Temporary full accuracy on iOS expires on its own. Android resets the permissions of apps that the user hasn't used for a few months. Don't store an answer for a later request.
- **Explain the permission before the dialog**: Put the request on the **On Tap** trigger of a button on a screen that explains the permission. Apple's [Human Interface Guidelines](https://developer.apple.com/design/human-interface-guidelines/privacy) recommend one button on such a screen, such as **Continue**, that opens the system alert.
- **Let the user go on after a refusal**: [App Review Guideline 5.1.2(i)](https://developer.apple.com/app-store/review/guidelines/#data-use-and-sharing) doesn't allow an app to require push notifications, location services, tracking, or other system functionality to use the app or its content. Add a way forward to **When denied**, such as **Navigate Next**. A **When denied** section that leaves the user without a way forward risks rejection. Guideline 5.1.1(iv) also asks apps to respect the user's permission settings and not to manipulate, trick, or force users to consent.
- **Reset the answers when you test**: To see a dialog again on iOS, delete the app, or open **Settings > General > Transfer or Reset > Reset > Reset Location & Privacy**, which resets every app. On Android, delete the app, or run `adb shell pm revoke <package> <permission>` and `adb shell pm clear-permission-flags <package> <permission> user-set user-fixed`. Don't install the test build with `adb install -g`: it grants every runtime permission, so no dialog appears.

## Notifications and tracking

### Push notifications \{#push\}

- **What the user sees**: On iOS, an alert that asks to allow notifications. On Android 13 and later, a dialog with **Allow** and **Don't allow**. The user can also swipe the Android dialog away, which leaves the permission unanswered. Android 12 and earlier show no dialog: notifications are on unless the user turns them off in the system settings.
- **Platforms**: iOS and Android.
- **iOS setup**: No `Info.plist` key. Request the permission with `UNUserNotificationCenter.requestAuthorization(options:)`. To receive remote push notifications, the app also needs the Push Notifications capability and registers with APNs. The permission itself doesn't need them.
- **Android setup**: `<uses-permission android:name="android.permission.POST_NOTIFICATIONS" />`, a runtime permission on Android 13 (API 33) and later. Target API 33 or higher: for an app that targets API 32 or lower, Android shows the dialog when the app creates its first notification channel, not when the flow asks. On Android 12 and earlier, answer from `NotificationManagerCompat.areNotificationsEnabled()` without a dialog.

Answer the request from the notification authorization status:

| OS | Native result | Answer | Section | `outcome` |
|:---|:--------------|:-------|:--------|:----------|
| iOS | `.notDetermined`, then the user allows | Granted, `granted` | **When allowed** | `granted` |
| iOS | `.notDetermined`, then the user declines | Not granted, `denied` | **When denied** | `denied` |
| iOS | `.denied` before the request | Not granted, `permanently_denied` | **When denied** | `permanently_denied` |
| iOS | `.authorized` | Granted, `granted` | **When allowed** | `granted` |
| iOS | `.provisional`, after a request with the `.provisional` option | Granted, `provisional` | **When allowed** | `provisional` |
| iOS | `requestAuthorization(options:)` throws an error | Not granted, no status | **After response** | `no_status` |
| Android 13+ | Granted | Granted, `granted` | **When allowed** | `granted` |
| Android 13+ | Denied, Android shows the dialog again | Not granted, `denied` | **When denied** | `denied` |
| Android 13+ | Denied, Android no longer shows the dialog | Not granted, `permanently_denied` | **When denied** | `permanently_denied` |
| Android 12 and earlier | Notifications are on | Granted, `granted` | **When allowed** | `granted` |
| Android 12 and earlier | Notifications are off | Not granted, `permanently_denied` | **When denied** | `permanently_denied` |

- **Limitations**: iOS shows the alert once: later requests return the first answer. With the `.provisional` option, iOS grants quiet notifications without an alert, so the flow runs **When allowed** right away and the user sees no dialog. Request `.provisional` only if the flow expects that.
- **Cross-platform notes**: The `provisional` status exists only on iOS.

### App tracking (ATT) \{#tracking\}

- **What the user sees**: On iOS, the App Tracking Transparency alert with your purpose string. iOS shows no alert and returns the current status at once when tracking is restricted, the user turned off **Allow Apps to Request to Track** in Settings, another ATT request waits for an answer, or the app isn't active.
- **Platforms**: iOS only. Android has no such permission: answer `unsupported`, and the flow runs **After response**.
- **iOS setup**: `NSUserTrackingUsageDescription`. An app that uses the AppTrackingTransparency framework without this key crashes. Request the permission with `ATTrackingManager.requestTrackingAuthorization()`.
- **Android setup**: None: answer `unsupported` without a dialog. The advertising ID on Android uses the install-time permission `com.google.android.gms.permission.AD_ID`, which asks the user nothing. Don't report `granted` because the app has an advertising ID.

Answer the request from the tracking authorization status:

| OS | Native result | Answer | Section | `outcome` |
|:---|:--------------|:-------|:--------|:----------|
| iOS | `.notDetermined`, then the user allows | Granted, `granted` | **When allowed** | `granted` |
| iOS | `.notDetermined`, then the user declines | Not granted, `denied` | **When denied** | `denied` |
| iOS | `.denied` before the request | Not granted, `permanently_denied` | **When denied** | `permanently_denied` |
| iOS | `.restricted` | Not granted, `restricted` | **When denied** | `restricted` |
| iOS | `.authorized` | Granted, `granted` | **When allowed** | `granted` |
| iOS | `.notDetermined` after the request: the alert closed without a choice | Not granted, no status | **After response** | `no_status` |
| Android | Any request | Not granted, `unsupported` | **After response** | `unsupported` |

- **Limitations**:
  - iOS shows the alert only while the app is active. With **On Screen Appear** on the first screen after launch, the request can arrive before the app is active. Before the request, wait for `UIApplication.didBecomeActiveNotification`.
  - [App Review Guideline 5.1.2(i)](https://developer.apple.com/app-store/review/guidelines/#data-use-and-sharing) requires the ATT permission for tracking. The app can't require tracking for access to features or for rewards.
  - A screen before the ATT alert must not offer an incentive, imitate the system alert, show an image of it, or annotate the screen behind it. Apple's [Human Interface Guidelines](https://developer.apple.com/design/human-interface-guidelines/privacy#Tracking-requests) say that App Review rejects such screens.
  - After the user answers, send the ATT status to Adapty. See [Deal with ATT](ios-deal-with-att).

## Location

### Location while using the app \{#location_when_use\}

- **What the user sees**: On iOS, an alert with **Allow Once**, **Allow While Using App**, and **Don't Allow**, and a **Precise** switch. On Android 12 and later, a dialog with a choice of **Precise** or **Approximate**, and the buttons **While using the app**, **Only this time**, and **Don't allow**. If the app declares only approximate location, the Android dialog offers only approximate location.
- **Platforms**: iOS and Android.
- **iOS setup**: `NSLocationWhenInUseUsageDescription`. Request the permission with `CLLocationManager.requestWhenInUseAuthorization()`. The answer arrives in `locationManagerDidChangeAuthorization(_:)`. The app must be in the foreground to show the alert.
- **Android setup**: `ACCESS_COARSE_LOCATION`, and `ACCESS_FINE_LOCATION` for precise location. Request both permissions together: some Android 12 releases ignore a request for `ACCESS_FINE_LOCATION` alone.

Answer the request from the location authorization status:

| OS | Native result | Answer | Section | `outcome` |
|:---|:--------------|:-------|:--------|:----------|
| iOS | `.notDetermined`, then **Allow While Using App** or **Allow Once** | Granted, `granted` | **When allowed** | `granted` |
| iOS | `.notDetermined`, then **Don't Allow** | Not granted, `denied` | **When denied** | `denied` |
| iOS | `.denied` before the request, including Location Services turned off | Not granted, `permanently_denied` | **When denied** | `permanently_denied` |
| iOS | `.restricted` | Not granted, `restricted` | **When denied** | `restricted` |
| iOS | `.authorizedWhenInUse` or `.authorizedAlways` | Granted, `granted` | **When allowed** | `granted` |
| Android | Precise or approximate location granted | Granted, `granted` | **When allowed** | `granted` |
| Android | Denied, Android shows the dialog again | Not granted, `denied` | **When denied** | `denied` |
| Android | Denied, Android no longer shows the dialog | Not granted, `permanently_denied` | **When denied** | `permanently_denied` |

To report approximate location in analytics, pass `limited` with the granted answer instead of `granted`. The flow still runs **When allowed**.

- **Limitations**:
  - iOS doesn't call back in two cases. If the status isn't `.notDetermined`, `requestWhenInUseAuthorization()` does nothing. If `NSLocationWhenInUseUsageDescription` is missing, the request fails at once without a callback and without a crash. A handler that waits for the delegate never answers, and the flow stays on the screen. Read `authorizationStatus` first, and answer at once when it isn't `.notDetermined`.
  - **Allow Once** on iOS and **Only this time** on Android grant access while the app is in use. On iOS, the status then returns to `.notDetermined`, so the alert appears again later.
  - When the user changes precise location to approximate in the Android settings, Android restarts the app process.
- **Cross-platform notes**: Request this permission before **Location always** and **Precise location**: both need location access while the app is in use first.

### Location always \{#location_always\}

- **What the user sees**: Two steps on both OSes.
  - **iOS, no answer yet**: The alert for location while using the app. **Allow While Using App** grants provisional Always access. iOS asks the second question, **Keep Only While Using** or **Change to Always Allow**, later, typically while the app isn't running.
  - **iOS, location while using the app already granted**: The upgrade alert, with **Keep Only While Using** and **Change to Always Allow**, at once.
  - **Android 10**: The dialog includes **Allow all the time**.
  - **Android 11 and later**: The dialog has no **Allow all the time** option. The user turns on background location on a settings page.
- **Platforms**: iOS and Android. Android 9 and earlier grant background location together with foreground location.
- **iOS setup**: `NSLocationWhenInUseUsageDescription` and `NSLocationAlwaysAndWhenInUseUsageDescription`. Request the permission with `CLLocationManager.requestAlwaysAuthorization()`. Location updates in the background also need the Background Modes capability. The permission itself doesn't need it.
- **Android setup**: `ACCESS_BACKGROUND_LOCATION`, from Android 10 (API 29), in addition to `ACCESS_COARSE_LOCATION` and `ACCESS_FINE_LOCATION`. Request it in a separate request after foreground location is granted. For apps that target Android 11 or higher, a request for foreground and background location together grants neither. Google Play restricts background location to an app's core features.

Answer the request from the location authorization status:

| OS | Native result | Answer | Section | `outcome` |
|:---|:--------------|:-------|:--------|:----------|
| iOS | `.notDetermined`, then **Allow While Using App**: provisional Always access | Granted, `provisional` | **When allowed** | `provisional` |
| iOS | `.notDetermined`, then **Allow Once** | Not granted, `denied` | **When denied** | `denied` |
| iOS | `.notDetermined`, then **Don't Allow** | Not granted, `denied` | **When denied** | `denied` |
| iOS | `.authorizedWhenInUse`, first request, then **Change to Always Allow** | Granted, `granted` | **When allowed** | `granted` |
| iOS | `.authorizedWhenInUse`, first request, then **Keep Only While Using** | Not granted, `denied` | **When denied** | `denied` |
| iOS | `.authorizedWhenInUse`, the app requested Always access before | Not granted, `permanently_denied` | **When denied** | `permanently_denied` |
| iOS | `.authorizedAlways` | Granted, `granted` | **When allowed** | `granted` |
| iOS | `.denied` | Not granted, `permanently_denied` | **When denied** | `permanently_denied` |
| iOS | `.restricted` | Not granted, `restricted` | **When denied** | `restricted` |
| Android 10+ | Background location granted | Granted, `granted` | **When allowed** | `granted` |
| Android 10+ | Foreground location granted, background location denied, Android shows the request again | Not granted, `denied` | **When denied** | `denied` |
| Android 10+ | Background location denied, Android no longer shows the request | Not granted, `permanently_denied` | **When denied** | `permanently_denied` |
| Android 9 and earlier | Foreground location granted | Granted, `granted` | **When allowed** | `granted` |

- **Limitations**:
  - On iOS, **Keep Only While Using** doesn't call the delegate. A handler that waits for the delegate never answers. Wait until the app becomes active again after the alert, then read the status.
  - iOS accepts one Always request per install: later calls have no effect, also after **Allow Once**. iOS has no API that tells whether the app asked before, so the app saves its own flag after the first request.
  - iOS reports provisional Always access and full Always access with the same status, `.authorizedAlways`. Only a handler that saw the status change from `.notDetermined` knows that the access is provisional.
  - With provisional Always access, the user can choose **Keep Only While Using** later, outside the flow.
  - On Android 11 and later, the user leaves the app for the settings page. Read the permission state when the user comes back to the app, and answer then.
- **Cross-platform notes**: Both OSes need location access while the app is in use first. Request **Location while using the app** on an earlier screen.

### Precise location \{#location_full_accuracy\}

- **What the user sees**: On iOS, after the user turned off **Precise** in the location alert, an alert that asks for precise location once, with the text of your purpose key. On Android 12 and later, after the user chose approximate location, a dialog with **Change to precise location**, **Only this time**, and **Deny**. If the user chose **Only this time** with approximate location, the Android dialog has only **Only this time** and **Deny**.
- **Platforms**: iOS and Android. Android 11 and earlier have no approximate-only access: a location grant there is precise.
- **iOS setup**: `NSLocationWhenInUseUsageDescription` and `NSLocationTemporaryUsageDescriptionDictionary`. Each key of the dictionary is a purpose key, and its value is the text of the alert. Request the permission with `CLLocationManager.requestTemporaryFullAccuracyAuthorization(withPurposeKey:)`. The flow sends no purpose key, so the app code passes one of its own keys.
- **Android setup**: `ACCESS_COARSE_LOCATION` and `ACCESS_FINE_LOCATION`. When only approximate location is granted, request both permissions again.

```xml title="Info.plist"
<key>NSLocationTemporaryUsageDescriptionDictionary</key>
<dict>
    <key>StoreFinder</key>
    <string>Find the store closest to you.</string>
</dict>
```

Answer the request from the location accuracy:

| OS | Native result | Answer | Section | `outcome` |
|:---|:--------------|:-------|:--------|:----------|
| iOS | `accuracyAuthorization` is `.fullAccuracy` before the request | Granted, `granted` | **When allowed** | `granted` |
| iOS | `.reducedAccuracy`, then the user allows | Granted, `granted` | **When allowed** | `granted` |
| iOS | `.reducedAccuracy`, then the user declines, or the request fails | Not granted, `denied` | **When denied** | `denied` |
| iOS | Location access `.denied` | Not granted, `denied` | **When denied** | `denied` |
| iOS | Location access `.restricted` | Not granted, `restricted` | **When denied** | `restricted` |
| Android 12+ | `ACCESS_FINE_LOCATION` granted | Granted, `granted` | **When allowed** | `granted` |
| Android 12+ | Only `ACCESS_COARSE_LOCATION` granted after the request | Not granted, `denied` | **When denied** | `denied` |
| Android 12+ | No location access, Android shows the dialog again | Not granted, `denied` | **When denied** | `denied` |
| Android 12+ | No location access, Android no longer shows the dialog | Not granted, `permanently_denied` | **When denied** | `permanently_denied` |
| Android 11 and earlier | `ACCESS_FINE_LOCATION` granted | Granted, `granted` | **When allowed** | `granted` |

- **Limitations**:
  - The iOS request needs location access while the app is in use. Without it, request **Location while using the app** first: its alert has a **Precise** switch.
  - The iOS request fails with the `promptDeclined` error when the purpose key is missing from the dictionary, the app already has precise location, or the app is in the background.
  - Precise location on iOS is temporary: it expires on its own, and the alert can appear again in a later session.
- **Cross-platform notes**: Android has no temporary precise location: a granted `ACCESS_FINE_LOCATION` stays until the user changes it.

## Camera and media

### Camera \{#camera\}

- **What the user sees**: On iOS, an alert with your purpose string. On Android 11 and later, a dialog with **While using the app**, **Only this time**, and **Don't allow**.
- **Platforms**: iOS and Android.
- **iOS setup**: `NSCameraUsageDescription`. Without it, a request for camera access raises an exception, and iOS terminates the app. Request the permission with `AVCaptureDevice.requestAccess(for: .video)`.
- **Android setup**: `CAMERA`, a runtime permission. The `CAMERA` permission implies a `<uses-feature>` element for every camera feature.

Answer the request from the camera authorization status:

| OS | Native result | Answer | Section | `outcome` |
|:---|:--------------|:-------|:--------|:----------|
| iOS | `.notDetermined`, then the user allows | Granted, `granted` | **When allowed** | `granted` |
| iOS | `.notDetermined`, then the user declines | Not granted, `denied` | **When denied** | `denied` |
| iOS | `.denied` before the request | Not granted, `permanently_denied` | **When denied** | `permanently_denied` |
| iOS | `.restricted` | Not granted, `restricted` | **When denied** | `restricted` |
| iOS | `.authorized` | Granted, `granted` | **When allowed** | `granted` |
| Android | Granted, including **Only this time** | Granted, `granted` | **When allowed** | `granted` |
| Android | Denied, Android shows the dialog again | Not granted, `denied` | **When denied** | `denied` |
| Android | Denied, Android no longer shows the dialog | Not granted, `permanently_denied` | **When denied** | `permanently_denied` |
| Android | The device has no camera: `FEATURE_CAMERA_ANY` is missing | Not granted, `unsupported` | **After response** | `unsupported` |

- **Limitations**: Until the user allows camera access, iOS gives the app black frames. **Only this time** on Android expires shortly after the app goes to the background.

### Microphone \{#microphone\}

- **What the user sees**: On iOS, an alert with your purpose string. On Android 11 and later, a dialog with **While using the app**, **Only this time**, and **Don't allow**.
- **Platforms**: iOS and Android.
- **iOS setup**: `NSMicrophoneUsageDescription`. Without it, the app exits when it tries to use the microphone. Request the permission with `AVCaptureDevice.requestAccess(for: .audio)`, or with `AVAudioApplication.requestRecordPermission()` on iOS 17 and later.
- **Android setup**: `RECORD_AUDIO`, a runtime permission.

Answer the request from the microphone authorization status:

| OS | Native result | Answer | Section | `outcome` |
|:---|:--------------|:-------|:--------|:----------|
| iOS | `.notDetermined`, then the user allows | Granted, `granted` | **When allowed** | `granted` |
| iOS | `.notDetermined`, then the user declines | Not granted, `denied` | **When denied** | `denied` |
| iOS | `.denied` before the request | Not granted, `permanently_denied` | **When denied** | `permanently_denied` |
| iOS | `.restricted` | Not granted, `restricted` | **When denied** | `restricted` |
| iOS | `.authorized` | Granted, `granted` | **When allowed** | `granted` |
| Android | Granted, including **Only this time** | Granted, `granted` | **When allowed** | `granted` |
| Android | Denied, Android shows the dialog again | Not granted, `denied` | **When denied** | `denied` |
| Android | Denied, Android no longer shows the dialog | Not granted, `permanently_denied` | **When denied** | `permanently_denied` |

- **Limitations**: Without the permission, recordings contain silence. The status of `AVAudioApplication` has no restricted value: with it, your app never passes `restricted`.
- **Cross-platform notes**: On Android, **Microphone** and **Speech recognition** use the same permission, `RECORD_AUDIO`. After the user answers one of them, a request for the other one returns the same answer without a dialog.

### Photos \{#photos\}

- **What the user sees**: On iOS, an alert with **Limit Access**, **Allow Full Access**, and **Don't Allow**. On Android 14 and later, a dialog with **Select photos and videos**, **Allow all**, and **Don't allow**. **Select photos and videos** opens a system picker.
- **Platforms**: iOS and Android.
- **iOS setup**: `NSPhotoLibraryUsageDescription`, or `NSPhotoLibraryAddUsageDescription` if the app only adds photos. Without the key, the app crashes when it accesses the photo library. Request the permission with `PHPhotoLibrary.requestAuthorization(for: .readWrite)`. The older `requestAuthorization(_:)` reports limited access as `.authorized`.
- **Android setup**: Request `READ_MEDIA_IMAGES` and `READ_MEDIA_VIDEO` together on Android 13 and later, with `READ_MEDIA_VISUAL_USER_SELECTED` on Android 14 and later. On Android 12 and earlier, request `READ_EXTERNAL_STORAGE`. Declare all four permissions:

```xml title="AndroidManifest.xml"
<uses-permission android:name="android.permission.READ_EXTERNAL_STORAGE" android:maxSdkVersion="32" />
<uses-permission android:name="android.permission.READ_MEDIA_IMAGES" />
<uses-permission android:name="android.permission.READ_MEDIA_VIDEO" />
<uses-permission android:name="android.permission.READ_MEDIA_VISUAL_USER_SELECTED" />
```

Answer the request from the photo library authorization status:

| OS | Native result | Answer | Section | `outcome` |
|:---|:--------------|:-------|:--------|:----------|
| iOS | `.authorized` | Granted, `granted` | **When allowed** | `granted` |
| iOS | `.limited`: the user selected some photos | Granted, `limited` | **When allowed** | `limited` |
| iOS | `.notDetermined`, then the user declines | Not granted, `denied` | **When denied** | `denied` |
| iOS | `.denied` before the request | Not granted, `permanently_denied` | **When denied** | `permanently_denied` |
| iOS | `.restricted` | Not granted, `restricted` | **When denied** | `restricted` |
| Android 13+ | `READ_MEDIA_IMAGES` or `READ_MEDIA_VIDEO` granted | Granted, `granted` | **When allowed** | `granted` |
| Android 14+ | Only `READ_MEDIA_VISUAL_USER_SELECTED` granted | Granted, `limited` | **When allowed** | `limited` |
| Android 12 and earlier | `READ_EXTERNAL_STORAGE` granted | Granted, `granted` | **When allowed** | `granted` |
| Android | Nothing granted, Android shows the dialog again | Not granted, `denied` | **When denied** | `denied` |
| Android | Nothing granted, Android no longer shows the dialog | Not granted, `permanently_denied` | **When denied** | `permanently_denied` |

- **Limitations**:
  - Declare `READ_MEDIA_VISUAL_USER_SELECTED` to report a partial grant on Android 14. Without it, Android reports `READ_MEDIA_IMAGES` and `READ_MEDIA_VIDEO` as granted after the user selects some photos, until the app goes to the background. Your app then passes `granted` for access to a selection only.
  - With limited access on iOS, the system offers the user to update the selection once per app life cycle. To turn this off, set `PHPhotoLibraryPreventAutomaticLimitedAccessAlert` to `true` in `Info.plist`.
  - Access to the selected media on Android 14 can expire.
  - The system photo pickers, `PHPickerViewController` on iOS and the photo picker on Android, need no permission. [App Review Guideline 5.1.1](https://developer.apple.com/app-store/review/guidelines/#data-collection-and-storage) asks apps to use such a picker instead of full access where they can. Request this permission when the app shows its own gallery.
- **Cross-platform notes**: Both OSes report a partial grant, so pass `limited` on both.

### Media library \{#media_library\}

- **What the user sees**: On iOS, an alert with your purpose string for media and Apple Music. On Android, a runtime permission dialog.
- **Platforms**: iOS and Android.
- **iOS setup**: `NSAppleMusicUsageDescription`. The app must have this key to access the media library. Request the permission with `MPMediaLibrary.requestAuthorization()`.
- **Android setup**: `READ_MEDIA_AUDIO` on Android 13 and later, and `READ_EXTERNAL_STORAGE` with `android:maxSdkVersion="32"` for Android 12 and earlier.

Answer the request from the media library authorization status:

| OS | Native result | Answer | Section | `outcome` |
|:---|:--------------|:-------|:--------|:----------|
| iOS | `.notDetermined`, then the user allows | Granted, `granted` | **When allowed** | `granted` |
| iOS | `.notDetermined`, then the user declines | Not granted, `denied` | **When denied** | `denied` |
| iOS | `.denied` before the request | Not granted, `permanently_denied` | **When denied** | `permanently_denied` |
| iOS | `.restricted` | Not granted, `restricted` | **When denied** | `restricted` |

### Health data \{#health\}

- **What the user sees**: On iOS, the Health access sheet for the data types that the app requests. On Android, the Health Connect permissions screen, with an entry for each data type.
- **Platforms**: iOS and Android. On Android, the app requests Health Connect permissions, not a runtime permission.
- **iOS setup**:
  - The HealthKit capability.
  - `NSHealthShareUsageDescription` to read health data, and `NSHealthUpdateUsageDescription` to write it. Without these keys, the app crashes when it requests access.

  - A `<queries>` element with the package `com.google.android.apps.healthdata`.
  - Request the permissions with the contract from `PermissionController.createRequestPermissionResultContract()`. Android 14 and later include Health Connect. On Android 13 and earlier, the user needs the Health Connect app from Google Play.

### Local network \{#local_network\}

- **What the user sees**: On iOS, an alert with your purpose string the first time the app accesses the local network. On Android 17 and later, a runtime permission dialog for apps that target Android 17.

  - iOS doesn't report the local network status. iOS can deny the operation that shows the alert before the user answers, so a failed operation doesn't mean a refusal. Put the next step of the flow in **After response**.
  - In the background, iOS denies a local network operation without an alert and doesn't store the result. The alert appears at the next operation in the foreground.
  - The iOS Simulator doesn't apply local network privacy. Test on a device.
