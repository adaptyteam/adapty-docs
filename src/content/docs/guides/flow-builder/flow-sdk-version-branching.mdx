title: "Support new and old SDKs with a single flow"
description: "When a flow feature needs a newer Adapty SDK than some of your app builds have, send their users to a duplicate screen without the feature, in the same flow."
metadataTitle: "Support new and old SDKs with a single flow | Flows & paywalls | Adapty Docs"
---

Flows were introduced with Adapty SDK v4.0, but some of their features may require a later version. If you want to use these capabilities, you need to update the Adapty SDK bundled with your app. However, not all users are quick to update to the latest app version. And if you release a flow with a new feature straightaway, users of older app versions may see an incomplete or broken flow.

To solve this issue, update your flow to branch users based on their active SDK version:

- **New SDK**: The flow shows the new feature
- **Old SDK**: The flow does not show the new feature

Your metrics and A/B tests stay intact. You don't need to [copy the flow](copy-flows) or split your user traffic across multiple flows with [audiences](audience).

## 1. Set up the screens

Create at least three screens:

1. Set up the welcome screen. The users will see it before the flow branches. It is required to check the app's SDK version before presenting version-specific content.
2. Set up the new SDK route — one or more screens that take advantage of the new feature.
3. Set up the fallback route for the other users. To speed up the process, you can duplicate screens from the first route, rename them, and remove the incompatible elements.

Use [**Navigate to Screen**](onboarding-navigation-branching#static-navigation) to connect the screens within each route. If you reorder the screens, the [**Navigate next**](onboarding-actions#navigate-next) action may silently break.

Give each screen a distinct name that allows you to differentiate between the two routes. A unique name helps you locate the right screen when editing the flow, setting up navigation actions, or filtering your [flow metrics](flow-metrics).

## 2. Branch the flow by SDK version

On the welcome screen, select the element that moves users forward, such as the "Continue" button. Set it to trigger a [conditional action](onboarding-actions#conditional-actions) with the following rules:

- **if**: `sdk.version` ≥ the minimum SDK version that supports the feature (ex: `4.3.0`)
- **then**: Navigate to the first screen of the new SDK route.
- **else**: Navigate to the first screen of the fallback route, or end the flow with **Close Flow**.

:::warning
The `sdk.version` variable holds the Adapty SDK version of the app build that displays the flow, not the version of your app.
:::

## 3. Publish the flow and verify each branch

When the flow is ready, [publish it](builder-save-publish#publish-a-flow). The preview in the Adapty app doesn't allow you to mock the SDK version. Instead, verify each branch in a live app build:

1. Create two app builds for each platform:
    - One with the latest Adapty SDK
    - One with the SDK shipped with your latest app release
2. Make sure the flow placement is identical across builds.
3. Trigger and complete the flow in each build.
    - The builds with the new SDK should follow the new route.
    - The builds with the old SDK should follow the old route.

To troubleshoot a user who landed on the wrong branch, read the **Adapty SDK version** attribute on their [profile](profiles-crm#user-attributes).

## 4. Phase out the old route

Once no app build your users run has an old SDK, replace the conditional action on the welcome screen with static navigation. Delete the screens that targeted the legacy users.
