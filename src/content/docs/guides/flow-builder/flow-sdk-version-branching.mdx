Flows need Adapty SDK 4.0 or later, but some flow features need a later Adapty SDK version. The article of each feature states the version it needs. For example, [custom elements](flow-custom-elements) show their native view only with Adapty SDK 4.4 or later. Your users don't all update the app at once, so different users run builds with different Adapty SDK versions.

To give each user content that their app build can display, use the **SDK version** (`sdk.version`) condition in one flow:

- **Screens**: Send users with a later Adapty SDK to the main screen, and everyone else to a compatible copy of it.
- **Elements**: Show the new element to users with a later Adapty SDK, and a compatible element to everyone else.

Your metrics and A/B tests stay intact. You don't need to [copy the flow](copy-flows) or split your user traffic across multiple flows with [audiences](audience).

## How the SDK version condition works

The SDK version is a system variable. You select it on the **System** tab of a condition, as `sdk.version`, in two places:

- A [conditional action](onboarding-actions#conditional-actions), to send users to a screen.
- A [visibility condition](onboarding-element-visibility), to show or hide an element.

The SDK version has two comparisons:

| Comparison | Description in the builder | Use it for |
|---|---|---|
| **This version and above** (≥) | The main element. Shown when the SDK supports it. | The screen or element with the new feature |
| **Below this version** (&lt;) | The fallback. Shown instead when the SDK doesn't support it. | The compatible screen or element |

In the value field, select a version from the list, or enter a version as `major.minor` or `major.minor.patch`, such as `4.3.2`. The list shows Adapty SDK minor versions, newest first. The newest version in the list is marked **Latest**. A version without a patch number counts as patch 0, so `4.4` is `4.4.0`. An empty value makes the rule incomplete, which [blocks previewing and publishing](flow-common-issues#a-flow-wont-preview-or-publish). If the value isn't a version, such as `4.x`, the builder marks the field. When you publish such a flow, the publication fails, and the builder shows the error at the condition. Correct the value and publish again. Until then, the last published version of the flow stays in your app.

The flow compares versions number by number: major, then minor, then patch. So `4.10.0` is above `4.9.0`.

On the device, the flow reads the version of the native Adapty SDK for iOS or Android in the app build:

- **iOS**: The version of the Adapty iOS SDK.
- **Android**: The version of the core library `io.adapty:android-sdk`, not the version of the BOM `io.adapty:adapty-bom`. The two versions can differ. For example, BOM 4.4.2 includes `android-sdk` 4.4.0, and BOM 4.3.3 includes `android-sdk` 4.3.2. To find the `android-sdk` version of your build, open the dependency list of the BOM version that you use, or run `./gradlew app:dependencies` and find `io.adapty:android-sdk` in the output.
- **React Native, Flutter, Unity, Kotlin Multiplatform, and Capacitor**: The version of the native Adapty SDK that the cross-platform SDK includes, as above. This version can differ from the version of the cross-platform SDK. For example, React Native SDK 4.4.1 reports `android-sdk` 4.4.0 on Android, and the version of the included Adapty iOS SDK on iOS.

So in conditions, enter the native Adapty SDK version that the feature needs, not the version of the BOM or of the cross-platform SDK. The Adapty iOS SDK and the core library `android-sdk` don't always release the same patch versions, so a threshold with a patch number can match on one platform and not on the other. For example, an Android app on BOM 4.4.2 reports `android-sdk` 4.4.0, so it doesn't match **This version and above** `4.4.1`. To cover both platforms, use a threshold without a patch number, such as `4.4`.

If the flow can't get the Adapty SDK version, it counts the version as the oldest. So **Below this version** matches, and **This version and above** doesn't match. Users then see the compatible screen or element.

## Show a screen by Adapty SDK version

A conditional action runs when users interact with a screen, so it can't select the first screen of the flow. Send users to the main or the compatible screen from a screen that all users see first, such as a welcome screen.

1. Set up the main screen, with the new feature. To connect the screens of the main route, use [**Navigate to Screen**](onboarding-navigation-branching#static-navigation), not [**Navigate next**](onboarding-actions#navigate-next). With **Navigate to Screen**, the navigation doesn't depend on the order of the screens in the flow.
2. Make a compatible copy of the main screen: duplicate the main screen, and remove the new feature from the copy. To tell the two screens apart in navigation and in [flow metrics](flow-metrics), give them distinct names. On the copy, set the **Destination** of each **Navigate to Screen** action to the screens of the compatible route.
3. On the screen before the main screen, select the element that moves users forward, such as the **Continue** button.
4. In the **Interactions** panel, set its action to **Conditional Action**.
5. In the **if** block, click the **Variable** field, open the **System** tab, and select `sdk.version`. Select **This version and above**, and enter the minimum Adapty SDK version of the new feature, such as `4.4`.
6. In the **then** block, add **Navigate to Screen** with the main screen.
7. In the **else** block, add **Navigate to Screen** with the compatible screen.

:::

Use **This version and above** with the main screen in **then**, and the compatible screen in **else**. This way, the compatible screen also covers users whose Adapty SDK version the flow can't get.

## Show an element by Adapty SDK version

To replace one element instead of a whole screen, put a pair of elements on the screen: the new element and a compatible element. Give both elements the same version.

1. Select the new element. In the **Visibility** section of the right panel, select **Conditional**.
2. Click the **Variable** field, open the **System** tab, and select `sdk.version`. Select **This version and above**, and enter the minimum Adapty SDK version of the new element, such as `4.4`.
3. Select the compatible element. In the **Visibility** section, select **Conditional**.
4. Click the **Variable** field, open the **System** tab, and select `sdk.version`. Select **Below this version**, and enter the same version as in step 2.

:::note

:::

With the same version in both conditions, each user sees exactly one element of the pair, unless a **Show** or **Hide** action changes one of them.

You can also add the SDK version to a condition group with other conditions, such as `system.platform`. The element then shows when the whole group matches.

## Test both versions

The canvas and the [preview in the Adapty dashboard](paywall-device-compatibility-preview#preview-in-the-adapty-dashboard) evaluate a visibility condition on `sdk.version` as for the **Latest** version in the value list, with any patch number. They don't run conditional actions.

To see each branch and each element of the pair, [publish the flow](builder-save-publish#publish-a-flow). Then open it in a build of your app with an Adapty SDK version below the version in the conditions, and in a build with that version or later. In the [preview in the Adapty mobile app](paywall-device-compatibility-preview#preview-on-devices), you can't select the Adapty SDK version that the flow compares.

## Limitations

- **Hidden elements are still in the flow**: A visibility condition decides only what users see. An app build with an earlier Adapty SDK still loads every element of the flow, hidden elements too. So a condition can't make an earlier Adapty SDK read an element that it doesn't support. The same applies to screens: a conditional action decides only where users go, and the app build still loads the main screen too. A new element that has its own fallback, such as a [custom element](flow-custom-elements#set-fallback-content), shows its fallback on earlier versions.
- **A condition on a custom element also hides its fallback**: The custom element and its fallback content are one element on the screen. A visibility condition on the custom element applies to both:

  | Condition on the custom element | Adapty SDK in the app build | Users see |
  |---|---|---|
  | None | 4.3.2 | The fallback content |
  | **This version and above** `4.4` | 4.3.2 | Neither the native view nor the fallback content |
  | **This version and above** `4.4` | 4.4.0 or later | The custom element, as with no condition |

  The hidden custom element doesn't cause an error in an earlier Adapty SDK. The custom element has its own version check: an Adapty SDK earlier than 4.4 reads only its fallback content. The visibility condition then hides that fallback content too.

  To show compatible content to users with an earlier Adapty SDK, use the fallback of the custom element.
- **A custom variable with the ID `sdk.version`**: If the flow already has a custom variable with the ID `sdk.version`, conditions on `sdk.version` read that custom variable. The **System** tab of that flow doesn't offer the SDK version.
- **First frame on iOS with Adapty SDK 4.0 and 4.1**: In these versions, a screen can draw its first frame before the flow applies the visibility conditions. So on the first screen of the flow, an element that a visibility condition hides can appear for one frame when the screen opens.
