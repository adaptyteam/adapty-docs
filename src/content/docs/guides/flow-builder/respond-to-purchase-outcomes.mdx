When a purchase finishes, the Adapty SDK calls your app with the result. Nothing changes on screen until your app reacts. It can close the flow, leave the paywall open for another attempt, or open a flow that confirms the purchase.

The builder can't branch on a purchase result: no [trigger](onboarding-actions#trigger-types) fires when a purchase finishes, and no [variable](onboarding-variables) carries its outcome. So the transition belongs in your code, where the result arrives.

Split the work across two flows:

- Build your paywall.
- Build the post-purchase flow.
- When a purchase succeeds, close the first flow and open the second.

## Before you start

- [Create products](create-product) in the Adapty Dashboard.
- Install Adapty SDK v4.0 or later — flows require it.
- Build a paywall — for example, follow the [Create a basic paywall screen](basic-paywall-screen) recipe.

## 1. Build the post-purchase flow

Build the post-purchase flow [from a template or a blank canvas](paywall-builder-templates). The flow runs after the sale, so it needs no products. To send the user back to your app's own UI, add a button with the **Close Flow** action to the final screen.

<ZoomImage id="post-purchase-flow-close-action.webp" width="700px" alt="Post-purchase flow in the builder with a Thank you screen, the Start button selected, and its On Tap trigger set to the Close Flow action" />

Use a [**Custom Action**](onboarding-actions#custom-actions) when the flow has more than one way out. Create multiple buttons, each with its own action ID, so your app can tell **Set up now** from **Set up later**.

## 2. Add the post-purchase flow to its own placement

To fetch the post-purchase flow, it needs a unique placement. You cannot reuse your paywall's placement. 

1. [Publish the flow](builder-save-publish).
2. [Create a flow placement](create-placement). Note the **Placement ID** — we'll use it in the next step to fetch the flow.
3. Assign the post-purchase flow to the new placement.

## 3. Branch on the purchase result

Your app receives the purchase result through two callbacks:

- **Completion**: The purchase reached a conclusion — it succeeded, the user cancelled it, or the payment is pending approval (a parent's confirmation, for example). On success, the callback carries the updated `AdaptyProfile`.
- **Failure**: An error stopped the purchase, and the callback carries an `AdaptyError` — payment restrictions, invalid products, network failures, or transaction verification failures.

Branch on the outcome:

- On success, close the paywall, then present the post-purchase flow.
- On a cancellation, a pending payment, or a failure, leave the paywall open.

:::note
The same flow works after a restore, so a user who reinstalls or switches devices gets the same setup screens. Restores report through their own callback. Confirm the returned profile has your [access level](access-level) active, then close and present the same way.
:::

## 4. Load and present the post-purchase flow

Load and present the post-purchase flow. To open it without a wait, fetch it alongside the paywall, rather than inside the handler. The SDK will download and cache the images in advance.

To warm the cache for several placements in one call, use [`preloadFlows`](ios-optimize-paywall-fetching#preload-placements) (SDK 4.1+).
