Interactive flow elements change their look based on user actions: a tapped quiz option becomes **Selected**, a focused input becomes **Active**. Style each state separately to give users visual feedback without app code.

Some states are condition-driven. You set up a condition, and they apply while it is met:

- [**Disabled**](#add-the-disabled-state): users can't interact with the element.
- [Custom states](#add-a-custom-state): you name the state and style the element for a case that no built-in state covers. No action switches an element to a custom state. Instead, [change a custom variable on tap](#switch-an-element-to-a-custom-state-on-tap), and base the condition of the state on that variable.

An element is [only in one state at a time](#when-several-states-apply-to-one-element).

## Available states by element kind

| Element kind | Built-in states | Addable states |
|---|---|---|
| [Selectable elements](#selectable-element-states) | **Default**, **Selected** | **Disabled**, **custom** states (except on tab headers) |
| [Inputs](#input-states) | **Default**, **Active**, **Invalid** | **Disabled**, **custom** states (except on pickers) |
| [Any element with a tap interaction](#add-a-state) — buttons, images, containers, and so on (except texts and icons) | **Default** | **Disabled**, **custom** states (except on bottom sheets) |
| [Progress indicator steps](#step-states-for-progress-indicators) | **Completed**, **Current**, **Upcoming** | — |

**Addable** states are condition-driven: they apply while a condition that you [set up](#add-a-state) is met.

The conditions of other elements can also evaluate element states. For example, you can [explain why a button is disabled](element-states-in-conditions#explain-why-a-button-is-disabled).

## Style a state

<ZoomImage id="element-states-panel.webp" width="300px" alt="States section in the right panel of a selected element" float="right" />


1. Select an element. The **States** section in the right panel shows a tab for each state that the element has.
2. In the **States** section, activate the target state. If the section has no tab for the state, [add the state](#add-a-state).
3. Change any property — fill, border, typography, and so on. The change is scoped to that state.

    Nested elements become stateful alongside the parent. Any change to a child is scoped to the parent's active state.

4. The Adapty SDK applies the matching style at runtime.

## Selectable element states

<ZoomImage id="selectable-state-demo.webp" width="600px" alt="Selectable element with Selected state activated and a style override applied" />

Selectable elements — quiz options, products, tabs, toggles and checkboxes, and any [custom selectable element](flow-selectable-elements#make-an-element-selectable) — have two states out of the box:

- **Default**: The element's resting appearance.
- **Selected**: Applies when the user taps the element. The element returns to **Default** when the user de-selects it.

In a single-choice group, selecting one element de-selects the others. Multi-choice groups let several be Selected at the same time. Toggles are independent — selecting a toggle has no effect on its siblings. See [group types](flow-selectable-elements#group-types).

:::tip
To reuse state-specific styles, add them to one element, such as a product card. Then ask the [AI Editor](flow-ai-editor) to apply them to the other elements. State-specific styles don't carry over between siblings on their own.
:::

## Input states

- **Default**: The input's resting appearance.
- **Active**: Applies while the input is focused.
- **Invalid**: Applies when the input's content fails validation, for example, when an email field doesn't contain `@`. See [Input validation](builder-inputs-and-forms#input-validation).
- **Disabled**: The input is not interactive. [Add this state](#add-the-disabled-state) manually.

Style each state the same way as a selectable element: activate the target state, change properties.

## Step states for progress indicators

:::link
Main article: [Progress indicators](builder-loaders-and-progress-bars#step-states)
:::

Progress indicators show users how much of an onboarding flow they have completed. Each step has three states:

- **Completed**: Steps the user has passed.
- **Current**: The user's current step.
- **Upcoming**: Steps the user hasn't reached yet.

## When several states apply to one element

Several states can apply to one element at once. For example:

- Users submit an invalid address in an email field, then tap the field again to fix it. The field has focus, so **Active** applies. The address is still invalid, so **Invalid** applies too.
- Users turn on a trial toggle, so **Selected** applies. Then they pick a plan without a trial. The toggle has a **Disabled** condition for that plan, so **Disabled** applies too.

An element is only in one state at a time. When several states apply, the element is in the state that comes last in this list:

1. **Selected**
2. **Invalid**
3. **Active**
4. **Disabled**
5. Custom states, in the order you added them

In the examples, the email field is **Active**, and the trial toggle is **Disabled**. The element looks the way you styled that state. A condition that evaluates the state of the element only matches that state. When no state in the list applies, the element is **Default**.

A custom state only changes the look. If **Disabled** applies too, the element is in the custom state, but users can't interact with it.

## Add a state

### Add the Disabled state

<ZoomImage id="element-states-add-state-menu.webp" width="300px" float="right" alt="The Add state menu of a button, with Disabled and Custom state" />

To stop users from interacting with an element, add the **Disabled** state:

1. Select the target element.
2. If the **States** section has no **Disabled** tab, click **+ Add state**, and select **Disabled**. If the element already has states other than **Default**, click **Settings** <Inline id="settings.svg" alt="Settings" /> before **+ Add state**.
3. Hover over **Disabled**, and click **Set conditions**.
4. Add a condition. If you want to disable the **submit** button unless the input passes validation, compare the input's `isValid` variable to `false`. For the **Disabled** state to apply, fill in every **Value** field.
5. Style the Disabled state to visually communicate the restriction (for example, lower the opacity).

<ZoomImage id="element-states-disabled-condition.webp" width="400px" alt="The Edit conditional state popover with the condition email.isValid = False" />

The Adapty SDK evaluates the condition at runtime and applies the Disabled state when appropriate — no app code needed.

A **Disabled** condition can also evaluate the state of another element. For example, you can [disable two elements together](element-states-in-conditions#synchronize-element-states).

### Add a custom state

To style an element for a case that no built-in state covers, add a custom state. For example:

- Emphasize an annual plan card while a trial toggle is on.
- Change the color of a **Remind me** button after users tap it. To set this up, [switch the button to a custom state on tap](#switch-an-element-to-a-custom-state-on-tap).

A custom state only changes the look. To stop users from interacting with an element, [add the **Disabled** state](#add-the-disabled-state).

[Every element that can have the **Disabled** state](#available-states-by-element-kind) can also have custom states, except tab headers, pickers, and bottom sheets. If you remove the **On Tap** trigger of a button, an image, or a container, its custom states stay in the **States** section but stop applying.

<ZoomImage id="element-states-edit-state-dialog.webp" width="350px" float="right" alt="The Edit state dialog with the name Reminder set and the condition reminder.set = True" />

1. Select the target element.
2. In the **States** section, click **+ Add state**, and select **Custom state**. If the element already has states other than **Default**, click **Settings** <Inline id="settings.svg" alt="Settings" /> before **+ Add state**.
3. In the **Name** field, enter a name for the state.
4. Add a condition. If one true row is enough, click **all** to switch it to **any**. For the state to apply, fill in every **Value** field.
5. Click **Save**.
6. To style the state, activate its tab in the **States** section, and [change the properties of the element](#style-a-state). On a text field, a custom state only changes the fill, border, and corner radius.

<ZoomImage id="element-states-custom-state-tab.webp" width="700px" alt="The Reminder set tab active in the States section, with the Remind me button styled for that state" />

The condition of a custom state can also [evaluate the state of another element](element-states-in-conditions#add-an-element-state-to-a-condition), such as whether a toggle is **Selected**.

### Switch an element to a custom state on tap

No action switches an element to a custom state. Instead, change a custom variable on tap, and base the condition of the state on that variable.

1. [Create a custom variable](onboarding-variables#create-a-custom-variable) of type **Boolean**, with the initial value `false`.
2. Select the element that users tap. On the **Interactions** tab, [add a **Set variable** action](onboarding-variables#update-a-variable-via-an-interaction) to its **On Tap** trigger, and set the variable to `true`.
3. [Add a custom state](#add-a-custom-state) to the element that switches. In the condition, pick the variable on the **Custom** tab of the **Variable** field. Set the **Value** field to `true`.

<ZoomImage id="element-states-custom-variable-picker.webp" width="500px" alt="The Custom tab of the Variable field, with the reminder.set variable picked in the condition of a custom state" />
