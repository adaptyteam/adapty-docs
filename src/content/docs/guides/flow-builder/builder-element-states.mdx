Interactive flow elements change their look based on user actions: a tapped quiz option becomes **Selected**, a focused input becomes **Active**. Some states are condition-driven: you can **disable** a button, or add a [custom state](#custom-states) with your own name and condition. Style each state separately to give users visual feedback without app code.

## Available states by element kind

| Element kind | Built-in states | Addable states |
|---|---|---|
| [Selectable elements](#selectable-element-states) | **Default**, **Selected** | **Disabled**, [custom states](#custom-states) |
| [Inputs](#input-states) | **Default**, **Active**, **Invalid** | **Disabled**; [custom states](#custom-states) on text, email, password, number, and phone inputs |
| [Any element with a tap interaction](#condition-driven-disabled-state) — buttons, images, icons, containers, and so on | **Default** | **Disabled**, [custom states](#custom-states) on [supported elements](#elements-that-support-custom-states) |
| [Progress indicator steps](#step-states-for-progress-indicators) | **Completed**, **Current**, **Upcoming** | — |

**Addable** states don't appear by default — open **States settings** <Inline id="settings.svg" alt="Settings" /> to add them. They are condition-driven: you define when they activate. See [Condition-driven Disabled state](#condition-driven-disabled-state) and [Custom states](#custom-states).

The conditions of other elements can also evaluate element states. For example, you can [explain why a button is disabled](element-states-in-conditions#explain-why-a-button-is-disabled).

## When several states apply to one element

Several states can apply to one element at once. For example:

- Users submit an invalid address in an email field, then tap the field again to fix it. The field has focus, so **Active** applies. The address is still invalid, so **Invalid** applies too.
- Users turn on a trial toggle, so **Selected** applies. Then they pick a plan without a trial. The toggle has a **Disabled** condition for that plan, so **Disabled** applies too.
- A **Continue** button has a **Disabled** state and a custom state named **Locked**. Both conditions are true, so both states apply.

An element is only in one state at a time. When several states apply, the element is in the state that comes last in this list:

1. **Selected**
2. **Invalid**
3. **Active**
4. **Disabled**
5. A [custom state](#custom-states)

When several custom states apply, the element is in the custom state that comes last in the **States** settings list.

In the examples, the email field is **Active**, the trial toggle is **Disabled**, and the **Continue** button is **Locked**. The element looks the way you styled that state. A condition that evaluates the state of the element only matches that state. When none of these states applies, the element is **Default**.

A custom state only sets the look of the element. A **Disabled** element still ignores taps when a custom state sets its look.

## How to style a state

<ZoomImage id="element-states-panel.webp" width="300px" alt="States section in the right panel of a selected element" float="right" />


1. Select an element. The **States** section in the right panel lists the states the element supports.
2. In the **States** section, activate the target state. If necessary, add the [condition-driven Disabled state](#condition-driven-disabled-state) or a [custom state](#custom-states).
3. Change any property — fill, border, typography, and so on. The change is scoped to that state.

    Nested elements become stateful alongside the parent. Any change to a child is scoped to the parent's active state.

4. The Builder applies the matching style at runtime.

## Selectable element states

<ZoomImage id="selectable-state-demo.webp" width="600px" alt="Selectable element with Selected state activated and a style override applied" />

Selectable elements — quiz options, products, tabs, toggles and checkboxes, and any [custom selectable element](flow-selectable-elements#make-an-element-selectable) — have two states out of the box:

- **Default**: The element's resting appearance.
- **Selected**: Applies when the user taps the element. The Builder reverts to Default when the user de-selects the element.

In a single-choice group, selecting one element de-selects the others. Multi-choice groups let several be Selected at the same time. Toggles are independent — selecting one has no effect on its siblings. See [group types](flow-selectable-elements#group-types).

:::tip
To reuse state-specific styles, add them to one element, such as a product card. Then ask the [AI Editor](flow-ai-editor) to apply them to the other elements. State-specific styles don't carry over between siblings on their own.
:::

## Input states

- **Default**: The input's resting appearance.
- **Active**: Applies while the input is focused.
- **Invalid**: Applies when the input's content fails validation. For example, when an email field doesn't contain `@`. See [Input validation](builder-inputs-and-forms#input-validation).
- **Disabled**: The input is not interactive. Add this state manually; see [Condition-driven Disabled state](#condition-driven-disabled-state).
- **Custom states**: Text, email, password, number, and phone inputs only. In a custom state, only the fill, border, and corner radius of an input change. See [Custom states](#custom-states).

Style each state the same way as a selectable element: activate the target state, change properties.

## Condition-driven Disabled state

The Disabled state prevents the user from interacting with an element. Unlike Default, Selected, Active, or Invalid, the Disabled state does not activate on its own — it requires a user-defined trigger condition.

Disabled is available on:

- **Inputs**: Any [input field](builder-inputs-and-forms) — text, email, password, number, phone, date and/or time.
- **Selectable elements**: Quiz options, products, tabs, toggles and checkboxes, and any [custom selectable element](flow-selectable-elements#make-an-element-selectable).
- **Any element with a tap interaction**: For example, a button, image, or icon that triggers a navigation action.

### Add the Disabled state

<ZoomImage id="add-disabled-state.webp" width="300px" float="right" alt="States section with the Add state menu open and the Disabled option" />

To add and configure a Disabled state:

1. Select the target element.
2. In the **States** section, click **Add state**, and select **Disabled**. If the element already has states, click **Settings** <Inline id="settings.svg" alt="Settings" /> first: **Add state** is under the list of states. On an element that can't have custom states, the control is the **Disabled state** button.
3. The Disabled state appears in the **States** section.
4. Next to the new Disabled state, click **Edit conditional state** <Inline id="visibility-conditional.svg" alt="Edit conditional state" />.
5. Add a condition. If you want to disable the **submit** button unless the input passes validation, compare the input's `isValid` variable to `false`.
6. Style the Disabled state to visually communicate the restriction (for example, lower the opacity).

{ <ZoomImage id="set-disabled-condition.webp" width="700px" alt="Set condition for disabled state " />}

The Adapty SDK evaluates the condition at runtime and applies the Disabled state when appropriate — no app code needed.

A **Disabled** condition can also evaluate the state of another element. For example, you can [disable two elements together](element-states-in-conditions#synchronize-element-states).

## Custom states

A custom state is a state with your own name and your own condition. For example, a **Locked** state can make a button gray while the user has a free plan. The element is in the custom state while its condition is true.

Each element can have up to 5 custom states.

### Elements that support custom states

- **Elements with a tap action**: Buttons, containers, images, videos, timers, and carousels. First, add an [**On Tap** trigger](onboarding-actions#set-up-interactions) with at least one action on the **Interactions** tab.
- **Selectable elements**: Elements in a selectable group, and selectable elements with a tap action.
- **Inputs**: Text, email, password, number, and phone inputs.

Other elements, such as icons, bottom sheets, tab items, tab content, pickers, and progress indicator steps, can't have custom states.

<ZoomImage id="custom-state-needs-tap.webp" width="300px" float="right" alt="Add state menu with the Custom state option turned off and the caption Add a tap action to use custom states" />

To add a custom state to a button, container, image, video, timer, or carousel, first add an **On Tap** trigger with at least one action. Until then, the **States** section has no **Add state** control. If the element already has states, the **Custom state** option is off, with the caption "Add a tap action to use custom states". After you add a tap action, the option is on.

### Add a custom state

<ZoomImage id="custom-state-add-menu.webp" width="300px" float="right" alt="States section with the Add state menu open, listing Disabled and Custom state" />

1. Select the element.
2. In the **States** section, click **Add state**. If the element already has states, click **Settings** <Inline id="settings.svg" alt="Settings" /> first: **Add state** is under the list of states.
3. Select **Custom state**. The **Edit state** panel opens.

    <ZoomImage id="custom-state-edit-panel.webp" width="400px" alt="Edit state panel with the name Locked and the condition plan equals free" />

4. In **Name**, enter a name for the state, such as **Locked**. The name follows the [name rules](#name-rules).
5. Add a condition. For example, compare the `plan` variable to `free`. To add more conditions, click **Add Condition**, and select if **all** or **any** of them must be true.
6. Click **Save**. The new state appears as a tab in the **States** section.
7. Activate the tab of the new state, and [style it](#how-to-style-a-state). The styles of nested elements, such as the text in a button, also apply on the device.

To close the **Edit state** panel without changes, click **Cancel** or the close button, press **Escape**, or click outside the panel.

When an element has 5 custom states, the **Custom state** option is off, with the caption "Up to 5 custom states". To add another custom state, delete one first. When a flow config from JSON or an AI tool has more than 5 custom states on an element, the states stay, and you can edit them.

### Name rules

The builder ignores letter case: **Locked** and **locked** are the same name. It also removes the spaces at the start and the end of the name when you save. When the name breaks a rule, the **Save** button is off and an error shows under the field:

| Rule | Error |
|---|---|
| The name is not empty. | **Name is required** |
| The name has 30 characters or fewer. | **Max 30 characters** |
| The name is not **Default** or the name of a built-in state: **Selected**, **Active**, **Invalid**, **Disabled**, **Completed**, **Current**, **Upcoming**, or `focused`. | **This name is reserved** |
| The name is different from the names of the other custom states of the element. | **A state with this name already exists** |

### Edit a custom state

<ZoomImage id="custom-state-tab-tooltip.webp" width="300px" float="right" alt="Tooltip of the Locked state tab with the Edit state button" />

To change the name or the condition of a custom state, open the **Edit state** panel in one of these ways:

- In the **States** settings list, click the row of the state, or click the condition icon <Inline id="visibility-conditional.svg" alt="Condition" /> in that row.
- Hover over the tab of the state, and click **Edit state** in the tooltip.

After you save, the state keeps its styles. The conditions of other elements that evaluate this state show the new name.

### Delete a custom state

In the **States** settings list, click the trash icon in the row of the state. If conditions of other elements evaluate the state, a dialog lists them first. After you click **Delete**, these conditions break, and you can't publish the flow until you fix them. See [Troubleshooting](element-states-in-conditions#troubleshooting).

The builder deletes the state and its styles. If the tab of the deleted state was active, the **Default** tab becomes active.

To restore the state, undo the deletion. The state comes back at the same place in the list, with its styles.

### Incomplete conditions

A condition row is incomplete when one of its sides is empty. For example, you added a row and didn't fill it, or you picked a variable and entered no value. A condition with an incomplete row never becomes true, also when the other rows are true. The element never enters the state, and the device shows its **Default** style. This rule applies to **Disabled** conditions too: the element stays interactive.

The builder doesn't show a warning for an incomplete row, so fill or delete each row before you publish. A row with a value or **is empty** but no variable stops the publish with an [**Invalid State Condition** error](flow-common-issues#a-flow-wont-preview-or-publish).

### Limitations

<ZoomImage id="custom-state-device-warning.webp" width="300px" float="right" alt="States settings list with the warning Not shown on the device. Add a tap action to the element. under two custom states" />

- **Elements that don't show the state on the device**: The canvas shows a custom state on any element. The device only shows it on [supported elements](#elements-that-support-custom-states). An unsupported element can have a custom state, for example from JSON or an AI tool, or after you delete its tap action.

    In this case, the **States** settings list and the tab tooltip show a warning: "Not shown on the device. Add a tap action to the element." or "Not shown on the device for this element type." You can still edit, delete, and publish the state.
- **Inputs**: In a custom state, only the fill, border, and corner radius of an input change. Other properties, such as the text color, keep their **Default** values. The **Edit state** panel of an input shows the caption "Only fill, border and corner radius change in a custom state".
- **Videos and carousels**: When a video or a carousel changes state on the device, the video plays again from the start, and the carousel goes back to its first slide. Don't add custom states to a video or a carousel that must keep its playback position or its current slide.

## Step states for progress indicators

:::link
Main article: [Progress indicators](builder-loaders-and-progress-bars#step-states)
:::

Progress indicators show users how far they've gotten in an onboarding flow. Each step has three states:

- **Completed**: Steps the user has passed.
- **Current**: The user's current step.
- **Upcoming**: Steps the user hasn't reached yet.
