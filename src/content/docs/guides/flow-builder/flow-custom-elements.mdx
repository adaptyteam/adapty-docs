With a custom element in the Flow & Paywall Builder, you can add a native view to a flow screen. It can be a Lottie / Rive animation, an interactive chart, a map, a camera preview — or any view from your actual app.

<DocVideo id="custom-elements-examples.mp4" alt="Three flow screens with native views: a Lottie ring that fills up to 4 of 7 days, a weight chart that the user drags along, and a map of fitness centers near the user." />

To display a native view on a flow screen:

1. [Add a custom element](#add-and-configure) to the screen, and enter its **Type** and **ID**.
2. [Add fallback content](#set-fallback-content) inside the custom element. Users see it when your app doesn't display the view.
3. [Set up the view in the code of your app](#set-up-your-app-code). Use the Adapty SDK to assign it the same Type and ID.
4. [Test the flow on a device](#test-and-distribute), and publish it.
5. [Distribute the new app version](#what-changes-require-an-app-release) with the native view. Users on older versions see the fallback.

:::tip
Use a custom element only for a view that responds to touch, changes with data from your app, or uses the camera. For a picture or a recorded animation, use an [**Image**](custom-media#image) or a [**Video**](custom-media#video) element instead. Neither needs code in your app, and you can replace the file without an app release.
:::

## Setup

### 1. Add and configure \{#add-and-configure\}

1. Open the **Add element** panel. In the **Media** group, click **Custom element**.

   <ZoomImage id="flow-custom-element-card.webp" width="200px" alt="Custom element in the Media group of the Add element panel" />

   :::warning
   If the native view responds to touch, keep the custom element out of containers that also respond to touch, such as a carousel. Otherwise, a swipe in the native view also moves the carousel.
   :::

2. In the **Type** field, enter the name of the view that your app draws, such as `lottie_animation`:
   - **Naming rules**: Use only lowercase letters, numbers, and underscores.
   - **Exact match**: Your app must register the same Type, letter for letter. With any other spelling, users see the fallback.
   - **Suggestions**: The field suggests the Types already used in this flow, not the ones that your app registers.
3. In the **ID** field, enter an ID, such as `welcome_wave`. The ID distinguishes between custom elements of the same Type.

   <ZoomImage id="flow-custom-element-type-id.webp" width="500px" alt="Type and ID fields in the Element section of the custom element settings" />

4. To reserve a set amount of space for the native view, give the custom element a **Fixed** height.
   - **Shared area**: The native view and the fallback content share the same area.
   - **Alignment**: If the native content does not take up the entire area, its placement is determined by the element's alignment grid.

   :::important
   With a **Hug** height, a native view without a height of its own, such as a map or a scrolling list, collapses to almost zero height.
   :::

5. (Optional) To cut the native view to the rounded **Corners** of the custom element, in the **Layout** section, select the **Clip content** checkbox.

To use the same native view in several custom elements:

- **On several screens or flows**: Enter the same Type in each custom element.
- **On one screen**: Enter the same Type and a different ID in each custom element, so that your app can tell them apart. Re-using the same Type/ID pair within the same screen yields a warning.
- **In a duplicated or pasted custom element**: If its ID is already taken on the screen, the builder renames the ID during duplication: `custom_1` becomes `custom_2`. Make sure that the code of your app references the correct ID.

### 2. Set fallback content \{#set-fallback-content\}

Users see the fallback in place of the native view when:

- Their version of your app doesn't include the view code.
- Your app's version of the Adapty SDK doesn't include custom element support.
- The custom element's Type and ID do not match a view in your app code.
- Your app code matches the Type and ID but returns no view. For example, the view needs a file that isn't on the device, or a permission that the user denied.

To set the fallback, add elements to the custom element container. Without a fallback, users in these cases see an empty area the size of the custom element. The canvas shows the fallback, never the native view.

<ZoomImage id="flow-custom-element-placeholder.webp" width="400px" alt="Empty custom element on the canvas with the text Add elements here as a fallback" />

:::important
Keep navigation buttons, purchase buttons, and other essential UI parts outside the custom element. Users see either the native view or the fallback, never both.
:::

Use only **Relative** or **Absolute** position for the children of the custom element. You can't publish a flow with a **Fixed** element inside a custom element.

### 3. Set up your app code \{#set-up-your-app-code\}

When a screen with a custom element opens, the Adapty SDK passes the element's Type and ID to a resolver function in your app code. The resolver returns one of the following:

- **The view that matches the Type and ID**: Users see the native view. In the code, spell the Type and ID exactly as in the builder.
- **No view**: Users see the fallback. For example, return no view when a file that the view needs isn't on the device.

For the iOS code, follow [Display custom elements with the iOS SDK](ios-flow-custom-elements). It shows how to write the resolver and test the native view on a device.

:::tip
A native view can visualize user data, given that it was collected in an earlier flow. See [Show an interactive weight goal chart in a paywall](custom-element-interactive-chart).
:::

### 4. Test and distribute \{#test-and-distribute\}

To [publish the flow](builder-save-publish), make sure that every custom element has a Type that follows the [naming rules](#add-and-configure). You can publish the flow before you release the app — users of older app versions will see the fallback.

An error in the native view can crash the app. Before you release the app, test every screen that has a custom element. To do this, open a build with the native view on [a registered test device](test-devices) to avoid viewing a cached version of the flow.

## What changes require an app release

Custom element display native code from your app bundle. This code cannot be updated without an app release. The fallback content or the settings of the custom element can.

| Changed content | What you do | Users who haven't updated the app see |
|---|---|---|
| Native view content for an existing custom element, such as a different animation | Distribute the new content with an app update | Fallback content |
| Native view content for a new custom element | Distribute the new content with an app update, and modify the custom element to reference the new content | Fallback content |
| Fallback content, custom element properties | Publish the flow. No app update needed | The updated content |

## Troubleshooting

- **Users see the fallback instead of the native view**: Make sure that the Type and ID match the ones in your app, letter for letter. Users of app versions without the view see the fallback until they update the app. To find the cause in the code, follow [Test on a device](ios-flow-custom-elements#test-on-a-device) in the iOS guide.
- **Users see an empty area**: [Add a fallback](#set-fallback-content) and publish the flow. If you still see an empty area on a [test device](test-devices), the native view appears without its content. Make sure that your app shows no view when the content is missing.
- **The native view doesn't fit the custom element**: Make sure that your app fits the view to the area of the custom element. To cut the view to the rounded **Corners**, in the **Layout** section, select the **Clip content** checkbox.
