A [flow](adapty-flow-builder) can ask users for a system permission with the **Request permission** action, for example push notifications on an onboarding screen that explains what the notifications are for, or camera access before a feature that scans documents. The Adapty SDK doesn't show the system permission dialog itself. It passes the request to an `AdaptyUISystemRequestsHandler` in your app. Your app shows the dialog and returns the user's answer, and the flow continues.

## Before you start

You need:

- **Adapty Kotlin Multiplatform SDK 4.1.0 or later**: Version 4.1.0 is the first stable release with `AdaptyUISystemRequestsHandler`.
- **A flow with the Request permission action**: In the Flow & Paywall Builder, add the **Request permission** action to an element's **On Tap** or **On Screen Appear** trigger. In the action, select the permission in the **Permission** field, and add the actions to run after the user answers to its outcome sections, such as **Navigate Next** in **After response**. For the action settings, see [Request permission](onboarding-actions#request-permission).
- **The declarations of the permissions that your handler requests**: A purpose string in `Info.plist` on iOS, and a permission in the Android manifest. See [Declare the permissions](#declare-the-permissions).
- **For push notifications on Android, `targetSdk` 33 or higher**: Only apps that target Android 13 or later choose when the notification permission dialog appears.

## How the flow requests a permission

1. The flow reaches the **Request permission** action: the user taps the element, or the screen appears.
2. The Adapty SDK calls `handlePermission` on your handler with the permission selected in the action, such as `AdaptyUIPermission.PUSH` or `AdaptyUIPermission.CAMERA`.
3. Your app requests the permission from the OS and returns `AdaptyUIPermissionResult.granted()` or `AdaptyUIPermissionResult.denied()` with a status.
4. The flow runs the actions of one outcome section.

<FlowPermissionAnswers />

The flow waits on the screen until your app returns the answer. If your app never answers, the flow stays on the screen. If the OS doesn't show the dialog, for example because the user already answered it, your handler returns at once, and the flow runs the outcome actions right away. If those actions leave the screen, the user sees the screen that requests the permission only for a moment.

With **On Screen Appear**, the flow doesn't send the request again when the user comes back to the screen with a **Navigate back** action, unless every outcome section of the action is empty. With **On Tap**, each tap sends a new request. The flow sends one permission request at a time: while a request waits for your answer, a tap on an element that requests a permission does nothing.

## Implement the handler

:::warning
**Request only the permissions that your app declares, and answer `AdaptyUIPermissionResult.denied("unsupported")` for any other permission.** For most permissions, iOS terminates the app when the app requests a permission whose purpose string is missing from `Info.plist`. A flow author can add a request for any permission at any time, and the flow also reaches app versions released before the request was added.
:::

To answer permission requests, implement `AdaptyUISystemRequestsHandler` in common code. Return a result for every request, and catch the exceptions of your platform code. The Adapty SDK doesn't catch exceptions from `handlePermission`: an uncaught exception crashes the app, and the flow gets no answer.

In this example, the handler requests push notifications and camera access, and answers every other permission as unsupported without a dialog:

```kotlin showLineNumbers title="commonMain"
import com.adapty.kmp.AdaptyUISystemRequestsHandler
import com.adapty.kmp.models.AdaptyUIFlowView
import com.adapty.kmp.models.AdaptyUIPermission
import com.adapty.kmp.models.AdaptyUIPermissionResult
import kotlin.coroutines.cancellation.CancellationException

class MySystemRequestsHandler : AdaptyUISystemRequestsHandler {
    override suspend fun handlePermission(
        view: AdaptyUIFlowView,
        permission: AdaptyUIPermission,
        customArgs: Map<String, String>?,
    ): AdaptyUIPermissionResult {
        val granted = try {
            when (permission) {
                AdaptyUIPermission.PUSH -> requestPushPermission()
                AdaptyUIPermission.CAMERA -> requestCameraPermission()
                // A permission this app version doesn't request: answer without a dialog.
                else -> return AdaptyUIPermissionResult.denied("unsupported")
            }
        } catch (e: CancellationException) {
            throw e
        } catch (e: Exception) {
            // Not an answer from the user: the flow runs After response.
            return AdaptyUIPermissionResult.denied()
        }
        return if (granted) {
            AdaptyUIPermissionResult.granted("granted")
        } else {
            AdaptyUIPermissionResult.denied("denied")
        }
    }
}
```

`requestPushPermission` and `requestCameraPermission` are your platform code. See [Request the permissions on each platform](#request-the-permissions-on-each-platform).

`handlePermission` receives:

- **`view`**: The flow view that sent the request.
- **`permission`**: The permission selected in the action. `AdaptyUIPermission` has a constant for each value in [Declare the permissions](#declare-the-permissions), named in upper case: for example, `AdaptyUIPermission.LOCATION_WHEN_USE` for `location_when_use`. The `value` property returns the value as a string.
- **`customArgs`**: Custom arguments of the request. The **Request permission** action sends none, so the value is `null`.

`granted` and `denied` take the status as an optional `detail` string, such as `AdaptyUIPermissionResult.denied("permanently_denied")`.

A granted notification permission lets your app show notifications. To receive push notifications, register the device with your push provider, such as APNs or Firebase Cloud Messaging, as your app does outside flows.

`AdaptyUISystemRequestsHandler` also has `handleAppReviewRequest`. Its default shows the native review prompt, so you don't need to override it.

## Request the permissions on each platform

Common code can't show the system dialogs, so `requestPushPermission` and `requestCameraPermission` are `expect` functions with an `actual` implementation for each platform. If your app already uses a Kotlin Multiplatform permissions library, you can call it from `handlePermission` instead. See [Use moko-permissions](#use-moko-permissions).

```kotlin title="commonMain"
expect suspend fun requestPushPermission(): Boolean
expect suspend fun requestCameraPermission(): Boolean
```

On iOS, ask `UNUserNotificationCenter` and `AVCaptureDevice` for authorization:

```kotlin showLineNumbers title="iosMain"
import kotlinx.coroutines.suspendCancellableCoroutine
import platform.AVFoundation.AVCaptureDevice
import platform.AVFoundation.AVMediaTypeVideo
import platform.AVFoundation.requestAccessForMediaType
import platform.UserNotifications.UNAuthorizationOptionAlert
import platform.UserNotifications.UNAuthorizationOptionBadge
import platform.UserNotifications.UNAuthorizationOptionSound
import platform.UserNotifications.UNUserNotificationCenter
import kotlin.coroutines.resume

actual suspend fun requestPushPermission(): Boolean =
    suspendCancellableCoroutine { continuation ->
        UNUserNotificationCenter.currentNotificationCenter().requestAuthorizationWithOptions(
            UNAuthorizationOptionAlert or UNAuthorizationOptionBadge or UNAuthorizationOptionSound,
        ) { granted, _ ->
            continuation.resume(granted)
        }
    }

actual suspend fun requestCameraPermission(): Boolean =
    suspendCancellableCoroutine { continuation ->
        AVCaptureDevice.requestAccessForMediaType(AVMediaTypeVideo) { granted ->
            continuation.resume(granted)
        }
    }
```

On Android, the notification permission exists from Android 13. On earlier versions, return whether notifications are turned on for the app. Ask from the activity that is on screen, which is the flow's activity while a flow is shown. In this example, `ResumedActivity` tracks it. Register it in `Application.onCreate` with `registerActivityLifecycleCallbacks(ResumedActivity)`:

```kotlin showLineNumbers title="androidMain"
import android.Manifest
import android.app.Activity
import android.app.Application
import android.content.pm.PackageManager
import android.os.Build
import android.os.Bundle
import androidx.activity.ComponentActivity
import androidx.activity.result.ActivityResultLauncher
import androidx.activity.result.contract.ActivityResultContracts
import androidx.core.app.NotificationManagerCompat
import androidx.core.content.ContextCompat
import kotlinx.coroutines.suspendCancellableCoroutine
import kotlin.coroutines.resume

object ResumedActivity : Application.ActivityLifecycleCallbacks {
    var current: ComponentActivity? = null
        private set

    override fun onActivityResumed(activity: Activity) {
        current = activity as? ComponentActivity
    }

    override fun onActivityPaused(activity: Activity) {
        if (current === activity) current = null
    }

    override fun onActivityCreated(activity: Activity, savedInstanceState: Bundle?) {}
    override fun onActivityStarted(activity: Activity) {}
    override fun onActivityStopped(activity: Activity) {}
    override fun onActivitySaveInstanceState(activity: Activity, outState: Bundle) {}
    override fun onActivityDestroyed(activity: Activity) {}
}

actual suspend fun requestPushPermission(): Boolean {
    // No activity on screen: the exception makes the handler answer without a status.
    val activity = ResumedActivity.current ?: throw IllegalStateException("No resumed activity")
    if (Build.VERSION.SDK_INT < Build.VERSION_CODES.TIRAMISU) {
        return NotificationManagerCompat.from(activity).areNotificationsEnabled()
    }
    return requestAndroidPermission(activity, Manifest.permission.POST_NOTIFICATIONS)
}

actual suspend fun requestCameraPermission(): Boolean {
    val activity = ResumedActivity.current ?: throw IllegalStateException("No resumed activity")
    return requestAndroidPermission(activity, Manifest.permission.CAMERA)
}

private suspend fun requestAndroidPermission(activity: ComponentActivity, permission: String): Boolean {
    if (ContextCompat.checkSelfPermission(activity, permission) == PackageManager.PERMISSION_GRANTED) {
        return true
    }
    return suspendCancellableCoroutine { continuation ->
        lateinit var launcher: ActivityResultLauncher<String>
        launcher = activity.activityResultRegistry.register(
            "flow_permission",
            ActivityResultContracts.RequestPermission(),
        ) { granted ->
            launcher.unregister()
            continuation.resume(granted)
        }
        launcher.launch(permission)
        continuation.invokeOnCancellation { launcher.unregister() }
    }
}
```

### Use moko-permissions

[moko-permissions](https://github.com/icerockdev/moko-permissions) 0.20.1 can request the permission values in this table. For the other values, write `expect` and `actual` functions as in the example. Some moko-permissions results can't carry the status that the flow needs, so take these limits into account:

| Value | moko-permissions | Limits |
|:------|:-----------------|:-------|
| `push` | `Permission.REMOTE_NOTIFICATION` | On iOS, it reports provisional authorization as granted, so your app can't pass `provisional`. On Android 12 and earlier, `providePermission()` always throws `RequestCanceledException`: read `getPermissionState()` there instead. |
| `camera` | `Permission.CAMERA` | On iOS, a restricted camera throws `IllegalStateException`. |
| `microphone` | `Permission.RECORD_AUDIO` | On iOS, a restricted microphone throws `IllegalStateException`. |
| `location_when_use` | `Permission.LOCATION` | On Android 12 and later, it needs both precise and approximate location, so a user who chooses approximate location gets a refusal exception. `Permission.COARSE_LOCATION` accepts approximate location. |
| `location_always` | `Permission.BACKGROUND_LOCATION` | On iOS, it throws `DeniedException` without a dialog when location while using the app is already granted. On Android 11 and later, it requests foreground and background location together, and Android grants neither. Use your own code for this value. |
| `photos` | `Permission.GALLERY` | On iOS, it reports limited access as granted, so your app can't pass `limited`, and restricted access throws `IllegalStateException`. On Android 13 and later, it requests images and videos, and needs both. |
| `contacts` | `Permission.CONTACTS` | On iOS 18 and later, it reports limited access as granted. On Android, it also requests `WRITE_CONTACTS`: `Permission.READ_CONTACTS` requests only `READ_CONTACTS`. |
| `bluetooth` | `Permission.BLUETOOTH_CONNECT` | On iOS, it throws `DeniedException` when Bluetooth is turned off. `getPermissionState()` reports a restricted permission as granted, while `providePermission()` throws `DeniedAlwaysException` for it. |
| `motion` | `Permission.MOTION` | Don't use it for the flow. On iOS, it returns before the user answers. On Android, it also requests `BODY_SENSORS`, and on Android 10 and 11 it requests only `BODY_SENSORS`. |

Map the results of moko-permissions to the status:

- **Before the request**: Read `getPermissionState()`, so that you can tell a new refusal from an earlier one.
- **On iOS**: `DeniedAlwaysException` after the state `NotDetermined` means that the user declined the dialog: pass `denied`. After the state `DeniedAlways`, iOS showed no dialog: pass `permanently_denied`. `DeniedException` isn't an answer from the user, for example when Bluetooth is turned off: answer without a status.
- **On Android**: Pass `denied` for `DeniedException`, and `permanently_denied` for `DeniedAlwaysException`. For `RequestCanceledException`, answer without a status.
- **For `IllegalStateException`**: Catch it, and answer without a status. moko-permissions also throws it when you request a permission before you bind its `PermissionsController` to an activity.
- **Binding on Android**: Bind the `PermissionsController` to the activity that shows the flow.

moko-permissions has no `restricted`, `limited`, or `provisional` result. To pass these statuses, use your own `actual` code.

## Declare the permissions

The OS shows a permission dialog only to an app that declares the permission: in `Info.plist` of the iOS app, and in the Android manifest. For each permission that your handler requests, add these declarations:

<FlowPermissionDeclarations />

The handler in this guide requests notifications and camera access. On iOS, the app adds `NSCameraUsageDescription` to `Info.plist`. On Android, the app declares these permissions:

```xml title="AndroidManifest.xml"
<uses-permission android:name="android.permission.POST_NOTIFICATIONS" />
<uses-permission android:name="android.permission.CAMERA" />
```

For what each permission shows users, the OS versions it needs, and the status to pass for each result, see [System permissions](flow-permissions).

## Register the handler

:::warning
**Without a handler, the flow stops at the permission request.** If your app registers no handler, the Adapty SDK sends the flow no answer, on iOS and on Android. The flow stays on the screen that sent the request and doesn't run the outcome actions.
:::

To send permission requests to your handler, call `AdaptyUI.setSystemRequestsHandler` once at app startup, before your app shows the first flow. For example, call it where you call `AdaptyUI.setFlowsEventsObserver`.

```kotlin showLineNumbers title="Kotlin"
import com.adapty.kmp.AdaptyUI

AdaptyUI.setSystemRequestsHandler(MySystemRequestsHandler())
```

## Test the permission request

iOS shows most permission dialogs only once per app install. Android stops showing a permission dialog after the user allows the permission or denies it twice. To see the dialog again while you test the flow, delete the app from the device and install it again. Then open the flow and reach the **Request permission** action. If the screen stays and no dialog appears, the flow got no answer: make sure that your app registers the handler before it presents the flow. If the flow moves on without a dialog, make sure that the app declares the permission on both platforms. For notifications on Android, the app must also target Android 13 or later.

To see how users answer permission requests, read the flow's analytics events in the `flowViewDidReceiveAnalyticEvent` method of your flows events observer. For details, see [Handle flow & paywall events](kmp-handling-events).
