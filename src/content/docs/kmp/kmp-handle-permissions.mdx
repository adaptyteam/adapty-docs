A [flow](adapty-flow-builder) can ask users for a system permission with the **Request permission** action. For example, an onboarding screen can explain what push notifications are for and then request them, or a flow can request camera access before a feature that scans documents. The Adapty SDK doesn't show the system permission dialog itself. It passes the permission request to an `AdaptyUISystemRequestsHandler` implementation in your app. Your app shows the dialog and passes the result back to the flow. The flow then continues.

## Before you start

You need:

- **Adapty Kotlin Multiplatform SDK 4.1.0 or later**: Version 4.1.0 is the first stable release with the `AdaptyUISystemRequestsHandler` interface.
- **A flow with the Request permission action**: In the Flow & Paywall Builder, add the **Request permission** action to an element's **On Tap** or **On Screen Appear** trigger. In the action, select the permission in the **Permission** field. Add the actions for each result. The default **After response** action is **Navigate Next**. For the action settings, see [Request permission](onboarding-actions#request-permission).
- **The declarations of the permissions that your handler requests**: On iOS, a purpose string: the text in `Info.plist` that tells users why your app needs the permission. On Android, a permission in the Android manifest. See [Declare the permissions](#declare-the-permissions).
- **For push notifications on Android, the `targetSdk` property set to 33 or higher**: Only apps that target Android 13 or later choose when the notification permission dialog appears.

:::note
**If your handler already requests push notifications**: It keeps working. For `AdaptyUIPermissionResult.denied()`, the flow runs the **After response** actions. To have the flow run the **When denied** actions for users who decline, return `AdaptyUIPermissionResult.denied("denied")`. To request other permissions, add their cases to the handler.
:::

## How the flow requests a permission

1. The flow reaches the **Request permission** action: the user taps the element, or the screen appears.
2. The Adapty SDK calls the `handlePermission` method of your handler with the permission selected in the action, such as `AdaptyUIPermission.PUSH` or `AdaptyUIPermission.CAMERA`.
3. Your app requests the permission from the OS and returns `AdaptyUIPermissionResult.granted()` or `AdaptyUIPermissionResult.denied()`.

<FlowPermissionAnswers />

The flow waits on the screen until your app passes the result. If your app never passes a result, the flow stays on the screen. If the user already granted or declined the permission, the OS shows no dialog and returns the permission state to your app at once. The flow then runs the actions for the result right away. If those actions leave the screen, the user sees the screen that requests the permission only for a moment.

The flow sends your app one permission request at a time. [The trigger of the action](onboarding-actions#request-permission) decides how often the flow sends the request. Your handler can receive the same permission again, for example on each tap: return the result that matches the current permission state.

## Implement the handler

:::warning
**Request only the permissions that your app declares, and return `AdaptyUIPermissionResult.denied("unsupported")` for any other permission.** For most permissions, iOS terminates the app when the app requests a permission whose purpose string is missing from `Info.plist`. A flow author can add a request for any permission at any time, and the flow also reaches app versions released before the request was added.
:::

To pass the results of permission requests to the flow, implement the `AdaptyUISystemRequestsHandler` interface in common code. Common code can't show the system dialogs, so the handler sends each permission to its own `expect` function, with an `actual` implementation in the `iosMain` and `androidMain` source sets. The functions call the platform APIs.

The handler must return a result for every permission request. The Adapty SDK doesn't catch exceptions from the `handlePermission` method: an uncaught exception crashes the app, and the flow receives no result. To keep the app running, the handler catches the exceptions of every function and returns `AdaptyUIPermissionResult.denied()` without a string.

This handler requests push notifications and camera access. For every other permission, it returns `AdaptyUIPermissionResult.denied("unsupported")` without a dialog:

```kotlin showLineNumbers title="commonMain"
import com.adapty.kmp.AdaptyUISystemRequestsHandler
import com.adapty.kmp.models.AdaptyUIFlowView
import com.adapty.kmp.models.AdaptyUIPermission
import com.adapty.kmp.models.AdaptyUIPermissionResult
import kotlin.coroutines.cancellation.CancellationException

class MySystemRequestsHandler : AdaptyUISystemRequestsHandler {
    override suspend fun handlePermission(
        view: AdaptyUIFlowView,
        permission: AdaptyUIPermission,
        customArgs: Map<String, String>?,
    ): AdaptyUIPermissionResult = try {
        when (permission) {
            AdaptyUIPermission.PUSH -> requestPush()
            AdaptyUIPermission.CAMERA -> requestCamera()
            // Add a case for each permission that your app requests.
            // A permission that this app version doesn't request: pass the result without a dialog.
            else -> AdaptyUIPermissionResult.denied("unsupported")
        }
    } catch (e: CancellationException) {
        throw e
    } catch (e: Throwable) {
        // An exception that leaves handlePermission crashes the app.
        // Pass the result without a string instead: the flow runs the After response actions.
        AdaptyUIPermissionResult.denied()
    }
}

// One function for each permission, with an actual in iosMain and one in androidMain.
expect suspend fun requestPush(): AdaptyUIPermissionResult
expect suspend fun requestCamera(): AdaptyUIPermissionResult
```

Copy the `actual` functions for push notifications and camera access from [Code for each permission](#code-for-each-permission). If your app doesn't request one of these permissions, delete its case and its `expect` declaration: the `else` branch then returns `AdaptyUIPermissionResult.denied("unsupported")` for it. To request another permission, add its case to the `when` expression and declare its `expect` function. Then copy or adapt its `actual` functions from that section.

The `handlePermission` method receives:

- **`view`**: The flow view that sent the request.
- **`permission`**: The permission selected in the action. The `AdaptyUIPermission` class has a constant for each value in [Declare the permissions](#declare-the-permissions), named in upper case: for example, `AdaptyUIPermission.LOCATION_WHEN_USE` for `location_when_use`. The `value` property returns the value as a string.
- **`customArgs`**: Custom arguments of the request. The **Request permission** action sends none, so the value is `null`.

To pass the result to the flow:

1. In the `handlePermission` method, show the system dialog.
2. Return `AdaptyUIPermissionResult.granted()` if the user granted the permission, and `AdaptyUIPermissionResult.denied()` otherwise.
3. To have the flow run the **When denied** actions, pass `"denied"`, `"restricted"`, or `"permanently_denied"` as the argument of `AdaptyUIPermissionResult.denied`. For example, `AdaptyUIPermissionResult.denied("permanently_denied")`. Without this argument, the flow runs the **After response** actions.

<FlowPermissionStrings />

The `AdaptyUIPermissionResult.granted` function takes the string as an optional argument too. For example, `AdaptyUIPermissionResult.granted("limited")`. For the result and the string to pass for what the OS reports about each permission, see System permissions on [iOS](ios-system-permissions) and [Android](android-system-permissions).

On Android, the functions request runtime permissions with the `requestRuntimePermissions` function. It asks from the activity on screen, which is the flow's activity while a flow is shown. The `ResumedActivity` object tracks that activity: in the `Application.onCreate` method, register it with `registerActivityLifecycleCallbacks(ResumedActivity)`.

With the string `denied` or `permanently_denied`, the flow runs the **When denied** actions. The two strings only differ in the `outcome` property of the [`flow_permission_answered`](#track-permission-requests-in-analytics) event. To tell them apart, the `requestRuntimePermissions` function calls the `shouldShowRequestPermissionRationale()` method and keeps a flag for each permission, as [System permissions on Android](android-system-permissions#rules-for-every-permission) describes. The flag only changes the actions that the flow runs in one case. If the user closes the first dialog without a choice, the function passes a not-granted result without a string, and the flow runs the **After response** actions.

```kotlin showLineNumbers title="androidMain"
import android.app.Activity
import android.app.Application
import android.content.Context
import android.content.pm.PackageManager
import android.os.Bundle
import androidx.activity.ComponentActivity
import androidx.activity.result.ActivityResultLauncher
import androidx.activity.result.contract.ActivityResultContracts
import androidx.core.content.ContextCompat
import kotlinx.coroutines.suspendCancellableCoroutine
import java.util.UUID
import kotlin.coroutines.resume

// The activity on screen: while a flow is shown, the flow's activity.
// Register it in Application.onCreate: registerActivityLifecycleCallbacks(ResumedActivity).
object ResumedActivity : Application.ActivityLifecycleCallbacks {
    var current: ComponentActivity? = null
        private set

    override fun onActivityResumed(activity: Activity) {
        current = activity as? ComponentActivity
    }

    override fun onActivityPaused(activity: Activity) {
        if (current === activity) current = null
    }

    override fun onActivityCreated(activity: Activity, savedInstanceState: Bundle?) {}
    override fun onActivityStarted(activity: Activity) {}
    override fun onActivityStopped(activity: Activity) {}
    override fun onActivitySaveInstanceState(activity: Activity, outState: Bundle) {}
    override fun onActivityDestroyed(activity: Activity) {}
}

class RuntimeRequest(
    // Whether each requested permission is granted after the request.
    val granted: Map<String, Boolean>,
    // The string to pass if the permission isn't granted.
    val deniedDetail: String?,
)

// Requests the permissions together, in one dialog.
suspend fun requestRuntimePermissions(vararg permissions: String): RuntimeRequest {
    // No activity on screen: the exception makes the handler pass the result without a string.
    val activity = ResumedActivity.current ?: error("No resumed activity")
    fun isGranted(permission: String) =
        ContextCompat.checkSelfPermission(activity, permission) == PackageManager.PERMISSION_GRANTED
    if (permissions.all(::isGranted)) {
        return RuntimeRequest(permissions.associateWith { true }, null)
    }
    // Android can't tell whether the app requested a permission before, so the app keeps a flag.
    val requested = activity.getSharedPreferences("flow_permissions", Context.MODE_PRIVATE)
    val requestedBefore = permissions.any { requested.getBoolean(it, false) }
    val rationaleBefore = permissions.any { activity.shouldShowRequestPermissionRationale(it) }
    requested.edit().apply { permissions.forEach { putBoolean(it, true) } }.apply()

    suspendCancellableCoroutine { continuation ->
        lateinit var launcher: ActivityResultLauncher<Array<String>>
        // A key of its own for each request.
        launcher = activity.activityResultRegistry.register(
            "flow_permission_${UUID.randomUUID()}",
            ActivityResultContracts.RequestMultiplePermissions(),
        ) {
            launcher.unregister()
            if (continuation.isActive) continuation.resume(Unit)
        }
        continuation.invokeOnCancellation { launcher.unregister() }
        launcher.launch(arrayOf(*permissions))
    }

    val deniedDetail = when {
        // A rationale before or after the request: the user declined the dialog.
        rationaleBefore || permissions.any { activity.shouldShowRequestPermissionRationale(it) } -> "denied"
        // No rationale before or after a repeated request: Android showed no dialog.
        requestedBefore -> "permanently_denied"
        // The user closed the dialog without a choice: the flow runs After response.
        else -> null
    }
    return RuntimeRequest(permissions.associateWith(::isGranted), deniedDetail)
}
```

Each request registers its launcher with a key of its own, so two requests don't receive each other's callback. If the activity is recreated while the dialog is open, for example after a change of font size or display size, what Android reports doesn't reach the function. The flow then receives no result and stays on the screen. After 60 seconds, the flow reports the `flow_permission_unanswered` event to your analytics.

The flags are in the `flow_permissions` shared preferences file. To start a new installation without old flags, exclude `flow_permissions.xml` from backups, as [Android backup rules](sdk-installation-android#android-backup-rules-auto-backup-configuration) describes. With restored flags, the `requestRuntimePermissions` function returns `permanently_denied` for a first dialog closed without a choice.

The `AdaptyUISystemRequestsHandler` interface also has the `handleAppReviewRequest` method. Its default shows the native review prompt, so you don't need to override it.

:::note
The [moko-permissions](https://github.com/icerockdev/moko-permissions) library has no `restricted`, `limited`, or `provisional` state. It can't tell a refusal in the dialog from a refusal without a dialog either. To pass the strings that the flow needs, call the platform APIs, as the functions in [Code for each permission](#code-for-each-permission) do.
:::

## Register the handler

:::warning
**Without a handler, the flow stops at the permission request.** If your app registers no handler, the Adapty SDK passes no result to the flow, on iOS and on Android. The flow stays on the screen that sent the request and doesn't run the **When allowed**, **When denied**, or **After response** actions.
:::

To send permission requests to your handler, call the `AdaptyUI.setSystemRequestsHandler` method once at app startup, before your app shows the first flow. For example, call it where you call the `AdaptyUI.setFlowsEventsObserver` method.

```kotlin showLineNumbers title="Kotlin"
import com.adapty.kmp.AdaptyUI

AdaptyUI.setSystemRequestsHandler(MySystemRequestsHandler())
```

## Declare the permissions

For each permission that your handler requests, add these declarations to `Info.plist` of the iOS app and to the Android manifest:

<FlowPermissionDeclarations />

For example, an app that requests notifications and camera access adds the `NSCameraUsageDescription` key to `Info.plist` on iOS. On Android, the app declares these permissions:

```xml title="AndroidManifest.xml"
<uses-permission android:name="android.permission.POST_NOTIFICATIONS" />
<uses-permission android:name="android.permission.CAMERA" />
```

For what each permission shows users, the OS versions it needs, and the result to pass in each case, see System permissions on [iOS](ios-system-permissions) and [Android](android-system-permissions).

## Test the permission request

iOS shows most permission dialogs only once per app install. Android stops showing a permission dialog after the user grants the permission or declines it twice. To see the dialog again while you test the flow, delete the app from the device and install it again. On Android, to reset the permission and the `flow_permissions` flags together, clear the app data with `adb shell pm clear <package>`. Then open the flow and reach the **Request permission** action. If the screen stays and no dialog appears, your app passed no result to the flow: make sure that your app registers the handler before it presents the flow. If the flow moves on without a dialog, make sure that the app declares the permission on both platforms. For notifications on Android, the app must also target Android 13 or later.

## Track permission requests in analytics

To see which permission requests users grant or decline, read the analytics events that your flows events observer receives in the `flowViewDidReceiveAnalyticEvent` method. For details, see [Handle flow & paywall events](kmp-handling-events).

## Code for each permission

Each permission has an `actual` function for the `iosMain` source set and one for the `androidMain` source set. The Adapty SDK calls the `handlePermission` method on the main thread on both platforms, and the functions call the OS from there. When iOS has no request method, or doesn't always call back, the iOS function waits 50 seconds at most: after 60 seconds without a result, the flow reports the `flow_permission_unanswered` event.

This section has the functions for push notifications, camera access, and location while using the app. The [camera function](#camera) requests the permission directly, and the iOS [location function](#location_when_use) waits for a delegate callback. The functions for other permissions follow the same patterns. For what to request and which result to pass, see System permissions on [iOS](ios-system-permissions) and [Android](android-system-permissions). For a permission that Android doesn't have, such as `tracking`, its `actual` function in the `androidMain` source set returns `AdaptyUIPermissionResult.denied("unsupported")`.

### Push notifications \{#push\}

Add the `POST_NOTIFICATIONS` permission to the Android manifest. iOS needs no key in `Info.plist`. See System permissions on [iOS](ios-system-permissions#push) and [Android](android-system-permissions#push).

```kotlin showLineNumbers title="iosMain"
import com.adapty.kmp.models.AdaptyUIPermissionResult
import kotlinx.coroutines.suspendCancellableCoroutine
import platform.Foundation.NSError
import platform.UserNotifications.UNAuthorizationOptionAlert
import platform.UserNotifications.UNAuthorizationOptionBadge
import platform.UserNotifications.UNAuthorizationOptionSound
import platform.UserNotifications.UNAuthorizationStatus
import platform.UserNotifications.UNAuthorizationStatusAuthorized
import platform.UserNotifications.UNAuthorizationStatusDenied
import platform.UserNotifications.UNAuthorizationStatusEphemeral
import platform.UserNotifications.UNAuthorizationStatusNotDetermined
import platform.UserNotifications.UNAuthorizationStatusProvisional
import platform.UserNotifications.UNUserNotificationCenter
import kotlin.coroutines.resume

actual suspend fun requestPush(): AdaptyUIPermissionResult {
    val center = UNUserNotificationCenter.currentNotificationCenter()
    val before = suspendCancellableCoroutine<UNAuthorizationStatus> { continuation ->
        center.getNotificationSettingsWithCompletionHandler { settings ->
            continuation.resume(settings?.authorizationStatus ?: UNAuthorizationStatusNotDetermined)
        }
    }
    when (before) {
        UNAuthorizationStatusAuthorized, UNAuthorizationStatusEphemeral ->
            return AdaptyUIPermissionResult.granted("granted")
        // Quiet notifications, after an earlier request with UNAuthorizationOptionProvisional.
        UNAuthorizationStatusProvisional -> return AdaptyUIPermissionResult.granted("provisional")
        // The user declined earlier: iOS shows no alert.
        UNAuthorizationStatusDenied -> return AdaptyUIPermissionResult.denied("permanently_denied")
    }
    val (allowed, error) = suspendCancellableCoroutine<Pair<Boolean, NSError?>> { continuation ->
        center.requestAuthorizationWithOptions(
            UNAuthorizationOptionAlert or UNAuthorizationOptionBadge or UNAuthorizationOptionSound,
        ) { granted, error ->
            continuation.resume(granted to error)
        }
    }
    return when {
        error != null -> AdaptyUIPermissionResult.denied()
        allowed -> AdaptyUIPermissionResult.granted("granted")
        else -> AdaptyUIPermissionResult.denied("denied")
    }
}
```

```kotlin showLineNumbers title="androidMain"
import android.Manifest
import android.os.Build
import androidx.core.app.NotificationManagerCompat
import com.adapty.kmp.models.AdaptyUIPermissionResult

actual suspend fun requestPush(): AdaptyUIPermissionResult {
    if (Build.VERSION.SDK_INT < Build.VERSION_CODES.TIRAMISU) {
        // Android 12 and earlier have no dialog: pass the result from the notification setting.
        val activity = ResumedActivity.current ?: error("No resumed activity")
        return if (NotificationManagerCompat.from(activity).areNotificationsEnabled()) {
            AdaptyUIPermissionResult.granted("granted")
        } else {
            AdaptyUIPermissionResult.denied("permanently_denied")
        }
    }
    val request = requestRuntimePermissions(Manifest.permission.POST_NOTIFICATIONS)
    return if (request.granted.getValue(Manifest.permission.POST_NOTIFICATIONS)) {
        AdaptyUIPermissionResult.granted("granted")
    } else {
        AdaptyUIPermissionResult.denied(request.deniedDetail)
    }
}
```

- To grant quiet notifications without an alert, add the `UNAuthorizationOptionProvisional` option to the iOS options, and return `AdaptyUIPermissionResult.granted("provisional")`.
- With a granted notification permission, your app can show notifications. To receive push notifications, register the device with your push provider, such as APNs or Firebase Cloud Messaging, as your app does outside flows.

### Camera \{#camera\}

Add the `NSCameraUsageDescription` key to `Info.plist`, and the `CAMERA` permission to the Android manifest. See System permissions on [iOS](ios-system-permissions#camera) and [Android](android-system-permissions#camera).

```kotlin showLineNumbers title="iosMain"
import com.adapty.kmp.models.AdaptyUIPermissionResult
import kotlinx.coroutines.suspendCancellableCoroutine
import platform.AVFoundation.AVAuthorizationStatusAuthorized
import platform.AVFoundation.AVAuthorizationStatusDenied
import platform.AVFoundation.AVAuthorizationStatusRestricted
import platform.AVFoundation.AVCaptureDevice
import platform.AVFoundation.AVMediaTypeVideo
import platform.AVFoundation.authorizationStatusForMediaType
import platform.AVFoundation.requestAccessForMediaType
import kotlin.coroutines.resume

actual suspend fun requestCamera(): AdaptyUIPermissionResult =
    when (AVCaptureDevice.authorizationStatusForMediaType(AVMediaTypeVideo)) {
        AVAuthorizationStatusAuthorized -> AdaptyUIPermissionResult.granted("granted")
        AVAuthorizationStatusRestricted -> AdaptyUIPermissionResult.denied("restricted")
        // The user declined earlier: iOS shows no alert.
        AVAuthorizationStatusDenied -> AdaptyUIPermissionResult.denied("permanently_denied")
        else -> {
            val allowed = suspendCancellableCoroutine { continuation ->
                AVCaptureDevice.requestAccessForMediaType(AVMediaTypeVideo) { continuation.resume(it) }
            }
            if (allowed) {
                AdaptyUIPermissionResult.granted("granted")
            } else {
                AdaptyUIPermissionResult.denied("denied")
            }
        }
    }
```

```kotlin showLineNumbers title="androidMain"
import android.Manifest
import android.content.pm.PackageManager
import com.adapty.kmp.models.AdaptyUIPermissionResult

actual suspend fun requestCamera(): AdaptyUIPermissionResult {
    val activity = ResumedActivity.current ?: error("No resumed activity")
    if (!activity.packageManager.hasSystemFeature(PackageManager.FEATURE_CAMERA_ANY)) {
        return AdaptyUIPermissionResult.denied("unsupported")
    }
    val request = requestRuntimePermissions(Manifest.permission.CAMERA)
    return if (request.granted.getValue(Manifest.permission.CAMERA)) {
        AdaptyUIPermissionResult.granted("granted")
    } else {
        AdaptyUIPermissionResult.denied(request.deniedDetail)
    }
}
```

- To install the app on Android devices without a back camera, also declare `<uses-feature android:name="android.hardware.camera" android:required="false" />`.

### Location while using the app \{#location_when_use\}

Add the `NSLocationWhenInUseUsageDescription` key to `Info.plist`. Add the `ACCESS_COARSE_LOCATION` and `ACCESS_FINE_LOCATION` permissions to the Android manifest. See System permissions on [iOS](ios-system-permissions#location_when_use) and [Android](android-system-permissions#location_when_use).

```kotlin showLineNumbers title="iosMain"
import com.adapty.kmp.models.AdaptyUIPermissionResult
import kotlinx.coroutines.suspendCancellableCoroutine
import kotlinx.coroutines.withTimeoutOrNull
import platform.CoreLocation.CLLocationManager
import platform.CoreLocation.CLLocationManagerDelegateProtocol
import platform.CoreLocation.kCLAuthorizationStatusAuthorizedAlways
import platform.CoreLocation.kCLAuthorizationStatusAuthorizedWhenInUse
import platform.CoreLocation.kCLAuthorizationStatusDenied
import platform.CoreLocation.kCLAuthorizationStatusNotDetermined
import platform.CoreLocation.kCLAuthorizationStatusRestricted
import platform.darwin.NSObject
import kotlin.coroutines.resume
import kotlin.time.Duration.Companion.seconds

private class WhenInUseLocationRequest : NSObject(), CLLocationManagerDelegateProtocol {
    val manager = CLLocationManager()
    private var onDecided: (() -> Unit)? = null

    init {
        manager.delegate = this
    }

    suspend fun request() {
        // Never wait longer than the flow does: 60 seconds.
        withTimeoutOrNull(50.seconds) {
            suspendCancellableCoroutine { continuation ->
                onDecided = { if (continuation.isActive) continuation.resume(Unit) }
                manager.requestWhenInUseAuthorization()
            }
        }
        onDecided = null
    }

    // iOS also calls this method when it creates the manager, with the current authorization status.
    override fun locationManagerDidChangeAuthorization(manager: CLLocationManager) {
        if (manager.authorizationStatus != kCLAuthorizationStatusNotDetermined) onDecided?.invoke()
    }
}

actual suspend fun requestLocationWhenInUse(): AdaptyUIPermissionResult {
    val location = WhenInUseLocationRequest()
    val before = location.manager.authorizationStatus
    // With any other authorization status, iOS ignores the request and doesn't call the delegate.
    if (before == kCLAuthorizationStatusNotDetermined) location.request()
    return when (location.manager.authorizationStatus) {
        kCLAuthorizationStatusAuthorizedWhenInUse, kCLAuthorizationStatusAuthorizedAlways ->
            AdaptyUIPermissionResult.granted("granted")
        kCLAuthorizationStatusRestricted -> AdaptyUIPermissionResult.denied("restricted")
        kCLAuthorizationStatusDenied -> AdaptyUIPermissionResult.denied(
            // Denied before the request, also with Location Services off: iOS shows no alert.
            if (before == kCLAuthorizationStatusNotDetermined) "denied" else "permanently_denied",
        )
        // The user made no choice before the timeout.
        else -> AdaptyUIPermissionResult.denied()
    }
}
```

```kotlin showLineNumbers title="androidMain"
import android.Manifest
import android.content.pm.PackageManager
import androidx.core.content.ContextCompat
import com.adapty.kmp.models.AdaptyUIPermissionResult

actual suspend fun requestLocationWhenInUse(): AdaptyUIPermissionResult {
    val activity = ResumedActivity.current ?: error("No resumed activity")
    val fine = Manifest.permission.ACCESS_FINE_LOCATION
    val coarse = Manifest.permission.ACCESS_COARSE_LOCATION
    // Approximate location is granted too: don't ask for precise location again.
    // To report approximate location in analytics, pass "limited" for it instead.
    val hasLocation = listOf(fine, coarse).any {
        ContextCompat.checkSelfPermission(activity, it) == PackageManager.PERMISSION_GRANTED
    }
    if (hasLocation) return AdaptyUIPermissionResult.granted("granted")
    // Request both: some Android 12 releases ignore a request for precise location alone.
    val request = requestRuntimePermissions(fine, coarse)
    return if (request.granted.values.any { it }) {
        AdaptyUIPermissionResult.granted("granted")
    } else {
        AdaptyUIPermissionResult.denied(request.deniedDetail)
    }
}
```
