A [flow](adapty-flow-builder) can ask users for a system permission with the **Request permission** action. For example, a flow can ask for push notifications on an onboarding screen that explains them, or for camera access before a feature that scans documents. The Adapty SDK doesn't show the system permission dialog itself. It passes the permission request to an `AdaptyUISystemRequestsHandler` subclass in your app. Your app shows the dialog and passes the result back to the flow. The flow then continues.

## Before you start

You need:

- **Adapty Flutter SDK 4.0.0 or later**: Earlier versions don't have the `AdaptyUISystemRequestsHandler` class. See [Install & configure SDK](sdk-installation-flutter).
- **A flow with the Request permission action**: In the Flow & Paywall Builder, add the **Request permission** action to an element's **On Tap** or **On Screen Appear** trigger. In the action, select the permission in the **Permission** field. Add the actions for each result. The default **After response** action is **Navigate Next**. For the action settings, see [Request permission](onboarding-actions#request-permission).
- **A library that shows the permission dialogs**: The examples use [permission_handler](https://pub.dev/packages/permission_handler), with [device_info_plus](https://pub.dev/packages/device_info_plus) to read the Android version. Any other package or your own platform code works the same way.
- **The declarations of the permissions that your handler requests**: On iOS, a purpose string: the text in `Info.plist` that tells users why your app needs the permission. On Android, a permission in the Android manifest. See [Declare the permissions](#declare-the-permissions).
- **For push notifications on Android, the `targetSdk` property set to 33 or higher**: Only apps that target Android 13 or later choose when the notification permission dialog appears.
- **permission_handler 13.0.2 or later, with permission_handler_apple 9.6.4 or later**: Add `permission_handler: ^13.0.2` and `permission_handler_apple: ^9.6.4` to `pubspec.yaml`. permission_handler 13.0.2 depends on permission_handler_android 14.1.0. Version 14.1.0 reports a first dialog closed without a choice as `PermissionStatus.denied`, not `PermissionStatus.permanentlyDenied`. permission_handler_apple 9.6.4 fixes the `Permission.locationAlways.status` property for a user who only granted location access while using the app.

:::warning
**On Android, show a flow that requests permissions with the `AdaptyUIFlowPlatformView` widget.** A flow presented with the `AdaptyUI().createFlowView(...).present()` method receives the permission result only after it closes, so it waits on the screen. For the `AdaptyUIFlowPlatformView` widget, your `MainActivity` class extends the `FlutterFragmentActivity` class: see [Embed in widget hierarchy](flutter-present-paywalls#embed-in-widget-hierarchy).
:::

:::note
**If your handler already requests push notifications**: It keeps working. For `AdaptyUIPermissionResult.denied()`, the flow runs the **After response** actions. To have the flow run the **When denied** actions for users who decline, return `AdaptyUIPermissionResult.denied('denied')`. To request other permissions, add their cases to the handler.
:::

## How the flow requests a permission

1. The flow reaches the **Request permission** action: the user taps the element, or the screen appears.
2. The Adapty SDK calls the `handlePermission` method of your handler with the permission selected in the action, such as `AdaptyUIPermission.push` or `AdaptyUIPermission.camera`.
3. Your app requests the permission from the OS and returns `AdaptyUIPermissionResult.granted()` or `AdaptyUIPermissionResult.denied()`.

<FlowPermissionAnswers />

The flow waits on the screen until your app passes the result. If your app never passes a result, the flow stays on the screen. If the user already granted or declined the permission, the OS shows no dialog, and permission_handler returns the permission status to your app at once. The flow then runs the actions for the result. If those actions leave the screen, the user sees the screen that requests the permission only for a moment.

The flow sends your app one permission request at a time. [The trigger of the action](onboarding-actions#request-permission) determines how often the flow sends the request. Your handler can receive the same permission again, for example on each tap: return the result that matches the current permission state.

## Implement the handler

:::warning
**Request only the permissions that your app declares, and return `AdaptyUIPermissionResult.denied('unsupported')` for any other permission.** For most permissions, iOS terminates the app when the app requests a permission whose purpose string is missing from `Info.plist`. A flow author can add a request for any permission at any time, and the flow also reaches app versions released before the request was added.
:::

To pass the results of permission requests to the flow, create a class that extends the `AdaptyUISystemRequestsHandler` class, and implement its `handlePermission` method. In this example, the handler requests push notifications and camera access. For every other permission, it returns `AdaptyUIPermissionResult.denied('unsupported')` without a dialog:

```dart showLineNumbers title="Flutter"
import 'dart:io' show Platform;

import 'package:adapty_flutter/adapty_flutter.dart';
import 'package:device_info_plus/device_info_plus.dart';
import 'package:permission_handler/permission_handler.dart';

class FlowSystemRequestsHandler extends AdaptyUISystemRequestsHandler {
  @override
  Future<AdaptyUIPermissionResult> handlePermission(
    AdaptyUIFlowView view,
    AdaptyUIPermission permission,
    Map<String, String>? customArgs,
  ) async {
    try {
      return await switch (permission) {
        AdaptyUIPermission.push => requestPush(),
        AdaptyUIPermission.camera => requestCamera(),
        // Add a case for each permission that your app requests.
        // A permission that this app version doesn't request: pass the result without a dialog.
        _ => Future.value(const AdaptyUIPermissionResult.denied('unsupported')),
      };
    } catch (_) {
      // Not the user's choice: the flow runs the After response actions.
      return const AdaptyUIPermissionResult.denied();
    }
  }

  // The base method does nothing: this keeps the native review prompt.
  @override
  Future<void> handleAppReviewRequest(AdaptyUIFlowView view) {
    return AdaptyUI().requestAppReview();
  }
}
```

To request another permission, add a case for it to the `switch` expression. Then add its function, as [Code for each permission](#code-for-each-permission) shows.

The `requestAndAnswer` function requests a permission with permission_handler and returns the result for the flow. [Strings for each permission status](#strings-for-each-permission-status) lists the string that the function passes for each value of the `PermissionStatus` enum.

With the string `denied` or `permanently_denied`, the flow runs the **When denied** actions. The two strings only differ in the `outcome` property of the `flow_permission_answered` event. To tell them apart, the `requestAndAnswer` function compares the permission state before and after the permission request. The comparison only changes the actions that the flow runs in one case. When the dialog closes without a choice, or on iOS doesn't appear, the function passes a not-granted result without a string. The flow then runs the **After response** actions.

The functions for each permission use the following helpers:

```dart showLineNumbers title="Flutter"
/// How long to wait for an iOS alert: under 60 seconds, when the flow reports flow_permission_unanswered.
const iosAlertTimeout = Duration(seconds: 50);

/// The result for a permission_handler status.
AdaptyUIPermissionResult answerFromStatus(PermissionStatus status) {
  return switch (status) {
    PermissionStatus.granted => const AdaptyUIPermissionResult.granted('granted'),
    PermissionStatus.limited => const AdaptyUIPermissionResult.granted('limited'),
    PermissionStatus.provisional => const AdaptyUIPermissionResult.granted('provisional'),
    PermissionStatus.restricted => const AdaptyUIPermissionResult.denied('restricted'),
    PermissionStatus.permanentlyDenied => const AdaptyUIPermissionResult.denied('permanently_denied'),
    PermissionStatus.denied => const AdaptyUIPermissionResult.denied('denied'),
  };
}

/// Requests [permission] and passes the result with the string that the flow expects.
/// On iOS, [timeout] limits the wait for the alert.
Future<AdaptyUIPermissionResult> requestAndAnswer(
  Permission permission, {
  Duration? timeout,
}) async {
  if (Platform.isIOS) {
    // On iOS, permission_handler reports "not asked yet" as denied.
    final before = await permission.status;
    // Decided earlier: iOS shows no alert, so pass the result at once.
    if (before != PermissionStatus.denied) return answerFromStatus(before);

    var request = permission.request();
    if (timeout != null) {
      request = request.timeout(timeout, onTimeout: () => permission.status);
    }
    return switch (await request) {
      // permission_handler reports "Don't Allow" in this alert as permanentlyDenied.
      PermissionStatus.permanentlyDenied => const AdaptyUIPermissionResult.denied('denied'),
      // Still not asked: the alert closed without a choice, or didn't appear.
      PermissionStatus.denied => const AdaptyUIPermissionResult.denied(),
      final after => answerFromStatus(after),
    };
  }

  final rationaleBefore = await permission.shouldShowRequestRationale;
  return answerOnAndroid(await permission.request(), permission, rationaleBefore);
}

/// Applies the Android rationale rule to a permission_handler result.
Future<AdaptyUIPermissionResult> answerOnAndroid(
  PermissionStatus status,
  Permission permission,
  bool rationaleBefore,
) async {
  // A rationale before the request: the user saw the dialog and declined it again.
  if (status == PermissionStatus.permanentlyDenied && rationaleBefore) {
    return const AdaptyUIPermissionResult.denied('denied');
  }
  // No rationale before or after: the user closed the first dialog without a choice.
  if (status == PermissionStatus.denied && !await permission.shouldShowRequestRationale) {
    return const AdaptyUIPermissionResult.denied();
  }
  return answerFromStatus(status);
}

/// The Android API level of the device.
Future<int> androidSdkInt() async => (await DeviceInfoPlugin().androidInfo).version.sdkInt;
```

The `handlePermission` method receives:

- **`view`**: The flow view that sent the request.
- **`permission`**: The permission selected in the action. The `AdaptyUIPermission` class has a constant for each value in [Declare the permissions](#declare-the-permissions), named in camel case: for example, `AdaptyUIPermission.locationWhenInUse` for `location_when_use`. The `value` property returns the value as a string.
- **`customArgs`**: Custom arguments of the request. The **Request permission** action sends none, so the value is `null`.

To pass the result to the flow:

1. In the `handlePermission` method, show the system dialog.
2. Return `AdaptyUIPermissionResult.granted()` if the user granted the permission, and `AdaptyUIPermissionResult.denied()` otherwise.
3. To have the flow run the **When denied** actions, pass `'denied'`, `'restricted'`, or `'permanently_denied'` as the argument of `AdaptyUIPermissionResult.denied`. For example, `AdaptyUIPermissionResult.denied('permanently_denied')`. Without this argument, the flow runs the **After response** actions.

<FlowPermissionStrings />

The `AdaptyUIPermissionResult.granted` constructor takes the string as an optional argument too. For example, `AdaptyUIPermissionResult.granted('limited')`.

If the `handlePermission` method throws, Adapty Flutter SDK versions before 4.4.1 pass no result to the flow, so the `FlowSystemRequestsHandler` class catches errors itself. If the `handlePermission` method never completes, the flow stays on the screen, so the `requestAndAnswer` function accepts a timeout for the iOS alert. After a timeout, permission_handler on iOS keeps its call open until iOS returns the authorization status. Until then, every other permission_handler call throws, so for the next permission request, the flow runs the **After response** actions.

With a handler registered, the Adapty SDK passes app review requests to the `handleAppReviewRequest` method. The base method does nothing, so the example keeps the native review prompt.

## Register the handler

:::warning
**Without a handler, the user sees no permission dialog.** If your app registers no handler, Adapty Flutter SDK versions before 4.4.1 pass no result to the flow, on iOS and on Android. The flow stays on the screen that sent the permission request. From version 4.4.1, the SDK passes a not-granted result without a string, and the flow runs the **After response** actions.
:::

To send the permission requests from all flows to your handler, call the `AdaptyUI().setSystemRequestsHandler` method once, before you present a flow. For example, call it right after you set the flow events observer:

```dart showLineNumbers title="Flutter"
AdaptyUI().setSystemRequestsHandler(FlowSystemRequestsHandler());
```

## Declare the permissions

For each permission that your handler requests, add these declarations to `ios/Runner/Info.plist` on iOS and to `android/app/src/main/AndroidManifest.xml` on Android:

<FlowPermissionDeclarations />

For example, an app that requests only notifications and camera access adds the `NSCameraUsageDescription` key to `Info.plist` on iOS. On Android, the app declares these permissions:

```xml showLineNumbers title="android/app/src/main/AndroidManifest.xml"
<manifest xmlns:android="http://schemas.android.com/apk/res/android">
    <uses-permission android:name="android.permission.POST_NOTIFICATIONS" />
    <uses-permission android:name="android.permission.CAMERA" />
    <!-- ... -->
</manifest>
```

On iOS with Swift Package Manager, permission_handler_apple includes a permission only when its purpose string is in `Info.plist`, and doesn't need `Podfile` macros. A permission that isn't included returns denied, and iOS shows no dialog. Follow these rules from the [permission_handler README](https://pub.dev/packages/permission_handler):

- **After you add or change an `Info.plist` key**: Clear the Xcode package cache once, with `rm -rf ~/Library/Developer/Xcode/DerivedData`.
- **When you build from Xcode.app**: permission_handler can't find `Info.plist`, so it leaves out every permission, and every request returns denied. Set the `PERMISSION_HANDLER_INFO_PLIST` variable with `launchctl setenv`, as the README describes.

For what each permission shows users, which OS versions it needs, and which result to pass, see System permissions on [iOS](ios-system-permissions) and [Android](android-system-permissions).

## Test the permission request

iOS shows most permission dialogs only once per app install. Android stops showing a permission dialog after the user grants the permission or declines it twice. To see the dialog again while you test the flow, delete the app from the device and install it again. Then open the flow and reach the **Request permission** action.

If no dialog appears, look for the cause:

- **The screen stays**: Your app passed no result to the flow. Make sure that your app registers the handler before it presents the flow, and that on Android the flow is shown with the `AdaptyUIFlowPlatformView` widget.
- **The flow moves on**: Make sure that the app registers the handler and declares the permission on both platforms. On iOS, clear DerivedData after you add the `Info.plist` key. For notifications on Android, the app targets Android 13 or later.

## Code for each permission

Each function in this section requests one permission and returns the result for the flow. Functions for other permissions follow two patterns. The `requestCamera` function shows a direct request, and the `requestLocationWhenInUse` function shows a request with a timeout for the iOS alert. For what to request on each OS and which result to pass, see System permissions on [iOS](ios-system-permissions) and [Android](android-system-permissions).

### Library calls for each permission

The functions use [permission_handler](https://pub.dev/packages/permission_handler) to show the system dialogs. This table lists the `Permission` constant to request for each value. A dash means that permission_handler has no request for the permission on that OS. For such a permission, return `AdaptyUIPermissionResult.denied('unsupported')`, or request it in your own platform code through a [platform channel](https://docs.flutter.dev/platform-integration/platform-channels).

|:------|:----|:--------|

| `tracking` | `Permission.appTrackingTransparency` | — |
| `location_when_use` | `Permission.locationWhenInUse` | `Permission.locationWhenInUse`, which requests precise and approximate location |
| `location_always` | `Permission.locationAlways`, after `Permission.locationWhenInUse` is granted | `Permission.locationAlways`, after `Permission.locationWhenInUse` is granted |
| `location_full_accuracy` | `Permission.locationWhenInUse`, then `Geolocator.requestTemporaryFullAccuracy` from [geolocator](https://pub.dev/packages/geolocator) | `Permission.locationWhenInUse`, then `Geolocator.getLocationAccuracy` from geolocator |
| `camera` | `Permission.camera` | `Permission.camera` |
| `microphone` | `Permission.microphone` | `Permission.microphone` |
| `photos` | `Permission.photos` | `Permission.photos` with `Permission.videos` on Android 13 and later, `Permission.storage` on Android 12 and earlier |
| `media_library` | `Permission.mediaLibrary` | `Permission.audio` on Android 13 and later, `Permission.storage` on Android 12 and earlier |
| `music` | — | — |

| `contacts` | `Permission.contacts` | `Permission.contacts` |

Only call these permission_handler constants on iOS: `Permission.reminders`, `Permission.mediaLibrary`, `Permission.appTrackingTransparency`, and `Permission.assistant`. On Android, permission_handler shows no dialog for them: `Permission.reminders` and `Permission.mediaLibrary` return granted, so the flow would run the **When allowed** actions. `Permission.appTrackingTransparency` and `Permission.assistant` return denied. On Android, `Permission.sensors` is the body sensors permission: for `motion`, request `Permission.activityRecognition`.

### Push notifications \{#push\}

Add the `POST_NOTIFICATIONS` permission to the Android manifest. iOS needs no key in `Info.plist`. See System permissions on [iOS](ios-system-permissions#push) and [Android](android-system-permissions#push).

```dart showLineNumbers title="Flutter"
Future<AdaptyUIPermissionResult> requestPush() async {
  if (Platform.isAndroid && await androidSdkInt() < 33) {
    // Android 12 and earlier show no dialog: pass the result from the notification settings.
    return await Permission.notification.isGranted
        ? const AdaptyUIPermissionResult.granted('granted')
        : const AdaptyUIPermissionResult.denied('permanently_denied');
  }
  return requestAndAnswer(Permission.notification);
}
```

- With a granted notification permission, your app can show notifications. To receive push notifications, register the device with your push provider, as your app does outside flows.
- **Differs from System permissions**: When the `requestAuthorization(options:)` method fails on iOS, permission_handler reports `PermissionStatus.permanentlyDenied`, so the `requestPush` function passes `denied` instead of no string.

### Location while using the app \{#location_when_use\}

Add the `NSLocationWhenInUseUsageDescription` key to `Info.plist`. Add the `ACCESS_COARSE_LOCATION` and `ACCESS_FINE_LOCATION` permissions to the Android manifest. See System permissions on [iOS](ios-system-permissions#location_when_use) and [Android](android-system-permissions#location_when_use).

```dart showLineNumbers title="Flutter"
Future<AdaptyUIPermissionResult> requestLocationWhenInUse() {
  // On Android, this requests precise and approximate location together.
  return requestAndAnswer(Permission.locationWhenInUse, timeout: iosAlertTimeout);
}
```

- **Differs from System permissions**: On Android, permission_handler reports approximate location as denied before the request. Users who only granted approximate location see the dialog at every request, until they grant precise location. permission_handler returns granted for either choice in the dialog.

### Camera \{#camera\}

Add the `NSCameraUsageDescription` key to `Info.plist`, and the `CAMERA` permission to the Android manifest. See System permissions on [iOS](ios-system-permissions#camera) and [Android](android-system-permissions#camera).

```dart showLineNumbers title="Flutter"
Future<AdaptyUIPermissionResult> requestCamera() async {
  if (Platform.isAndroid) {
    final features = (await DeviceInfoPlugin().androidInfo).systemFeatures;
    if (!features.contains('android.hardware.camera.any')) {
      return const AdaptyUIPermissionResult.denied('unsupported');
    }
  }
  return requestAndAnswer(Permission.camera);
}
```

### Strings for each permission status

For each value of the `PermissionStatus` enum of permission_handler, the `requestAndAnswer` function passes the following string:

| `PermissionStatus` | String to pass | Actions that the flow runs |
|:-------------------|:---------------|:--------|
| `granted` | `granted` | **When allowed** |
| `limited` | `limited` | **When allowed** |
| `provisional` | `provisional` | **When allowed** |
| `restricted` | `restricted` | **When denied** |
| `denied` on Android, with a rationale after the request | `denied` | **When denied** |
| `denied` on Android, without a rationale after the request: the user closed the first dialog without a choice | No string | **After response** |
| `denied` on iOS after the request: the alert closed without a choice, or didn't appear | No string | **After response** |
| `permanentlyDenied` on iOS, returned by the request | `denied` | **When denied** |
| `permanentlyDenied` on iOS before the request | `permanently_denied` | **When denied** |
| `permanentlyDenied` on Android, with a rationale before the request: the user declined the dialog again | `denied` | **When denied** |
| `permanentlyDenied` on Android, without a rationale before the request: Android showed no dialog | `permanently_denied` | **When denied** |

On iOS, permission_handler returns `PermissionStatus.permanentlyDenied` for most refusals, also right after the alert, and returns `PermissionStatus.denied` for a permission that the app hasn't requested yet. The `requestAndAnswer` function reads the `permission.status` property first: `PermissionStatus.permanentlyDenied` before the request is an earlier refusal, and `PermissionStatus.permanentlyDenied` after it is a refusal in this alert. A dismissed location alert returns `PermissionStatus.denied`. On Android, permission_handler returns `PermissionStatus.denied` for the first refusal, and `PermissionStatus.permanentlyDenied` when the user declines again or Android shows no dialog. To tell these cases apart, the function reads the rationale before the request: with a rationale, the user saw the dialog, and the function passes the string `denied`.
