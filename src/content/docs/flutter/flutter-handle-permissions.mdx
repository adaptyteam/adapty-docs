A [flow](adapty-flow-builder) can ask users for a system permission with the **Request permission** action, for example push notifications on an onboarding screen that explains what the notifications are for, or camera access before a feature that scans documents. The Adapty SDK doesn't show the system permission dialog itself. It passes the request to an `AdaptyUISystemRequestsHandler` in your app. Your app shows the dialog and returns the user's answer, and the flow continues.

## Before you start

You need:

- **Adapty Flutter SDK 4.0.0 or later**: Earlier versions don't have `AdaptyUISystemRequestsHandler`. See [Install & configure SDK](sdk-installation-flutter).
- **A flow with the Request permission action**: In the Flow & Paywall Builder, add the **Request permission** action to an element's **On Tap** or **On Screen Appear** trigger. In the action, select the permission in the **Permission** field, and add the actions to run after the user answers to its outcome sections, such as **Navigate Next** in **After response**. For the action settings, see [Request permission](onboarding-actions#request-permission).
- **A library that shows the permission dialogs**: The example uses [permission_handler](https://pub.dev/packages/permission_handler). Any other package or your own platform code works the same way.
- **The declarations of the permissions that your handler requests**: A purpose string in `Info.plist` on iOS, and a permission in the Android manifest. See [Declare the permissions](#declare-the-permissions).
- **For push notifications on Android, `targetSdk` 33 or higher**: Only apps that target Android 13 or later choose when the notification permission dialog appears.
- **permission_handler 13.0.2 or later, with permission_handler_apple 9.6.4 or later**: Add `permission_handler: ^13.0.2` to `pubspec.yaml`. It brings permission_handler_android 14.1.0, which reports the first refusal as `denied`. The Adapty Flutter SDK 4.x builds for iOS with Swift Package Manager only, and permission_handler_apple 9.6.4 turns on each permission whose purpose string is in `Info.plist`. See [Request each permission](#request-each-permission).

## How the flow requests a permission

1. The flow reaches the **Request permission** action: the user taps the element, or the screen appears.
2. The Adapty SDK calls `handlePermission` on your handler with the permission selected in the action, such as `AdaptyUIPermission.push` or `AdaptyUIPermission.camera`.
3. Your app requests the permission from the OS and returns `AdaptyUIPermissionResult.granted()` or `AdaptyUIPermissionResult.denied()` with a status.
4. The flow runs the actions of one outcome section.

<FlowPermissionAnswers />

The flow waits on the screen until your app returns the answer. If your app never answers, the flow stays on the screen. If the OS doesn't show the dialog, for example because the user already answered it, permission_handler returns the earlier answer at once, and the flow runs the outcome actions right away. If those actions leave the screen, the user sees the screen that requests the permission only for a moment.

With **On Screen Appear**, the flow doesn't send the request again when the user comes back to the screen with a **Navigate back** action, unless every outcome section of the action is empty. With **On Tap**, each tap sends a new request. The flow sends one permission request at a time: while a request waits for your answer, a tap on an element that requests a permission does nothing.

## Implement the handler

:::warning
**Request only the permissions that your app declares, and answer `AdaptyUIPermissionResult.denied('unsupported')` for any other permission.** For most permissions, iOS terminates the app when the app requests a permission whose purpose string is missing from `Info.plist`. A flow author can add a request for any permission at any time, and the flow also reaches app versions released before the request was added.
:::

To answer permission requests, create a class that extends `AdaptyUISystemRequestsHandler` and implement `handlePermission`. In this example, the handler requests push notifications and camera access, and answers every other permission as unsupported without a dialog:

```dart showLineNumbers title="Flutter"
import 'package:adapty_flutter/adapty_flutter.dart';
import 'package:permission_handler/permission_handler.dart';

class FlowSystemRequestsHandler extends AdaptyUISystemRequestsHandler {
  // The permissions this app version requests, with their permission_handler counterparts.
  static final _requested = <AdaptyUIPermission, Permission>{
    AdaptyUIPermission.push: Permission.notification,
    AdaptyUIPermission.camera: Permission.camera,
  };

  @override
  Future<AdaptyUIPermissionResult> handlePermission(
    AdaptyUIFlowView view,
    AdaptyUIPermission permission,
    Map<String, String>? customArgs,
  ) async {
    final osPermission = _requested[permission];
    if (osPermission == null) {
      // A permission this app version doesn't request: answer without a dialog.
      return const AdaptyUIPermissionResult.denied('unsupported');
    }

    try {
      final status = await osPermission.request();
      return switch (status) {
        PermissionStatus.granted => const AdaptyUIPermissionResult.granted('granted'),
        PermissionStatus.limited => const AdaptyUIPermissionResult.granted('limited'),
        PermissionStatus.provisional => const AdaptyUIPermissionResult.granted('provisional'),
        PermissionStatus.restricted => const AdaptyUIPermissionResult.denied('restricted'),
        PermissionStatus.permanentlyDenied => const AdaptyUIPermissionResult.denied('permanently_denied'),
        _ => const AdaptyUIPermissionResult.denied('denied'),
      };
    } catch (_) {
      // Not an answer from the user: the flow runs After response.
      return const AdaptyUIPermissionResult.denied();
    }
  }

  // The base method does nothing: this keeps the native review prompt.
  @override
  Future<void> handleAppReviewRequest(AdaptyUIFlowView view) {
    return AdaptyUI().requestAppReview();
  }
}
```

`handlePermission` receives:

- **`view`**: The flow view that sent the request.
- **`permission`**: The permission selected in the action. `AdaptyUIPermission` has a constant for each value in [Declare the permissions](#declare-the-permissions), named in camel case: for example, `AdaptyUIPermission.locationWhenInUse` for `location_when_use`. The `value` property returns the value as a string.
- **`customArgs`**: Custom arguments of the request. The **Request permission** action sends none, so the value is `null`.

`AdaptyUIPermissionResult.granted()` and `AdaptyUIPermissionResult.denied()` take the status as an optional string, such as `AdaptyUIPermissionResult.denied('permanently_denied')`.

If `handlePermission` throws or never completes, the flow gets no answer and stays on the screen. The example catches errors for this reason.

A granted notification permission lets your app show notifications. To receive push notifications, register the device with your push provider, as your app does outside flows.

With a handler registered, the Adapty SDK passes app review requests to `handleAppReviewRequest`, whose base method does nothing. The example keeps the native review prompt.

## Request each permission

The example uses [permission_handler](https://pub.dev/packages/permission_handler) to show the system dialogs. This table lists the `Permission` that the handler requests for each value. A dash means that permission_handler has no such request: answer `unsupported`, or request the permission in your own platform code.

| Value | iOS | Android |
|:------|:----|:--------|
| `push` | `Permission.notification` | `Permission.notification` |
| `tracking` | `Permission.appTrackingTransparency` | — |
| `location_when_use` | `Permission.locationWhenInUse` | `Permission.locationWhenInUse`, which requests precise and approximate location |
| `location_always` | `Permission.locationAlways`, after `Permission.locationWhenInUse` is granted | `Permission.locationAlways`, after `Permission.locationWhenInUse` is granted |
| `location_full_accuracy` | — | `Permission.location` |
| `camera` | `Permission.camera` | `Permission.camera` |
| `microphone` | `Permission.microphone` | `Permission.microphone` |
| `photos` | `Permission.photos` | `Permission.photos` on Android 13 and later, `Permission.storage` on Android 12 and earlier |
| `media_library` | `Permission.mediaLibrary` | `Permission.audio` on Android 13 and later, `Permission.storage` on Android 12 and earlier |
| `music` | — | — |
| `speech` | `Permission.speech` | `Permission.microphone` |
| `contacts` | `Permission.contacts` | `Permission.contacts` |
| `calendar` | `Permission.calendarFullAccess` | `Permission.calendarFullAccess` |
| `reminders` | `Permission.reminders` | — |
| `health` | — | — |
| `motion` | `Permission.sensors` | `Permission.activityRecognition` |
| `bluetooth` | `Permission.bluetooth` | `[Permission.bluetoothScan, Permission.bluetoothConnect].request()`, granted when both are granted |
| `local_network` | — | `Permission.accessLocalNetwork`, on Android 17 and later |
| `homekit` | — | — |
| `focus_status` | — | — |
| `siri` | `Permission.assistant` | — |

Map the iOS-only permissions only on iOS, for example with a separate map for each platform and `Platform.isIOS`. On Android, permission_handler answers them without a dialog: `Permission.reminders` and `Permission.mediaLibrary` return granted, so the flow would run **When allowed**. `Permission.appTrackingTransparency` and `Permission.assistant` return denied. On Android, `Permission.sensors` is the body sensors permission, so request `Permission.activityRecognition` for `motion`. These Android requests also need care:

- **`Permission.calendarFullAccess`**: Returns denied without a dialog unless the manifest declares both `READ_CALENDAR` and `WRITE_CALENDAR`.
- **`Permission.accessLocalNetwork`**: Returns denied without a dialog below Android 17, where the app has local network access through `INTERNET`. Answer `granted` there without the request.

Pass the status from permission_handler's `PermissionStatus`:

| `PermissionStatus` | Status to pass | Section |
|:-------------------|:---------------|:--------|
| `granted` | `granted` | **When allowed** |
| `limited` | `limited` | **When allowed** |
| `provisional` | `provisional` | **When allowed** |
| `denied` | `denied` | **When denied** |
| `restricted` | `restricted` | **When denied** |
| `permanentlyDenied` | `permanently_denied` | **When denied** |

On iOS, permission_handler returns `permanentlyDenied` for most refusals, also right after the dialog, so a refusal on iOS usually has the `outcome` `permanently_denied`. A dismissed location dialog and a declined **Location always** upgrade return `denied`. On Android, the first refusal is `denied`, and a later one is `permanentlyDenied`.

On iOS with Swift Package Manager, permission_handler_apple includes a permission only when its purpose string is in `Info.plist`, and doesn't need `Podfile` macros. For **Reminders**, it looks for `NSRemindersUsageDescription`, so declare that key also when the app supports only iOS 17 and later. A permission that isn't included returns denied, and iOS shows no dialog. Follow these rules from the [permission_handler README](https://pub.dev/packages/permission_handler):

- **After you add or change an `Info.plist` key**: Clear the Xcode package cache once, with `rm -rf ~/Library/Developer/Xcode/DerivedData`.
- **When you build from Xcode.app**: permission_handler can't find `Info.plist`, so it leaves out every permission, and every request returns denied. Set the `PERMISSION_HANDLER_INFO_PLIST` variable with `launchctl setenv`, as the README describes.
- **With an older permission_handler_apple and CocoaPods**: Add a macro to `GCC_PREPROCESSOR_DEFINITIONS` in the `Podfile` for each permission, such as `PERMISSION_NOTIFICATIONS=1` and `PERMISSION_CAMERA=1`. Versions earlier than 9.6.4 also have known issues with finding `Info.plist` and with `Permission.locationAlways`, so update instead where you can.

## Declare the permissions

The OS shows a permission dialog only to an app that declares the permission: in `ios/Runner/Info.plist` on iOS, and in `android/app/src/main/AndroidManifest.xml` on Android. For each permission that your handler requests, add these declarations:

<FlowPermissionDeclarations />

The handler in this guide requests notifications and camera access. On iOS, the app adds `NSCameraUsageDescription` to `Info.plist`. On Android, the app declares these permissions:

```xml showLineNumbers title="android/app/src/main/AndroidManifest.xml"
<manifest xmlns:android="http://schemas.android.com/apk/res/android">
    <uses-permission android:name="android.permission.POST_NOTIFICATIONS" />
    <uses-permission android:name="android.permission.CAMERA" />
    <!-- ... -->
</manifest>
```

For what each permission shows users, the OS versions it needs, and the status to pass for each result, see [System permissions](flow-permissions).

## Register the handler

:::warning
**Without a handler, the flow stops at the permission request.** If your app registers no handler, the Adapty SDK sends the flow no answer, on iOS and on Android. The flow stays on the screen that sent the request and doesn't run the outcome actions.
:::

To send the permission requests from all flows to your handler, call `AdaptyUI().setSystemRequestsHandler` once, before you present a flow. For example, call it right after you set the flow events observer:

```dart showLineNumbers title="Flutter"
AdaptyUI().setSystemRequestsHandler(FlowSystemRequestsHandler());
```

## Test the permission request

iOS shows most permission dialogs only once per app install. Android stops showing a permission dialog after the user allows the permission or denies it twice. To see the dialog again while you test the flow, delete the app from the device and install it again. Then open the flow and reach the **Request permission** action. If the screen stays and no dialog appears, the flow got no answer: make sure that your app registers the handler before it presents the flow. If the flow moves on without a dialog, make sure that the app declares the permission on both platforms. On iOS, also make sure that you cleared DerivedData after you added the `Info.plist` key. For notifications on Android, the app must also target Android 13 or later.

To see how users answer permission requests, read the flow's analytics events in the `flowViewDidReceiveAnalyticEvent` method of your flow events observer. For details, see [Handle flow & paywall events](flutter-handling-events).
