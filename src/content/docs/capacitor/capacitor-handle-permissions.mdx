A [flow](adapty-flow-builder) can ask users for a system permission with the **Request permission** action. For example, an onboarding screen can explain push notifications and then ask for them, or a flow can ask for camera access before a feature that scans documents. The Adapty SDK doesn't show the system permission dialog itself. It passes the permission request to the `onRequestPermission` handler in your app. Your app shows the dialog and passes the result to the flow, which then continues.

## Before you start

You need:

- **Adapty Capacitor SDK 4.1.0 or later**: Version 4.1.0 is the first stable release with the `onRequestPermission` handler.
- **A flow with the Request permission action**: In the Flow & Paywall Builder, add the **Request permission** action to an element's **On Tap** or **On Screen Appear** trigger. In the action, select the permission in the **Permission** field. Add the actions for each result. The default **After response** action is **Navigate Next**. For the action settings, see [Request permission](onboarding-actions#request-permission).
- **Plugins that show the permission dialogs**: The code in this guide uses the official plugins [`@capacitor/push-notifications`](https://capacitorjs.com/docs/apis/push-notifications), [`@capacitor/geolocation`](https://capacitorjs.com/docs/apis/geolocation), and [`@capacitor/camera`](https://capacitorjs.com/docs/apis/camera), with [`@capacitor/local-notifications`](https://capacitorjs.com/docs/apis/local-notifications) and [`@capacitor/device`](https://capacitorjs.com/docs/apis/device) as helpers. Install only the plugins of the permissions that your app requests. Any other plugin that shows the dialogs works too.
- **The declarations of the permissions that your handler requests**: On iOS, a purpose string: the text in `Info.plist` that tells users why your app needs the permission. On Android, a permission in the Android manifest. See [Declare the permissions](#declare-the-permissions).
- **For push notifications on Android, the `targetSdk` property set to 33 or higher**: Only apps that target Android 13 or later choose when the notification permission dialog appears.

:::note
**If your handler already requests push notifications**: It keeps working. When the handler resolves with `{ status: 'denied' }`, the flow runs the **After response** actions. To have the flow run the **When denied** actions, also set the `detail` property to `'denied'`, `'restricted'`, or `'permanently_denied'`. To request other permissions, add their cases to the handler.
:::

## How the flow requests a permission

1. The flow reaches the **Request permission** action: the user taps the element, or the screen appears.
2. The Adapty SDK calls your `onRequestPermission` handler with the permission selected in the action, such as `push` or `camera`.
3. Your app shows the system dialog. The promise of your handler resolves to an object with the result in the `status` property and a string in the `detail` property. For example: `{ status: 'denied', detail: 'permanently_denied' }`.

<FlowPermissionAnswers />

The flow waits on the screen until your handler's promise resolves. If the promise never resolves, the flow stays on the screen. If the OS shows no dialog, for example because the user already granted or declined the permission, the plugin returns the current permission state at once. On Android 12 and earlier, apps need no runtime permission for notifications, so the code in this guide reads the notification setting instead of showing a dialog. In both cases, your handler passes the result at once. The flow then runs the actions for the result right away. If those actions leave the screen, the user sees the screen that requests the permission only for a moment.

The flow sends your handler one permission request at a time. [The trigger of the action](onboarding-actions#request-permission) decides how often the flow sends the request. Your handler can receive the same permission again, for example on each tap. Each time, pass the result for what the OS currently reports.

## Implement the handler

:::warning
**Request only the permissions that your app declares. For any other permission, resolve the promise of the handler with `{ status: 'denied', detail: 'unsupported' }`.** For most permissions, iOS terminates the app when the app requests a permission whose purpose string is missing from `Info.plist`. A flow author can add a request for any permission at any time, and the flow also reaches app versions released before the request was added.
:::

The `onRequestPermission` handler is asynchronous. It returns a promise that resolves to an object with the result. In `permissions.ts`, the handler requests push notifications and camera access, and passes `unsupported` for every other permission, without a dialog. The file also defines two helpers for the functions:

- **`unsupported()`**: Returns the result for a permission that the app doesn't request.
- **`toFlowAnswer()`**: Converts the permission state that the plugin reports before and after the request into the result for the flow.

With `denied` or `permanently_denied`, the flow runs the **When denied** actions. The two strings only differ in the `outcome` property of [`flow_permission_answered`](#track-permission-requests-in-analytics). The `toFlowAnswer()` function tells them apart with the permission state before the request. Compared with code that passes `denied` for every refusal, the `toFlowAnswer()` function only changes the actions that the flow runs in one case. If the user closes the dialog without a choice, the `toFlowAnswer()` function returns `{ status: 'denied' }`, and the flow runs the **After response** actions.

```typescript showLineNumbers title="permissions.ts"
import { Capacitor, type PermissionState } from '@capacitor/core';
import type { FlowEventHandlers, FlowPermissionResponse } from '@adapty/capacitor';

const isAndroid = Capacitor.getPlatform() === 'android';

// The result for a permission that the app doesn't request: the flow runs the After response actions.
function unsupported(): FlowPermissionResponse {
  return { status: 'denied', detail: 'unsupported' };
}

// Converts a plugin's permission state before and after the request to the result the flow expects.
function toFlowAnswer(
  before: PermissionState | 'limited',
  after: PermissionState | 'limited',
): FlowPermissionResponse {
  switch (after) {
    case 'granted':
      return { status: 'granted', detail: 'granted' };
    case 'limited':
      return { status: 'granted', detail: 'limited' };
    case 'prompt-with-rationale':
      // Android: the user declined the dialog, and Android can show it again.
      return { status: 'denied', detail: 'denied' };
    case 'denied':
      if (before === 'denied') {
        // Denied before the request, so the OS showed no dialog.
        // iOS: this includes a restriction by a device policy, which the plugins report as denied.
        return { status: 'denied', detail: 'permanently_denied' };
      }
      if (isAndroid && before === 'prompt') {
        // Android: no rationale before or after the first request, so the user closed the dialog without a choice.
        return { status: 'denied' };
      }
      // iOS: the user declined the alert. Android: the user declined the dialog again.
      return { status: 'denied', detail: 'denied' };
    default:
      // 'prompt': the user closed the dialog without a choice, so the flow runs After response.
      return { status: 'denied' };
  }
}

export const onRequestPermission: FlowEventHandlers['onRequestPermission'] = async (permission) => {
  switch (permission) {
    case 'push':
      return requestPush();
    case 'camera':
      return requestCamera();
    // Add a case for each permission that your app requests.
    default:
      // A permission that this app version doesn't request: pass the result without a dialog.
      return unsupported();
  }
};
```

To request another permission, add a case for it, and a function that requests it. For the function, start from [Code for each permission](#code-for-each-permission). A permission without a case needs no plugin and no declarations. Put the imports of each function at the top of `permissions.ts`. When two functions use the same import, keep one copy of it.

The `onRequestPermission` handler receives:

- **`permission`**: The permission selected in the action, as a string from the **Value** column in [Declare the permissions](#declare-the-permissions).
- **`customArgs`**: Custom arguments of the request. The **Request permission** action sends none, so the object is empty.

To pass the result to the flow:

1. In the `onRequestPermission` handler, show the system dialog.
2. Resolve the promise of the handler with an object. Set its `status` property to `'granted'` if the user granted the permission, and to `'denied'` otherwise.
3. To have the flow run the **When denied** actions, also set the `detail` property to `'denied'`, `'restricted'`, or `'permanently_denied'`. For example, `{ status: 'denied', detail: 'permanently_denied' }`. Without the `detail` property, the flow runs the **After response** actions.

<FlowPermissionStrings />

On iOS, if the `status` property holds any value other than `'granted'` or `'denied'`, the flow receives no result and stays on the screen.

When your handler throws an error or its promise rejects, the Adapty SDK passes `denied` without a string. The flow then runs the **After response** actions.

## Register the handler

:::warning
**Without an `onRequestPermission` handler, the user is never asked.** On a flow view without the handler, the Adapty SDK passes `denied` without a dialog and without a string, and writes a warning to its log. The flow runs the **After response** actions right away. The `outcome` property of [`flow_permission_answered`](#track-permission-requests-in-analytics) then reports `no_status`.
:::

Set the handler on every flow view your app creates, together with your other [flow event handlers](capacitor-handling-events), before you present the view.

```typescript showLineNumbers title="Capacitor"
import { createFlowView } from '@adapty/capacitor';
import { onRequestPermission } from './permissions';

const view = await createFlowView(flow);

await view.setEventHandlers({
  onRequestPermission,
});

await view.present();
```

## Declare the permissions

For each permission that your handler requests, add these declarations to `ios/App/App/Info.plist` on iOS and to `android/app/src/main/AndroidManifest.xml` on Android:

For example, an app that requests notifications and camera access adds the `NSCameraUsageDescription` key to `Info.plist` on iOS. On Android, the app declares these permissions:

```xml title="android/app/src/main/AndroidManifest.xml"
<uses-permission android:name="android.permission.POST_NOTIFICATIONS" />
<uses-permission android:name="android.permission.CAMERA" />
```

For what each permission shows users, the OS versions it needs, and the result to pass for what the OS reports, see System permissions on [iOS](ios-system-permissions) and [Android](android-system-permissions).

## Test the permission request

iOS shows most permission dialogs only once per app install. Android stops showing a permission dialog after the user grants the permission or declines it twice. To see the dialog again while you test the flow, delete the app from the device and install it again. Then open the flow and reach the **Request permission** action.

If the flow moves on without a dialog, make sure that:

- The flow view has the `onRequestPermission` handler.
- The app declares the permission on iOS and on Android. Without the `CAMERA` permission in the manifest, the `@capacitor/camera` plugin reports camera access as `granted` without a dialog.
- For notifications on Android, the app targets Android 13 or later.

## Code for each permission

Each function in this section requests one permission and returns the result for the flow. The functions use the `isAndroid` constant and the `unsupported()` and `toFlowAnswer()` functions from `permissions.ts`.

Functions for the other permissions follow one of two patterns. The `requestCamera()` function makes a direct request. The `requestLocationWhenInUse()` function stops waiting after a timeout, because the plugin never returns when iOS shows no alert. For what to request and which result to pass for each permission, see System permissions on [iOS](ios-system-permissions) and [Android](android-system-permissions).

### Plugin calls for each permission

The official Capacitor plugins request these permissions. The `requestPermissions()` method of each plugin returns a permission state for each permission, and the `checkPermissions()` method returns the state before the request:

| Value | Plugin and call | State to read |
|:------|:----------------|:--------------|
| `push` | `@capacitor/push-notifications`: `PushNotifications.requestPermissions()`. On Android 12 and earlier, `@capacitor/local-notifications`: `LocalNotifications.checkPermissions()` | `receive`, or `display` on Android 12 and earlier |
| `location_when_use` | `@capacitor/geolocation`: `Geolocation.requestPermissions({ permissions: ['location'] })` | `coarseLocation` |
| `location_full_accuracy` | `@capacitor/geolocation`: `Geolocation.requestPermissions({ permissions: ['location'] })`, on Android | `location` |
| `camera` | `@capacitor/camera`: `Camera.requestPermissions({ permissions: ['camera'] })` | `camera` |
| `photos` | `@capacitor/camera`: `Camera.requestPermissions({ permissions: ['photos'] })`, on iOS | `photos` |
| `calendar` | `@capacitor/calendar`: `Calendar.requestPermissions()` | `readCalendar` and `writeCalendar` |
| `health` | `@capacitor/health-fitness`: `HealthFitness.requestHealthPermissions()` | None: on Android, the call resolves after a grant and rejects with an error code otherwise. On iOS, pass the result without a string |

No official plugin requests the other permissions. To request such a permission, use a community plugin or a local plugin with your own native code. Without a case for the permission, the `default` branch of the handler passes `unsupported` for it.

The `toFlowAnswer()` function passes the following results to the flow:

| State after the request | State before the request | OS | Result to pass | Actions |
|:------------------------|:-------------------------|:---|:---------------|:--------|
| `granted` | Any | iOS and Android | Granted, `granted` | **When allowed** |
| `limited` | Any | iOS, for photos | Granted, `limited` | **When allowed** |
| `prompt-with-rationale` | Any | Android: the user declined the dialog | Not granted, `denied` | **When denied** |
| `denied` | `denied`: the OS showed no dialog | iOS and Android | Not granted, `permanently_denied` | **When denied** |
| `denied` | `prompt` | iOS: the user declined the alert | Not granted, `denied` | **When denied** |
| `denied` | `prompt-with-rationale` | Android: the user declined the dialog again | Not granted, `denied` | **When denied** |
| `denied` | `prompt` | Android: the user closed the dialog without a choice | Not granted, no string | **After response** |
| `prompt` | `prompt` | iOS: the user closed the dialog without a choice | Not granted, no string | **After response** |

On iOS, the Capacitor plugins report a restricted permission as `denied`, so your app can't pass `restricted`: it passes `permanently_denied`. On Android, a request never returns `prompt`. A dialog that the user closed without a choice returns `denied`, the same as a refusal without a dialog, so the `toFlowAnswer()` function reads the state before the request to tell them apart. On Android, Capacitor stores the state of a refusal in the app's own storage, so the state before the request is `prompt` until the app requests the permission through a Capacitor plugin.

### Push notifications \{#push\}

Add the `POST_NOTIFICATIONS` permission to the Android manifest. iOS needs no purpose string. See System permissions on [iOS](ios-system-permissions#push) and [Android](android-system-permissions#push).

```typescript showLineNumbers title="permissions.ts"
import { Device } from '@capacitor/device';
import { LocalNotifications } from '@capacitor/local-notifications';
import { PushNotifications } from '@capacitor/push-notifications';

async function requestPush(): Promise<FlowPermissionResponse> {
  if (isAndroid) {
    const { androidSDKVersion = 0 } = await Device.getInfo();
    if (androidSDKVersion < 33) {
      // Android 12 and earlier show no dialog, so read whether notifications are on.
      const { display } = await LocalNotifications.checkPermissions();
      return display === 'granted'
        ? { status: 'granted', detail: 'granted' }
        : { status: 'denied', detail: 'permanently_denied' };
    }
  }
  const before = await PushNotifications.checkPermissions();
  // Already allowed, also with provisional access on iOS, where a request would show the alert.
  if (before.receive === 'granted') return { status: 'granted', detail: 'granted' };
  // Shows the system dialog, or returns the current state without it.
  const after = await PushNotifications.requestPermissions();
  return toFlowAnswer(before.receive, after.receive);
}
```

- With a granted notification permission, your app can show notifications. To receive push notifications, register the device with your push provider, as your app does outside flows.
- On Android 12 and earlier, the `PushNotifications` plugin returns `granted` also when the user turned notifications off in the settings. So the function reads the Android version with the [`@capacitor/device`](https://capacitorjs.com/docs/apis/device) plugin, and the notification setting with the [`@capacitor/local-notifications`](https://capacitorjs.com/docs/apis/local-notifications) plugin.
- **Differs from System permissions**: The app can't pass `provisional`. On iOS, the `checkPermissions()` method reports provisional access as `granted`, and the `requestPermissions()` method always asks with an alert. So the function passes `granted` for provisional access, without a request.

### Location while using the app \{#location_when_use\}

Add the `NSLocationWhenInUseUsageDescription` and `NSLocationAlwaysAndWhenInUseUsageDescription` keys to `Info.plist`. Add the `ACCESS_COARSE_LOCATION` and `ACCESS_FINE_LOCATION` permissions to the Android manifest. See System permissions on [iOS](ios-system-permissions#location_when_use) and [Android](android-system-permissions#location_when_use).

```typescript showLineNumbers title="permissions.ts"
import { Geolocation } from '@capacitor/geolocation';

async function requestLocationWhenInUse(): Promise<FlowPermissionResponse> {
  try {
    const before = await Geolocation.checkPermissions();
    // On Android, 'location' requests precise and approximate location together, so the user can choose either.
    const request = Geolocation.requestPermissions({ permissions: ['location'] });
    // iOS: without an alert, for example in the background, the plugin never returns, so wait at most 50 seconds.
    // The flow reports flow_permission_unanswered after 60 seconds without a result.
    const timeout = new Promise<null>((resolve) => setTimeout(() => resolve(null), 50_000));
    const after = isAndroid ? await request : await Promise.race([request, timeout]);
    if (after === null) return { status: 'denied' };
    // Approximate location is enough, so read coarseLocation, which equals location on iOS.
    return toFlowAnswer(before.coarseLocation, after.coarseLocation);
  } catch (error) {
    if ((error as { code?: string }).code === 'OS-PLUG-GLOC-0007') {
      // Location services are off: iOS reports denied, and on Android this says nothing about the permission.
      return isAndroid ? { status: 'denied' } : { status: 'denied', detail: 'permanently_denied' };
    }
    throw error;
  }
}
```

- The `@capacitor/geolocation` plugin needs both iOS keys, although it requests only location while using the app.
- On Android, the `location` state is `granted` only when the user selects precise location. To have the flow run the **When allowed** actions for users who select approximate location, read the `coarseLocation` state.
- On iOS, the plugin waits without a timeout until the user makes a choice. The function stops waiting after 50 seconds and passes a not-granted result without a string.
- **Differs from System permissions**: The plugin reports restricted location access as `denied`, so the function passes `permanently_denied` to the flow instead of `restricted`.

### Camera \{#camera\}

Add the `NSCameraUsageDescription` key to `Info.plist`, and the `CAMERA` permission to the Android manifest. See System permissions on [iOS](ios-system-permissions#camera) and [Android](android-system-permissions#camera).

```typescript showLineNumbers title="permissions.ts"
import { Camera } from '@capacitor/camera';

async function requestCamera(): Promise<FlowPermissionResponse> {
  const before = await Camera.checkPermissions();
  const after = await Camera.requestPermissions({ permissions: ['camera'] });
  return toFlowAnswer(before.camera, after.camera);
}
```

- Without the `CAMERA` permission in the Android manifest, the plugin reports the `camera` state as `granted` without a dialog.
- **Differs from System permissions**: The function doesn't pass `restricted` or `unsupported` to the flow:
  - On iOS, the plugin reports a restricted camera as `denied`, so the function passes `permanently_denied`.
  - On Android, the plugin doesn't report whether the device has a camera. To read the `FEATURE_CAMERA_ANY` system feature, use a local plugin.
