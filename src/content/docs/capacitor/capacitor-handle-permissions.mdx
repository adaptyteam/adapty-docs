A [flow](adapty-flow-builder) can ask users for a system permission with the **Request permission** action. For example, an onboarding screen can explain what push notifications are for and then ask for them. A feature that scans documents can ask for camera access first. The Adapty SDK doesn't show the system permission dialog itself. It passes the request to the `onRequestPermission` handler in your app. Your app shows the dialog and returns the user's answer, and the flow continues.

## Before you start

You need:

- **Adapty Capacitor SDK 4.1.0 or later**: Version 4.1.0 is the first stable release with the `onRequestPermission` handler.
- **A flow with the Request permission action**: In the Flow & Paywall Builder, add the **Request permission** action to an element's **On Tap** or **On Screen Appear** trigger. In the action, select the permission in the **Permission** field. Then add the actions to run after the user answers to the outcome sections of the action, such as **Navigate Next** in **After response**. For the action settings, see [Request permission](onboarding-actions#request-permission).
- **Plugins that show the permission dialogs**: The code in this guide uses the official plugins [`@capacitor/push-notifications`](https://capacitorjs.com/docs/apis/push-notifications), [`@capacitor/geolocation`](https://capacitorjs.com/docs/apis/geolocation), [`@capacitor/camera`](https://capacitorjs.com/docs/apis/camera), [`@capacitor/calendar`](https://capacitorjs.com/docs/apis/calendar), and [`@capacitor/health-fitness`](https://capacitorjs.com/docs/apis/health-fitness), with [`@capacitor/local-notifications`](https://capacitorjs.com/docs/apis/local-notifications) and [`@capacitor/device`](https://capacitorjs.com/docs/apis/device) as helpers. Install only the plugins of the permissions that your app requests. Any other plugin that shows the dialogs works too.
- **The declarations of the permissions that your handler requests**: A purpose string in `Info.plist` on iOS, and a permission in the Android manifest. See [Declare the permissions](#declare-the-permissions).
- **For push notifications on Android, `targetSdk` 33 or higher**: Only apps that target Android 13 or later choose when the notification permission dialog appears.

## How the flow requests a permission

1. The flow reaches the **Request permission** action: the user taps the element, or the screen appears.
2. The Adapty SDK calls your `onRequestPermission` handler with the permission selected in the action, such as `push` or `camera`.
3. Your app shows the system dialog and resolves the handler's promise to an object, such as `{ status: 'denied', detail: 'denied' }`. Put the answer in the `status` property, and the status of the answer in the `detail` property.

<FlowPermissionAnswers />

The flow waits on the screen until your handler's promise resolves. If the promise never resolves, the flow stays on the screen. If the OS doesn't show the dialog, the plugin returns the current permission state at once, and the flow runs the outcome actions right away. For example, the OS shows no dialog when the user already answered it. On Android 12 and earlier, apps need no runtime permission for notifications, so the code in this guide answers from the notification setting without a dialog. If the outcome actions leave the screen, the user sees the screen that requests the permission only for a moment.

With **On Screen Appear**, the flow doesn't send the request again when the user comes back to the screen with a **Navigate back** action. The exception is an action whose outcome sections are all empty: the flow then sends the request again. With **On Tap**, each tap sends a new request. The flow sends one permission request at a time: while a request waits for your answer, a tap on an element that requests a permission does nothing.

## Implement the handler

:::warning
**Request only the permissions that your app declares, and answer `{ status: 'denied', detail: 'unsupported' }` for any other permission.** For most permissions, iOS terminates the app when the app requests a permission whose purpose string is missing from `Info.plist`. A flow author can add a request for any permission at any time, and the flow also reaches app versions released before the request was added.
:::

The `onRequestPermission` handler is asynchronous. It returns a promise that resolves to an object with the user's answer. In `permissions.ts`, the handler sends each permission to a function that requests it. It answers every other value as unsupported without a dialog. The file also defines two helpers for the functions:

- **`unsupported()`**: Returns the answer for a permission that the app doesn't request.
- **`toFlowAnswer()`**: Converts the plugin's permission state before and after the request to the answer for the flow.

```typescript showLineNumbers title="permissions.ts"
import { Capacitor, type PermissionState } from '@capacitor/core';
import type { FlowEventHandlers, FlowPermissionResponse } from '@adapty/capacitor';

const isAndroid = Capacitor.getPlatform() === 'android';

// The answer for a permission that the app doesn't request: the flow runs After response.
function unsupported(): FlowPermissionResponse {
  return { status: 'denied', detail: 'unsupported' };
}

// Converts a plugin's permission state before and after the request to the answer the flow expects.
function toFlowAnswer(
  before: PermissionState | 'limited',
  after: PermissionState | 'limited',
): FlowPermissionResponse {
  switch (after) {
    case 'granted':
      return { status: 'granted', detail: 'granted' };
    case 'limited':
      return { status: 'granted', detail: 'limited' };
    case 'prompt-with-rationale':
      // Android: the user declined the dialog, and Android can show it again.
      return { status: 'denied', detail: 'denied' };
    case 'denied':
      if (before === 'denied') {
        // Denied before the request, so the OS showed no dialog.
        // iOS: this includes a restriction by a device policy, which the plugins report as denied.
        return { status: 'denied', detail: 'permanently_denied' };
      }
      if (isAndroid && before === 'prompt') {
        // Android: no rationale before or after the first request, so the user closed the dialog without a choice.
        return { status: 'denied' };
      }
      // iOS: the user declined the alert. Android: the user declined the dialog again.
      return { status: 'denied', detail: 'denied' };
    default:
      // 'prompt': the user closed the dialog without a choice, so the flow runs After response.
      return { status: 'denied' };
  }
}

export const onRequestPermission: FlowEventHandlers['onRequestPermission'] = async (permission) => {
  switch (permission) {
    case 'push':
      return requestPush();
    case 'tracking':
      return requestTracking();
    case 'location_when_use':
      return requestLocationWhenInUse();
    case 'location_always':
      return requestLocationAlways();
    case 'location_full_accuracy':
      return requestLocationFullAccuracy();
    case 'camera':
      return requestCamera();
    case 'microphone':
      return requestMicrophone();
    case 'photos':
      return requestPhotos();
    case 'media_library':
      return requestMediaLibrary();
    case 'music':
      return requestMusic();
    case 'speech':
      return requestSpeech();
    case 'contacts':
      return requestContacts();
    case 'calendar':
      return requestCalendar();
    case 'reminders':
      return requestReminders();
    case 'health':
      return requestHealth();
    case 'motion':
      return requestMotion();
    case 'bluetooth':
      return requestBluetooth();
    case 'local_network':
      return requestLocalNetwork();
    case 'homekit':
      return requestHomeKit();
    case 'focus_status':
      return requestFocusStatus();
    case 'siri':
      return requestSiri();
    default:
      // A permission that this app version doesn't know: answer without a dialog.
      return unsupported();
  }
};
```

Copy the functions from [Code for each permission](#code-for-each-permission) only for the permissions that your app requests. For the other permissions, replace the call in their `case` with `return unsupported();`. Your app then needs no plugins and no purpose strings for those permissions. Put the imports of each function at the top of `permissions.ts`. When two functions use the same import, keep one copy of it.

`onRequestPermission` receives:

- **`permission`**: The permission selected in the action, as a string from the **Value** column in [Declare the permissions](#declare-the-permissions).
- **`customArgs`**: Custom arguments of the request. The **Request permission** action sends none, so the object is empty.

The promise resolves to an object with these properties:

- **`status`**: The user's answer: `granted` if the user allowed the permission, and `denied` otherwise.
- **`detail`**: The status of the answer, such as `granted` or `permanently_denied`. Put the statuses from [How the flow requests a permission](#how-the-flow-requests-a-permission) in this property, not in the `status` property. Without `detail`, a refusal runs **After response**.

The Adapty SDK answers `denied` without a status when your handler throws an error or its promise rejects, so the flow runs **After response**.

A granted notification permission lets your app show notifications. To receive push notifications, register the device with your push provider, as your app does outside flows.

## Code for each permission

Each function requests one permission and returns the answer for the flow. The functions use `isAndroid`, `unsupported()`, and `toFlowAnswer()` from `permissions.ts`. For a permission that no official Capacitor plugin requests, the function answers `unsupported`. To request such a permission, use a community plugin or a local plugin with your own native code.

### Push notifications \{#push\}

Declare `POST_NOTIFICATIONS` in the Android manifest. iOS needs no purpose string. See [System permissions](flow-permissions#push).

```typescript showLineNumbers title="permissions.ts"
import { Device } from '@capacitor/device';
import { LocalNotifications } from '@capacitor/local-notifications';
import { PushNotifications } from '@capacitor/push-notifications';

async function requestPush(): Promise<FlowPermissionResponse> {
  if (isAndroid) {
    const { androidSDKVersion = 0 } = await Device.getInfo();
    if (androidSDKVersion < 33) {
      // Android 12 and earlier show no dialog, so read whether notifications are on.
      const { display } = await LocalNotifications.checkPermissions();
      return display === 'granted'
        ? { status: 'granted', detail: 'granted' }
        : { status: 'denied', detail: 'permanently_denied' };
    }
  }
  const before = await PushNotifications.checkPermissions();
  // Already allowed, also with provisional access on iOS, where a request would show the alert.
  if (before.receive === 'granted') return { status: 'granted', detail: 'granted' };
  // Shows the system dialog, or returns the current state without it.
  const after = await PushNotifications.requestPermissions();
  return toFlowAnswer(before.receive, after.receive);
}
```

- On Android 12 and earlier, `PushNotifications` returns `granted` also when the user turned notifications off in the settings. So the function reads the Android version with [`@capacitor/device`](https://capacitorjs.com/docs/apis/device), and the notification setting with [`@capacitor/local-notifications`](https://capacitorjs.com/docs/apis/local-notifications).
- **Differs from System permissions**: The app can't pass `provisional`. On iOS, `checkPermissions()` reports provisional access as `granted`, and `requestPermissions()` always asks with an alert. So the function answers `granted` for provisional access, without a request.

### Location while using the app \{#location_when_use\}

Declare `NSLocationWhenInUseUsageDescription` and `NSLocationAlwaysAndWhenInUseUsageDescription` on iOS, and `ACCESS_COARSE_LOCATION` and `ACCESS_FINE_LOCATION` on Android. See [System permissions](flow-permissions#location_when_use).

```typescript showLineNumbers title="permissions.ts"
import { Geolocation } from '@capacitor/geolocation';

async function requestLocationWhenInUse(): Promise<FlowPermissionResponse> {
  try {
    const before = await Geolocation.checkPermissions();
    // On Android, 'location' requests precise and approximate location together, so the user can choose either.
    const request = Geolocation.requestPermissions({ permissions: ['location'] });
    // iOS: without an alert, for example in the background, the plugin never answers, so wait at most 30 seconds.
    const timeout = new Promise<null>((resolve) => setTimeout(() => resolve(null), 30_000));
    const after = isAndroid ? await request : await Promise.race([request, timeout]);
    if (after === null) return { status: 'denied' };
    // Approximate location is enough, so read coarseLocation, which equals location on iOS.
    return toFlowAnswer(before.coarseLocation, after.coarseLocation);
  } catch (error) {
    if ((error as { code?: string }).code === 'OS-PLUG-GLOC-0007') {
      // Location services are off: iOS reports denied, and on Android this isn't an answer to the permission.
      return isAndroid ? { status: 'denied' } : { status: 'denied', detail: 'permanently_denied' };
    }
    throw error;
  }
}
```

- `@capacitor/geolocation` needs both iOS keys, although it requests only location while using the app.
- On Android, the `location` state is `granted` only when the user allows precise location. Read `coarseLocation`, or users who choose approximate location go to **When denied**.
- On iOS, the plugin waits for the user's answer without a timeout. So the function answers without a status after 30 seconds.
- **Differs from System permissions**: The plugin reports restricted location access as `denied`, so the function passes `permanently_denied` to the flow instead of `restricted`.

### Precise location \{#location_full_accuracy\}

Declare `ACCESS_COARSE_LOCATION` and `ACCESS_FINE_LOCATION` on Android. See [System permissions](flow-permissions#location_full_accuracy).

```typescript showLineNumbers title="permissions.ts"
import { Geolocation } from '@capacitor/geolocation';

async function requestLocationFullAccuracy(): Promise<FlowPermissionResponse> {
  // iOS: @capacitor/geolocation can't request temporary precise location.
  if (!isAndroid) return unsupported();
  try {
    const before = await Geolocation.checkPermissions();
    const after = await Geolocation.requestPermissions({ permissions: ['location'] });
    // On Android, 'location' is granted only with precise location.
    if (after.location === 'granted') return { status: 'granted', detail: 'granted' };
    // The user kept approximate location.
    if (after.coarseLocation === 'granted') return { status: 'denied', detail: 'denied' };
    return toFlowAnswer(before.coarseLocation, after.coarseLocation);
  } catch (error) {
    // Location services are off: this isn't an answer to the permission.
    if ((error as { code?: string }).code === 'OS-PLUG-GLOC-0007') return { status: 'denied' };
    throw error;
  }
}
```

- On iOS, request precise location with `requestTemporaryFullAccuracyAuthorization(withPurposeKey:)` in a local plugin, or answer `unsupported`.

### Calendar \{#calendar\}

On iOS, declare `NSCalendarsFullAccessUsageDescription` and `NSCalendarsWriteOnlyAccessUsageDescription` for iOS 17 and later, and `NSCalendarsUsageDescription` for iOS 16 and earlier. `@capacitor/calendar` asks for all three keys. On Android, declare `READ_CALENDAR` and `WRITE_CALENDAR`. See [System permissions](flow-permissions#calendar).

```typescript showLineNumbers title="permissions.ts"
import { Calendar } from '@capacitor/calendar';

async function requestCalendar(): Promise<FlowPermissionResponse> {
  const before = await Calendar.checkPermissions();
  // On iOS, a request for readCalendar asks for full access.
  const after = await Calendar.requestPermissions({ permissions: ['readCalendar', 'writeCalendar'] });
  if (after.readCalendar === 'granted' && after.writeCalendar === 'granted') {
    return { status: 'granted', detail: 'granted' };
  }
  if (after.writeCalendar === 'granted') {
    // iOS 17 and later: the app can only add events.
    return { status: 'granted', detail: 'limited' };
  }
  return toFlowAnswer(before.readCalendar, after.readCalendar);
}
```

- To request only access to add events, request `['writeCalendar']`, and answer `granted` when `writeCalendar` is `granted`. On iOS 17 and later, the plugin then asks for write-only access, with the text of `NSCalendarsWriteOnlyAccessUsageDescription`.
- **Differs from System permissions**: The plugin reports restricted calendar access as `denied`, so the function passes `permanently_denied` to the flow instead of `restricted`.

### Health data \{#health\}

Add the HealthKit capability and `NSHealthShareUsageDescription` on iOS, and set up Health Connect on Android. See [System permissions](flow-permissions#health).

```typescript showLineNumbers title="permissions.ts"
import { HealthFitness } from '@capacitor/health-fitness';

async function requestHealth(): Promise<FlowPermissionResponse> {
  const off = JSON.stringify({ IsActive: false, AccessType: 'READ' });
  try {
    // The flow sends no data types, so this example requests read access to steps, calories, distance, and speed.
    await HealthFitness.requestHealthPermissions({
      customPermissions: '[]',
      allVariables: off,
      fitnessVariables: JSON.stringify({ IsActive: true, AccessType: 'READ' }),
      healthVariables: off,
      profileVariables: off,
      workoutVariables: off,
    });
  } catch (error) {
    const code = (error as { code?: string }).code ?? '';
    // Android: the user granted none of the requested permissions.
    if (isAndroid && code === 'OS-PLUG-HLFT-0300') return { status: 'denied', detail: 'denied' };
    // Android: Health Connect isn't available, isn't installed, or needs an update.
    if (isAndroid && ['OS-PLUG-HLFT-0301', 'OS-PLUG-HLFT-0302', 'OS-PLUG-HLFT-0303'].includes(code)) {
      return unsupported();
    }
    throw error;
  }
  // Android: the user granted at least one permission.
  // iOS: the plugin doesn't report the answer.
  return isAndroid ? { status: 'granted', detail: 'granted' } : { status: 'denied' };
}
```

- On iOS, `requestHealthPermissions()` resolves without the user's answer, so the function answers without a status. Put the next step of the flow in **After response**. For the Android setup of the plugin, see [`@capacitor/health-fitness`](https://capacitorjs.com/docs/apis/health-fitness).
- The error codes `OS-PLUG-HLFT-0300` to `OS-PLUG-HLFT-0303` come from the source code of the plugin's Android library, `ionhealthfitness-android` 1.0.1. The plugin documentation doesn't list them, so they can change in a later version.
- **Differs from System permissions**: The function doesn't pass `limited`, `permanently_denied`, or `restricted` to the flow:
  - On Android, the plugin resolves when the user grants at least one of the requested permissions. So the function passes `granted` also for a partial grant.
  - On Android, the plugin doesn't count the cancels of the Health Connect screen. So the function passes `denied` after the second cancel too.
  - On iOS, the plugin rejects a request that fails, also for restricted health data. The Adapty SDK then answers without a status.

### Local network \{#local_network\}

On Android, declare `ACCESS_LOCAL_NETWORK` only if the app targets Android 17 (API 37) or higher. See [System permissions](flow-permissions#local_network).

```typescript showLineNumbers title="permissions.ts"
import { Device } from '@capacitor/device';

// The targetSdkVersion of your Android app.
const ANDROID_TARGET_SDK = 36;

async function requestLocalNetwork(): Promise<FlowPermissionResponse> {
  // iOS has no request method and no status for the local network.
  if (!isAndroid) return unsupported();
  // Below Android 17, apps access the local network with INTERNET, without a dialog.
  const { androidSDKVersion = 0 } = await Device.getInfo();
  if (ANDROID_TARGET_SDK < 37 || androidSDKVersion < 37) {
    return { status: 'granted', detail: 'granted' };
  }
  // No official plugin requests ACCESS_LOCAL_NETWORK.
  return unsupported();
}
```

- The code reads the Android version with the [`@capacitor/device`](https://capacitorjs.com/docs/apis/device) plugin. Set `ANDROID_TARGET_SDK` to the `targetSdkVersion` of your app.
- **Differs from System permissions**: For an app that targets Android 17 or higher on Android 17, no official plugin requests `ACCESS_LOCAL_NETWORK`, so the code answers `unsupported`. To request it, add a local plugin with your own native code.

## Request each permission

The official Capacitor plugins request these permissions. Each plugin's `requestPermissions()` returns a permission state for each permission, and `checkPermissions()` returns the state before the request:

| Value | Plugin and call | State to read |
|:------|:----------------|:--------------|
| `push` | `@capacitor/push-notifications`: `PushNotifications.requestPermissions()`. On Android 12 and earlier, `@capacitor/local-notifications`: `LocalNotifications.checkPermissions()` | `receive`, or `display` on Android 12 and earlier |
| `location_when_use` | `@capacitor/geolocation`: `Geolocation.requestPermissions({ permissions: ['location'] })` | `coarseLocation` |
| `location_full_accuracy` | `@capacitor/geolocation`: `Geolocation.requestPermissions({ permissions: ['location'] })`, on Android | `location` |
| `camera` | `@capacitor/camera`: `Camera.requestPermissions({ permissions: ['camera'] })` | `camera` |
| `photos` | `@capacitor/camera`: `Camera.requestPermissions({ permissions: ['photos'] })`, on iOS | `photos` |
| `calendar` | `@capacitor/calendar`: `Calendar.requestPermissions()` | `readCalendar` and `writeCalendar` |
| `health` | `@capacitor/health-fitness`: `HealthFitness.requestHealthPermissions()` | None: on Android, the call resolves after a grant and rejects with an error code otherwise. On iOS, answer without a status |

For the other values, the official plugins have no request: the functions answer `unsupported`. `toFlowAnswer` passes these statuses:

| State after the request | State before the request | OS | Status to pass | Section |
|:------------------------|:-------------------------|:---|:---------------|:--------|
| `granted` | Any | iOS and Android | `granted` | **When allowed** |
| `limited` | Any | iOS, for photos | `limited` | **When allowed** |
| `prompt-with-rationale` | Any | Android: the user declined the dialog | `denied` | **When denied** |
| `denied` | `denied`: the OS showed no dialog | iOS and Android | `permanently_denied` | **When denied** |
| `denied` | `prompt` | iOS: the user declined the alert | `denied` | **When denied** |
| `denied` | `prompt-with-rationale` | Android: the user declined the dialog again | `denied` | **When denied** |
| `denied` | `prompt` | Android: the user closed the dialog without a choice | No status | **After response** |
| `prompt` | `prompt` | iOS: the user closed the dialog without a choice | No status | **After response** |

On iOS, the Capacitor plugins report a restricted permission as `denied`, so your app can't pass `restricted`: it passes `permanently_denied`. On Android, a request never returns `prompt`. A dialog that the user closed without a choice returns `denied`, the same as a refusal without a dialog, so `toFlowAnswer` reads the state before the request to tell them apart. On Android, Capacitor stores the state of a refusal in the app's own storage, so the state before the request is `prompt` until the app requests the permission through a Capacitor plugin.

## Declare the permissions

The OS shows a permission dialog only to an app that declares the permission: in `ios/App/App/Info.plist` on iOS, and in `android/app/src/main/AndroidManifest.xml` on Android. For each permission that your handler requests, add these declarations:

<FlowPermissionDeclarations />

For example, an app that requests notifications and camera access adds `NSCameraUsageDescription` to `Info.plist` on iOS. On Android, the app declares these permissions:

```xml title="android/app/src/main/AndroidManifest.xml"
<uses-permission android:name="android.permission.POST_NOTIFICATIONS" />
<uses-permission android:name="android.permission.CAMERA" />
```

For what each permission shows users, the OS versions it needs, and the status to pass for each result, see [System permissions](flow-permissions).

## Register the handler

:::warning
**Without an `onRequestPermission` handler, the user is never asked.** On a flow view without the handler, the Adapty SDK answers `denied` without a dialog and without a status, and writes a warning to its log. The flow runs the **After response** actions right away, and reports the answer with the `outcome` `no_status`.
:::

Set the handler on every flow view your app creates, together with your other [flow event handlers](capacitor-handling-events), before you present the view. Flow authors can add the **Request permission** action to any flow later, without an app update. A flow view without the handler answers `denied` without asking the user.

```typescript showLineNumbers title="Capacitor"
import { createFlowView } from '@adapty/capacitor';
import { onRequestPermission } from './permissions';

const view = await createFlowView(flow);

await view.setEventHandlers({
  onRequestPermission,
});

await view.present();
```

## Test the permission request

iOS shows most permission dialogs only once per app install. Android stops showing a permission dialog after the user allows the permission or denies it twice. To see the dialog again while you test the flow, delete the app from the device and install it again. Then open the flow and reach the **Request permission** action.

If the flow moves on without a dialog, make sure that:

- The flow view has the `onRequestPermission` handler.
- The app declares the permission on iOS and on Android. Without `CAMERA` in the manifest, `@capacitor/camera` reports camera access as `granted` without a dialog.
- For notifications on Android, the app targets Android 13 or later.

To see how users answer permission requests, read the flow's analytics events in the `onAnalytics` handler of the flow view. For details, see [Handle flow & paywall events](capacitor-handling-events).
