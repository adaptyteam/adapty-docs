## Avant de commencer \{#before-you-start\}

Vous avez besoin de :

- **Adapty Capacitor SDK 4.4 ou version ultérieure** : les versions antérieures affichent le paywall de secours pour chaque élément personnalisé.
- **Code natif pour iOS et Android** : il n'est pas possible d'afficher du HTML provenant de votre application web dans un élément personnalisé. Écrivez ce code en Swift pour iOS et en Kotlin pour Android. Ajoutez le code Swift à la cible `App` dans Xcode, et le code Kotlin dans le dossier de `MainActivity.java`. Commencez chaque nouveau fichier Kotlin par la ligne `package` de `MainActivity.java`.
- **Un schéma de nommage pour les éléments personnalisés** : donnez à chaque vue native un Type, par exemple `lottie_animation`. Utilisez uniquement des lettres minuscules, des chiffres et des underscores dans les Types. Pour distinguer les éléments personnalisés du même Type, attribuez à chacun un ID, par exemple `welcome_wave`. Les Types et les ID dans votre code doivent correspondre à ceux définis dans le [Flow & Paywall Builder](flow-custom-elements#add-and-configure).

Utilisez les mêmes types et identifiants dans votre code iOS et Android. À moins de configurer une [audience](audience) distincte pour chaque plateforme, les utilisateurs iOS et Android voient les mêmes flows.

## Configurer votre projet Android \{#set-up-your-android-project\}

Dans votre projet Android, ajoutez Kotlin et la bibliothèque Adapty UI. Pour construire des vues natives sous forme de composables, configurez également Jetpack Compose.

### Ajouter Kotlin \{#add-kotlin\}

Le template Capacitor ne comprend pas de configuration Kotlin. Pour compiler le code Kotlin de cette page, dans `android/build.gradle`, définissez `kotlin_version` à `2.2.20`, la version Kotlin par défaut de `@adapty/capacitor`. Ajoutez ensuite le plugin Gradle Kotlin aux dépendances `buildscript`. Si `android/build.gradle` contient déjà les deux, conservez vos lignes.

```groovy showLineNumbers title="android/build.gradle"
buildscript {
    ext.kotlin_version = '2.2.20'
    dependencies {
        classpath "org.jetbrains.kotlin:kotlin-gradle-plugin:$kotlin_version"
    }
}
```

Ensuite, appliquez le plugin au module de l'application. Définissez la cible JVM de Kotlin sur 21, la version Java que Capacitor définit pour le module de l'application :

```groovy showLineNumbers title="android/app/build.gradle"

apply plugin: 'org.jetbrains.kotlin.android'

kotlin {
    compilerOptions {
        jvmTarget = JvmTarget.JVM_21
    }
}
```

### Ajouter la bibliothèque Adapty UI

Dans `android/app/build.gradle`, ajoutez `io.adapty:android-ui` au bloc `dependencies`, sans version. `@adapty/capacitor` définit la version. Une version différente de `android-ui` peut casser les flows.

```groovy showLineNumbers title="android/app/build.gradle"
dependencies {
    implementation 'io.adapty:android-ui'
}
```

### Configurer Jetpack Compose \{#set-up-jetpack-compose\}

Le template Capacitor ne [configure pas Compose](https://developer.android.com/develop/ui/compose/setup-compose-dependencies-and-compiler) dans le module de l'application. Une `View` Android n'a pas besoin de configuration Compose. Pour créer des vues natives en tant que composables, ajoutez le plugin Gradle du compilateur Compose aux dépendances `buildscript` :

```groovy showLineNumbers title="android/build.gradle"
buildscript {
    dependencies {
        classpath "org.jetbrains.kotlin:compose-compiler-gradle-plugin:$kotlin_version"
    }
}
```

Ensuite, appliquez le plugin au module app et définissez `compose true` dans le bloc `buildFeatures` :

```groovy showLineNumbers title="android/app/build.gradle"
apply plugin: 'org.jetbrains.kotlin.plugin.compose'

android {
    buildFeatures {
        compose true
    }
}
```

Pour la vue Lottie sur cette page, ajoutez également `com.airbnb.android:lottie-compose`.

## Créer des vues pour les éléments personnalisés \{#create-views-for-custom-elements\}

Pour chaque Type, créez une vue native pour iOS et pour Android, ou réutilisez-en une depuis votre code natif. Les vues suivantes de Type `lottie_animation` jouent une animation Lottie. La vue Android est un composable qui utilise la bibliothèque `com.airbnb.android:lottie-compose` :

<Tabs groupId="platform" queryString>
<TabItem value="ios" label="iOS (Swift)" default>

```swift showLineNumbers title="Swift"

struct LottieElementView: View {
    let animation: LottieAnimation?

    var body: some View {
        LottieView(animation: animation)
            .resizable()
            .looping()
    }
}
```

</TabItem>
<TabItem value="android" label="Android (Kotlin)">

```kotlin showLineNumbers title="Kotlin"

@Composable
fun LottieElement(animationFile: String) {
    val composition by rememberLottieComposition(LottieCompositionSpec.Asset(animationFile))
    LottieAnimation(
        composition = composition,
        iterations = LottieConstants.IterateForever,
    )
}
```

### Exigences et bonnes pratiques \{#requirements-and-best-practices\}

- **Dimensionnement** :
  - **Padding et alignement** : Assurez-vous que la vue native s'adapte au conteneur que vous lui avez alloué dans le Flow & Paywall Builder, en tenant compte du padding. Si la vue n'occupe pas toute la zone, elle s'affiche par défaut dans le coin supérieur gauche de cette zone. Pour la déplacer, modifiez l'alignement dans la section **Layout** de l'élément personnalisé.
  - **Hauteur Hug** : Si la hauteur de l'élément personnalisé est définie sur **Hug**, une vue qui s'étire pour remplir l'espace disponible (comme une carte ou une liste paresseuse) va se réduire à zéro, ou s'étirer jusqu'à la hauteur de l'écran. Donnez plutôt à l'élément personnalisé une hauteur [**Fixed**](flow-custom-elements#add-and-configure).
- **Thème** : Les vues natives n'héritent pas des styles de votre application web. Définissez les couleurs et les polices dans le code natif.
- **Actions de flow** : La vue native ne peut pas exécuter des actions de flow, comme la transition vers l'écran suivant. Le contexte de l'élément peut envoyer des messages au flow, avec `sendMessage` sur iOS et `send` sur Android, mais ils sont réservés aux futures fonctionnalités du Flow & Paywall Builder. Gardez les boutons de navigation, les boutons d'achat et les autres boutons avec des actions de flow en dehors de l'élément personnalisé.
- **Éléments sélectionnables** : Gardez l'élément personnalisé en dehors des cartes produit et des autres [éléments sélectionnables](flow-selectable-elements). Quand la sélection change, la vue native peut perdre son état.
- **Gestion de la navigation** : Quand l'utilisateur passe à l'écran suivant, le SDK supprime la vue native de l'écran. Arrêtez ce que la vue a démarré, comme les sessions caméra, les lecteurs et les mises à jour de localisation :
  - **Vue SwiftUI** : Utilisez l'action `onDisappear`. Pour le travail asynchrone, utilisez `.task` : SwiftUI l'annule quand la vue disparaît.
  - **Composable** : Utilisez le bloc `onDispose` d'un `DisposableEffect`. Pour le travail asynchrone, utilisez `LaunchedEffect` : Compose l'annule quand le composable quitte la composition.
  - **`View` Android** : Surchargez `onDetachedFromWindow` dans votre sous-classe `View`, ou ajoutez un `View.OnAttachStateChangeListener` à la `View`.

  Lorsque l'utilisateur revient, le SDK appelle à nouveau le resolver, et la vue native démarre sans l'état de la précédente. Sur Android, une rotation fait que le SDK rappelle le resolver.
- **Vues UIKit** : Sur iOS, encapsulez-les dans `UIViewRepresentable`.
- **Carousels** : Sur Android, dans un [carousel](builder-containers#carousel), les vues natives de toutes les diapositives restent actives pendant que l'écran est ouvert, pas seulement la vue de la diapositive visible. Évitez d'intégrer des aperçus de caméra et des lecteurs avec son dans les carousels.

## Écrire un resolver pour faire correspondre les éléments et vues personnalisés \{#write-a-resolver-to-match-custom-elements-and-views\}

Écrivez un resolver pour chaque plateforme. Le resolver reçoit le type et l'ID d'un élément personnalisé, et retourne la vue native correspondante.

<Tabs groupId="platform" queryString>
<TabItem value="ios" label="iOS (Swift)" default>

Pour écrire un resolver, faites en sorte qu'un type soit conforme au protocole `AdaptyUICustomElementsResolver`, et implémentez la méthode `view(forType:id:context:)`.

Pour le type `lottie_animation`, le resolver suivant retourne `LottieElementView`. L'ID désigne le fichier d'animation dans le bundle de l'app, par exemple `welcome_wave` :

```swift showLineNumbers title="Swift"

struct CustomElementsResolver: AdaptyUICustomElementsResolver {
    func view(
        forType type: String,
        id: String,
        context: AdaptyUICustomElementContext
    ) -> AnyView? {
        switch type {
        case "lottie_animation":
            // the ID names the animation file, such as welcome_wave.json
            guard let animation = LottieAnimation.named(id) else {
                return nil // no file for this ID: show the fallback
            }
            return AnyView(LottieElementView(animation: animation))
        default:
            return nil
        }
    }
}
```

Dans le cas `default`, retournez `nil`.

</TabItem>
<TabItem value="android" label="Android (Kotlin)">

Pour écrire un resolver, implémentez l'interface `AdaptyCustomElementsResolver`. Sa méthode `resolve` retourne la vue correspondante sous l'une des formes suivantes :

- **Un composable** : Retournez `AdaptyCustomElementContent.compose`, avec le composable dans son lambda.
- **Une `View` Android** : Retournez `AdaptyCustomElementContent.view`, avec une fonction qui crée la `View`. Nommez le paramètre `factory` : `AdaptyCustomElementContent.view(factory = { context, _ -> ChartView(context) })`. Sans le nom, Kotlin passe un lambda de fin au paramètre optionnel `update`, et le code ne compile pas.

Pour le type `lottie_animation`, le resolver suivant retourne la [vue Lottie](#create-views-for-custom-elements). L'identifiant désigne le fichier d'animation dans le dossier `assets`, `android/app/src/main/assets`, par exemple `welcome_wave` pour `welcome_wave.json` :

```kotlin showLineNumbers title="Kotlin"

class CustomElementsResolver(context: Context) : AdaptyCustomElementsResolver {
    // the animation files in the assets folder, listed once
    private val animationFiles: Set<String> = try {
        context.assets.list("").orEmpty().toSet()
    } catch (e: IOException) {
        emptySet() // no list of files: every Lottie element shows the fallback
    }

    override fun resolve(type: String, id: String): AdaptyCustomElementContent? =
        when (type) {
            "lottie_animation" -> {
                // the ID names the animation file, such as welcome_wave.json
                val file = "$id.json"
                if (file in animationFiles) {
                    AdaptyCustomElementContent.compose { LottieElement(file) }
                } else {
                    null // no file for this ID: show the fallback
                }
            }
            else -> null
        }
}
```

Pour tout autre Type, retournez `null`.

</TabItem>
</Tabs>

Si vous [ajoutez un élément personnalisé avec un nouveau Type](flow-custom-elements#what-changes-require-an-app-release) après avoir publié l'application, les utilisateurs de la version publiée voient son fallback.

Le resolver a les exigences suivantes :

- **Données réseau et lecteurs** : Conservez les données réseau et les lecteurs dans l'état de la [vue native](#create-views-for-custom-elements), pas dans le resolver. Le SDK appelle le resolver de nombreuses fois pendant que l'écran est ouvert. Le code dans le resolver s'exécute à nouveau à chaque appel, ce qui répète les requêtes réseau et remet les lecteurs à zéro. La vue native conserve son état entre ces appels, de sorte que les données ne se chargent qu'une fois et que les lecteurs continuent de jouer. Créez les lecteurs, sessions et requêtes réseau dans la vue native :
  - **Vue SwiftUI** : Créez les lecteurs, sessions et requêtes réseau dans `.task` ou un `@StateObject`, et non dans la valeur initiale d'une propriété `@State`. Swift réévalue cette valeur initiale à chaque fois que le resolver crée la vue.
  - **Composable** : Créez les lecteurs et sessions dans `remember`, et les requêtes réseau dans `LaunchedEffect`.
  - **`View` Android** : Créez les lecteurs, sessions et requêtes réseau dans `onAttachedToWindow`.
- **Une vue native par élément personnalisé** : Certaines vues natives changent pendant que l'écran est ouvert, par exemple lorsque leurs données se chargent ou lorsque l'utilisateur appuie dessus. Implémentez cette logique dans la vue native elle-même, pas dans le resolver. Si le resolver retourne une vue différente pour le même élément personnalisé, la vue perd son état.
- **Une nouvelle `View` à chaque apparition** : Sur Android, créez une nouvelle `View` à chaque appel de `factory`. Le SDK appelle `factory` à chaque fois que l'élément personnalisé apparaît, par exemple à l'ouverture de l'écran, au retour de l'utilisateur sur l'écran, ou après une rotation.
- **Données de l'application** : Stockez un objet qui contient les données, tel qu'un `ObservableObject` ou un `StateFlow` avec une [série quotidienne](capacitor-custom-element-lottie-animation), dans une propriété du resolver. Passez l'objet à la vue native, et observez-le dans celle-ci :
  - **Vue SwiftUI** : Observez un `ObservableObject` avec `@ObservedObject`.
  - **Composable** : Collectez un `StateFlow` avec `collectAsState`, ou observez un `LiveData` avec `observeAsState`.
  - **`View` Android** : Observez l'objet dans `onAttachedToWindow`, et arrêtez dans `onDetachedFromWindow`.

  Une valeur que vous copiez dans le resolver, comme le nombre de jours consécutifs, reste telle qu'elle était au moment de la création du resolver. Si votre code JavaScript possède les données, comme un compteur de jours consécutifs, envoyez chaque nouvelle valeur vers le code natif via un <InlineTooltip tooltip="plugin Capacitor local">[iOS](https://capacitorjs.com/docs/ios/custom-code), [Android](https://capacitorjs.com/docs/android/custom-code)</InlineTooltip>, et mettez l'objet à jour à cet endroit.

### Définir les conditions pour le contenu de secours \{#set-conditions-for-fallback-content\}

<FlowCustomElementsFallbackConditions />

Pour une permission, ne retournez aucune vue uniquement si l'utilisateur l'a refusée avant l'ouverture de l'écran. Sur Android, `ContextCompat.checkSelfPermission` retourne la même valeur, `PERMISSION_DENIED`, dans deux cas : avant que votre application demande la permission à l'utilisateur pour la première fois, et après que l'utilisateur l'a refusée. Pour distinguer ces deux cas, enregistrez le résultat de la demande de permission et lisez ce résultat enregistré dans le resolver. Si votre application n'a pas encore demandé la permission, retournez la vue native et demandez la permission à l'intérieur de la vue. Par exemple, demandez l'accès à la localisation lorsqu'une [vue carte](capacitor-custom-element-map#3-match-the-map-to-the-custom-element) apparaît, et affichez la carte dès que l'utilisateur accorde l'accès. Si vous ne retournez aucune vue et que l'utilisateur accorde l'accès par la suite, il verra toujours le fallback. Un changement de permission ne fait pas que le SDK rappelle le resolver. La vue native n'apparaît qu'après que le SDK rappelle à nouveau le resolver, par exemple lorsque l'utilisateur revient à l'écran.

## Transmettre le resolver au SDK \{#pass-the-resolver-to-the-sdk\}

Configurez le resolver une seule fois par plateforme, au lancement de l'application. Le SDK l'appelle dans chaque flow. Les utilisateurs voient vos vues natives dans les nouveaux flows et tests A/B sans publication d'une nouvelle version de l'application. Ces vues affichent toujours les données propres à chaque utilisateur, comme une [série quotidienne](capacitor-custom-element-lottie-animation), car elles les lisent directement depuis votre application.

### iOS

Dans `AppDelegate.swift`, importez `AdaptyUI` et appelez `AdaptyUI.setCustomElementsResolver(_:)` dans la méthode `application(_:didFinishLaunchingWithOptions:)`. Les lignes surlignées indiquent ce qu'il faut ajouter. Conservez le reste de la classe `AppDelegate` tel quel :

```swift showLineNumbers title="ios/App/App/AppDelegate.swift" {1,11}

@UIApplicationMain
class AppDelegate: UIResponder, UIApplicationDelegate {

    var window: UIWindow?

    func application(_ application: UIApplication, didFinishLaunchingWithOptions launchOptions: [UIApplication.LaunchOptionsKey: Any]?) -> Bool {
        AdaptyUI.setCustomElementsResolver(CustomElementsResolver())
        // the rest of your launch code
        return true
    }
}
```

Si vous écrivez le resolver dans `AppDelegate.swift` également, importez aussi `AdaptyUIBuilder` dans ce fichier.

### Android

Le template Capacitor ne contient pas de classe `Application`. Créez `MainApplication.kt` dans le dossier de `MainActivity.java`, et appelez `AdaptyUI.setCustomElementsResolver` dans sa méthode `onCreate`. Si votre application possède déjà une classe `Application`, ajoutez-y les lignes mises en évidence à la place :

```kotlin showLineNumbers title="MainApplication.kt" {4,9}
package com.example.app


class MainApplication : Application() {
    override fun onCreate() {
        super.onCreate()
        AdaptyUI.setCustomElementsResolver(CustomElementsResolver(this))
    }
}
```

Pour qu'Android instancie cette classe au démarrage de l'application, dans `android/app/src/main/AndroidManifest.xml`, définissez l'attribut `android:name` de l'élément `application` sur `.MainApplication`. Conservez les autres attributs tels quels :

```xml showLineNumbers title="android/app/src/main/AndroidManifest.xml" {2}
<application
    android:name=".MainApplication"
    android:allowBackup="true"
    android:icon="@mipmap/ic_launcher">
```

:::tip
Pour afficher la même vue dans chaque élément personnalisé d'un Type, passez une map de Types et de vues plutôt qu'un resolver. Avec une map, vous écrivez moins de code qu'avec un resolver, mais vous ne pouvez pas [définir de conditions pour le contenu de secours](#set-conditions-for-fallback-content).

<Tabs groupId="platform" queryString>
<TabItem value="ios" label="iOS (Swift)" default>

Le dictionnaire est de type `[String: AdaptyUICustomElementBuilder]`. Si vous écrivez le dictionnaire dans `AppDelegate.swift`, importez également `Lottie`.

```swift showLineNumbers title="Swift"
AdaptyUI.setCustomElementsResolver([
    "lottie_animation": .init { _, id, _ in LottieElementView(animation: .named(id)) },
])
```

</TabItem>
<TabItem value="android" label="Android (Kotlin)">

Passez le dictionnaire à `AdaptyCustomElementsResolver.of` :

```kotlin showLineNumbers title="Kotlin"
val appWideViews = mapOf(
    "confetti" to AdaptyCustomElementContent.compose { LottieElement("confetti.json") },
)
AdaptyUI.setCustomElementsResolver(AdaptyCustomElementsResolver.of(appWideViews))
```

</TabItem>
</Tabs>

Vous ne pouvez pas attacher un resolver à un seul flow. Pour afficher des données issues de votre code JavaScript, envoyez-les à votre code natif avant l'ouverture du flow. Lisez ensuite les données dans le resolver. Par exemple, un paywall affiche le [poids que l'utilisateur a saisi dans un flow précédent](capacitor-custom-element-interactive-chart).

## Tester sur un appareil \{#test-on-a-device\}

Le Flow & Paywall Builder ne peut pas exécuter le code de votre application, donc son canvas n'affiche que le fallback. Une erreur dans la vue native peut faire planter l'application. Avant de publier l'application, testez chaque écran contenant un élément personnalisé sur un appareil iOS et sur un appareil Android :

1. Pour voir la dernière version publiée de chaque flow au lieu d'une version en cache, enregistrez l'appareil en tant que [device de test](test-devices).
2. Pour voir les avertissements du SDK Adapty dans la console Xcode et dans Logcat, réglez le [niveau de log](sdk-installation-capacitor#logging) sur `warn` ou un niveau plus détaillé.
3. Sur l'appareil, lancez un build qui inclut le resolver. Ouvrez chaque écran contenant un élément personnalisé et vérifiez que la vue native s'affiche et s'adapte à l'élément personnalisé. Si la vue défile ou réagit aux glissements, testez ces gestes.
4. Si le fallback s'affiche à la place de la vue native, recherchez cet avertissement dans la console Xcode ou dans Logcat : `custom element <type>:<id> is not served by a resolver`. Vérifiez ensuite que :
   - Le Type et l'ID dans l'avertissement correspondent exactement à ceux de votre code, lettre pour lettre.
   - Votre application dispose du fichier, des données ou des permissions dont la vue a besoin.
   - Votre application définit le resolver au démarrage : dans la classe `AppDelegate` sur iOS, et sur Android, dans la classe `Application` indiquée dans `AndroidManifest.xml`.

   Si l'avertissement n'apparaît pas, vérifiez que l'application utilise Adapty Capacitor SDK 4.4 ou une version ultérieure.
5. Sur Android, si l'élément personnalisé reste vide, recherchez l'un de ces avertissements dans Logcat :
   - `custom element <type>:<id> is not served by a resolver` : L'élément personnalisé n'a pas de contenu de secours et aucun resolver ne renvoie de vue pour lui. Vérifiez chaque point de l'étape 4.
   - `content does not report its size` : Le composable n'a pas de hauteur propre. Donnez à l'élément personnalisé une hauteur [**Fixed**](flow-custom-elements#add-and-configure).

   Le SDK enregistre l'avertissement de taille uniquement pour les composables. Si une `View` Android reste vide sans avertissement, donnez également une hauteur **Fixed** à l'élément personnalisé.
6. Pour prévisualiser le paywall de secours, ne retournez aucune vue pour le Type, puis rouvrez l'écran.
