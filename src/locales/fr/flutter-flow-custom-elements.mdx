## Avant de commencer \{#before-you-start\}

Vous avez besoin de :

- **Adapty Flutter SDK 4.4 ou version ultérieure** : Les versions antérieures affichent le paywall de secours pour chaque élément personnalisé.
- **Code natif pour iOS et Android** : Vous ne pouvez pas afficher un widget Flutter dans un élément personnalisé. Écrivez les vues et le resolver en Swift pour iOS et en Kotlin pour Android. Ajoutez le code Swift à la cible `Runner` dans Xcode, et le code Kotlin dans `android/app/src/main/kotlin`.
- **La bibliothèque Adapty UI sur Android** : Dans le fichier Gradle de votre module d'application Android, par exemple `android/app/build.gradle.kts`, ajoutez `implementation("io.adapty:android-ui")` au bloc `dependencies`. N'ajoutez pas de version ni le BOM Adapty : `adapty_flutter` gère la version, et une version plus récente d'`android-ui` peut casser les flows.
- **Jetpack Compose sur Android, pour les composables** : Le template Flutter ne [configure pas Compose](https://developer.android.com/develop/ui/compose/setup-compose-dependencies-and-compiler) dans le module de l'application. Pour retourner des composables depuis le resolver, appliquez le plugin Gradle du compilateur Compose et activez `compose = true` dans le bloc `buildFeatures`. Une `View` Android n'a pas besoin de configuration Compose. Pour la vue Lottie présentée sur cette page, ajoutez également `com.airbnb.android:lottie-compose`.
- **Un schéma de nommage pour les éléments personnalisés** : Donnez à chaque vue native un Type, par exemple `lottie_animation`. N'utilisez que des lettres minuscules, des chiffres et des underscores dans les Types. Pour distinguer des éléments personnalisés du même Type, attribuez à chacun un ID, par exemple `welcome_wave`. Les Types et les IDs dans votre code doivent correspondre à ceux définis dans le [Flow & Paywall Builder](flow-custom-elements#add-and-configure).

Utilisez les mêmes types et identifiants dans votre code iOS et Android. À moins de configurer une [audience](audience) distincte pour chaque plateforme, les utilisateurs iOS et Android voient les mêmes flows.

## Créer des vues pour les éléments personnalisés \{#create-views-for-custom-elements\}

Pour chaque Type, créez une vue native pour iOS et pour Android, ou réutilisez-en une depuis votre code natif. Les vues suivantes de type `lottie_animation` jouent une animation Lottie. La vue Android est un composable qui utilise la bibliothèque `com.airbnb.android:lottie-compose` :

<Tabs groupId="platform" queryString>
<TabItem value="ios" label="iOS (Swift)" default>

```swift showLineNumbers title="Swift"

struct LottieElementView: View {
    let animation: LottieAnimation?

    var body: some View {
        LottieView(animation: animation)
            .resizable()
            .looping()
    }
}
```

</TabItem>
<TabItem value="android" label="Android (Kotlin)">

```kotlin showLineNumbers title="Kotlin"

@Composable
fun LottieElement(animationFile: String) {
    val composition by rememberLottieComposition(LottieCompositionSpec.Asset(animationFile))
    LottieAnimation(
        composition = composition,
        iterations = LottieConstants.IterateForever,
    )
}
```

</TabItem>
</Tabs>

### Exigences et bonnes pratiques \{#requirements-and-best-practices\}

- **Dimensionnement** :
  - **Padding et alignement** : Assurez-vous que la vue native s'adapte au conteneur que vous avez alloué dans le Flow & Paywall Builder, en tenant compte du padding. Si la vue n'occupe pas toute la zone, elle apparaît par défaut dans le coin supérieur gauche de cette zone. Pour la déplacer, modifiez l'alignement dans la section **Layout** de l'élément personnalisé.
  - **Hauteur Hug** : Si la hauteur de l'élément personnalisé est définie sur **Hug**, une vue qui s'étire pour remplir l'espace disponible (comme une carte ou une liste paresseuse) va se réduire à zéro, ou s'étirer jusqu'à la hauteur de l'écran. Donnez plutôt à l'élément personnalisé une hauteur [**Fixed**](flow-custom-elements#add-and-configure).
- **Thème** : Les vues natives n'héritent pas des couleurs et polices de votre thème Flutter. Définissez-les dans le code natif.
- **Actions de flow** : La vue native ne peut pas exécuter des actions de flow, comme la transition vers l'écran suivant. Le contexte de l'élément peut envoyer des messages au flow, avec `sendMessage` sur iOS et `send` sur Android, mais ils sont réservés aux futures fonctionnalités du Flow & Paywall Builder. Gardez les boutons de navigation, les boutons d'achat et les autres boutons avec des actions de flow en dehors de l'élément personnalisé.
- **Éléments sélectionnables** : Gardez l'élément personnalisé en dehors des cartes produit et des autres [éléments sélectionnables](flow-selectable-elements). Lorsque la sélection change, la vue native peut perdre son état.
- **Gestion de la navigation** : Lorsque l'utilisateur passe à l'écran suivant, le SDK supprime la vue native de l'écran. Arrêtez ce que la vue a démarré, comme les sessions caméra, les lecteurs et les mises à jour de localisation :
  - **Vue SwiftUI** : Utilisez l'action `onDisappear`. Pour le travail asynchrone, utilisez `.task` : SwiftUI l'annule lorsque la vue disparaît.
  - **Composable** : Utilisez le bloc `onDispose` d'un `DisposableEffect`. Pour le travail asynchrone, utilisez `LaunchedEffect` : Compose l'annule lorsque le composable quitte la composition.
  - **`View` Android** : Remplacez `onDetachedFromWindow` dans votre sous-classe `View`, ou ajoutez un `View.OnAttachStateChangeListener` à la `View`.

  Lorsque l'utilisateur revient, ou sur Android après un changement de configuration tel qu'une rotation, le SDK rappelle le resolver, et la vue native démarre sans l'état de la précédente.
- **Vues UIKit** : Sur iOS, encapsulez-les dans `UIViewRepresentable`.
- **Carousels** : Sur Android, dans un [carousel](builder-containers#carousel), les vues natives de toutes les diapositives restent actives pendant que l'écran est ouvert, pas seulement la vue de la diapositive visible. Évitez les aperçus de caméra et les lecteurs avec son dans les carousels.

## Écrire un résolveur pour faire correspondre les éléments et vues personnalisés \{#write-a-resolver-to-match-custom-elements-and-views\}

Écrivez un résolveur pour chaque plateforme. Le résolveur reçoit le Type et l'ID d'un élément personnalisé et renvoie la vue native correspondante.

<Tabs groupId="platform" queryString>
<TabItem value="ios" label="iOS (Swift)" default>

Pour écrire un résolveur, faites en sorte qu'un type soit conforme au protocole `AdaptyUICustomElementsResolver` et implémentez la méthode `view(forType:id:context:)`.

Pour le Type `lottie_animation`, le résolveur suivant renvoie `LottieElementView`. L'ID désigne le fichier d'animation dans le bundle de l'application, par exemple `welcome_wave` :

```swift showLineNumbers title="Swift"

struct CustomElementsResolver: AdaptyUICustomElementsResolver {
    func view(
        forType type: String,
        id: String,
        context: AdaptyUICustomElementContext
    ) -> AnyView? {
        switch type {
        case "lottie_animation":
            // the ID names the animation file, such as welcome_wave.json
            guard let animation = LottieAnimation.named(id) else {
                return nil // no file for this ID: show the fallback
            }
            return AnyView(LottieElementView(animation: animation))
        default:
            return nil
        }
    }
}
```

Dans le cas `default`, retournez `nil`.

</TabItem>
<TabItem value="android" label="Android (Kotlin)">

Pour créer un resolver, implémentez l'interface `AdaptyCustomElementsResolver`. Sa méthode `resolve` renvoie la vue correspondante sous l'une des formes suivantes :

- **Un composable** : Retournez `AdaptyCustomElementContent.compose`, avec le composable dans sa lambda.
- **Une `View` Android** : Retournez `AdaptyCustomElementContent.view`, avec une fonction qui crée la `View`. Nommez le paramètre `factory` : `AdaptyCustomElementContent.view(factory = { context, _ -> ChartView(context) })`. Sans le nom, Kotlin passe une lambda de fin au paramètre optionnel `update`, et le code ne compile pas.

Pour le type `lottie_animation`, le résolveur suivant renvoie la [vue Lottie](#create-views-for-custom-elements). L'ID désigne le fichier d'animation dans le dossier `assets`, `android/app/src/main/assets`, par exemple `welcome_wave` pour `welcome_wave.json` :

```kotlin showLineNumbers title="Kotlin"

class CustomElementsResolver(context: Context) : AdaptyCustomElementsResolver {
    // the animation files in the assets folder, listed once
    private val animationFiles: Set<String> = try {
        context.assets.list("").orEmpty().toSet()
    } catch (e: IOException) {
        emptySet() // no list of files: every Lottie element shows the fallback
    }

    override fun resolve(type: String, id: String): AdaptyCustomElementContent? =
        when (type) {
            "lottie_animation" -> {
                // the ID names the animation file, such as welcome_wave.json
                val file = "$id.json"
                if (file in animationFiles) {
                    AdaptyCustomElementContent.compose { LottieElement(file) }
                } else {
                    null // no file for this ID: show the fallback
                }
            }
            else -> null
        }
}
```

Pour tout autre Type, retournez `null`.

</TabItem>
</Tabs>

Si vous [ajoutez un élément personnalisé avec un nouveau Type](flow-custom-elements#what-changes-require-an-app-release) après la sortie de l'application, les utilisateurs de la version publiée voient son fallback.

Le resolver doit respecter les exigences suivantes :

- **Données réseau et lecteurs** : Conservez les données réseau et les lecteurs dans l'état de la [vue native](#create-views-for-custom-elements), pas dans le resolver. Le SDK appelle le resolver plusieurs fois pendant que l'écran est ouvert. Le code du resolver s'exécute à nouveau à chaque appel, ce qui provoque la répétition des requêtes réseau et le redémarrage des lecteurs. La vue native conserve son état entre ces appels, de sorte que les données ne se chargent qu'une seule fois et que les lecteurs continuent de lire. Créez les lecteurs, sessions et requêtes réseau dans la vue native :
  - **Vue SwiftUI** : Créez les lecteurs, sessions et requêtes réseau dans `.task` ou un `@StateObject`, pas dans la valeur initiale d'une propriété `@State`. Swift évalue cette valeur initiale à nouveau chaque fois que le resolver crée la vue.
  - **Composable** : Créez les lecteurs et sessions dans `remember`, et les requêtes réseau dans `LaunchedEffect`.
  - **`View` Android** : Créez les lecteurs, sessions et requêtes réseau dans `onAttachedToWindow`.
- **Une vue native par élément personnalisé** : Certaines vues natives changent pendant que l'écran est ouvert, par exemple lorsque leurs données se chargent ou lorsque l'utilisateur appuie dessus. Implémentez cette logique dans la vue native elle-même, pas dans le resolver. Si le resolver retourne une vue différente pour le même élément personnalisé, la vue perd son état.
- **Une nouvelle `View` à chaque apparition** : Sur Android, créez une nouvelle `View` à chaque appel de `factory`. Le SDK appelle `factory` à chaque fois que l'élément personnalisé apparaît, par exemple lorsque l'écran s'ouvre, lorsque l'utilisateur revient à l'écran ou après une rotation.
- **Données de l'application** : Stockez un objet contenant les données, comme un `ObservableObject` ou un `StateFlow` avec une [série quotidienne](flutter-custom-element-lottie-animation), dans une propriété du resolver. Passez l'objet à la vue native et observez-le là :
  - **Vue SwiftUI** : Observez un `ObservableObject` avec `@ObservedObject`.
  - **Composable** : Collectez un `StateFlow` avec `collectAsState`, ou observez un `LiveData` avec `observeAsState`.
  - **`View` Android** : Observez l'objet dans `onAttachedToWindow`, et arrêtez dans `onDetachedFromWindow`.

  Une valeur que vous copiez dans le resolver, comme le nombre de jours de série, reste telle qu'elle était au moment où vous avez créé le resolver. Si votre code Dart possède les données, comme une série quotidienne, envoyez chaque nouvelle valeur vers le code natif via un [canal de plateforme](https://docs.flutter.dev/platform-integration/platform-channels) et mettez à jour l'objet là-bas.

### Définir les conditions du contenu de secours \{#set-conditions-for-fallback-content\}

<FlowCustomElementsFallbackConditions />

Pour une permission, ne renvoyez aucune vue uniquement si l'utilisateur l'a refusée avant l'ouverture de l'écran. Sur Android, `ContextCompat.checkSelfPermission` renvoie la même valeur, `PERMISSION_DENIED`, dans deux cas : avant que votre application n'ait demandé la permission pour la première fois, et après que l'utilisateur l'a refusée. Pour distinguer ces deux cas, enregistrez le résultat de la demande de permission et lisez cette valeur enregistrée dans le resolver. Si votre application n'a pas encore demandé la permission, renvoyez la vue native et demandez la permission à l'intérieur de la vue. Par exemple, demandez l'accès à la localisation lorsqu'une [vue de carte](flutter-custom-element-map#3-match-the-map-to-the-custom-element) apparaît, et affichez la carte dès que l'utilisateur accorde l'accès. Si vous ne renvoyez aucune vue et que l'utilisateur accorde l'accès par la suite, il verra toujours le fallback. Un changement de permission n'amène pas le SDK à rappeler le resolver. La vue native n'apparaît qu'après que le SDK rappelle le resolver, par exemple lorsque l'utilisateur revient sur l'écran.

## Transmettre le resolver au SDK \{#pass-the-resolver-to-the-sdk\}

Configurez le resolver une seule fois pour chaque plateforme, au lancement de l'application. Le SDK l'appelle dans chaque flow, y compris un flow intégré avec `AdaptyUIFlowPlatformView`. Les utilisateurs voient vos vues natives dans les nouveaux flows et tests A/B sans mise à jour de l'application. Ces vues affichent toujours les données propres à chaque utilisateur, comme une [série quotidienne](flutter-custom-element-lottie-animation), car elles les lisent depuis votre application.

<Tabs groupId="platform" queryString>
<TabItem value="ios" label="iOS (Swift)" default>

Dans `ios/Runner/AppDelegate.swift`, importez `AdaptyUI` et appelez `AdaptyUI.setCustomElementsResolver(_:)` dans la méthode `application(_:didFinishLaunchingWithOptions:)`. Conservez le reste de la classe `AppDelegate` tel quel :

```swift showLineNumbers title="ios/Runner/AppDelegate.swift"

// in application(_:didFinishLaunchingWithOptions:), before `return super.application(...)`
AdaptyUI.setCustomElementsResolver(CustomElementsResolver())
```

Si vous écrivez le resolver dans `AppDelegate.swift` également, importez aussi `AdaptyUIBuilder`.

</TabItem>
<TabItem value="android" label="Android (Kotlin)">

Appelez `AdaptyUI.setCustomElementsResolver` dans la méthode `onCreate` de votre classe `Application`. Si votre application n'a pas encore de classe `Application`, créez-en une :

```kotlin showLineNumbers title="Kotlin"

class App : Application() {
    override fun onCreate() {
        super.onCreate()
        AdaptyUI.setCustomElementsResolver(CustomElementsResolver(this))
    }
}
```

Dans `android/app/src/main/AndroidManifest.xml`, indiquez votre classe `Application` dans l'attribut `android:name` de `<application>`. Le template Flutter définit cet attribut à `${applicationName}`, qui correspond à la classe `Application` de base :

```xml showLineNumbers title="AndroidManifest.xml" {2}
<application
    android:name=".App"
    android:label="your_app">
    <!-- the rest of your application element -->
</application>
```

</TabItem>
</Tabs>

:::tip
Pour afficher la même vue dans chaque élément personnalisé d'un Type, passez une map de Types et de vues à la place d'un resolver. Sur iOS, la map est un dictionnaire `[String: AdaptyUICustomElementBuilder]`. Sur Android, passez la map à `AdaptyCustomElementsResolver.of`. Une map nécessite moins de code qu'un resolver, mais vous ne pouvez pas [définir des conditions pour le contenu de remplacement](#set-conditions-for-fallback-content).

```swift showLineNumbers title="Swift"
AdaptyUI.setCustomElementsResolver([
    "lottie_animation": .init { _, id, _ in LottieElementView(animation: .named(id)) },
])
```

```kotlin showLineNumbers title="Kotlin"
val appWideViews = mapOf(
    "confetti" to AdaptyCustomElementContent.compose { LottieElement("confetti.json") },
)
AdaptyUI.setCustomElementsResolver(AdaptyCustomElementsResolver.of(appWideViews))
```
:::

Vous ne pouvez pas attacher un resolver à un seul flow. Pour afficher des données que votre application n'a qu'au moment où elle ouvre un flow, envoyez les données à votre code natif avant l'ouverture du flow. Ensuite, lisez les données dans le resolver. Par exemple, un paywall affiche le [poids que l'utilisateur a saisi dans un flow précédent](flutter-custom-element-interactive-chart).

## Tester sur un appareil \{#test-on-a-device\}

Le Flow & Paywall Builder ne peut pas exécuter le code de votre application, donc son canvas n'affiche que le fallback. Une erreur dans la vue native peut faire planter l'application. Avant de publier l'application, testez chaque écran contenant un élément personnalisé sur un appareil iOS et sur un appareil Android :

1. Pour voir la dernière version publiée de chaque flow plutôt qu'une version mise en cache, enregistrez l'appareil en tant que [device de test](test-devices).
2. Sur l'appareil, lancez un build incluant le resolver. Ouvrez chaque écran contenant un élément personnalisé et vérifiez que la vue native s'affiche et s'adapte à l'élément personnalisé. Si la vue défile ou réagit aux glissements, testez ces gestes.
3. Si le fallback s'affiche à la place de la vue native, recherchez cet avertissement dans la console Xcode ou dans Logcat : `custom element <type>:<id> is not served by a resolver`. Vérifiez ensuite que :
   - Le Type et l'ID dans l'avertissement correspondent exactement à ceux de votre code, lettre par lettre.
   - Votre application dispose du fichier, des données ou des autorisations dont la vue a besoin.
   - Votre application définit le resolver au démarrage : dans la classe `AppDelegate` sur iOS, et dans la classe `Application` désignée par `AndroidManifest.xml` sur Android.

   Si l'avertissement n'apparaît pas, vérifiez que l'application utilise Adapty Flutter SDK 4.4 ou une version ultérieure, et que le [niveau de log](sdk-installation-flutter#logging) n'est pas `AdaptyLogLevel.error`.
4. Sur Android, si l'élément personnalisé reste vide, recherchez l'un de ces avertissements dans Logcat :
   - `custom element <type>:<id> is not served by a resolver` : L'élément personnalisé n'a pas de contenu de secours, et aucun résolveur ne retourne de vue pour lui. Vérifiez chaque élément de l'étape 3.
   - `content does not report its size` : Le composable n'a pas de hauteur propre. Donnez à l'élément personnalisé une hauteur [**Fixe**](flow-custom-elements#add-and-configure).

   Le SDK ne journalise l'avertissement de taille que pour les composables. Si une `View` Android reste vide sans avertissement, donnez également une hauteur **Fixed** à l'élément personnalisé.
5. Pour prévisualiser le paywall de secours, ne retournez aucune vue pour le Type et rouvrez l'écran.

Chaque exemple présente la configuration dans le builder et le code pour votre application :
