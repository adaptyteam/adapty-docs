Le skill growth-advisor répond à la question « que dois-je tester ensuite ? » à partir de vos propres chiffres d'abonnement. Votre outil de codage IA lit vos analytics, prix, placements, flows et tests A/B passés, évalue chaque partie de votre activité par rapport au marché, et vous restitue une liste courte d'hypothèses classées selon les sommes en jeu. Les hypothèses que vous conservez sont sauvegardées dans [AI Growth Advisor](autopilot), où votre équipe peut les consulter. Lorsque vous en choisissez une, le skill construit ce dont le test A/B a besoin, configure le test, et revient avec vous sur les résultats dès qu'ils sont disponibles.

:::note
growth-advisor ne modifie rien dans votre compte sans votre accord. Toutes les lectures sont en lecture seule, et chaque écriture — une copie de flow, un segment, un produit, un prix, un test A/B, une modification de placement — attend votre confirmation.
:::

## Ce que vous pouvez demander \{#what-you-can-ask\}

Parlez comme si vous briefiez un collègue. Inutile de nommer le skill :

```
Audit my app. What should I test next to grow revenue?

Revenue dropped last month. Why?

Is our annual plan too cheap in Germany?

My A/B test on the onboarding paywall ended. What now?

Where do users leave our onboarding?

I have three ideas: a weekly plan, a trial on annual, and a second placement.
Which one should I test first?

Which country refunds the most, and do people who start a trial renew better?

Here's our App Store link. Where are we losing money?

How did this week go?

What's in my backlog?

Check my app every Monday and tell me if something is off.
```

Une question sur vos chiffres obtient une réponse à partir de vos chiffres, sans audit associé. « Comment s'est passée cette semaine ? » déclenche un [bilan de santé](#health-check) plutôt qu'un audit. Une application sans données reçoit un plan de départ basé sur les médianes du marché issues du rapport State of Paywalls 2026 d'Adapty, avec chaque chiffre clairement identifié comme une estimation.

## Avant de commencer \{#before-you-start\}

- **Un compte Adapty avec des données** : le skill lit les mêmes analytics que votre tableau de bord. Sans données, il vous fournit un plan de départ. Sans compte, il travaille à partir de ce que vous lui envoyez (voir [Sans compte Adapty](#without-an-adapty-account)).
- **Un outil IA connecté à votre compte Adapty** : le skill fonctionne via le [CLI Adapty](developer-cli-analytics) ou le [serveur Adapty MCP](adapty-mcp). Il préfère le CLI, car l'audit effectue ses lectures via celui-ci. Utilisez un agent de code tel que Claude Code, Codex, Copilot CLI ou Gemini CLI, ou bien claude.ai, où le CLI nécessite une [configuration à chaque conversation](developer-cli-cowork). Avec MCP uniquement, le skill propose de configurer le CLI ; si vous refusez, il effectue les lectures via MCP et indique celles qui n'ont pas pu s'exécuter.

## Comment fonctionne l'audit \{#how-the-audit-works\}

Quand vous demandez quoi faire sans poser de question précise, le skill lance un audit. Il examine l'ensemble de l'activité sur les six derniers mois, pas uniquement ce qui a changé récemment : une faiblesse persistante coûte plus cher qu'un simple creux récent.

1. **Comment votre application génère des revenus** : le skill identifie le store qui rapporte le plus, votre marché principal, votre produit phare par chiffre d'affaires, et ce que chaque placement affiche actuellement. La réponse s'ouvre sur les chiffres : combien votre application gagne et d'où vient l'argent.
2. **Ce que vous avez déjà essayé** : le skill liste vos tests A/B passés sur les paywalls et les flows, avec leurs dates, audiences et résultats, et repère les paywalls qui ont tourné en parallèle sans aucun test. Vous n'avez pas besoin de saisir votre historique de tests ; la réponse les énonce comme des faits, vous n'avez qu'à corriger ce qui est inexact.
3. **Un tableau de bord** : le skill évalue chaque partie de l'activité comme solide, dans la moyenne, ou faible : d'où vient l'argent, le funnel de l'installation jusqu'au paiement, la répartition des offres, les renouvellements, les remboursements et la configuration de vos placements. Le funnel commence par la portée des paywalls — la part des installations qui voient un paywall — et note le passage vue paywall → essai ainsi que vue paywall → achat. Les remboursements sont ventilés par durée d'offre. Chacun de vos principaux pays est comparé à sa région, de sorte qu'un pays faible peut constituer la conclusion principale. Les conversions sont étalonnées sur la grille de référence du marché selon votre offre, région et catégorie, issue du State of Paywalls 2026 d'Adapty, et les renouvellements et remboursements sont comparés au State of In-App Subscriptions 2026 d'Adapty. Les points faibles sont classés par dollars mensuels en jeu.
4. **La cause** : le skill suit le signal le plus fort en descendant par store, canal d'attribution, durée d'offre, pays ou semaine, jusqu'à ce qu'un groupe l'explique. Avant d'incriminer le trafic ou un changement précis, il vérifie les autres causes possibles.
5. **Les écrans** : avant de dire quoi que ce soit sur un écran, le skill affiche le flow en direct et, pour un flow, lit son funnel pour trouver l'écran où les utilisateurs décrochent. Un paywall que votre application dessine elle-même nécessite une capture d'écran. L'audit liste les captures d'écran nécessaires sous **Send me screenshots** et indique quelle hypothèse chacune permet de vérifier.

## Ce que vous obtenez en retour \{#what-you-get-back\}

Le skill répond avec une courte synthèse et le tableau de bord, puis une liste d'hypothèses regroupées par placement, dans l'ordre où les tester. Chaque hypothèse indique pourquoi votre application en a besoin, quel résultat attendre et d'où vient cette estimation, ce que le changement représente en dollars par mois, combien de temps le test A/B prendrait avec votre volume d'achats, et qui fait quoi. Une hypothèse peut cibler tous les utilisateurs d'un placement ou un [segment](segments) spécifique, comme les anciens abonnés.

Lorsque vos chiffres indiquent un problème qu'une fonctionnalité Adapty résout, la réponse nomme cette fonctionnalité dans les prochaines étapes, à raison d'une au maximum par réponse. Par exemple, de faibles renouvellements avec des annulations volontaires amènent à mentionner [Retention Messaging](retention-messaging), une part élevée de remboursements fait apparaître [Refund Saver](refund-saver), et des essais payants qui convertissent bien moins bien que les essais organiques conduisent à envoyer les événements d'essai sur lesquels les réseaux publicitaires optimisent, comme le [Qualified trial](ua-facebook) de Meta.

## Votre backlog \{#your-backlog\}

Les hypothèses que vous conservez sont enregistrées dans le backlog de votre application dans Adapty. Votre équipe consulte le backlog sur la page [AI Growth Advisor](autopilot) du tableau de bord, et le skill repart de là lors de votre prochaine conversation.

Après chaque liste d'hypothèses, le skill vous demande lesquelles ajouter à votre backlog et lesquelles ignorer :

- **Ajouté** : Enregistré dans le backlog. Chaque test A/B que le skill met en place pour une hypothèse y est lié, ce qui permet au tableau de bord d'afficher le statut du test sur l'hypothèse.
- **Ignoré** : Enregistré et archivé avec la raison que vous donnez, afin que le skill ne le suggère plus. Précisez pourquoi vous l'ignorez : « nous l'avons déjà essayé » pousse le skill à proposer l'étape suivante de ce changement. Un « pas maintenant » reste dans le backlog.

Ne rien répondre ne sauvegarde rien. Le skill n'archive jamais une hypothèse de lui-même, même si elle semble ancienne.

Une hypothèse portant sur un placement qui n'existe pas encore, comme une offre de suivi, rejoint le backlog une fois que son flow est publié et que le skill a créé le placement correspondant.

À votre retour, le skill consulte le backlog avant de proposer quoi que ce soit de nouveau. Il vous indique d'abord ce qui est en attente : un test en cours prêt à être arrêté, un test terminé sans résultat, ou une hypothèse dont le flow ou le placement a disparu. Il ne propose pas une hypothèse qui se trouve déjà dans le backlog, en cours de test ou déjà testée. Pour consulter ce que vous avez enregistré, demandez « Qu'y a-t-il dans mon backlog ? ».

## Bilan de santé \{#health-check\}

« Comment s'est passée cette semaine ? » ou « Est-ce que tout va bien avec mon appli ? » déclenche un bilan de santé, pas un audit. Le skill compare les 7 derniers jours avec une semaine habituelle de votre appli, ou les 28 derniers jours avec les 28 précédents, pour le chiffre d'affaires, les nouveaux abonnements payants, les nouveaux essais, les installations et les remboursements. La réponse s'ouvre sur un verdict : une semaine normale, ou le changement le plus coûteux avec le jour où il a démarré et l'argent perdu jusqu'ici. Un bilan de santé ne vous compare pas au marché et ne propose pas d'hypothèses. Pour un changement, le skill propose d'en trouver la cause ; pour une semaine normale, de suggérer quoi tester ensuite.

Pour obtenir un bilan hebdomadaire, consultez [Planifier des vérifications récurrentes](growth-advisor-recurring-checks).

## Prix \{#prices\}

Le skill lit le prix de chaque produit dans chaque pays et store, tel que le store le facture, en devise locale. Il compare ensuite chaque prix à l'indice de prix d'Adapty issu du rapport State of In-App Subscriptions : du 10e au 90e percentile pour votre catégorie et votre offre, dans 22 pays. Pour les autres pays, le skill compare avec la région ou avec l'historique du pays lui-même.

À partir de là, le skill peut suggérer ces hypothèses de prix dans la même liste que les autres :

- **Augmenter ou baisser le prix de base** de votre offre principale sur votre marché principal.
- **Augmenter ou baisser le prix dans un pays** dont le tarif est décalé par rapport à votre marché principal. Pour un écart sur un seul marché, le skill vérifie d'abord que le paywall est dans la langue de ce marché.
- **Modifier la hiérarchie des offres** lorsque le tarif annuel est trop élevé ou trop bas par rapport aux tarifs hebdomadaires ou mensuels.

Le skill ne suggère une hausse de prix que sur les marchés de niveau 1, comme les États-Unis, le Royaume-Uni, l'Allemagne ou le Japon : dans la bibliothèque de tests A/B d'Adapty, la même hausse s'est révélée perdante ailleurs. Le nouveau prix part du tarif actuel appliqué par le store et vise un point de prix familier aux acheteurs, comme 38,99 €. Le skill ne consulte pas les prix des concurrents.

Le test A/B s'exécute sur une copie du produit, pas sur le produit en production. Le skill crée la copie, la pousse vers le store, configure ses prix, construit la copie du flow qui la vend, et met en place un segment de pays ainsi que le test A/B. Un prix gagnant est ensuite appliqué au produit original. Les abonnés existants conservent leur prix, sauf si vous demandez à les migrer.

Pour modifier un prix en production sans test, demandez-le explicitement. Le skill sauvegarde les prix actuels dans un fichier pour permettre leur restauration, prévisualise les nouveaux prix et vous indique quand chaque store les applique.

:::warning
Les prix ne peuvent être lus que pour un store connecté à Adapty. Sur l'App Store, cela nécessite la [clé API App Store Connect](app-store-connect-api-key), et pas seulement la clé d'achat intégré.
:::

## De l'hypothèse au test A/B \{#from-hypothesis-to-ab-test\}

Pour chaque hypothèse, le skill propose un test A/B et offre de le configurer. Avant de procéder, il vérifie que tout ce dont le test a besoin existe, et indique ce qui manque et qui doit le créer :

| Le test nécessite | Qui le réalise |
|---|---|
| Un flow modifié : nouveau design, nouveaux textes ou nouvelle sélection de produits | Le skill crée une copie du flow via le [skill flow-generator](flow-generator-skill), avec un seul changement par hypothèse, afin que le test montre l'effet de cette modification. Avant de publier la copie, le skill propose de la vérifier avec le [skill flow-audit](flow-audit-skill). Un flow ne rejoint un test qu'une fois publié. |
| Une nouvelle durée de plan | Le skill crée le produit et le pousse vers App Store Connect et Google Play Console, après que vous ayez confirmé ses identifiants de produit en store et son prix en USD. |
| Une copie de produit pour un test de prix | Le skill crée la copie, la pousse et fixe ses prix. Vous approuvez le nouvel identifiant de produit en store. |
| Un essai ou une offre | Vous le créez dans App Store Connect ou Google Play Console. Sur l'App Store, un essai nécessite un nouveau produit ; sur Google Play, c'est une offre sur le plan existant. Une fois que vous donnez au skill l'identifiant d'offre du store, il ajoute l'offre au produit dans Adapty. |
| Un paywall à partir de produits déjà dans Adapty | Le skill le crée. |
| Un paywall avec un nouveau design | Vous le créez dans le [Paywall Builder](adapty-paywall-builder). |
| Un segment | Le skill le crée via le skill audiences. |
| Un nouveau placement | Le skill le crée après que vous ayez approuvé son identifiant développeur. Votre application nécessite une modification du code et une mise en production pour le récupérer. |

Chaque élément créé par le skill attend votre validation. Lorsqu'un élément est à votre charge, la liste **Next steps** du skill l'indique, et le skill configure le test dès que vous lui confirmez que l'élément est prêt. Il ne configure jamais un test avec un élément qui n'existe pas encore.

Une fois tous les éléments en place, le [skill ab-tests](ab-tests-skill) crée le test en tant que brouillon. Avant de le démarrer, il vous montre précisément qui voit quoi. Un [test A/B](ab-tests) est l'option par défaut, et le seul moyen de mesurer l'impact du changement.

Pour afficher le changement sans test, demandez-le. Le skill peut l'afficher sur un nouveau placement, ou pour une partie ou la totalité des utilisateurs d'un placement existant. Avant de modifier un placement existant, le skill sauvegarde le placement dans un fichier pour vous permettre de le restaurer. Il répertorie également tout test A/B en cours sur le placement. Le changement n'affecte pas ce test. Dans le backlog, l'hypothèse apparaît alors comme appliquée sans test. Une fois le délai prévu écoulé, le skill compare les semaines avant et après le changement et vous demande si cela a fonctionné.

## Quand un test A/B se termine \{#when-an-ab-test-ends\}

Dites au skill qu'un test s'est terminé. Il retrouve le test, affiche les revenus et la probabilité d'être le meilleur de chaque variante, et vous demande quelle variante a gagné. La variante en tête n'est pas forcément la gagnante tant que vous ne le confirmez pas : avec moins d'environ 200 achats par variante, le test n'est pas encore concluant. Si le test est toujours en cours, le skill propose de l'arrêter avec votre variante gagnante, puis suggère la prochaine hypothèse pour ce placement. Le résultat que vous indiquez est enregistré sur l'hypothèse comme gagné, perdu ou non concluant.

Pendant qu'un test est en cours, le skill indique à quelle distance chaque variante se trouve d'environ 200 achats, sans jamais révéler laquelle est en tête.

## Sans compte Adapty \{#without-an-adapty-account\}

Envoyez un lien App Store ou Google Play, le code de l'application, ou des captures d'écran de votre onboarding et de votre paywall, et demandez comment générer plus de revenus. Le skill répond en détail à partir de ce que vous avez envoyé, des médianes du marché et de la bibliothèque de tests A/B d'Adapty :

- **Un lien vers le store** : le skill lit la catégorie, les abonnements dans la liste des achats intégrés, les langues et ce que les avis disent sur le paiement.
- **Des captures d'écran** : le skill lit les durées des formules, la formule présélectionnée, l'essai gratuit et le bouton d'achat.
- **Le code de l'application** : le skill lit les identifiants de produits, les écrans de paywall et d'onboarding, leur contenu dans chaque langue et les autres endroits où le paywall s'ouvre.

La skill analyse les écrans avec les skills paywall-teardown et onboarding-teardown. Les prix et la conversion nécessitent vos propres chiffres, c'est pourquoi la dernière étape suivante propose de configurer Adapty dans l'application. Une fois la configuration effectuée, la prochaine réponse s'appuiera sur vos propres données.

## Limites \{#limits\}

- **Pas de données de dépenses publicitaires** : le skill peut répartir les installations, les essais et les revenus par canal d'attribution, mais pas les dépenses ni le ROAS. Pour cela, utilisez le [skill adapty-attribution](developer-cli-attribution-skill).
- **Certains tests A/B restent dans le tableau de bord** : le skill lit les résultats des tests A/B de paywall et de flow classiques. Pour les tests portant sur plusieurs placements et les tests d'onboarding, il indique le nom du test et vous consultez les résultats dans le tableau de bord. Le skill ne peut pas non plus configurer un test sur plusieurs placements : il vous donne les étapes à suivre dans le tableau de bord.
- **Benchmarks par région et grande catégorie** : les médianes du marché couvrent une région et une catégorie, pas votre niche exacte, et votre catégorie ne figure pas dans vos données Adapty. Indiquez au skill votre catégorie App Store pour un résultat plus proche. Si vous avez votre propre benchmark, collez-le : le skill l'utilise et indique sa provenance.
- **Pas de prix concurrents** : le skill compare vos prix avec l'indice de prix Adapty, pas avec ce que pratiquent les autres applications.
- **Les essais et les offres sont créés dans le store** : le skill ne peut pas créer un essai ou une offre dans App Store Connect ou Google Play Console. Il vous donne les étapes à suivre et ajoute l'offre dans Adapty une fois que vous lui avez fourni l'identifiant de l'offre du store.

## Retours à Adapty \{#feedback-to-adapty\}

Après chaque réponse utilisant vos données Adapty, le skill envoie à Adapty une courte note indiquant le type de question à laquelle il a répondu et si quelque chose l'a gêné. La note ne contient aucun chiffre, nom ou mot de votre conversation, uniquement l'identifiant de votre application. Le skill indique ensuite, en une seule ligne, qu'il a envoyé la note. Pour arrêter les notes pour le reste de la conversation, demandez à l'agent de ne plus envoyer de retours.

Pour interroger vos analytics vous-même, sans le skill, consultez la [référence CLI analytics](developer-cli-analytics). Pour récupérer des analytics depuis un serveur ou une tâche planifiée, sans possibilité de connexion via un navigateur, utilisez l'[API Export Analytics](export-analytics-api) avec une clé API secrète.
