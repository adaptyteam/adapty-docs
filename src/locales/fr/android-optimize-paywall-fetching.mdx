Une récupération de paywall fiable sur Android remplit trois conditions : un affichage rapide, le renvoi du paywall ciblé par audience, et un repli gracieux lorsque le réseau est lent. Les règles ci-dessous couvrent le timing, la mise en cache et les patterns de secours pour y parvenir.

:::tip
Ces règles supposent que `Adapty.activate()` et `Adapty.identify()` ont déjà été résolus. Voir [Ordre des appels dans le SDK Android](android-sdk-call-order).
:::

## Règles et pièges \{#rules-and-pitfalls\}

| Faire ceci | Ne pas faire ceci | Pourquoi |
|---|---|---|
| Récupérez le placement que vous êtes sur le point d'afficher, ou préchauffez le cache avec [`preloadFlows`](#preload-placements) (SDK 4.1+). | Lancez vos propres appels `getFlow` concurrents au démarrage. | Un burst de préchargement maison bloque le thread principal et provoque un écran noir. `preloadFlows` est conçu pour ça et exécute le lot en parallèle pour vous. |
| Appelez `getPaywall` après que l'attribution a eu le temps de se résoudre — par exemple, 1 à 2 secondes après `activate` ou après le déclenchement de `setOnProfileUpdatedListener`. | Appelez `getPaywall` dans `Application.onCreate()`. | L'attribution n'est pas encore arrivée. Le paywall se résout par rapport à l'audience par défaut et contourne silencieusement les segments et la personnalisation ASA. |
| Définissez un `loadTimeout` et configurez un [paywall de secours](fallback-paywalls) pour chaque placement. | Attendez `getPaywall` indéfiniment. | Sans délai d'expiration, les utilisateurs avec une mauvaise connexion voient un écran vide jusqu'à ce que le réseau réponde — ou ferment l'application. |

Consultez [Récupérer les paywalls et les produits](fetch-paywalls-and-products-android) pour la référence des paramètres `fetchPolicy` et `loadTimeout`, et [Placements](placements) pour choisir le bon placement.

## Précharger les placements \{#preload-placements\}

:::info
Ces méthodes sont disponibles à partir de la version 4.1 du SDK.
:::

`preloadFlows` et `preloadOnboardings` écrivent le JSON du placement dans le cache du SDK à l'avance — une requête par placement, et rien de plus. Malgré leurs noms, aucune de ces méthodes ne récupère la mise en page de l'interface du flow ni ses médias.

Un appel ultérieur à `getFlow` ou `getOnboarding` ne lit ce cache que si vous passez `AdaptyPlacementFetchPolicy.ReturnCacheDataElseLoad` ou `ReturnCacheDataIfNotExpiredElseLoad(maxAgeMillis)`. La politique par défaut, `ReloadRevalidatingCacheData`, interroge le réseau à chaque appel : un préchargement associé à une récupération avec la politique par défaut génère donc une requête supplémentaire sans gain — la copie mise en cache ne sert que de solution de repli hors ligne.

Utilisez cette méthode lorsque vous savez quels placements la session va nécessiter, mais que vous ne souhaitez pas les afficher tout de suite — par exemple, juste après la résolution de `activate` et `identify`, pour le paywall derrière un bouton que l'utilisateur n'a pas encore appuyé.

Adapty.getFlow(

    // ...
}

**Paramètres :**

- `placementIds` (requis) : les placements à précharger. Les identifiants vides et dupliqués sont ignorés.
- `locale` (facultatif, uniquement pour `preloadOnboardings`) : la locale de l'onboarding à mettre en cache.
- `loadTimeout` (facultatif) : délai d'attente appliqué à chaque placement dans le lot, et non au lot dans son ensemble. Par défaut à 5 secondes ; les valeurs inférieures à 1 seconde sont relevées à 1 seconde.

**Comportements à connaître :**

- Le callback se déclenche uniquement après que tous les placements ont été tentés, et il signale les échecs par placement ensemble. L'échec d'un placement n'empêche pas les autres.
- Si un placement expire, rencontre une erreur serveur ou échoue avec une erreur réseau, le SDK bascule sur les variantes de secours pour ce placement. Les autres échecs sont signalés tels quels.
- Le préchargement se contente de réchauffer le cache. Il ne renvoie aucun contenu — vous appelez toujours `getFlow` ou `getOnboarding` pour afficher le contenu.

### Ce que couvre un préchargement \{#what-a-preload-covers\}

Un flow s'affiche à l'écran par couches, et un préchargement ne couvre que la première :

| Couche | Récupérée par | Réchauffée par un préchargement |
|---|---|---|
| Placement JSON — la variation choisie, ses identifiants de produits et le Remote Config | `getFlow` | Oui |
| Mise en page UI — la structure, le style et le texte de l'écran | `getFlowConfiguration` | Non |
| Images, y compris la vignette qui remplace un élément vidéo | `getFlowConfiguration`, en arrière-plan | Non |
| Fichiers vidéo | Le lecteur système, au moment du rendu de l'écran | Non mis en cache par le SDK |

`getFlowConfiguration` attend le layout, donc sur un cache froid cet appel représente quand même un aller-retour réseau après un préchargement. Une fois que le SDK a le layout, il lance la mise en cache des images indépendamment de l'appel : cela ne bloque pas l'affichage de l'écran, et aucun callback ni erreur ne signale la fin de l'opération.

### Identifier quel placement a échoué \{#find-out-which-placement-failed\}

Le callback reçoit une `AdaptyPreloadPlacementsError` couvrant l'ensemble du lot, avec le code `REQUEST_FAILED` (2005). Pour voir les échecs individuels, lisez sa propriété `preloadErrors` — une map indexée par ID de placement :

```kotlin showLineNumbers
Adapty.preloadFlows(listOf("onboarding", "main_paywall")) { error ->
    if (error is AdaptyPreloadPlacementsError) {
        error.preloadErrors.forEach { (placementId, placementError) ->
            // log or retry the individual placement
        }
    }
}
```

`preloadErrors` existe uniquement sur `AdaptyPreloadPlacementsError`, donc vérifiez d'abord le type — tout autre `AdaptyError` provient d'autre chose qu'une défaillance par placement.

### Ignorer la segmentation d'audience \{#skip-audience-segmentation\}

Pour préchauffer le cache sans attendre la segmentation d'audience, utilisez les variantes d'audience par défaut. Aucune des deux n'accepte de `loadTimeout` :

```kotlin showLineNumbers
Adapty.preloadFlowsForDefaultAudience(listOf("main_paywall")) { error -> }
Adapty.preloadOnboardingsForDefaultAudience(listOf("intro")) { error -> }
```

## Optimiser pour une mauvaise connectivité \{#tune-for-poor-connectivity\}

Pour les marchés où la connectivité est régulièrement mauvaise (zones rurales, transports en commun, régions affectées par le routage) :

- Définissez `fetchPolicy` sur `AdaptyPlacementFetchPolicy.ReturnCacheDataElseLoad` pour chaque récupération, sauf la toute première.
- Configurez un [paywall de secours](fallback-paywalls) pour chaque placement dans l'Adapty Dashboard.
- Définissez `loadTimeout` entre 3 et 5 secondes et acceptez le paywall de secours lorsque le délai expire.
- Ne bloquez pas l'affichage du paywall sur `getProfile`. Appelez `getPaywall` indépendamment pour qu'un profil lent ne bloque pas l'interface.
