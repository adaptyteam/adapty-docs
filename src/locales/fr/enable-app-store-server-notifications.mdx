Le SDK Adapty signale les achats effectués dans votre application. Les notifications serveur signalent les changements qui se produisent en dehors de l'application, par exemple :

- Un abonnement se renouvelle.
- Un utilisateur désactive le renouvellement automatique.
- Un paiement échoue en raison d'un problème de facturation.
- Un abonnement expire.
- Un utilisateur demande un remboursement. [Refund Saver](refund-saver) répond à la demande.
- Apple rembourse un achat.

Entrez l'URL de notification d'Adapty dans App Store Connect, puis vérifiez que les notifications parviennent bien à Adapty.

## Saisir l'URL de notification dans App Store Connect \{#enter-the-notification-url-in-app-store-connect\}

## Vérifier que les notifications parviennent à Adapty \{#check-that-notifications-reach-adapty\}

Pour confirmer que les notifications parviennent à Adapty, effectuez un [achat en sandbox](test-purchases-in-sandbox). Vérifiez ensuite le statut de la section **App Store server notifications** dans Adapty. L'achat apparaît dans Adapty même sans notifications, car le SDK le signale. Une fois qu'Apple envoie une notification concernant l'achat, Adapty fait passer le statut de **Waiting** à **Active**. Une notification de test envoyée par Apple ne modifie pas le statut.

Le statut indique alors depuis combien de temps la dernière notification est arrivée :

- **Active** : il y a moins de 24 heures.
- **Delayed** : il y a entre 24 et 72 heures.
- **Stalled** : il y a 72 heures ou plus.

**Delayed** et **Stalled** ne signifient pas forcément que quelque chose est cassé : dans une application avec peu d'abonnés, il peut se passer des jours sans aucune notification. **Active** indique seulement que des notifications parviennent à l'URL.

Pour vérifier que les notifications concernent bien votre application, contrôlez la configuration :

1. Dans App Store Connect, ouvrez la page **App Information** de votre application.
2. Assurez-vous que **Production Server URL** et **Sandbox Server URL** correspondent bien à l'URL indiquée dans Adapty.
3. Effectuez un autre achat en sandbox et vérifiez que le statut affiche **Active**.

## Transmettre les notifications à un autre serveur \{#raw-events-forwarding\}

Si un autre serveur a besoin des notifications Apple, Adapty peut les lui transmettre. Dans Adapty, rendez-vous dans [**App settings** > **iOS SDK**](https://app.adapty.io/settings/ios-sdk). Dans la section **App Store server notifications**, saisissez l'URL de ce serveur dans le champ **URL for forwarding raw Apple events**, puis cliquez sur **Save**.

<ZoomImage id="app-settings-forwarding-url.webp" width="700px" />

Adapty transfère les notifications reçues d'Apple vers l'autre serveur. Si vous renseignez l'URL de notification d'Adapty dans le champ **Sandbox Server URL** d'App Store Connect, Adapty transfère également les notifications sandbox. Le corps transféré conserve la charge utile signée d'Apple telle quelle, afin que l'autre serveur puisse vérifier la signature. Adapty ne transmet pas les en-têtes de requête d'Apple.

Adapty ne transfère pas :

- Les achats que le SDK signale sans notification d'Apple.
- Une notification de test d'Apple.
- Une notification qu'Adapty a déjà reçue au cours de la dernière heure.

Pour éviter une boucle, ne renvoyez pas les notifications transférées vers l'URL de notification. N'entrez pas non plus d'URL Adapty dans le champ **URL for forwarding raw Apple events**.

Si votre backend doit conserver son URL dans App Store Connect, [transmettez les notifications à Adapty depuis votre backend](forwarding-events-to-adapty) à la place.

## Authenticité des notifications \{#notification-authenticity\}

Traitez l'URL de notification comme un identifiant confidentiel. Adapty identifie l'application par l'URL seule, donc toute personne disposant de cette URL peut envoyer un payload à cette adresse.

Une notification de test ne crée jamais d'événement dans le [Fil d'événements](event-feed), quelle qu'en soit la source.
