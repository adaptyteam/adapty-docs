Le panneau **Interactions** vous permet de définir comment les éléments du flow réagissent aux événements — tels que les appuis, les apparitions d'éléments et les soumissions de formulaires. Pour chaque événement, vous assignez une ou plusieurs actions : naviguer entre les écrans, afficher ou masquer des éléments, ouvrir des URLs, définir des variables, etc. Utilisez des conditions pour personnaliser le flow en fonction des données utilisateur.

Chaque interaction suit une chaîne en trois parties :

1. **Élément** : Le composant d'écran qui déclenche l'interaction — un bouton, une réponse à un quiz, un champ de saisie, ou autre chose.
2. **Déclencheur** : L'événement qui active la logique, comme un appui, l'apparition d'un élément, ou la soumission d'un formulaire.
3. **Action** : La tâche que le flow exécute en réponse. Un seul déclencheur peut enchaîner plusieurs actions.

## Configurer les interactions \{#set-up-interactions\}

Pour configurer une interaction :

1. Sélectionnez un élément à l'écran ou dans le panneau **Layers**.
2. À droite, passez au panneau **Interactions** et cliquez sur **Add trigger**.

<ZoomImage id="add-trigger.webp" width="500px" alt="Bouton Add trigger" />

3. Dans la section **Button triggers**, sélectionnez le [type de déclencheur](#trigger-types).

<ZoomImage id="trigger-type.webp" width="500px" alt="Sélection du type de déclencheur" />

4. Cliquez sur **Add action**, cliquez sur le nom de l'action, puis sélectionnez un [type d'action](#action-types) dans le menu déroulant de la fenêtre **Edit action**.

<ZoomImage id="add-action.gif" width="500px" alt="Add action button" />

5. Configurez les propriétés de l'action en fonction du [type d'action](#action-types) sélectionné.
6. Si nécessaire, cliquez sur **Add action** pour ajouter d'autres actions pour le même déclencheur.

## Types de déclencheurs \{#trigger-types\}

Les déclencheurs s'activent en réponse aux actions de l'utilisateur, aux changements d'état des éléments ou au chargement de l'écran. **On screen appear** est universel ; les autres sont spécifiques à un élément.

| Déclencheur | Se déclenche quand... | Pris en charge sur |
|---|---|---|
| **On screen appear** | L'écran se charge | Tous les éléments |
| **On tap** | L'utilisateur appuie sur l'élément | [Boutons](paywall-buttons), [options de quiz](onboarding-quizzes), [bascules](builder-toggles), [comptes à rebours](flow-timer), [vidéos, images et icônes](custom-media), [texte](onboarding-text), [conteneurs, carrousels et feuilles de bas de page](builder-containers), [onglets](builder-tabs), [produits](paywall-product-block) |
| **On changed** | L'utilisateur modifie la valeur de l'entrée (saisie, sélection d'une date ou d'une heure) | Tous les [éléments de saisie](builder-inputs-and-forms) |
| **On submit** | L'utilisateur soumet une saisie de texte en appuyant sur Entrée ou Terminé sur le clavier | [Saisies textuelles](builder-inputs-and-forms) |
| **On timer end** | Un élément [Compte à rebours](flow-timer) atteint zéro | [Compte à rebours](flow-timer) |
| **On playback finished** | Une [Vidéo](custom-media) arrive à sa fin | [Vidéo](custom-media) |
| **On load complete** | Une barre de progression atteint 100 % | [Barres de progression](builder-loaders-and-progress-bars#run-actions-when-a-progress-bar-is-full) |

Pour les éléments sans interactions natives (comme un [spinner](builder-loaders-and-progress-bars#spinners)), **On screen appear** est le seul déclencheur disponible.

## Types d'actions \{#action-types\}

### Naviguer vers un écran \{#navigate-to-screen\}

Il s'agit de l'action principale pour déplacer les utilisateurs entre les écrans. Vous définissez l'écran de destination et, optionnellement, ajoutez une [animation de transition](flow-screen-transitions).

Pour amener les utilisateurs vers un autre écran quelques secondes après l'ouverture de l'écran actuel, [retardez une action **Navigate to Screen** sous le déclencheur **On Screen Appear**](flow-screen-transitions#move-users-to-another-screen-automatically).

Pour une navigation dynamique, consultez [Navigation et branchement](onboarding-navigation-branching) ou la section [Actions conditionnelles](#conditional-actions).

<ZoomImage id="navigate-to-screen-settings.webp" width="300px" alt="Fenêtre de modification d'action pour Accéder à l'écran avec Paywall comme destination, Glisser vers le haut avec Rebond en douceur, une durée de 400 ms et aucun délai" />

### Naviguer vers l'écran suivant \{#navigate-next\}

Passe l'utilisateur à l'écran suivant dans l'ordre des écrans du flow. Utilisez cette option pour les flows linéaires, où l'ordre des écrans dans l'éditeur correspond à l'ordre dans lequel vous souhaitez que les utilisateurs les voient.

La transition vers l'écran suivant utilise toujours l'animation push par défaut. Pour [personnaliser l'animation](flow-screen-transitions#customize-a-transition), changez l'action en **Navigate to screen**.

### Revenir en arrière \{#navigate-back\}

Renvoie l'utilisateur à l'écran précédent dans son historique de navigation, plutôt qu'à l'écran précédent dans la séquence.

La transition retour utilise [la même animation](flow-screen-transitions) que la transition vers l'écran actuel, jouée à l'envers.

### Ouvrir une URL \{#open-url\}

:::tip
Utilisez les [liens en ligne](onboarding-text#inline-link) pour insérer des liens dans du texte courant.
:::

Ouvre une adresse web spécifique. Utilisez cette action pour envoyer les utilisateurs vers des pages web, des articles ou des profils de réseaux sociaux en dehors des écrans natifs de votre application.

Pour cette action, vous pouvez configurer deux paramètres :
- **URL address** : Définissez une URL. Vous pouvez également la rendre dynamique — par exemple, pour rediriger les utilisateurs vers différentes pages selon leur réponse à un quiz ou les données qu'ils ont soumises. Pour cela, cliquez sur <Inline id="variable.webp" alt="Variable icon" /> et sélectionnez la variable à utiliser. Pour définir une URL différente pour une locale spécifique, modifiez la valeur correspondante dans le [panneau **Localizations**](add-paywall-locale-in-adapty-paywall-builder#set-locale-specific-action-urls).
- **Open in external browser** : Définissez où vous souhaitez ouvrir les liens externes. Par défaut, ils s'ouvrent dans un navigateur intégré à l'application pour maintenir les utilisateurs dans l'app. Cochez la case **Open in external browser** si vous souhaitez ouvrir les liens dans un navigateur externe.

<ZoomImage id="open-url.webp" width="500px" alt="Open URL" />

### Fermer le flow \{#close-flow\}

Ferme le flow en cours.

Cette action ne dispose pas de paramètre d'animation. Votre application est responsable de la transition entre le flow et votre interface native.

### Afficher/masquer des éléments \{#showhide-elements\}

Affiche ou masque un élément spécifique à l'écran.

Cette action remplace l'état initial défini dans **Visibility** dans le panneau **Design**. Si **Visibility** est réglé sur **Hide**, l'action **Show element** fera apparaître l'élément.

Vous pouvez [retarder le changement ou l'animer](flow-show-hide-animations), par exemple pour afficher un bouton de fermeture quelques secondes après l'ouverture de l'écran.

:::important
Une action **Show element** ou **Hide element** sans élément cible [bloque la prévisualisation et la publication](flow-common-issues#a-flow-wont-preview-or-publish). Sélectionnez une cible ou supprimez l'action.
:::

<YouTube id="3w3YSOmI3tQ" />

### Démarrer le chargeur \{#start-loader\}

Démarre une barre de progression dont l'option **Autostart** est désactivée. Utilisez-la pour [enchaîner les barres de progression les unes après les autres](builder-loaders-and-progress-bars#play-progress-bars-one-after-another).

### Afficher une alerte \{#show-alert\}

Affiche une fenêtre contextuelle native qui peut être fermée. La fenêtre ne met pas le flow en pause. Les actions en file d'attente avec l'alerte continuent de s'exécuter pendant l'affichage de celle-ci.

Pour les alertes, vous devez configurer leur **Title** et leur **Message**. Dans les deux cas, vous pouvez utiliser des variables pour rendre le contenu dynamique. Pour cela, cliquez sur <Inline id="variable.webp" alt="Variable icon" /> et sélectionnez la variable souhaitée.

:::important
Une action **Show alert** avec une configuration vide ou incomplète [bloque la prévisualisation et la publication](flow-common-issues#a-flow-wont-preview-or-publish). Renseignez les deux champs ou supprimez l'action.
:::

<ZoomImage id="show-alert.webp" width="500px" alt="Show alert" />

### Définir une variable \{#set-variable\}

Met à jour la valeur d'une variable dans le flow. Avant d'ajouter cette action, créez des variables dans le panneau **Variables** à gauche (voir [Variables](onboarding-variables)).

Cliquez sur **Add variable** et définissez autant de variables et de valeurs que nécessaire.

Pour [basculer un élément vers un état personnalisé](builder-element-states#switch-an-element-to-a-custom-state-on-tap) au tap, utilisez cette action pour définir une variable. Basez ensuite la condition de l'état sur cette variable.

:::important
Une action **Set variable** sans affectation [bloque la prévisualisation et la publication](flow-common-issues#a-flow-wont-preview-or-publish). Configurez au moins une affectation ou supprimez l'action.
:::

<ZoomImage id="set-variable.webp" width="500px" alt="Set variable" />

### Achat \{#purchase\}

Déclenche un flux d'achat directement depuis un bouton ou une interaction dans votre onboarding. Utilisez cette action pour permettre aux utilisateurs de s'abonner ou d'acheter un produit sans quitter le flow.

Vous pouvez configurer deux comportements pour cette action :
- **In-App Store** : Lance un achat natif. Définissez **Product** sur un produit spécifique, ou sur `products.selectedProduct` pour la sélection actuelle de l'utilisateur sur l'écran.
- **Web Payment** : Redirige l'utilisateur vers un [paywall web](web-paywall) au lieu de déclencher un achat natif. Utilisez cette option lorsque vous souhaitez gérer la transaction en dehors de l'application, par exemple pour des offres d'abonnement web.

Pour un achat **In-App Store**, vous pouvez [configurer des actions de suivi pour chaque résultat d'achat](respond-to-purchase-outcomes#add-actions-for-a-result). Par exemple, déclenchez **Navigate to Screen** en réponse à **When succeeded** pour afficher l'écran suivant aux acheteurs.

:::important
Une action **Purchase** sans **Product** ni **Web Paywall URL** cible [bloque la prévisualisation et la publication](flow-common-issues#a-flow-wont-preview-or-publish). Assignez une cible ou supprimez l'action.
:::

<ZoomImage id="onboarding-purchase-action.webp" width="500px" alt="Configuration de l'action d'achat dans la fenêtre Modifier l'action" />

### Restaurer les achats \{#restore-purchases\}

Déclenche le flow de restauration des achats sur l'appareil. Les utilisateurs appuient sur ce bouton lorsqu'ils ont déjà acheté un abonnement sur un autre appareil ou après avoir réinstallé l'application, et qu'ils ont besoin de récupérer l'accès à leurs produits.

Adapty gère la restauration via le flow natif du store. Vous pouvez [configurer les actions de suivi pour chaque résultat de restauration](respond-to-purchase-outcomes#respond-to-a-purchase-restoration) : **When restore completed** et **When restore failed**.

L'action **Restore purchases** est également préconfigurée sur le lien **Restore** dans le préréglage de bouton **Links** (voir [Configurer les achats](paywall-product-block#restore-purchases)).

### Sélectionner un produit \{#select-product\}

Définit quel produit est sélectionné dans un groupe de produits à l'écran. Utilisez cette action quand un élément autre que la carte produit doit changer la sélection — par exemple, un toggle qui fait basculer l'utilisateur entre un abonnement annuel et un abonnement hebdomadaire.

Quand l'action s'exécute, la sélection se déplace vers le produit cible. La mise en surbrillance de la carte, tout texte lié à `products.selectedProduct`, et la cible de l'action [Acheter](#purchase) suivent toutes la nouvelle sélection.

Pour cette action, définissez **Product** sur l'élément produit cible. Le sélecteur n'affiche que les éléments produits appartenant à un [groupe sélectionnable](flow-selectable-elements) de produits sur le même écran. Si l'écran comporte plusieurs groupes de produits, le sélecteur liste les produits valides de tous ces groupes. Les produits provenant d'autres écrans, les éléments produits hors d'un groupe et les autres types d'éléments n'apparaissent pas. Chaque produit est affiché sous son titre de produit Adapty plutôt que sous le nom de son élément.

<ZoomImage id="select-product-action.webp" width="500px" alt="Sélectionner un produit dans la fenêtre Modifier l'action avec le sélecteur de produits affichant les fiches produits" />

Vous pouvez aussi ajouter **Select product** dans une [action conditionnelle](#conditional-actions) — par exemple, pour sélectionner un produit quand un interrupteur est activé et un autre quand il est désactivé.

**Select product** n'est pas disponible dans deux endroits :

- **Dans les composants réutilisables** : La sélection de produit fonctionne par écran, donc une action dans un composant ne peut pas résoudre un produit. Si une action enregistrée se retrouve dans un composant, le champ **Product** affiche un avertissement à la place du sélecteur.
- **Sur le déclencheur On tap d'une carte produit** : Appuyer sur une carte la sélectionne déjà, donc une sélection explicite sur cette même interaction entrerait en conflit. L'action reste disponible sur cette carte pour d'autres déclencheurs, et sur tous les autres éléments.

:::important
Une action **Select product** [bloque la prévisualisation et la publication](flow-common-issues#a-flow-wont-preview-or-publish) lorsque le produit cible est manquant, se trouve sur un autre écran, ou n'appartient plus à un groupe de produits. Assignez un produit valide ou supprimez l'action.
:::

### Demander l'autorisation \{#request-permission\}

Invite l'utilisateur à autoriser les notifications push, par exemple sur un écran d'onboarding qui explique à quoi servent les notifications. Votre application affiche la boîte de dialogue système et renvoie la réponse de l'utilisateur au flow. Le flow exécute ensuite les actions de la section **After response**.

Vous pouvez ajouter cette action aux déclencheurs **On Tap** et **On Screen Appear**. Dans la fenêtre **Edit action**, la ligne **Permission** affiche **Push notifications**, seule autorisation demandée par cette action.

<ZoomImage id="request-permission-action.webp" width="500px" alt="Action Demander une autorisation dans la fenêtre Modifier l'action avec Notifications push comme autorisation et Naviguer Suivant dans Après la réponse" />

Les actions de la section **After response** s'exécutent après que l'utilisateur a répondu, qu'il ait accordé ou refusé la permission. Une nouvelle action **Request permission** commence par **Navigate Next** dans cette section. À l'intérieur de la section, vous ne pouvez pas ajouter d'action **Purchase**, **Restore purchases** ou une autre action **Request permission**. Si vous supprimez toutes les actions de la section, le flow reste sur l'écran après la réponse de l'utilisateur. Sans actions **After response**, le flow envoie également la demande à chaque fois que l'écran s'affiche, y compris après un **Navigate back**, et à chaque appui.

Lorsque le système n'affiche pas la boîte de dialogue, par exemple parce que l'utilisateur a déjà autorisé les notifications, votre application répond immédiatement et le flow exécute aussitôt les actions **After response**. Si ces actions quittent l'écran, celui-ci n'apparaît qu'un instant. La fréquence à laquelle le flow envoie la demande dépend du déclencheur :

- **On Screen Appear** : le flow envoie la requête dès que l'écran apparaît. Il ne la renvoie pas si l'utilisateur revient à l'écran via **Navigate back**.
- **On Tap** : le flow envoie la requête à chaque appui. Tant qu'une requête attend une réponse, le flow n'en envoie aucune autre, que ce soit depuis cet élément ou depuis n'importe quel autre.

Sur un écran qui explique les notifications, placez l'action sur le déclencheur **On Tap** de son bouton, afin que les utilisateurs lisent l'écran avant que la boîte de dialogue ne le recouvre. Utilisez **On Screen Appear** lorsqu'un écran précédent a déjà expliqué la demande.

:::warning
**Configurez votre application pour répondre à la demande avant de publier le flow.** Le SDK Adapty n'affiche pas la boîte de dialogue système : il transmet la demande au code de votre application. Sans ce code, l'utilisateur ne voit aucune boîte de dialogue, et le comportement du flow dépend du SDK Adapty intégré dans votre application :

- **iOS, Flutter, Unity, et Kotlin Multiplatform SDKs** : Le flow reste à l'écran et n'exécute pas les actions **After response**.
- **Android, React Native, et Capacitor SDKs** : Le flow exécute immédiatement les actions **After response**, sans jamais interroger l'utilisateur.

Une flow publiée atteint également les versions de l'application publiées avant que votre application puisse répondre à la requête. Affichez une flow avec **Request permission** uniquement aux versions de l'application qui y répondent, par exemple avec une [audience](audience) construite à partir d'un [segment](segments) sur **App version (current)**.

Pour configurer votre application, consultez le guide pour [iOS](ios-handle-permissions), [Android](android-handle-permissions), [React Native](react-native-handle-permissions), [Flutter](flutter-handle-permissions), [Unity](unity-handle-permissions), [Kotlin Multiplatform](kmp-handle-permissions), ou [Capacitor](capacitor-handle-permissions).
:::

## Ordre des actions \{#action-order\}

Les actions démarrent dans l'ordre indiqué dans le panneau **Interactions**, de haut en bas. Le flow lance chaque action et passe à la suivante sans attendre qu'elle se termine, donc une navigation ou une alerte ne bloque jamais les actions situées en dessous.

Ce que cela implique pour les actions les plus concernées :

- **Set variable** : La nouvelle valeur est définie avant le démarrage de l'action suivante, donc une action conditionnelle placée en dessous lit la valeur mise à jour.
- **Navigate to screen** : Les actions qui suivent s'exécutent quand même, mais au moment où le flow lance l'action suivante, l'utilisateur se trouve peut-être déjà sur l'écran suivant. Si cette action affiche ou masque un élément de l'écran qu'il vient de quitter, il ne le verra pas. Placez les actions qui modifient l'écran actuel avant la navigation.
- **Show alert** : Les actions qui suivent s'exécutent pendant que l'alerte est ouverte. Si l'une d'elles navigue vers un autre écran, l'alerte reste ouverte pendant la navigation.
- **Purchase** et **Restore purchases** : Les actions qui suivent s'exécutent au moment du tap, sans attendre le résultat. Pour naviguer ou fermer le flow après le résultat, ajoutez plutôt l'action de navigation ou **Close Flow** pour [un résultat d'achat ou de restauration](respond-to-purchase-outcomes#add-actions-for-a-result), par exemple **When succeeded**.
- **Request permission** : Les actions qui suivent s'exécutent immédiatement, avant que l'utilisateur réponde. Pour naviguer ou fermer le flow après la réponse, ajoutez plutôt l'action de navigation ou **Close Flow** dans la section [**After response**](#request-permission). Si l'une des actions suivant la demande quitte l'écran, les actions **After response** ne s'exécutent pas du tout. Le builder affiche un avertissement lorsqu'une action de navigation ou **Close Flow** suit la demande dans la même liste.

## Actions personnalisées \{#custom-actions\}

Une action personnalisée déclenche un **Action ID** nommé que votre propre code applicatif gère. Utilisez-la lorsque les types d'actions intégrés ne couvrent pas ce dont vous avez besoin.

Adapty fournit le déclencheur ; votre application implémente le comportement :

1. Dans le builder, vous assignez un **Action ID** à l'interaction d'un élément.
2. Lorsque l'utilisateur déclenche l'interaction, le flow transmet l'ID à votre application.
3. Votre application fait correspondre l'ID et exécute votre code.

### Configurer une action personnalisée \{#set-up-a-custom-action\}

1. Dans la fenêtre **Edit action**, attribuez un **Action ID** — une chaîne que votre application reconnaîtra (par exemple, `show_discount`).
2. Dans le code de votre application, implémentez un gestionnaire pour cet Action ID. Consultez [Gérer les actions de paywall](handle-paywall-actions) pour les détails d'implémentation et les exemples de code.

:::important
Une action **Custom** sans **Action ID** [bloque la prévisualisation et la publication](flow-common-issues#a-flow-wont-preview-or-publish). Attribuez un Action ID ou supprimez l'action.
:::

<ZoomImage id="onboarding-custom-action.webp" width="500px" alt="Configuration d'une action personnalisée avec le champ Action ID dans la fenêtre Modifier l'action" />

### Ce que vous pouvez faire avec les actions personnalisées \{#what-you-can-do-with-custom-actions\}

Une action personnalisée ne fait rien par elle-même. Vous définissez un identifiant d'action statique dans le builder, et votre code applicatif gère ce qui se passe lorsqu'il reçoit cet identifiant. Chaque cas d'usage ci-dessous suit le même schéma : assignez un identifiant dans le flow, puis gérez-le dans votre code.

- **Déclencher un événement in-app** : Envoyez un identifiant comme `viewed_special_offer`, puis enregistrez l'événement dans vos analytics quand votre app le reçoit.
- **Demander une permission système autre que les notifications push** : Envoyez un identifiant comme `request_location`, puis appelez la boîte de dialogue de permission OS depuis votre app. Pour les permissions que la boîte de dialogue ne peut pas accorder, ouvrez plutôt les paramètres système du téléphone. Adapty n'affiche pas la boîte de dialogue — c'est votre app qui le fait. Pour demander les notifications push, utilisez plutôt l'action [**Request permission**](#request-permission) : ses actions **After response** s'exécutent après que l'utilisateur a répondu.
- **Démarrer une authentification native** : Envoyez un identifiant comme `login_google`, puis affichez votre propre écran de connexion. Le flow ne peut pas connecter l'utilisateur.
- **Appliquer une logique métier** : Envoyez un identifiant comme `apply_discount`, puis déverrouillez du contenu ou modifiez l'état de l'app de votre côté.
- **Transmettre une réponse de quiz à votre app** : Assignez un Action ID différent à chaque option (par exemple `goal_weight_loss` et `goal_muscle`), puis lisez l'identifiant dans votre code. Utilisez-le pour définir un [attribut utilisateur personnalisé](setting-user-attributes#custom-user-attributes) sur lequel vous pourrez segmenter plus tard. Comme l'action ne transporte qu'un identifiant fixe, c'est le seul moyen de rapporter le choix — le flow ne peut pas envoyer la valeur sélectionnée.

:::important
Une action personnalisée se déclenche dès que l'utilisateur sélectionne une option. Si l'utilisateur change sa réponse, le flow déclenche également le nouvel ID d'action. Votre application reçoit alors les deux dans l'ordre — par exemple, `goal_weight_loss`, puis `goal_muscle`. Faites en sorte que votre gestionnaire soit idempotent, de sorte que le dernier signal prévale.
:::

### Ce que les actions personnalisées ne peuvent pas faire \{#what-custom-actions-cant-do\}

Les actions personnalisées sont statiques. L'ID d'action est fixé au moment où vous créez le flow — il ne peut pas lire les [variables](onboarding-variables) ni les [saisies utilisateur](builder-inputs-and-forms). Lorsque l'action se déclenche, votre application reçoit uniquement cet ID, jamais l'e-mail, le numéro de téléphone ou toute autre information saisie par l'utilisateur. Les champs de saisie restent dans le flow en tant que variables pour le branchement et la personnalisation. Pour exploiter ces valeurs dans votre application, collectez-les via votre propre interface ou API.

Les actions personnalisées sont également unidirectionnelles. Votre application ne peut pas renvoyer de résultat au flow, et le flow n'attend pas que votre code se termine. Si une action **Navigate next** suit l'action personnalisée, l'utilisateur passe à l'écran suivant même si votre code échoue — par exemple, si l'utilisateur ferme votre écran de connexion sans s'être connecté. Combiné à l'Action ID statique, cela exclut toute validation de saisie utilisateur dans votre application — par exemple, vérifier un code SMS saisi par l'utilisateur et brancher le flow selon le résultat. Si la suite du flow dépend de ce que votre code a fait, [divisez le flow entre deux placements](#continue-the-flow-based-on-the-result).

### Poursuivre le flow en fonction du résultat \{#continue-the-flow-based-on-the-result\}

Si certains écrans ne doivent apparaître qu'après la réussite d'une action personnalisée — par exemple, les écrans qui suivent une connexion — divisez le flow entre deux [placements](placements) et laissez votre application décider quand afficher la deuxième partie :

1. Dans le premier placement, créez un flow qui se termine par une action personnalisée (par exemple, `login`).
2. Dans votre application, gérez l'Action ID : affichez votre écran de connexion et vérifiez si l'utilisateur s'est connecté.
3. Si l'utilisateur s'est connecté, affichez le flow du deuxième placement avec les écrans suivants.

De cette façon, votre application contrôle la transition en fonction du résultat réel, au lieu que le flow navigue en avant indépendamment du résultat.

## Actions conditionnelles \{#conditional-actions\}

<YouTube id="xmWSEPxnI0s" />

Utilisez les actions conditionnelles pour diviser le flow en différents chemins selon les données de l'utilisateur.

Voici quelques cas d'usage courants :

- Vous avez un quiz à l'écran et vous souhaitez diriger les utilisateurs vers différents écrans selon leurs réponses. Dans ce cas, ajoutez une action conditionnelle à un bouton.
- Vous souhaitez proposer différents produits et offres à différents groupes d'utilisateurs. Placez-les sur des écrans distincts et configurez des conditions sur un bouton de navigation.
- Vous souhaitez ignorer certaines étapes pour les utilisateurs ayant déjà terminé un tutoriel lors d'une session précédente.
- Vous souhaitez afficher un écran sur une seule plateforme, par exemple un écran expliquant l'App Tracking Transparency sur iOS. Voir [Afficher un écran sur une seule plateforme](#show-a-screen-on-one-platform-only).

Les actions conditionnelles fonctionnent comme une chaîne if / else-if / else. L'application lit les règles de haut en bas et s'arrête à la première correspondance :
1. **IF** : Le flow vérifie la condition principale.
    - Elle est True ? Le flow exécute immédiatement les actions THEN et s'arrête.
    - Elle est False ? Le flow passe à la section suivante.
2. **ELSE IF** : Vous pouvez ajouter des vérifications supplémentaires ici (ex. : « Si l'utilisateur n'est pas Premium, est-il en période d'essai ? »).
3. **ELSE** (Fallback) : Si aucune règle ci-dessus ne correspond, le flow exécute les actions de cette dernière section.

:::important
- Si une règle est ajoutée mais qu'aucune action ne lui est assignée, la condition sera satisfaite sans rien déclencher.
- Une règle incomplète (sans opérateur ni valeur) [bloque la prévisualisation et la publication](flow-common-issues#a-flow-wont-preview-or-publish).
:::

Pour chaque règle, sélectionnez une variable, l'[état d'un autre élément](element-states-in-conditions#add-an-element-state-to-a-condition), ou la [plateforme de l'appareil](#show-a-screen-on-one-platform-only) à évaluer, ainsi qu'une action à exécuter. Vous pouvez définir plusieurs actions par règle.

Vous ne pouvez pas sélectionner un attribut de profil ni un [tag personnalisé](flow-custom-tags) dans une condition. Pour afficher des écrans différents selon un attribut de profil, créez un flow distinct pour chaque groupe d'utilisateurs. Ensuite, dans le placement, affichez chaque flow à une [audience](audience) définie à partir de cet attribut. Pour une valeur provenant de votre application, comme la valeur d'un tag personnalisé, [définissez-la comme attribut personnalisé](setting-user-attributes) avant de créer l'audience.

:::important
Le flow n'exécute qu'une seule règle — la première qu'il trouve correspondante. Si vous avez besoin d'exécuter à la fois **IF** et **ELSE IF**, ajoutez les deux actions dans **IF**.
:::

Pour savoir comment rendre des éléments sélectionnables et les organiser en groupes à utiliser dans les conditions, consultez [Éléments sélectionnables et groupes](flow-selectable-elements).

### Afficher un écran sur une seule plateforme \{#show-a-screen-on-one-platform-only\}

Pour avoir un seul flow pour iOS et Android, envoyez les utilisateurs vers un écran spécifique à la plateforme grâce à une action conditionnelle sur l'écran précédent. Par exemple, affichez un écran expliquant l'App Tracking Transparency uniquement sur iOS :

1. Sur l'écran précédant l'écran iOS, sélectionnez le bouton qui fait avancer les utilisateurs, par exemple **Continue**.
2. Dans le panneau **Interactions**, changez son action en **Conditional Action**.
3. Dans le bloc **if**, cliquez sur le champ **Variable**, ouvrez l'onglet **System** et sélectionnez `system.platform`. Gardez `=`, et sélectionnez **iOS**.
4. Dans le bloc **then**, ajoutez **Navigate to Screen** avec l'écran iOS.
5. Dans le bloc **else**, ajoutez **Navigate to Screen** avec l'écran qui suit l'écran iOS.

Sur Android, les utilisateurs passent directement à l'écran suivant. L'écran iOS ne s'ouvre pas non plus avec **Navigate back**, car les utilisateurs ne l'ont jamais visité.

Le SDK Adapty transmet la plateforme automatiquement, votre application n'a donc pas besoin de la passer. Les appareils Android, y compris les appareils Huawei, correspondent à **Android**.

:::warning
Ne placez pas un écran spécifique à une plateforme comme premier écran du flow. Une action conditionnelle se déclenche lorsque les utilisateurs interagissent avec un écran, donc le flow s'ouvre toujours sur son premier écran, quelle que soit la plateforme.
:::

Pour afficher ou masquer un seul élément sur une plateforme, utilisez la [visibilité conditionnelle](onboarding-element-visibility#show-an-element-on-one-platform-only).
