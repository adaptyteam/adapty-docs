<SDKv4>

Pour afficher un flow à chaque utilisateur dans sa langue, transmettez ses langues au SDK iOS Adapty 4.5 ou ultérieur. Les utilisateurs voient un flow dans leur langue préférée disponible dans ce flow. Un flow qui ne propose aucune de ces langues s'affiche dans sa langue par défaut.

Avec le SDK 4.0–4.4, votre application transmet un code de langue à `getFlowConfiguration`, et le SDK [le fait correspondre exactement](#pass-the-users-languages-to-the-sdk). Pour mettre à jour votre code, consultez [Migrer le SDK iOS Adapty vers la v4.5](migration-to-ios-sdk-45).

Avec le SDK 4.5 ou ultérieur, trois cas obéissent à d'autres règles :

- Les applications qui choisissent la localisation d'un flow dans leur propre code [utilisent un résolveur personnalisé](#pick-a-flows-localization-in-your-own-code).
- Les paywalls de l'ancien Paywall Builder [correspondent uniquement à la première langue de l'utilisateur](#select-a-localization-strategy).
- Les paywalls personnalisés et les onboardings [fonctionnent comme dans le SDK 4.4](#localize-custom-paywalls-and-onboardings).

## Transmettre les langues de l'utilisateur au SDK \{#pass-the-users-languages-to-the-sdk\}

<Tabs groupId="ios-sdk-version" queryString>
<TabItem value="4.5" label="SDK 4.5 ou version ultérieure" default>

[`AdaptyUI.getFlowConfiguration`](get-pb-paywalls#fetch-the-view-configuration) requiert le paramètre `preferredLocales`. Transmettez-y les langues de l'utilisateur, par ordre de préférence décroissante. Le SDK ne lit pas lui-même les langues de l'appareil.

```swift showLineNumbers
let flowConfiguration = try await AdaptyUI.getFlowConfiguration(
    forFlow: flow,
    preferredLocales: Locale.preferredLanguages
)
```

Trois règles déterminent la localisation que voient les utilisateurs :

- Le SDK parcourt les langues de l'utilisateur dans l'ordre et choisit la première langue disponible dans le flow. C'est le mécanisme de correspondance de langue iOS : les règles qu'iOS applique pour choisir la langue d'une app. Le SDK reconnaît les variantes proches d'une langue : `de-AT` correspond à `de`, et `zh-TW` correspond à `zh-hant`. Les paywalls de l'ancien Paywall Builder n'utilisent que la première langue de l'utilisateur.
- La casse et les séparateurs n'ont pas d'importance : `pt_BR`, `pt-BR` et `pt-br` correspondent à la même locale. Transmettez les valeurs telles qu'iOS les retourne.
- Avec une liste vide, ou une liste qui ne correspond à aucune locale du flow, le SDK utilise la locale par défaut.

Passez l'une des trois listes. La liste définit l'ordre dans lequel le SDK essaie les langues, mais elle ne peut pas ajouter une langue absente du flow.

| Valeur | La langue dans laquelle le flow s'affiche | Compromis |
|---|---|---|
| `Locale.preferredLanguages` | La première langue de l'appareil que le flow prend en charge, même si votre application ne la prend pas en charge | Le flow peut s'afficher dans une langue différente de l'interface de votre app |
| `Bundle.main.preferredLocalizations` | La langue de l'interface de votre app | La liste ne contient qu'une seule langue. Si le flow ne la prend pas en charge, l'utilisateur voit la langue par défaut. Dans une app avec `Base.lproj` et sans localisation anglaise, la liste peut contenir `Base`. |
| `[selectedLanguage] + Locale.preferredLanguages` | La langue choisie dans le sélecteur de langue de votre app, puis les langues de l'appareil | — |

Les deux systèmes produisent des résultats différents dans deux cas :

- Votre application est uniquement en anglais, et le flow a du français et de l'anglais. Un utilisateur francophone voit le français avec `Locale.preferredLanguages`, et l'anglais avec `Bundle.main.preferredLocalizations`.
- Votre application a le coréen, mais pas le flow. Un utilisateur avec le coréen puis l'espagnol voit l'espagnol avec `Locale.preferredLanguages`, et la langue par défaut avec `Bundle.main.preferredLocalizations`.

:::tip
Ne passez pas `Locale.current.identifier`. Il ne contient qu'une seule langue, donc le SDK n'a pas d'autre langue à essayer. Son code n'a pas de script : `zh_TW` et non `zh-Hant-TW`. Avec cet identifiant, les paywalls de l'ancien Paywall Builder manquent leur localisation `zh-hant`.
:::

La plupart des applications ne passent pas `localizationStrategy`. [Sa valeur par défaut](#select-a-localization-strategy), `.auto`, convient aux flows du Flow & Paywall Builder et aux paywalls de l'ancien Paywall Builder.

</TabItem>
<TabItem value="4.4" label="SDK 4.0–4.4">

Passez un code de langue dans le paramètre `locale` de [`AdaptyUI.getFlowConfiguration`](get-pb-paywalls#fetch-the-view-configuration). Le SDK ne lit pas la langue de l'appareil, vous devez donc choisir le code de langue dans votre application.

```swift showLineNumbers
let flowConfiguration = try await AdaptyUI.getFlowConfiguration(
    forFlow: flow,
    locale: "pt-BR"
)
```

La correspondance est exacte. Le SDK compare le code que vous passez avec les codes de localisation du flow caractère par caractère : il ne change pas la casse, ne remplace pas les tirets bas (`_`) par des tirets (`-`), et ne se rabat pas sur le sous-tag de langue. Pour un flow avec une localisation `pt-BR`, seul `pt-BR` correspond : `pt-br`, `pt_BR` et `pt-PT` ne fonctionnent pas.

Quand le code ne correspond à aucune localisation, le flow s'affiche silencieusement dans sa [langue par défaut](add-paywall-locale-in-adapty-paywall-builder#set-the-default-locale) — le SDK ne renvoie pas d'erreur et n'enregistre pas d'avertissement.

Omettre le code de langue n'est pas la même chose que demander la localisation par défaut du flow : le SDK substitue un `en` fixe. Un flow dont la langue par défaut est `de` s'affiche quand même en `en` s'il dispose d'une localisation `en`, et ne revient à `de` que si ce n'est pas le cas.

:::warning
Passez le code de langue exactement tel qu'il est publié dans le flow : `pt-BR`, et non `pt-br` tel qu'il apparaît dans le champ **Select languages**. Pour les paywalls de l'ancien Paywall Builder, utilisez des codes en minuscules, comme `pt-br`.

Ne transmettez pas un identifiant de locale système tel quel. Sur un appareil configuré en portugais (Brésil), `Locale.current.identifier` renvoie `pt_BR`, qui ne correspond à aucune localisation. Sur un appareil configuré en anglais (États-Unis), `Locale.current.identifier(.bcp47)` renvoie `en-US`, ce qui ne correspond pas à un flow qui ne contient que `en`. Avant de transmettre un identifiant de locale système, convertissez-le en un code reconnu par le flow.
:::

</TabItem>
</Tabs>

## Tester quelle localisation un utilisateur voit \{#test-which-localization-a-user-sees\}

<Tabs groupId="ios-sdk-version" queryString>
<TabItem value="4.5" label="SDK 4.5 ou version ultérieure" default>

Lorsque le flow ne contient aucune des langues de l'utilisateur, le SDK utilise la locale par défaut, sans message d'erreur ni message de journal. Pour savoir quelle localisation un utilisateur voit, testez le flow sur un appareil :

1. Dans les paramètres de l'appareil, déplacez la langue de test en haut de la liste des langues.
2. Ouvrez le flow dans votre application.
3. Lisez `flowConfiguration.locale`. Ce champ contient le code de la localisation affichée. Le tableau de bord affiche ce code en minuscules : `pt-br` pour `pt-BR`.

Pour tester une langue sans modifier les paramètres de l'appareil, passez une liste `preferredLocales` fixe, par exemple `["pt-PT"]`, dans un build de débogage.

</TabItem>
<TabItem value="4.4" label="SDK 4.0–4.4">

Lorsque le code que vous passez ne correspond à aucune localisation du flow, le SDK utilise la langue par défaut, sans message d'erreur ni de log. Pour savoir quelle localisation voit un utilisateur, testez le flow sur un appareil :

1. Dans les paramètres de l'appareil, sélectionnez la langue et la région de test.
2. Ouvrez le flow dans votre application.
3. Lisez `flowConfiguration.locale`. Ce champ contient le code de la localisation affichée. S'il diffère du code que vous avez transmis, le flow ne possède pas de localisation avec exactement ce code.

Pour tester un code sans modifier les paramètres de l'appareil, passez un `locale` fixe, par exemple `"pt-BR"`, dans un build de débogage.

</TabItem>
</Tabs>

Lorsque certains textes ou images apparaissent encore dans la langue par défaut, la localisation affichée ne les contient pas. Pour combler ces lacunes, [traduisez les lignes manquantes](add-paywall-locale-in-adapty-paywall-builder#manage-localizations-and-translations) dans le Flow & Paywall Builder.

## Sélectionner les locales à ajouter à un flow \{#select-which-locales-to-add-to-a-flow\}

Pour couvrir le plus grand nombre d'utilisateurs avec le moins de locales possible, suivez ces trois règles lorsque vous [ajoutez des locales](add-paywall-locale-in-adapty-paywall-builder#add-and-set-up-a-locale) dans le champ **Select languages** :

- Ajoutez une langue sans région. Par exemple, `de` couvre les germanophones en Allemagne, en Autriche et en Suisse.
- N'ajoutez un code régional que pour une deuxième traduction d'une même langue, par exemple `fr-ca` en plus de `fr`.
- Ajoutez toutes les langues que lisent vos utilisateurs. Le SDK ne fait pas de correspondance entre les langues, par exemple du catalan vers l'espagnol. Les locuteurs catalans voient la prochaine langue préférée présente dans le flow, ou la langue par défaut.

:::important
Ces règles nécessitent iOS SDK 4.5 ou version ultérieure. Les applications utilisant iOS SDK 4.0–4.4 et les applications sur <InlineTooltip tooltip="autres SDK Adapty">[Android](android-localizations-and-locale-codes), [React Native](react-native-localizations-and-locale-codes), [Flutter](flutter-localizations-and-locale-codes), [Unity](unity-localizations-and-locale-codes), [Kotlin Multiplatform](kmp-localizations-and-locale-codes), [Capacitor](capacitor-localizations-and-locale-codes)</InlineTooltip> transmettent un seul code de langue. Leurs utilisateurs peuvent voir une localisation différente du même flow par rapport aux utilisateurs sur iOS SDK 4.5. Conservez chaque code que ces applications transmettent, comme un `zh` ou `pt-br` existant.
:::

### Sélectionner les codes pour le chinois, l'espagnol et le portugais \{#select-codes-for-chinese-spanish-and-portuguese\}

Le champ **Select languages** propose plusieurs codes pour le chinois, l'espagnol et le portugais. Ajoutez les codes indiqués dans le tableau :

| Langue | Ajouter | Ce que voient les utilisateurs |
|---|---|---|
| Chinois | `zh-hans` et `zh-hant`, pas un nouveau `zh`. N'ajoutez `zh-hk` que pour une traduction spécifique à Hong Kong. | `zh-hans` en Chine et à Singapour, et `zh-hant` à Taïwan, à Hong Kong et à Macao. |
| Cantonais | `yue`, toujours avec `zh-hant` | `yue` sur les appareils configurés en cantonais, et `zh-hant` sur les appareils configurés en chinois traditionnel. Sans `zh-hant`, les utilisateurs dont l'appareil est configuré en chinois traditionnel voient du cantonais écrit. |
| Espagnol | `es` et `es-419`, pas un nouveau `es-mx` | `es` en Espagne, et `es-419` en Amérique latine et aux États-Unis. |
| Portugais | `pt-br`, et `pt` traduit en portugais européen | `pt-br` au Brésil, et `pt` au Portugal. |

Si votre flow est localisé en plusieurs variantes régionales d'une même langue, proposez également une locale moins spécifique à une région — pour couvrir les variétés linguistiques qui ne font pas partie de celles que vous prenez explicitement en charge. Sans ce fallback, les utilisateurs des autres régions se voient servir une locale aléatoire dans le groupe linguistique — et vous ne pouvez pas choisir laquelle. Par exemple, un utilisateur avec `es-MX` peut voir `es-ar`, `es-co` ou `es-es`. Pour cibler ces utilisateurs, ajoutez la locale sans région `es`, ou la locale panafricaine `es-419`.

### Commencer avec un ensemble de paramètres régionaux recommandé \{#start-from-a-recommended-set-of-locales\}

Pour planifier les traductions par étapes, partez de l'un des trois ensembles suivants. Chaque ensemble contient le précédent.

| Ensemble | Paramètres régionaux | Total |
|---|---|---|
| Minimal | `en`, `es`, `pt-br`, `fr`, `de`, `it`, `ru`, `ja`, `ko`, `zh-hans`, `zh-hant` | 11 |
| Étendu | L'ensemble minimal et `tr`, `pl`, `nl`, `sv`, `da`, `no`, `fi`, `uk`, `ar`, `he`, `hi`, `id`, `th`, `vi`, `es-419`, `pt` | 27 |
| Large | L'ensemble étendu et `cs`, `sk`, `hu`, `ro`, `el`, `bg`, `hr`, `sl`, `lt`, `lv`, `et`, `ca`, `kk`, `ms`, `fil`, `fa`, `ur`, `bn`, `ta`, `te`, `mr`, `fr-ca` | 49 |

Dans ces ensembles, les utilisateurs voient les langues suivantes :

- Dans l'ensemble minimal, `es` couvre les hispanophones dans tous les pays, et `pt-br` couvre également les lusophones au Portugal.
- Dans l'ensemble étendu, `es-419` et `pt` sont des traductions supplémentaires. Avec eux, `es` sert l'Espagne, et `pt` sert le Portugal. Traduisez `pt` en portugais européen.
- Les locuteurs du catalan et du malais ne voient leur langue que dans leur propre locale : `ca` ou `ms`. Le SDK ne leur affiche pas l'espagnol ou l'indonésien à la place.

### Sélectionner la langue par défaut \{#select-the-default-locale\}

Les utilisateurs voient la langue par défaut lorsque le flow ne contient aucune de leurs langues. Un nouveau flow démarre avec `en` comme seule langue et langue par défaut. Pour la modifier, [définissez une autre langue comme langue par défaut](add-paywall-locale-in-adapty-paywall-builder#set-the-default-locale).

Respectez trois règles pour la langue par défaut :

- Pour les utilisateurs sans langue correspondante, sélectionnez la langue que la plupart d'entre eux comprennent. En général, c'est l'anglais, pas la langue de votre marché principal.
- Traduisez entièrement la langue par défaut. Les utilisateurs sans langue correspondante la voient en intégralité. Les autres utilisateurs voient ses textes et images là où leur langue correspondante en manque.
- Ne sélectionnez pas une langue à deux systèmes d'écriture, comme le chinois. Les utilisateurs de l'autre système d'écriture ne pourront peut-être pas lire la langue par défaut.

## Sélectionner une stratégie de localisation \{#select-a-localization-strategy\}

La plupart des applications ne passent pas `localizationStrategy`. Sa valeur par défaut, `.auto`, applique la correspondance de langue iOS aux flows du Flow & Paywall Builder, et la règle de la première langue aux paywalls de l'ancien Paywall Builder.

Selon la règle de la première langue, le SDK ne lit que la première langue dans `preferredLocales`. Il essaie d'abord le code complet, puis des codes plus courts (`pt-br`, puis `pt`), et affiche sinon la locale par défaut. Un paywall de l'ancien Paywall Builder continue de fonctionner avec cette règle, même après une republication. Pour que le SDK essaie toutes les langues dans `preferredLocales`, [migrez le paywall vers le Flow & Paywall Builder](convert-paywall-to-flow). Servez ensuite le nouveau flow depuis un placement de type flow.

Pour modifier la façon dont le SDK choisit une localisation, passez l'une des valeurs suivantes dans le paramètre `localizationStrategy` :

- `.system`: chaque flow utilise la correspondance de langue iOS, y compris les paywalls de l'ancien Paywall Builder.
- `.legacy`: chaque flow utilise la règle de première langue, et non la correspondance exacte du SDK 4.4. Ne passez pas `.legacy` pour les flows du Flow & Paywall Builder : il rate leurs locales avec une région ou un script, comme `pt-BR`.
- `.custom(resolver:fallbackResolver:)`: [votre code sélectionne la localisation](#pick-a-flows-localization-in-your-own-code).

### Choisir la localisation d'un flow dans votre propre code \{#pick-a-flows-localization-in-your-own-code\}

La correspondance des langues iOS ne couvre pas tous les scripts. Par exemple, lorsqu'un appareil liste l'azerbaïdjanais en script cyrillique (`az-Cyrl`) mais pas en latin, un flow avec `az` s'affiche dans sa locale par défaut. Pour afficher `az` à la place, ou pour choisir la localisation selon vos propres règles, créez un type conforme à `AdaptyUICustomLocalizationResolver`. Passez-le ensuite dans la valeur `.custom(resolver:)` du paramètre `localizationStrategy`. Ajoutez `import AdaptyUIBuilder` au fichier contenant le resolver.

D'autres SDK Adapty appliquent des règles différentes pour la correspondance des langues, ce qui signifie qu'un même utilisateur peut voir des localisations différentes d'un flow sur iOS et Android. Pour afficher la même localisation sur toutes les plateformes, écrivez un resolver qui renvoie le même code de locale que votre application sur les autres plateformes.

Les règles suivantes s'appliquent au resolver :

- Le SDK n'appelle pas le resolver pour un flow avec une seule localisation. Le flow s'affiche dans cette localisation.
- Le SDK appelle `resolve(for:from:)` avec la liste passée par votre application et un `AdaptyUILocalizationSource` contenant les `locales` et le `defaultLocale` du flow. L'ordre des `locales` n'est pas garanti.
- Pour afficher une localisation, retournez un code présent dans `locales` ou `defaultLocale`, en respectant exactement la casse : `ar`, pas `AR`.
- Si le resolver retourne un autre code ou `nil`, le SDK utilise la stratégie définie dans `fallbackResolver`. Par défaut, c'est `.auto`.
- Le SDK peut appeler le resolver depuis un thread autre que le thread principal.
- Retournez le code immédiatement, sans requête réseau ni traitement lent. Le SDK attend le resolver sans limite de temps, et le flow ne s'affiche qu'après le retour du resolver.

## Standard des codes de langue chez Adapty \{#locale-code-standard-at-adapty\}

Les codes de langue Adapty suivent le [standard BCP 47](https://en.wikipedia.org/wiki/IETF_language_tag) : un sous-tag de langue, suivi d'un sous-tag de script ou de région optionnel, séparés par des tirets. Le champ **Select languages** affiche les codes en minuscules : `en` (anglais), `pt-br` (portugais, Brésil), `zh-hans` (chinois simplifié) et `zh-hant` (chinois traditionnel).

## Localiser les paywalls et onboardings personnalisés \{#localize-custom-paywalls-and-onboardings\}

SDK 4.5 modifie uniquement les règles de localisation pour les flows. Les paywalls et onboardings personnalisés fonctionnent comme dans SDK 4.4.

### Récupérer la Remote Config d'un paywall personnalisé selon la langue \{#pick-a-custom-paywalls-remote-config-by-language\}

`getFlow` n'a pas de paramètre de langue. Pour un paywall personnalisé, il retourne toutes les localisations configurées dans `flow.remoteConfigs`. Chaque entrée contient un code `locale` et le contenu de la config (`jsonString`, ou le dictionnaire parsé `dictionary`). Sélectionnez l'entrée correspondant à l'utilisateur, avec votre propre logique de fallback :

```swift showLineNumbers
do {
    let flow = try await Adapty.getFlow(placementId: "YOUR_PLACEMENT_ID")
    let config = flow.remoteConfigs.first(where: { $0.locale == "en" })
        ?? flow.remoteConfigs.first
    // read your values from config?.dictionary
} catch {
    // handle the error
}
```

Adapty stocke ces codes `locale` dans le format décrit dans [Standard de code de langue dans Adapty](#locale-code-standard-at-adapty). Le SDK ne fait pas correspondre les Remote Configs à une langue, c'est donc à votre application de décider quelle entrée appliquer.

### Passer une locale à un onboarding \{#pass-a-locale-to-an-onboarding\}

<OnboardingDeprecation />

`getOnboarding` conserve son paramètre `locale` dans le SDK 4.5. Lorsque vous passez une `locale` à [`getOnboarding`](get-onboardings), le serveur sélectionne la localisation :

1. La chaîne de paramètres régionaux est convertie en minuscules et tous les underscores (`_`) sont remplacés par des tirets (`-`)
2. Adapty recherche la localisation avec le code de paramètres régionaux correspondant exactement
3. Si aucune correspondance n'est trouvée, Adapty prend la sous-chaîne avant le premier tiret (`pt` pour `pt-br`) et recherche la localisation correspondante
4. Si aucune correspondance n'est trouvée à nouveau, Adapty renvoie le contenu pour la langue par défaut de l'onboarding

Ainsi, `pt_BR`, `pt-BR` et `pt-br` renvoient tous à la même localisation d'onboarding.

</SDKv4>

## Pourquoi c'est important \{#why-this-is-important\}

Les codes de langue interviennent dans plusieurs scénarios — par exemple, lorsque vous essayez de récupérer le bon paywall pour la localisation actuelle de votre application.

Les codes de langue étant complexes et pouvant varier d'une plateforme à l'autre, nous nous appuyons sur un standard interne pour toutes les plateformes que nous prenons en charge. Cependant, en raison de cette complexité, il est vraiment important que vous compreniez exactement ce que vous envoyez à notre serveur pour obtenir la bonne localisation, et ce qui se passe ensuite — afin que vous receviez toujours ce que vous attendez.

## Standard des codes de langue chez Adapty \{#locale-code-standard-at-adapty\}

Pour les codes de langue, Adapty utilise une version légèrement modifiée du [standard BCP 47](https://en.wikipedia.org/wiki/IETF_language_tag) : chaque code est composé de sous-balises en minuscules, séparées par des tirets. Quelques exemples : `en` (anglais), `pt-br` (portugais (Brésil)), `zh` (chinois simplifié), `zh-hant` (chinois traditionnel).

## Correspondance des codes de langue \{#locale-code-matching\}

Lorsqu'Adapty reçoit un appel du SDK avec le code de langue et commence à chercher la localisation correspondante d'un paywall, voici ce qui se passe :

1. La chaîne de locale reçue est convertie en minuscules et tous les underscores (`_`) sont remplacés par des tirets (`-`)
2. On recherche ensuite la localisation dont le code de locale correspond exactement
3. Si aucune correspondance n'est trouvée, on extrait la sous-chaîne avant le premier tiret (`pt` pour `pt-br`) et on cherche la localisation correspondante
4. Si aucune correspondance n'est trouvée non plus, on renvoie le contenu dans la locale par défaut du paywall

Ainsi, un appareil iOS qui a envoyé `'pt_BR'`, un appareil Android qui a envoyé `pt-BR`, et un autre appareil qui a envoyé `pt-br` obtiendront le même résultat.

## Implémentation des localisations : méthode recommandée \{#implementing-localizations-recommended-way\}

Si vous vous posez des questions sur les localisations, il y a de grandes chances que vous travailliez déjà avec des fichiers de chaînes localisées dans votre projet. Dans ce cas, nous recommandons d'ajouter une paire clé-valeur avec le code de locale Adapty souhaité dans chacun de vos fichiers pour les localisations correspondantes. Extrayez ensuite la valeur de cette clé lors de l'appel à notre SDK, comme ceci :

```swift showLineNumbers
// 1. Modify your Localizable.strings files

/*
Localizable.strings - Spanish
*/
adapty_paywalls_locale = "es";
/*
Localizable.strings - Portuguese (Brazil)
*/
adapty_paywalls_locale = "pt-br";
// 2. Extract and use the locale code
let locale = NSLocalizedString("adapty_paywalls_locale", comment: "")
// pass locale code to AdaptyUI.getViewConfiguration or Adapty.getPaywall method
```

Ainsi, vous gardez un contrôle total sur la localisation qui sera récupérée pour chaque utilisateur de votre application.

## Implémenter les localisations : l'autre façon \{#implementing-localizations-the-other-way\}

Vous pouvez obtenir des résultats similaires (mais pas identiques) sans définir explicitement des codes de langue pour chaque localisation. Cela consiste à extraire un code de langue depuis d'autres objets fournis par votre plateforme, comme ceci :

```swift showLineNumbers
let locale = Locale.current.identifier
// pass locale code to AdaptyUI.getViewConfiguration or Adapty.getPaywall method
```

Notez que nous ne recommandons pas cette approche pour plusieurs raisons :

1. Sur iOS, les langues préférées et la locale actuelle ne sont pas identiques. Pour que la localisation soit correctement sélectionnée, vous devrez soit vous appuyer sur la logique d'Apple, qui fonctionne automatiquement si vous utilisez l'approche recommandée avec des fichiers de chaînes localisées, soit la recréer vous-même.
2. Il est difficile de prédire ce que le serveur d'Adapty recevra exactement. Par exemple, sur iOS, il est possible d'obtenir une locale comme `ar_OM@numbers='latn'` sur un appareil et de l'envoyer à notre serveur. Dans ce cas, vous obtiendrez non pas la localisation `ar-om` que vous recherchiez, mais plutôt `ar`, ce qui est probablement inattendu.

Should you decide to use this approach anyway — make sure you've covered all the relevant use cases.

</SDKv3>
