<SDKv4>

Чтобы каждый пользователь видел флоу на понятном ему языке, передайте список его языков в Adapty Android SDK 4.5 или более поздней версии. Пользователь увидит флоу на том из предпочтительных языков, который в нём поддерживается. Если ни один из указанных языков недоступен, флоу отображается на языке по умолчанию.

На SDK 4.0–4.4 ваше приложение передаёт один код локали в `getFlowConfiguration`, и SDK [сопоставляет его точно](#pass-the-users-languages-to-the-sdk). Чтобы обновить код, прочитайте [Миграцию Adapty Android SDK на v4.5](migration-to-android-sdk-45).

На SDK 4.5 и выше три случая подчиняются другим правилам:

- Приложения, которые выбирают локализацию флоу в своём коде, [используют кастомный резолвер](#pick-a-flows-localization-in-your-own-code).
- Пейволы из старого Paywall Builder [сопоставляют язык пользователя только по наивысшему приоритету](#select-a-localization-strategy).
- Кастомные пейволы и онбординги [работают так же, как в SDK 4.4](#localize-custom-paywalls-and-onboardings).

## Передача языков пользователя в SDK \{#pass-the-users-languages-to-the-sdk\}

<Tabs groupId="android-sdk-version" queryString>
<TabItem value="4.5" label="SDK 4.5 or later" default>

[`AdaptyUI.getFlowConfiguration`](android-get-pb-paywalls#fetch-the-view-configuration) требует параметр `preferredLocales`. Передавайте в нём языки пользователя в порядке убывания предпочтения. Ваше приложение само определяет, какие языки передавать — например, языки устройства или язык, выбранный в настройках приложения.

<Tabs groupId="current-os" queryString>
<TabItem value="kotlin" label="Kotlin" default>

```kotlin showLineNumbers
val preferredLocales = LocaleListCompat.getAdjustedDefault().toLanguageTags().split(",")

AdaptyUI.getFlowConfiguration(flow, preferredLocales) { result ->
    // handle the result
}
```

</TabItem>
<TabItem value="java" label="Java">

```java showLineNumbers
List<String> preferredLocales =
    Arrays.asList(LocaleListCompat.getAdjustedDefault().toLanguageTags().split(","));

AdaptyUI.getFlowConfiguration(flow, preferredLocales, result -> {
    // handle the result
});
```

</TabItem>
</Tabs>

Три правила определяют, какую локализацию увидит пользователь:

- SDK перебирает языки пользователя по порядку и выбирает первый, который есть во флоу. Используется механизм выбора ресурсов Android: те же правила, по которым Android подбирает переводы для приложения. SDK учитывает близкие варианты языка: `de-AT` совпадает с `de`, а `zh-TW` — с `zh-hant`. На Android 6 и ниже SDK выбирает первую локализацию флоу, совпадающую по языку и письму с настройками пользователя, независимо от региона. Пейволы из старого Paywall Builder используют только язык с наивысшим приоритетом.
- Регистр и разделители не важны: `pt_BR`, `pt-BR` и `pt-br` указывают на одну и ту же локаль. Передавайте значения в том виде, в котором их возвращает Android.
- При пустом списке или списке, не совпадающем ни с одной локалью флоу, SDK использует локаль по умолчанию.

Передайте один из трёх списков. Список задаёт порядок, в котором SDK перебирает языки, но добавить язык, которого нет во флоу, он не может.

| Значение | Флоу отображается на | Компромисс |
|---|---|---|
| `LocaleListCompat.getAdjustedDefault()` | Языке, который пользователь выбрал для вашего приложения в настройках Android или в самом приложении. Если язык не выбран — на первом языке устройства, поддерживаемом флоу | Ниже Android 13 язык, заданный через `AppCompatDelegate.setApplicationLocales`, применяется только после создания первого `AppCompatActivity`. Считывайте список после этого момента, а не в `Application.onCreate`. |
| `LocaleManagerCompat.getSystemLocales(context)` | Первом языке устройства, поддерживаемом флоу, даже если пользователь выбрал другой язык для вашего приложения | Флоу может отображаться на языке, отличном от языка интерфейса вашего приложения |
| `selectedLanguage`, затем `LocaleListCompat.getAdjustedDefault()` | Языке из выбора языка в вашем приложении, затем на языках устройства | — |

Чтобы передать список, преобразуйте его в коды локалей:

```kotlin showLineNumbers
// The language selected for your app, then the device languages
val appLocales = LocaleListCompat.getAdjustedDefault().toLanguageTags().split(",")

// The device languages
val deviceLocales = LocaleManagerCompat.getSystemLocales(context).toLanguageTags().split(",")

// The language from the language picker in your app, then the other languages
val pickerLocales = listOf(selectedLanguage) + appLocales
```

Первые два списка дают разные результаты, когда пользователь выбирает язык для вашего приложения. Например, если на устройстве установлен английский, а пользователь выбирает испанский для вашего приложения, то с `getAdjustedDefault()` он увидит испанский, а с `getSystemLocales()` — английский.

Языковой переключатель, сохраняющий язык через `AppCompatDelegate.setApplicationLocales`, не требует третьего списка. При таком подходе первый список начинается с выбранного языка.

:::tip
Не передавайте `Locale.getDefault().toLanguageTag()` в одиночку. Он содержит только один язык, и SDK не сможет попробовать другой.
:::

Большинство приложений не передают `localizationStrategy`. Без него SDK использует [`AdaptyUiLocalizationStrategy.Auto`](#select-a-localization-strategy), что подходит для флоу из Flow & Paywall Builder и пейволов из старого Paywall Builder.

</TabItem>
<TabItem value="4.4" label="SDK 4.0–4.4">

Передайте один код локали в параметре `locale` метода [`AdaptyUI.getFlowConfiguration`](android-get-pb-paywalls#fetch-the-view-configuration). Ваше приложение само решает, какой код передавать — например, локаль устройства или язык, выбранный пользователем в настройках приложения.

```kotlin showLineNumbers
AdaptyUI.getFlowConfiguration(flow, locale = "pt-BR") { result ->
    // handle the result
}
```

Совпадение точное. SDK сравнивает переданный вами код с кодами локализации флоу посимвольно: не меняет регистр, не заменяет подчёркивания (`_`) на дефисы (`-`) и не откатывается к языковому тегу. Для флоу с локализацией `pt-BR` подходит только `pt-BR`: `pt-br`, `pt_BR` и `pt-PT` — не совпадут.

Если код не совпадает ни с одной локализацией, флоу незаметно отображается в своей [локализации по умолчанию](add-paywall-locale-in-adapty-paywall-builder#set-the-default-locale) — SDK не возвращает ошибку и не выводит предупреждение.

Не указывать код локали — не то же самое, что запросить локализацию флоу по умолчанию: SDK подставляет фиксированный `en`. Флоу, у которого локаль по умолчанию — `de`, всё равно отображается на `en`, если у него есть локализация `en`, и только при её отсутствии возвращается к `de`. Это поведение актуально для Android SDK 4.0.1 и новее — в 4.0.0 отсутствие кода приводило к отображению локализации флоу по умолчанию.

:::warning
Передавайте код локали точно так, как он указан в опубликованном флоу: `pt-BR`, а не `pt-br` из поля **Select languages**. Для пейволов из старого Paywall Builder передавайте коды в нижнем регистре, например `pt-br`.

Не передавайте системный идентификатор локали как есть. На устройстве с португальским (Бразилия) `Locale.getDefault().toString()` возвращает `pt_BR`, что не совпадёт ни с одной локализацией. На устройстве с английским (США) `Locale.getDefault().toLanguageTag()` возвращает `en-US`, что не найдёт флоу, у которого есть только `en`. Перед передачей системного идентификатора локали преобразуйте его в код, который есть во флоу.
:::

</TabItem>
</Tabs>

## Проверьте, какую локализацию видит пользователь \{#test-which-localization-a-user-sees\}

<Tabs groupId="android-sdk-version" queryString>
<TabItem value="4.5" label="SDK 4.5 или новее" default>

Если флоу не поддерживает ни один из языков пользователя, SDK использует локализацию по умолчанию без ошибки. Чтобы узнать, какую локализацию видит пользователь, протестируйте флоу на устройстве:

1. Установите [уровень логирования](sdk-installation-android#logging) на `AdaptyLogLevel.VERBOSE`.
2. В настройках устройства переместите тестовый язык в начало списка языков.
3. Откройте флоу в приложении.
4. В Logcat найдите строку с `getFlowConfiguration: preferredLocales`. Она заканчивается кодом отображаемой локализации, например `strategy = Auto -> pt-BR`. В дашборде этот код отображается в нижнем регистре: `pt-br` для `pt-BR`.

Чтобы протестировать язык без изменения настроек устройства, передайте фиксированный список `preferredLocales`, например `listOf("pt-PT")`, в отладочной сборке.

</TabItem>
<TabItem value="4.4" label="SDK 4.0–4.4">

Если переданный код не совпадает ни с одной локализацией флоу, SDK использует локаль по умолчанию — без ошибок и предупреждений в логах. Чтобы узнать, какую локализацию видит пользователь, протестируйте флоу на устройстве:

1. В настройках устройства выберите тестовый язык и регион.
2. Откройте флоу в приложении.
3. Сравните флоу на устройстве с его локализациями в Flow & Paywall Builder. Если флоу отображается на языке локали по умолчанию, значит, флоу не содержит локализации с переданным кодом.

Чтобы протестировать код без изменения настроек устройства, передайте фиксированную `locale`, например `"pt-BR"`, в отладочной сборке.

</TabItem>
</Tabs>

Если часть флоу по-прежнему отображается на языке по умолчанию, значит для этой части нет перевода в выбранной локализации. Чтобы устранить пробелы, [переведите недостающие строки](add-paywall-locale-in-adapty-paywall-builder#manage-localizations-and-translations) в Flow & Paywall Builder.

## Выберите локали для флоу \{#select-which-locales-to-add-to-a-flow\}

Чтобы охватить большинство пользователей с минимальным набором локалей, следуйте трём правилам при [добавлении локалей](add-paywall-locale-in-adapty-paywall-builder#add-and-set-up-a-locale) в поле **Select languages**:

- Добавляйте язык без региона. Например, `de` охватывает немецкоязычных пользователей в Германии, Австрии и Швейцарии.
- Региональный локаль добавляйте только для второго перевода одного языка — например, `fr-ca` в дополнение к `fr`.
- Добавляйте все языки, которые читают ваши пользователи. SDK не подбирает похожие языки автоматически: например, каталанский не заменяется испанским. Носители каталанского увидят следующий предпочтительный язык, который есть во флоу, или локаль по умолчанию.

:::important
Эти правила требуют Android или iOS SDK версии 4.5 и выше. Приложения на SDK Adapty от 4.0 до 4.4 передают один код локали. Их пользователи могут видеть другую локализацию того же флоу, чем пользователи на SDK 4.5. Сохраняйте все коды, которые передают эти приложения, например существующий `zh` или `pt-br`.
:::

### Выбор кодов для китайского, испанского и португальского

В поле **Select languages** представлено несколько кодов для китайского, испанского и португальского языков. Добавьте коды из таблицы:

| Язык | Добавьте | Пользователи видят |
|---|---|---|
| Китайский | `zh-hans` и `zh-hant`, не новый `zh`. Добавляйте `zh-hk` только для отдельного перевода для Гонконга. | `zh-hans` в Китае и Сингапуре, и `zh-hant` на Тайване, в Гонконге и Макао. |
| Кантонский | `yue`, всегда вместе с `zh-hant` | `yue` на устройствах с кантонским языком и `zh-hant` на устройствах с традиционным китайским. SDK не показывает `zh-hant` пользователям с кантонским языком на устройстве и `yue` — с традиционным китайским. |
| Испанский | `es` и `es-419`, не новый `es-mx` | `es` в Испании и `es-419` в Латинской Америке и США. |
| Португальский | `pt-br` для бразильского португальского и `pt` для европейского португальского | `pt-br` в Бразилии и `pt` в Португалии. |

Если ваш флоу содержит несколько региональных вариантов одного языка, например `es-ar` и `es-co`, добавьте также `es-419`. Тогда пользователи из других латиноамериканских стран, например из Мексики, увидят `es-419`.

### Начните с рекомендуемого набора локалей \{#start-from-a-recommended-set-of-locales\}

Чтобы планировать переводы поэтапно, начните с одного из трёх наборов. Каждый последующий набор включает предыдущий.

| Набор | Локали | Итого |
|---|---|---|
| Минимальный | `en`, `es`, `pt-br`, `fr`, `de`, `it`, `ru`, `ja`, `ko`, `zh-hans`, `zh-hant` | 11 |
| Расширенный | Минимальный набор и `tr`, `pl`, `nl`, `sv`, `da`, `no`, `fi`, `uk`, `ar`, `he`, `hi`, `id`, `th`, `vi`, `es-419`, `pt` | 27 |
| Широкий | Расширенный набор и `cs`, `sk`, `hu`, `ro`, `el`, `bg`, `hr`, `sl`, `lt`, `lv`, `et`, `ca`, `kk`, `ms`, `fil`, `fa`, `ur`, `bn`, `ta`, `te`, `mr`, `fr-ca` | 49 |

В этих наборах пользователи видят следующие локали:

- В минимальном наборе `es` охватывает испаноязычных пользователей во всех странах, а `pt-br` охватывает также португалоязычных пользователей в Португалии.
- В расширенном наборе `es-419` и `pt` — это дополнительные переводы. С ними `es` обслуживает Испанию, а `pt` — Португалию. Переводите `pt` на европейский португальский.
- Пользователи, говорящие на каталанском и малайском, видят только свой язык в соответствующей локали: `ca` или `ms`. SDK не подставляет им испанский или индонезийский.

### Выберите язык по умолчанию \{#select-the-default-locale\}

Язык по умолчанию используется, когда у флоу нет локали, совпадающей с языком пользователя. Новый флоу создаётся только с `en` в качестве единственной и дефолтной локали. Чтобы изменить это, [установите другую локаль как дефолтную](add-paywall-locale-in-adapty-paywall-builder#set-the-default-locale).

Соблюдайте три правила для языка по умолчанию:

- Для пользователей без подходящей локали выбирайте язык, который большинство из них понимает. Как правило, это английский, а не язык вашего основного рынка.
- Переведите локаль по умолчанию полностью. Пользователи без подходящей локали видят весь флоу на локали по умолчанию. Пользователи с подходящей локалью видят флоу на своём языке. Непереведённые части отображаются на локали по умолчанию.
- Не выбирайте язык с двумя системами письма, например китайский. Пользователи другой системы письма могут не понять локаль по умолчанию.

## Выберите стратегию локализации \{#select-a-localization-strategy\}

Большинство приложений не передают `localizationStrategy`, поэтому SDK использует `AdaptyUiLocalizationStrategy.Auto`. Эта стратегия применяет механизм Android resource matching к флоу из Flow & Paywall Builder и правило единственного языка к пейволам из старого Paywall Builder.

В рамках правила одного языка SDK читает только язык с наивысшим приоритетом в `preferredLocales`. Сначала он пробует полный код, затем более короткие коды (`pt-br`, затем `pt`), а при отсутствии совпадений показывает локаль по умолчанию. Пейвол из старого Paywall Builder продолжает работать по этому правилу даже после повторной публикации. Чтобы SDK перебирал все языки в `preferredLocales`, [перенесите пейвол в Flow & Paywall Builder](convert-paywall-to-flow). Затем показывайте новый флоу из плейсмента флоу.

Чтобы изменить способ сопоставления языков пользователя с локалями флоу, передайте одно из следующих значений в параметре `localizationStrategy`:

- `AdaptyUiLocalizationStrategy.System`: каждый флоу использует сопоставление ресурсов Android, включая пейволы из старого Paywall Builder.
- `AdaptyUiLocalizationStrategy.Legacy`: каждый флоу использует правило единственного языка, а не точное сопоставление из SDK 4.4. Не используйте `Legacy` для флоу из Flow & Paywall Builder: он пропускает локали с регионом или скриптом, например `pt-BR`.
- `AdaptyUiLocalizationStrategy.Custom(resolver, fallbackResolver)`: [ваш код выбирает локализацию](#pick-a-flows-localization-in-your-own-code).

### Выбор локализации флоу в собственном коде \{#pick-a-flows-localization-in-your-own-code\}

Сопоставление ресурсов Android охватывает не все скрипты. Например, если устройство указывает азербайджанский в кириллическом написании (`az-Cyrl`), но не в латинице, флоу с `az` отображается в своей локали по умолчанию. Чтобы вместо этого показать `az` или выбрать локализацию по собственным правилам, реализуйте `AdaptyUiCustomLocalizationResolver`. Затем передайте его в `AdaptyUiLocalizationStrategy.Custom` через параметр `localizationStrategy`.

Другие SDK Adapty сопоставляют языки по иным правилам, поэтому один и тот же пользователь может видеть разные локализации флоу на Android и iOS. Чтобы на всех платформах отображалась одна и та же локализация, напишите резолвер, который возвращает тот же код локали, что и ваше приложение на других платформах.

К резолверу применяются следующие правила:

- SDK не вызывает резолвер для флоу с одной локализацией. Флоу отображается в этой локализации.
- SDK вызывает `resolve` со списком, который передало ваше приложение, объектом `AdaptyUiLocalizationSource` с полями `locales` и `defaultLocale` флоу, а также `callback`. Поле `locales` содержит локализации в том порядке, в котором они заданы во флоу.
- Чтобы показать нужную локализацию, передайте в `callback` код из `locales` или `defaultLocale`, строго в том же написании с учётом регистра: `ar`, не `AR`.
- Если `callback` получит любой другой код или `null`, SDK использует резолвер из `fallbackResolver`. Если `fallbackResolver` не задан, SDK использует `AdaptyUiLocalizationResolver.Auto`.
- SDK вызывает `resolve` в основном потоке. Вызовите `callback` ровно один раз из любого потока.
- Вызывайте `callback` сразу, без сетевых запросов и другой медленной работы. SDK ждёт ответа от `callback` без ограничения по времени, и флоу отобразится только после того, как ваш код вызовет `callback`.

## Стандарт кодов локалей в Adapty \{#locale-code-standard-at-adapty\}

Коды локалей в Adapty соответствуют [стандарту BCP 47](https://en.wikipedia.org/wiki/IETF_language_tag): языковой подтег, затем необязательный подтег письма или региона, разделённые дефисами. В поле **Select languages** коды отображаются в нижнем регистре: `en` (английский), `pt-br` (португальский, Бразилия), `zh-hans` (китайский упрощённый) и `zh-hant` (китайский традиционный).

## Локализация кастомных пейволов и онбордингов \{#localize-custom-paywalls-and-onboardings\}

SDK 4.5 меняет правила локализации только для флоу. Кастомные пейволы и онбординги работают так же, как в SDK 4.4.

### Выбор Remote Config кастомного пейвола по языку \{#pick-a-custom-paywalls-remote-config-by-language\}

`getFlow` не имеет параметра локали. Для кастомного пейвола он возвращает все настроенные локализации в `flow.remoteConfigs`. Каждая запись содержит код `locale` и содержимое конфига (`jsonString` или распарсенный `dataMap`). Выберите запись, соответствующую пользователю, с собственным фолбэком:

```kotlin showLineNumbers
Adapty.getFlow("YOUR_PLACEMENT_ID") { result ->
    when (result) {
        is AdaptyResult.Success -> {
            val flow = result.value
            val config = flow.remoteConfigs.firstOrNull { it.locale == "en" }
                ?: flow.remoteConfigs.firstOrNull()
            // read your values from config?.dataMap
        }
        is AdaptyResult.Error -> {
            // handle the error
        }
    }
}
```

Adapty хранит коды `locale` в формате, описанном в разделе [Стандарт кодов локали в Adapty](#locale-code-standard-at-adapty). SDK не сопоставляет Remote Config с локалью, поэтому выбор нужной записи остаётся на усмотрение вашего приложения.

### Передача локали в онбординг \{#pass-a-locale-to-an-onboarding\}

<OnboardingDeprecation />

`getOnboarding` сохраняет параметр `locale` в SDK 4.5. Когда вы передаёте `locale` в [`getOnboarding`](android-get-onboardings), сервер выбирает локализацию:

1. Строка локали приводится к нижнему регистру, а все символы подчёркивания (`_`) заменяются дефисами (`-`)
2. Adapty ищет локализацию с полностью совпадающим кодом локали
3. Если совпадение не найдено, Adapty берёт подстроку до первого дефиса (`pt` для `pt-br`) и ищет соответствующую локализацию
4. Если совпадение снова не найдено, Adapty возвращает контент для локали онбординга по умолчанию

Таким образом, `pt_BR`, `pt-BR` и `pt-br` — все они разрешаются в одну и ту же локализацию онбординга.

## Почему это важно \{#why-this-is-important\}

Есть несколько сценариев, в которых используются коды локалей — например, когда нужно получить правильный пейвол для текущей локализации приложения.

Поскольку коды локалей сложны и могут различаться в зависимости от платформы, мы придерживаемся внутреннего стандарта для всех поддерживаемых платформ. Тем не менее именно из-за этой сложности крайне важно понимать, что именно вы отправляете на наш сервер для получения правильной локализации и что происходит дальше — чтобы всегда получать то, что вы ожидаете.

## Стандарт кодов локализации в Adapty \{#locale-code-standard-at-adapty\}

Для кодов локализации Adapty использует слегка модифицированный [стандарт BCP 47](https://en.wikipedia.org/wiki/IETF_language_tag): каждый код состоит из подтегов в нижнем регистре, разделённых дефисами. Примеры: `en` (английский), `pt-br` (португальский (Бразилия)), `zh` (упрощённый китайский), `zh-hant` (традиционный китайский).

## Сопоставление кода локали \{#locale-code-matching\}

Когда Adapty получает вызов от клиентского SDK с кодом локали и начинает искать соответствующую локализацию пейвола, происходит следующее:

1. Входящая строка локали приводится к нижнему регистру, а все символы подчёркивания (`_`) заменяются дефисами (`-`)
2. Затем выполняется поиск локализации с полностью совпадающим кодом локали
3. Если совпадение не найдено, берётся подстрока до первого дефиса (`pt` для `pt-br`) и выполняется поиск соответствующей локализации
4. Если совпадение снова не найдено, возвращается контент для локали по умолчанию данного пейвола

Таким образом устройство iOS, отправившее `'pt_BR'`, устройство Android, отправившее `pt-BR`, и другое устройство, отправившее `pt-br`, получат одинаковый результат.

## Рекомендуемый способ реализации локализаций \{#implementing-localizations-recommended-way\}

Если вас интересуют локализации, скорее всего, вы уже работаете с файлами локализованных строк в своём проекте. В таком случае мы рекомендуем добавить в каждый из этих файлов пару ключ-значение с нужным кодом локали Adapty для соответствующей локализации, а затем извлекать значение по этому ключу при вызове нашего SDK:

```kotlin showLineNumbers
// 1. Modify your strings.xml files

/*
strings.xml - Spanish
*/
<string name="adapty_paywalls_locale">es</string>

/*
strings.xml - Portuguese (Brazil)
*/
<string name="adapty_paywalls_locale">pt-br</string>

// 2. Extract and use the locale code

val localeCode = context.getString(R.string.adapty_paywalls_locale)
// pass locale code to AdaptyUI.getViewConfiguration or Adapty.getPaywall method
```

Это позволяет полностью контролировать, какая локализация будет загружена для каждого пользователя вашего приложения.

## Альтернативный способ реализации локализаций \{#implementing-localizations-the-other-way\}

Похожего (но не идентичного) результата можно добиться без явного определения кодов локали для каждой локализации. Для этого можно извлечь код локали из других объектов, предоставляемых платформой:

```kotlin showLineNumbers
val locale = if (Build.VERSION.SDK_INT >= Build.VERSION_CODES.N)
    context.resources.configuration.locales[0]
else
    context.resources.configuration.locale

val localeCode = locale.toLanguageTag()
// pass locale code to AdaptyUI.getViewConfiguration or Adapty.getPaywall method
```

Обратите внимание, что мы не рекомендуем этот подход, так как сложно предсказать, какие именно данные получит сервер Adapty.

Если вы всё же решите использовать этот подход — убедитесь, что охватили все актуальные сценарии.
