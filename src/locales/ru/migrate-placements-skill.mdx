Скилл migrate-placements переводит приложение, работающее на пейволах, на флоу. Укажите вашему AI-инструменту аккаунт — и он прочитает каждый плейсмент через [Adapty CLI](developer-cli-quickstart), определит, сколько флоу нужно для миграции, и создаст новый флоу-плейсмент для каждого пейвол-плейсмента, который вы переносите. В результате вы получите таблицу соответствия старых идентификаторов плейсментов новым и один вызов, который нужно изменить в приложении.

**Скилл создаёт новые плейсменты, а не конвертирует существующие.** Тип контента плейсмента фиксируется при создании, поэтому пейвол-плейсмент никогда не станет флоу-плейсментом — см. [Создание нового плейсмента для вашего флоу](migrate-to-flows#create-a-new-placement-for-your-flow). Каждый новый флоу-плейсмент работает параллельно с заменяемым пейвол-плейсментом, а старый продолжает обслуживать пользователей до выхода обновления приложения.

Скилл не проектирует контент флоу — это делает [скилл flow-generator](flow-generator-skill) — и не пишет код приложения, за что отвечает [скилл SDK-интеграции](manage-adapty-with-ai#skill-based-integration) для вашей платформы. Он читает ваши пейвол-плейсменты и никогда их не изменяет.

## Перед началом работы \{#before-you-start\}

- **AI-инструмент, поддерживающий скиллы**: подходят Claude Code, GitHub Copilot CLI, OpenAI Codex и Gemini CLI.
- **Флоу для каждого переносимого пейвола или план его получения**: Скилл спрашивает по каждому пейволу, откуда берётся флоу, и один из вариантов ответа — действие, которое вы совершаете в дашборде. См. [Откуда берётся контент флоу](#where-the-flow-content-comes-from).
- **Adapty SDK v4 в вашем плане**: Флоу работают только на SDK v4 и выше, поэтому миграция завершается вместе с релизом приложения. До выхода релиза ничего из созданного скиллом не достигнет пользователей.

## Установка скилла \{#install-the-skill\}

migrate-placements входит в плагин `adapty-skills` ([`adaptyteam/adapty-skills`](https://github.com/adaptyteam/adapty-skills)) вместе с flow-generator и flow-audit — одна установка даёт вам все скиллы плагина.

:::tip
**Уже установили плагин для другого скилла Adapty? Этот скилл уже у вас есть.** Плагин обновляется автоматически, поэтому migrate-placements будет доступен в следующем сеансе без каких-либо дополнительных действий.
:::

Чтобы установить его в Claude Code впервые:

```bash
claude plugin marketplace add adaptyteam/adapty-skills
claude plugin install adapty-skills@adapty
```

Затем выполните `/reload-plugins`, чтобы активировать скиллы. Для других AI-инструментов следуйте [инструкциям по установке flow-generator](flow-generator-skill#install-the-skill) — тот же репозиторий, те же команды. Там скиллы копируются на место вместо установки плагина, поэтому для получения скилла, добавленного после последней установки, нужно повторить эти шаги.

Затем вызовите его — `/migrate-placements` в инструментах, которые поддерживают слеш-команды для скиллов, или «Use the migrate-placements skill» в тех, которые не поддерживают.

## Примеры запросов \{#example-prompts\}

#### Перенести плейсменты, обслуживающие пользователей

```
Migrate the active paywall placements in my app to flows. Skip the inactive
ones for now and tell me how many you left out.
```

#### Повторно использовать уже конвертированные флоу

```
Migrate my paywall placements to flows. I've already converted three of the
paywalls with Move to new builder — reuse those flows instead of building new ones.
```

#### Сначала отработать на неактивных плейсментах

```
Start with my inactive paywall placements so I can watch the whole thing run
without exposing users, then do the live ones.
```

#### Мигрировать одну область приложения

```
Migrate only the four onboarding placements in my app, not the in-app upsells.
Show me the placement IDs you'd create before you create anything.
```

## Как это работает \{#how-it-works\}

Восемь этапов, и только седьмой вносит изменения в ваш аккаунт.

1. **Подготовка и проверка.** Устанавливает или обновляет [Adapty CLI](developer-cli-quickstart), подтверждает вход в Adapty и считывает ID вашего приложения.
2. **Инвентаризация.** Читает каждый плейсмент в приложении, перебирая все страницы списка, а не ограничиваясь первой.
3. **Классификация и группировка.** Сортирует каждую аудиторию по категориям: пригодна для миграции, уже на флоу или нечего переносить, — затем группирует пригодные по пейволу, который они обслуживают. Эта группировка и есть план флоу: **один флоу на каждый уникальный пейвол**, общий для всех плейсментов, которые его используют, — так вы дорабатываете один флоу вместо пяти копий.
4. **Два вопроса.** Какую часть аккаунта переносить и откуда берётся каждый флоу. См. [Откуда берётся контент флоу](#where-the-flow-content-comes-from).
5. **Публикация флоу.** Для пейвола без флоу скилл создаёт его, сохраняет конфигурацию, публикует и ждёт, пока статус не станет `published`. Уже опубликованный флоу записывается как есть. Публикация важна здесь, потому что черновик флоу нельзя прикрепить к плейсменту.
6. **Показ результата на проверку.** Полный список ID плейсментов, которые предлагается создать, и то, что ещё не сделано.
7. **Создание плейсментов.** По одному `placements create` для каждого пейвол-плейсмента в области действия — после вашего подтверждения.
8. **Отчёт и передача.** Таблица соответствия старых и новых ID и информация об изменении SDK-вызова для разработчиков.

Предлагаемые ID формируются на основе существующих — `main` становится `main-flow` — и каждый проверяется на уникальность среди всех ID плейсментов в приложении.

## Откуда берётся контент флоу \{#where-the-flow-content-comes-from\}

Новому плейсменту нужен опубликованный флоу для работы, и скилл спрашивает по каждому пейволу, какой путь выбрать. Он никогда не выбирает за вас, потому что четыре варианта различаются тем, что увидят ваши пользователи.

| Вариант | Что происходит | Когда подходит |
|---|---|---|
| **Повторное использование** | Скилл прикрепляет уже имеющийся флоу. Если он ещё черновик — сначала публикует. | Вы уже создали или конвертировали флоу. Предлагается первым, если есть подходящий кандидат. |
| **Конвертация** | Вы нажимаете **Move to new builder** на странице пейвола; скилл ждёт, перечитывает аккаунт и считывает созданный флоу. | Пейвол был создан в устаревшем Paywall Builder. См. [Конвертация пейвола во флоу](convert-paywall-to-flow). |
| **Создание** | Скилл передаёт пейвол в [flow-generator](flow-generator-skill), который проектирует флоу. | Конвертация не может воспроизвести пейвол, или вы хотите переработать экран, а не скопировать его. |
| **Заглушка** | Скилл публикует минимальный однoэкранный флоу, чтобы плейсмент мог что-то отображать. | Крайний случай. Заглушка показывает пользователям placeholder, поэтому требует явного подтверждения. |

Скилл ищет существующие флоу перед тем, как что-то создавать, и сопоставляет их с вашими пейволами **только по названию** — Adapty не хранит информацию о том, из какого пейвола был создан флоу. Поэтому каждый найденный кандидат — это предложение для вашего подтверждения, и переименованный флоу найден не будет. Сверяйтесь с вашим [списком флоу](https://app.adapty.io/flows) — в CLI нет команды для удаления флоу, поэтому флоу, созданный по ошибке, нужно удалить в дашборде.

Доступность кнопки **Move to new builder** для конкретного пейвола скилл не может определить — она появляется только на пейволах, созданных в устаревшем Paywall Builder, а CLI не сообщает, каким билдером был создан пейвол. Скилл описывает кнопку и где её искать; вы сообщаете о том, что нашли.

## Что вы подтверждаете \{#what-you-approve\}

До создания чего-либо скилл выводит блок для ознакомления и ответа. В нём указаны ваше приложение, количество создаваемых плейсментов и полная таблица соответствия старых и новых ID — не сокращённый счётчик.

В том же блоке указано, что не входит в подтверждение:

- **Пейвол-плейсменты не затрагиваются**: Они продолжают работать на протяжении всего процесса, и это же является откатом — для пользователей ничего не меняется, пока приложение не выпустит новый вызов, поэтому невыход обновления откатывает миграцию.
- **Это ещё не достигает пользователей**: Приложение должно вызывать `getFlow` с новым ID плейсмента там, где сейчас вызывает старый.
- **Отказ останавливает создание плейсментов, но не флоу**: Любой флоу, созданный в ходе выполнения, остаётся в аккаунте, и CLI не умеет удалять флоу. Скилл указывает количество и место их удаления.

## Что вы получаете \{#what-you-get\}

Выполнение завершается счётчиками — созданных, пропущенных и неудачных с причинами — и таблицей, с которой работают разработчики:

| Старый пейвол-плейсмент | Новый флоу-плейсмент |
|---|---|
| `onboarding_main` | `onboarding_main-flow` |
| `paywall_settings` | `paywall_settings-flow` |

В SDK v4 `getFlow` читает как флоу-плейсменты, так и пейвол-плейсменты, поэтому приложение в любом случае вызывает один метод — меняется ID плейсмента, а не метод. Передайте реализацию скиллу SDK-интеграции для вашей платформы, который отвечает за вызовы на каждой платформе: [iOS](adapty-sdk-integration-skill) · [Android](adapty-sdk-integration-skill-android) · [React Native](adapty-sdk-integration-skill-react-native) · [Flutter](adapty-sdk-integration-skill-flutter) · [Unity](adapty-sdk-integration-skill-unity) · [Kotlin Multiplatform](adapty-sdk-integration-skill-kmp) · [Capacitor](adapty-sdk-integration-skill-capacitor).

Держите оба плейсмента активными, пока доля пользователей на v4 не станет достаточно высокой. У пользователей уже выпущенных версий старый ID плейсмента зашит в приложении, и они не смогут использовать флоу до обновления, поэтому каждый плейсмент измеряется по собственным метрикам в период параллельной работы — сравнивайте их как отдельные когорты. [Миграция на флоу](migrate-to-flows) охватывает весь переход.

## Что скилл не делает \{#what-it-wont-do\}

- **Конвертирует плейсмент на месте**: Такой операции не существует. Adapty отклоняет изменение типа, поэтому каждая миграция — это новый плейсмент.
- **Повторно использует старый ID плейсмента**: ID плейсментов уникальны в рамках всего приложения независимо от типа, поэтому новому флоу-плейсменту нужен ID, который не использует ни один другой плейсмент — включая заменяемый пейвол-плейсмент.
- **Затрагивает что-либо существующее**: Ни один существующий плейсмент, пейвол или флоу не редактируется и не удаляется. Скилл только читает их и создаёт рядом.
- **Создаёт плейсмент без вашего подтверждения**: Каждый предлагаемый ID проходит через [этап подтверждения](#what-you-approve) сначала.
- **Создаёт второй флоу для пейвола, у которого уже есть один**: Только если вы откажетесь от повторного использования существующего, поскольку дубликат придётся удалять вручную.
- **Пишет код вашего приложения**: Выполнение заканчивается на этапе передачи.

## Ограничения \{#limitations\}

#### Аудитория с несколькими сегментами требует предварительного разрешения \{#an-audience-with-several-segments-has-to-be-resolved-first\}

Аудитория, нацеленная более чем на один [сегмент](segments), может быть прочитана, но не записана обратно, поэтому скилл не может воссоздать её в новом плейсменте. Он сообщает о таких плейсментах как о заблокированных с указанием причины и не предлагает разбить или убрать сегмент — это изменило бы охват аудитории, а такое решение остаётся за вами. Разрешите ситуацию в дашборде, и остальная миграция продолжится без них.

#### A/B-тест аудитории недоступны скиллу \{#ab-test-audiences-arent-visible-to-the-skill\}

При чтении плейсмента возвращаются только пейвол- и флоу-аудитории, а остальные типы молча пропускаются. Аудитория [A/B-теста](ab-tests) относится к таким типам, и в ответе нет ничего, что указывало бы на пропущенную запись, поэтому скилл не может их обнаружить. Его счётчики описывают то, что вернул API. Для любого плейсмента, в котором, как вы знаете, запущен A/B-тест, просмотрите список аудиторий в дашборде — новый флоу-плейсмент не получит аудиторию, которую скилл никогда не видел.

#### Сквозная проверка возможна только после выпуска \{#nothing-is-verified-end-to-end-until-you-ship\}

Собственные проверки скилла останавливаются на «флоу опубликован, плейсмент существует». Работает ли флоу для реального пользователя — отдельный вопрос. Запускайте [flow-audit](flow-audit-skill) для каждого флоу перед публикацией и выполняйте тестовую покупку в песочнице через новый плейсмент после того, как приложение начнёт его вызывать.
