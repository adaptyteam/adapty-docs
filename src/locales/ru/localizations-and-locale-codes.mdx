<SDKv4>

Чтобы показывать каждому пользователю флоу на понятном ему языке, передайте список его языков в Adapty iOS SDK версии 4.5 или выше. Пользователь увидит флоу на том из предпочитаемых им языков, который поддерживает флоу. Если ни один из этих языков не поддерживается, флоу отображается на языке по умолчанию.

В SDK 4.0–4.4 приложение передаёт один код локали в `getFlowConfiguration`, и SDK [сопоставляет его точно](#pass-the-users-languages-to-the-sdk). Чтобы обновить код, читайте [Миграция Adapty iOS SDK на v4.5](migration-to-ios-sdk-45).

В SDK 4.5 и выше три случая подчиняются иным правилам:

- Приложения, которые выбирают локализацию флоу в собственном коде, [используют пользовательский резолвер](#pick-a-flows-localization-in-your-own-code).
- Пейволы из старого Paywall Builder [сопоставляют язык пользователя только по наивысшему приоритету](#select-a-localization-strategy).
- Кастомные пейволы и онбординги [работают так же, как в SDK 4.4](#localize-custom-paywalls-and-onboardings).

## Передайте языки пользователя в SDK \{#pass-the-users-languages-to-the-sdk\}

<Tabs groupId="ios-sdk-version" queryString>
<TabItem value="4.5" label="SDK 4.5 или новее" default>

[`AdaptyUI.getFlowConfiguration`](get-pb-paywalls#fetch-the-view-configuration) требует параметр `preferredLocales`. Передайте в него языки пользователя в порядке предпочтения (от наиболее предпочтительного). Ваше приложение само решает, какие языки передавать — например, системные языки устройства или язык, выбранный пользователем в настройках приложения.

```swift showLineNumbers
let flowConfiguration = try await AdaptyUI.getFlowConfiguration(
    forFlow: flow,
    preferredLocales: Locale.preferredLanguages
)
```

Три правила определяют, какую локализацию видят пользователи:

- SDK перебирает языки пользователя по порядку и выбирает первый, который есть во флоу. Это языковое сопоставление в стиле iOS: те же правила, по которым iOS выбирает язык приложения. SDK сопоставляет близкие варианты языка: `de-AT` совпадает с `de`, а `zh-TW` — с `zh-hant`. Пейволы из старого Paywall Builder используют только язык с наивысшим приоритетом.
- Регистр и разделители не важны: `pt_BR`, `pt-BR` и `pt-br` указывают на одну и ту же локаль. Передавайте значения в том виде, в котором их возвращает iOS.
- Если список пустой или ни одна локаль из него не совпадает с локалями флоу, SDK использует локаль по умолчанию.

Передайте один из трёх списков. Список задаёт порядок, в котором SDK перебирает языки, но не позволяет добавить язык, которого нет во флоу.

| Значение | Флоу отображается на | Компромисс |
|---|---|---|
| `Locale.preferredLanguages` | Первом языке устройства, который поддерживает флоу, даже если ваше приложение не переведено на него | Флоу может отображаться на другом языке, чем интерфейс вашего приложения |
| `Bundle.main.preferredLocalizations` | Языке интерфейса вашего приложения | Список содержит один язык. Если флоу не поддерживает его, пользователи видят локаль по умолчанию. В приложении с `Base.lproj` и без английской локализации список может содержать `Base`. |
| `[selectedLanguage] + Locale.preferredLanguages` | Языке, выбранном в переключателе языков вашего приложения, затем на языках устройства | — |

В двух случаях эти системные списки дают разные результаты:

- В вашем приложении есть только английский, а во флоу — французский и английский. Пользователь с французским языком видит французский через `Locale.preferredLanguages` и английский через `Bundle.main.preferredLocalizations`.
- В вашем приложении есть корейский, а во флоу — нет. Пользователь с корейским, а затем испанским, видит испанский через `Locale.preferredLanguages` и локаль по умолчанию через `Bundle.main.preferredLocalizations`.

:::tip
Не передавайте `Locale.current.identifier`. Он содержит только один язык, поэтому SDK не сможет попробовать другой. Его код не содержит скрипта: `zh_TW`, а не `zh-Hant-TW`. С таким идентификатором пейволы из старого Paywall Builder не найдут локализацию `zh-hant`.
:::

В большинстве приложений `localizationStrategy` не передаётся. Без него SDK использует [`.auto`](#select-a-localization-strategy), который подходит для флоу из Flow & Paywall Builder и пейволов из старого Paywall Builder.

</TabItem>
<TabItem value="4.4" label="SDK 4.0–4.4">

Передайте один код локали в параметре `locale` метода [`AdaptyUI.getFlowConfiguration`](get-pb-paywalls#fetch-the-view-configuration). Приложение само решает, какой код передать — например, локаль устройства или язык, выбранный пользователем в настройках.

```swift showLineNumbers
let flowConfiguration = try await AdaptyUI.getFlowConfiguration(
    forFlow: flow,
    locale: "pt-BR"
)
```

Совпадение точное. SDK сравнивает переданный вами код с кодами локализации флоу посимвольно: не меняет регистр, не заменяет подчёркивания (`_`) на дефисы (`-`) и не откатывается к языковому субтегу. Для флоу с локализацией `pt-BR` подойдёт только `pt-BR`: `pt-br`, `pt_BR` и `pt-PT` — не совпадут.

Если код не совпадает ни с одной локализацией, флоу незаметно отображается в своей [локали по умолчанию](add-paywall-locale-in-adapty-paywall-builder#set-the-default-locale) — SDK не возвращает ошибку и не пишет предупреждение.

Отсутствие кода локали — это не то же самое, что запрос дефолтной локализации флоу: SDK подставляет фиксированный `en`. Флоу, дефолтная локаль которого — `de`, всё равно отобразится на `en`, если у него есть локализация `en`, и только при её отсутствии вернётся к `de`.

:::warning
Передавайте код локали в точности так, как он указан в опубликованном флоу: например, `pt-BR`, а не `pt-br` из поля **Select languages**. Для пейволов из старого Paywall Builder используйте коды в нижнем регистре, например `pt-br`.

Не передавайте системный идентификатор локали как есть. На устройстве с Portuguese (Brazil) `Locale.current.identifier` вернёт `pt_BR`, что не совпадёт ни с одной локализацией. На устройстве с English (United States) `Locale.current.identifier(.bcp47)` вернёт `en-US`, что не найдёт флоу, у которого есть только `en`. Перед передачей системного идентификатора локали преобразуйте его в код, соответствующий флоу.
:::

## Проверьте, какую локализацию видит пользователь \{#test-which-localization-a-user-sees\}

<Tabs groupId="ios-sdk-version" queryString>
<TabItem value="4.5" label="SDK 4.5 или новее" default>

Если флоу не содержит ни одного языка пользователя, SDK использует локаль по умолчанию — без ошибок и предупреждений. Чтобы узнать, какую локализацию видит пользователь, протестируйте флоу на устройстве:

1. В настройках устройства переместите тестовый язык в начало списка языков.
2. Откройте флоу в вашем приложении.
3. Считайте `flowConfiguration.locale`. В нём содержится код отображаемой локализации. На дашборде этот код отображается в нижнем регистре: `pt-br` для `pt-BR`.

Чтобы протестировать язык без изменения настроек устройства, передайте фиксированный список `preferredLocales`, например `["pt-PT"]`, в отладочной сборке.

</TabItem>
<TabItem value="4.4" label="SDK 4.0–4.4">

Если переданный вами код не соответствует ни одной локализации флоу, SDK использует локализацию по умолчанию, не выдавая ошибку и не записывая предупреждение. Чтобы узнать, какую локализацию видит пользователь, протестируйте флоу на устройстве:

1. В настройках устройства выберите нужный язык и регион.
2. Откройте флоу в приложении.
3. Прочитайте `flowConfiguration.locale`. Оно содержит код отображаемой локализации. Если он отличается от переданного вами кода, значит в флоу нет локализации с точно таким кодом.

Чтобы протестировать код без изменения настроек устройства, передайте фиксированную `locale`, например `"pt-BR"`, в debug-сборке.

</TabItem>
</Tabs>

Если часть флоу по-прежнему отображается на языке по умолчанию, значит для этой части нет перевода в выбранной локализации. Чтобы заполнить пробелы, [переведите недостающие строки](add-paywall-locale-in-adapty-paywall-builder#manage-localizations-and-translations) в Flow & Paywall Builder.

## Выберите локали для добавления во флоу \{#select-which-locales-to-add-to-a-flow\}

Чтобы охватить большинство пользователей с минимальным количеством локалей, при [добавлении локалей](add-paywall-locale-in-adapty-paywall-builder#add-and-set-up-a-locale) в поле **Select languages** придерживайтесь трёх правил:

- Добавьте язык без указания региона. Например, `de` охватывает немецкоязычных пользователей в Германии, Австрии и Швейцарии.
- Региональную локаль добавляйте только для второго перевода одного языка — например, `fr-ca` в дополнение к `fr`.
- Добавьте все языки, на которых читают ваши пользователи. SDK не подбирает похожий язык автоматически — например, каталанский не заменяется испанским. Пользователи, говорящие на каталанском, увидят следующий предпочтительный язык, доступный во флоу, или язык по умолчанию.

:::important
Эти правила требуют iOS или [Android](android-localizations-and-locale-codes) SDK 4.5 или выше. Приложения на любой версии Adapty SDK от 4.0 до 4.4 передают один код локали. Их пользователи могут видеть другую локализацию того же флоу, чем пользователи на SDK 4.5. Сохраняйте все коды, которые эти приложения передают, например существующий `zh` или `pt-br`.
:::

### Выберите коды для китайского, испанского и португальского \{#select-codes-for-chinese-spanish-and-portuguese\}

В поле **Select languages** представлено несколько кодов для китайского, испанского и португальского языков. Добавьте коды из таблицы:

| Язык | Добавить | Пользователи видят |
|---|---|---|
| Китайский | `zh-hans` и `zh-hant`, не новый `zh`. Добавляйте `zh-hk` только для отдельного перевода для Гонконга. | `zh-hans` в Китае и Сингапуре, и `zh-hant` на Тайване, в Гонконге и Макао. |
| Кантонский | `yue`, всегда вместе с `zh-hant` | `yue` на устройствах с кантонским языком, и `zh-hant` на устройствах с традиционным китайским. Без `zh-hant` пользователи с традиционным китайским видят письменный кантонский. |
| Испанский | `es` и `es-419`, не новый `es-mx` | `es` в Испании, и `es-419` в Латинской Америке и США. |
| Португальский | `pt-br` для бразильского португальского, и `pt` для европейского португальского | `pt-br` в Бразилии, и `pt` в Португалии. |

Если ваш флоу локализован для нескольких региональных вариантов одного языка, добавьте также менее специфичный локаль — чтобы охватить языковые варианты, которые не входят в явно заданные вами. Без такого резерва пользователи из других регионов получат случайный локаль из языковой группы, и вы не сможете контролировать, какой именно. Например, пользователь с локалью `es-MX` может увидеть `es-ar`, `es-co` или `es-es`. Чтобы охватить таких пользователей, добавьте локаль без региона `es` или общеамериканский локаль `es-419`.

### Начните с рекомендованного набора локалей \{#start-from-a-recommended-set-of-locales\}

Чтобы планировать переводы поэтапно, начните с одного из трёх наборов. Каждый последующий набор включает предыдущий.

| Набор | Локали | Итого |
|---|---|---|
| Минимальный | `en`, `es`, `pt-br`, `fr`, `de`, `it`, `ru`, `ja`, `ko`, `zh-hans`, `zh-hant` | 11 |
| Расширенный | Минимальный набор и `tr`, `pl`, `nl`, `sv`, `da`, `no`, `fi`, `uk`, `ar`, `he`, `hi`, `id`, `th`, `vi`, `es-419`, `pt` | 27 |
| Широкий | Расширенный набор и `cs`, `sk`, `hu`, `ro`, `el`, `bg`, `hr`, `sl`, `lt`, `lv`, `et`, `ca`, `kk`, `ms`, `fil`, `fa`, `ur`, `bn`, `ta`, `te`, `mr`, `fr-ca` | 49 |

В этих наборах пользователи видят следующие локали:

- В минимальном наборе `es` охватывает испаноязычных пользователей во всех странах, а `pt-br` охватывает также португалоязычных пользователей в Португалии.
- В расширенном наборе `es-419` и `pt` — это дополнительные переводы. С ними `es` обслуживает Испанию, а `pt` — Португалию. Переводите `pt` на европейский португальский.
- Носители каталанского и малайского видят только свой язык в соответствующей локали: `ca` или `ms`. SDK не показывает им испанский или индонезийский вместо их языка.

### Выберите локаль по умолчанию \{#select-the-default-locale\}

Локаль по умолчанию используется, когда во флоу нет ни одного из языков пользователя. Новый флоу создаётся с `en` в качестве единственной локали и локали по умолчанию. Чтобы изменить это, [задайте другую локаль как локаль по умолчанию](add-paywall-locale-in-adapty-paywall-builder#set-the-default-locale).

Соблюдайте три правила для локали по умолчанию:

- Для пользователей без подходящей локали выбирайте язык, понятный большинству из них. Как правило, это английский, а не язык вашего основного рынка.
- Полностью переведите локаль по умолчанию. Пользователи без подходящей локали видят весь флоу на языке локали по умолчанию. Пользователи с подходящей локалью видят флоу на своём языке. Непереведённые части отображаются на языке локали по умолчанию.
- Не выбирайте язык с двумя системами письма, например китайский. Пользователи с другой системой письма могут не понять локаль по умолчанию.

## Выберите стратегию локализации \{#select-a-localization-strategy\}

Большинство приложений не передают `localizationStrategy`, поэтому SDK использует `.auto`. Эта стратегия применяет языковое сопоставление iOS для флоу из Flow & Paywall Builder и правило единственного языка для пейволов из старого Paywall Builder.

В рамках правила одного языка SDK считывает только язык с наивысшим приоритетом в `preferredLocales`. Он пробует полный код, затем укороченные коды (`pt-br`, затем `pt`), а при неудаче показывает локаль по умолчанию. Пейвол из старого Paywall Builder продолжает работать по этому правилу даже после повторной публикации. Чтобы SDK перебирал все языки в `preferredLocales`, [перенесите пейвол в Flow & Paywall Builder](convert-paywall-to-flow). Затем отображайте новый флоу через плейсмент флоу.

Чтобы изменить способ сопоставления языков пользователя с локалями флоу, передайте одно из следующих значений в параметре `localizationStrategy`:

- `.system`: все флоу используют iOS-сопоставление языков, включая пейволы из старого Paywall Builder.
- `.legacy`: все флоу используют правило единственного языка, а не точное сопоставление SDK 4.4. Не передавайте `.legacy` для флоу из Flow & Paywall Builder: он не находит локали с регионом или скриптом, например `pt-BR`.
- `.custom(resolver:fallbackResolver:)`: [выбор локализации — в вашем коде](#pick-a-flows-localization-in-your-own-code).

### Выбор локализации флоу в собственном коде \{#pick-a-flows-localization-in-your-own-code\}

iOS не всегда правильно определяет язык. Например, если на устройстве указан азербайджанский язык на кириллице (`az-Cyrl`), но не на латинице, флоу с локалью `az` будет отображаться в локализации по умолчанию. Чтобы принудительно показать `az` или выбирать локализацию по собственным правилам, создайте тип, соответствующий протоколу `AdaptyUICustomLocalizationResolver`. Затем передайте его в значении `.custom(resolver:)` параметра `localizationStrategy`. Добавьте `import AdaptyUIBuilder` в файл с резолвером.

Другие SDK Adapty подбирают язык по иным правилам, поэтому один и тот же пользователь может видеть разные локализации флоу на iOS и Android. Чтобы на всех платформах отображалась одна и та же локализация, напишите резолвер, который возвращает тот же код локали, что и приложение на других платформах.

К резолверу применяются следующие правила:

- SDK не вызывает резолвер для флоу с одной локализацией. Флоу отображается в этой локализации.
- SDK вызывает `resolve(for:from:)` со списком, который передало ваше приложение, и `AdaptyUILocalizationSource` с `locales` и `defaultLocale` флоу. `locales` приходят в произвольном порядке.
- Чтобы показать локализацию, верните код из `locales` или `defaultLocale`, написанный точно так же, включая регистр: `ar`, а не `AR`.
- Если резолвер возвращает любой другой код или `nil`, SDK использует стратегию из `fallbackResolver`. Без `fallbackResolver` SDK использует `.auto`.
- SDK может вызывать резолвер не из главного потока.
- Возвращайте код сразу, без сетевых запросов и другой медленной работы. SDK ждёт резолвер без ограничения по времени, и флоу отображается только после того, как резолвер вернёт значение.

## Стандарт кодов локалей в Adapty \{#locale-code-standard-at-adapty\}

Коды локалей Adapty следуют [стандарту BCP 47](https://en.wikipedia.org/wiki/IETF_language_tag): языковой подтег, затем необязательный подтег скрипта или региона, разделённые дефисами. Поле **Select languages** отображает коды в нижнем регистре: `en` (английский), `pt-br` (португальский, Бразилия), `zh-hans` (упрощённый китайский) и `zh-hant` (традиционный китайский).

## Локализация пользовательских пейволов и онбордингов \{#localize-custom-paywalls-and-onboardings\}

SDK 4.5 меняет правила локализации только для флоу. Пользовательские пейволы и онбординги работают так же, как в SDK 4.4.

### Выберите Remote Config пользовательского пейвола по языку \{#pick-a-custom-paywalls-remote-config-by-language\}

`getFlow` не имеет параметра локали. Для пользовательского пейвола метод возвращает все настроенные локализации в `flow.remoteConfigs`. Каждая запись содержит код `locale` и содержимое конфига (`jsonString` или распарсенный `dictionary`). Выберите запись, соответствующую пользователю, реализовав собственный фолбэк:

```swift showLineNumbers
do {
    let flow = try await Adapty.getFlow(placementId: "YOUR_PLACEMENT_ID")
    let config = flow.remoteConfigs.first(where: { $0.locale == "en" })
        ?? flow.remoteConfigs.first
    // read your values from config?.dictionary
} catch {
    // handle the error
}
```

Adapty хранит коды `locale` в формате, описанном в [Стандарт кода локали в Adapty](#locale-code-standard-at-adapty). SDK не сопоставляет Remote Config с локалью автоматически, поэтому выбор нужной записи остаётся на стороне приложения.

### Передача локали в онбординг \{#pass-a-locale-to-an-onboarding\}

<OnboardingDeprecation />

`getOnboarding` сохраняет параметр `locale` в SDK 4.5. Когда вы передаёте `locale` в [`getOnboarding`](get-onboardings), сервер выбирает локализацию:

1. Строка локали приводится к нижнему регистру, а все символы подчёркивания (`_`) заменяются дефисами (`-`)
2. Adapty ищет локализацию с полностью совпадающим кодом локали
3. Если совпадение не найдено, Adapty берёт подстроку до первого дефиса (`pt` для `pt-br`) и ищет соответствующую локализацию
4. Если совпадение снова не найдено, Adapty возвращает контент для локали онбординга по умолчанию

Таким образом, `pt_BR`, `pt-BR` и `pt-br` — все они разрешаются в одну и ту же локализацию онбординга.

## Почему это важно \{#why-this-is-important\}

Есть несколько сценариев, где используются коды локалей — например, когда нужно получить правильный пейвол для текущей локализации вашего приложения.

Поскольку коды локалей устроены непросто и могут различаться от платформы к платформе, мы используем внутренний стандарт для всех поддерживаемых платформ. Тем не менее именно из-за их сложности вам важно понимать, что именно вы отправляете на наш сервер для получения нужной локализации и что происходит дальше — чтобы вы всегда получали то, что ожидаете.

## Стандарт кодов локалей в Adapty \{#locale-code-standard-at-adapty\}

Для кодов локалей Adapty использует слегка модифицированный стандарт [BCP 47](https://en.wikipedia.org/wiki/IETF_language_tag): каждый код состоит из строчных подтегов, разделённых дефисами. Примеры: `en` (английский), `pt-br` (португальский (Бразилия)), `zh` (упрощённый китайский), `zh-hant` (традиционный китайский).

## Сопоставление кода локали \{#locale-code-matching\}

Когда Adapty получает вызов от SDK с кодом локали и начинает искать соответствующую локализацию пейвола, происходит следующее:

1. Входящая строка локали приводится к нижнему регистру, а все символы подчёркивания (`_`) заменяются дефисами (`-`)
2. Затем мы ищем локализацию с полностью совпадающим кодом локали
3. Если совпадение не найдено, берётся подстрока до первого дефиса (`pt` для `pt-br`) и выполняется поиск соответствующей локализации
4. Если совпадение снова не найдено, возвращается контент для локали пейвола по умолчанию

Таким образом устройство iOS, отправившее `'pt_BR'`, устройство Android, отправившее `pt-BR`, и другое устройство, отправившее `pt-br`, получат одинаковый результат.

## Реализация локализаций: рекомендуемый способ \{#implementing-localizations-recommended-way\}

Если вас интересуют локализации, скорее всего, вы уже работаете с файлами локализованных строк в своём проекте. В таком случае мы рекомендуем добавить пару ключ-значение с нужным кодом языка Adapty в каждый из ваших файлов для соответствующих локализаций, а затем извлекать значение по этому ключу при вызове нашего SDK:

```swift showLineNumbers
// 1. Modify your Localizable.strings files

/*
Localizable.strings - Spanish
*/
adapty_paywalls_locale = "es";
/*
Localizable.strings - Portuguese (Brazil)
*/
adapty_paywalls_locale = "pt-br";
// 2. Extract and use the locale code
let locale = NSLocalizedString("adapty_paywalls_locale", comment: "")
// pass locale code to AdaptyUI.getViewConfiguration or Adapty.getPaywall method
```

Так вы полностью контролируете, какая локализация будет загружена для каждого пользователя вашего приложения.

## Реализация локализаций: альтернативный способ \{#implementing-localizations-the-other-way\}

Похожего (но не идентичного) результата можно добиться, не задавая явно коды языков для каждой локализации. Для этого нужно извлекать код языка из других объектов, предоставляемых платформой:

```swift showLineNumbers
let locale = Locale.current.identifier
// pass locale code to AdaptyUI.getViewConfiguration or Adapty.getPaywall method
```

Мы не рекомендуем этот подход по ряду причин:

1. На iOS предпочитаемые языки и текущая локаль — не одно и то же. Чтобы локализация выбиралась корректно, придётся либо полагаться на логику Apple (которая работает автоматически при использовании рекомендованного подхода с файлами локализованных строк), либо воссоздавать её самостоятельно.
2. Сложно предсказать, что именно получит сервер Adapty. Например, на iOS устройство может вернуть локаль вида `ar_OM@numbers='latn'`, и в ответ вы получите не локализацию `ar-om`, которую ожидали, а `ar` — что, скорее всего, окажется неожиданным.

Should you decide to use this approach anyway — make sure you've covered all the relevant use cases.
