## Перед началом работы \{#before-you-start\}

Вам понадобится:

- **Adapty Flutter SDK версии 4.4 или выше**: более ранние версии показывают резервный вариант для каждого кастомного элемента.
- **Нативный код для iOS и Android**: Flutter-виджет нельзя отобразить в кастомном элементе. Напишите представления и резолвер на Swift для iOS и на Kotlin для Android. Добавьте Swift-код в таргет `Runner` в Xcode, а Kotlin-код — в `android/app/src/main/kotlin`.
- **Библиотека Adapty UI для Android**: в Gradle-файле модуля вашего Android-приложения (например, `android/app/build.gradle.kts`) добавьте `implementation("io.adapty:android-ui")` в блок `dependencies`. Не указывайте версию и не подключайте Adapty BOM: версию задаёт `adapty_flutter`, а более новый `android-ui` может сломать флоу.
- **Jetpack Compose на Android — для Composable-компонентов**: шаблон Flutter не [настраивает Compose](https://developer.android.com/develop/ui/compose/setup-compose-dependencies-and-compiler) в модуле приложения. Чтобы возвращать Composable из резолвера, подключите плагин Compose compiler Gradle и установите `compose = true` в блоке `buildFeatures`. Для Android `View` Compose не нужен. Для Lottie-представления, рассмотренного на этой странице, также добавьте `com.airbnb.android:lottie-compose`.
- **Схема именования кастомных элементов**: задайте каждому нативному представлению Type, например `lottie_animation`. Используйте в Types только строчные буквы, цифры и знаки подчёркивания. Чтобы различать кастомные элементы одного Type, присвойте каждому ID, например `welcome_wave`. Types и ID в коде должны совпадать с теми, что указаны в [Flow & Paywall Builder](flow-custom-elements#add-and-configure).

Используйте одинаковые типы и идентификаторы в коде для iOS и Android. Если вы не настроили отдельную [аудиторию](audience) для каждой платформы, пользователи iOS и Android будут видеть одинаковые флоу.

## Создание представлений для пользовательских элементов \{#create-views-for-custom-elements\}

Для каждого типа создайте нативное представление для iOS и Android или повторно используйте уже существующее из вашего нативного кода. Следующие представления типа `lottie_animation` воспроизводят анимацию Lottie. Представление для Android — это composable-компонент, использующий библиотеку `com.airbnb.android:lottie-compose`:

### Требования и лучшие практики \{#requirements-and-best-practices\}

- **Размер**:
  - **Отступы и выравнивание**: убедитесь, что нативный вид вписывается в контейнер, который вы выделили для него во Flow & Paywall Builder, с учётом отступов. Если вид не занимает всю область, по умолчанию он отображается в верхнем начальном углу этой области. Чтобы изменить положение, настройте выравнивание в разделе **Layout** кастомного элемента.
  - **Высота Hug**: если высота кастомного элемента задана как **Hug**, вид, который растягивается на всё доступное пространство (например, карта или ленивый список), схлопнется или растянется до высоты экрана. Задайте кастомному элементу [фиксированную высоту (**Fixed**)](flow-custom-elements#add-and-configure).
- **Тема**: нативные виды не наследуют цвета и шрифты вашей Flutter-темы. Задайте их в нативном коде.
- **Действия флоу**: нативный вид не может выполнять действия флоу, например переход на следующий экран. Контекст элемента позволяет отправлять сообщения во флоу — через `sendMessage` на iOS и `send` на Android, — но они зарезервированы для будущих возможностей Flow & Paywall Builder. Кнопки навигации, кнопки покупки и другие кнопки с действиями флоу размещайте за пределами кастомного элемента.
- **Выбираемые элементы**: размещайте кастомный элемент за пределами карточек продуктов и других [выбираемых элементов](flow-selectable-elements). При изменении выбора нативный вид может потерять своё состояние.
- **Обработка навигации**: когда пользователь переходит на следующий экран, SDK удаляет нативный вид с экрана. Остановите всё, что вид запустил, — например, сессии камеры, плееры и обновление геолокации:
  - **SwiftUI view**: используйте действие `onDisappear`. Для асинхронной работы используйте `.task` — SwiftUI отменяет его, когда вид исчезает.
  - **Composable**: используйте блок `onDispose` внутри `DisposableEffect`. Для асинхронной работы используйте `LaunchedEffect` — Compose отменяет его, когда composable покидает композицию.
  - **Android `View`**: переопределите `onDetachedFromWindow` в подклассе вашего `View` или добавьте `View.OnAttachStateChangeListener` к `View`.

  Когда пользователь возвращается, или на Android после изменения конфигурации (например, поворота экрана), SDK вызывает resolver заново, и нативный вид запускается без состояния предыдущего.
- **Виды UIKit**: На iOS оберните их в `UIViewRepresentable`.
- **Карусели**: На Android в [карусели](builder-containers#carousel) нативные виды на всех слайдах остаются активными, пока экран открыт, а не только вид на видимом слайде. Не помещайте в карусели превью с камеры и плееры со звуком.

## Написание резолвера для сопоставления пользовательских элементов и представлений \{#write-a-resolver-to-match-custom-elements-and-views\}

Напишите резолвер для каждой платформы. Резолвер получает тип и ID пользовательского элемента и возвращает соответствующее нативное представление.

<Tabs groupId="platform" queryString>
<TabItem value="ios" label="iOS (Swift)" default>

Чтобы написать резолвер, реализуйте соответствие типа протоколу `AdaptyUICustomElementsResolver` и реализуйте метод `view(forType:id:context:)`.

Для типа `lottie_animation` следующий резолвер возвращает `LottieElementView`. ID указывает имя файла анимации в бандле приложения, например `welcome_wave`:

```swift showLineNumbers title="Swift"

struct CustomElementsResolver: AdaptyUICustomElementsResolver {
    func view(
        forType type: String,
        id: String,
        context: AdaptyUICustomElementContext
    ) -> AnyView? {
        switch type {
        case "lottie_animation":
            // the ID names the animation file, such as welcome_wave.json
            guard let animation = LottieAnimation.named(id) else {
                return nil // no file for this ID: show the fallback
            }
            return AnyView(LottieElementView(animation: animation))
        default:
            return nil
        }
    }
}
```

В случае `default` возвращайте `nil`.

</TabItem>
<TabItem value="android" label="Android (Kotlin)">

Чтобы написать резолвер, реализуйте интерфейс `AdaptyCustomElementsResolver`. Его метод `resolve` возвращает подходящий view в одном из следующих видов:

- **Composable**: Верните `AdaptyCustomElementContent.compose`, внутри лямбды — сам composable.
- **Android `View`**: Верните `AdaptyCustomElementContent.view`, передав функцию создания `View`. Укажите имя параметра `factory`: `AdaptyCustomElementContent.view(factory = { context, _ -> ChartView(context) })`. Без имени Kotlin передаёт трейлинговую лямбду в опциональный параметр `update`, и код не компилируется.

Для типа `lottie_animation` следующий резолвер возвращает [Lottie view](#create-views-for-custom-elements). ID указывает на файл анимации в папке `assets`, `android/app/src/main/assets`, например `welcome_wave` для `welcome_wave.json`:

```kotlin showLineNumbers title="Kotlin"

class CustomElementsResolver(context: Context) : AdaptyCustomElementsResolver {
    // the animation files in the assets folder, listed once
    private val animationFiles: Set<String> = try {
        context.assets.list("").orEmpty().toSet()
    } catch (e: IOException) {
        emptySet() // no list of files: every Lottie element shows the fallback
    }

    override fun resolve(type: String, id: String): AdaptyCustomElementContent? =
        when (type) {
            "lottie_animation" -> {
                // the ID names the animation file, such as welcome_wave.json
                val file = "$id.json"
                if (file in animationFiles) {
                    AdaptyCustomElementContent.compose { LottieElement(file) }
                } else {
                    null // no file for this ID: show the fallback
                }
            }
            else -> null
        }
}
```

Для любого другого типа верните `null`.

</TabItem>
</Tabs>

Если вы [добавите пользовательский элемент с новым типом](flow-custom-elements#what-changes-require-an-app-release) после релиза приложения, пользователи выпущенной версии увидят его фолбэк.

К резолверу предъявляются следующие требования:

- **Сетевые данные и плееры**: Храните сетевые данные и плееры в состоянии [нативного вью](#create-views-for-custom-elements), а не в резолвере. SDK вызывает резолвер много раз, пока экран открыт. Код в резолвере выполняется заново при каждом вызове, поэтому сетевые запросы повторяются, а плееры начинают сначала. Нативный вью сохраняет своё состояние между этими вызовами, поэтому данные загружаются один раз, а плееры продолжают воспроизведение. Создавайте плееры, сессии и сетевые запросы внутри нативного вью:
  - **SwiftUI view**: Создавайте плееры, сессии и сетевые запросы в `.task` или `@StateObject`, а не в начальном значении свойства `@State`. Swift вычисляет это начальное значение заново каждый раз, когда резолвер создаёт вью.
  - **Composable**: Создавайте плееры и сессии в `remember`, а сетевые запросы — в `LaunchedEffect`.
  - **Android `View`**: Создавайте плееры, сессии и сетевые запросы в `onAttachedToWindow`.
- **Один нативный вью на каждый кастомный элемент**: Некоторые нативные вью изменяются, пока экран открыт, — например, когда загружаются их данные или когда пользователь нажимает на них. Реализуйте эту логику в самом нативном вью, а не в резолвере. Если резолвер возвращает другой вью для того же кастомного элемента, вью теряет своё состояние.
- **Новый `View` при каждом появлении**: На Android создавайте новый `View` при каждом вызове `factory`. SDK вызывает `factory` каждый раз, когда кастомный элемент появляется: при открытии экрана, при возврате пользователя на экран или после поворота.
- **Данные приложения**: Храните объект с данными, например `ObservableObject` или `StateFlow` с [ежедневной серией](flutter-custom-element-lottie-animation), в свойстве резолвера. Передайте объект в нативный вью и наблюдайте за ним там:
  - **SwiftUI view**: Наблюдайте за `ObservableObject` через `@ObservedObject`.
  - **Composable**: Собирайте `StateFlow` через `collectAsState` или наблюдайте за `LiveData` через `observeAsState`.
  - **Android `View`**: Начинайте наблюдение за объектом в `onAttachedToWindow`, а останавливайте — в `onDetachedFromWindow`.

  Значение, которое вы копируете в резолвер, например номер серии дней, остаётся таким, каким оно было в момент создания резолвера. Если нужные данные, например серия дней, находятся в вашем Dart-коде — передавайте каждое новое значение в нативный код через [platform channel](https://docs.flutter.dev/platform-integration/platform-channels) и обновляйте объект там.

### Задайте условия для резервного контента \{#set-conditions-for-fallback-content\}

<FlowCustomElementsFallbackConditions />

Возвращайте пустое представление только в том случае, если пользователь уже отказал в разрешении до открытия экрана. На Android метод `ContextCompat.checkSelfPermission` возвращает одинаковое значение — `PERMISSION_DENIED` — в двух ситуациях: до того, как приложение впервые запросило разрешение, и после того, как пользователь отказал. Чтобы различить эти случаи, сохраняйте результат запроса разрешения и читайте его в резолвере. Если приложение ещё не запрашивало разрешение, возвращайте нативное представление и запрашивайте разрешение внутри него. Например, запросите доступ к геолокации, когда появляется [представление карты](flutter-custom-element-map#3-match-the-map-to-the-custom-element), и показывайте карту сразу после того, как пользователь даст разрешение. Если вы вернёте пустое представление, а пользователь затем предоставит доступ, он всё равно увидит резервный вариант. Изменение разрешения не заставляет SDK повторно вызывать резолвер. Нативное представление появится только после следующего вызова резолвера со стороны SDK — например, когда пользователь вернётся на экран.

## Передайте resolver в SDK \{#pass-the-resolver-to-the-sdk\}

Настройте resolver один раз для каждой платформы при запуске приложения. SDK вызывает его в каждом флоу, включая флоу, встроенный с помощью `AdaptyUIFlowPlatformView`. Пользователи видят ваши нативные элементы в новых флоу и A/B-тестах без обновления приложения. Эти элементы по-прежнему отображают данные конкретного пользователя, например [ежедневную серию](flutter-custom-element-lottie-animation), считывая их из вашего приложения.

<Tabs groupId="platform" queryString>
<TabItem value="ios" label="iOS (Swift)" default>

В файле `ios/Runner/AppDelegate.swift` импортируйте `AdaptyUI` и вызовите `AdaptyUI.setCustomElementsResolver(_:)` в методе `application(_:didFinishLaunchingWithOptions:)`. Остальную часть класса `AppDelegate` оставьте без изменений:

```swift showLineNumbers title="ios/Runner/AppDelegate.swift"

// in application(_:didFinishLaunchingWithOptions:), before `return super.application(...)`
AdaptyUI.setCustomElementsResolver(CustomElementsResolver())
```

Если резолвер реализован в том же файле `AppDelegate.swift`, импортируйте там и `AdaptyUIBuilder`.

</TabItem>
<TabItem value="android" label="Android (Kotlin)">

Вызовите `AdaptyUI.setCustomElementsResolver` в методе `onCreate` вашего класса `Application`. Если у вашего приложения ещё нет класса `Application`, создайте его:

```kotlin showLineNumbers title="Kotlin"

class App : Application() {
    override fun onCreate() {
        super.onCreate()
        AdaptyUI.setCustomElementsResolver(CustomElementsResolver(this))
    }
}
```

В файле `android/app/src/main/AndroidManifest.xml` укажите класс `Application` в атрибуте `android:name` элемента `<application>`. Шаблон Flutter задаёт этому атрибуту значение `${applicationName}`, соответствующее базовому классу `Application`:

```xml showLineNumbers title="AndroidManifest.xml" {2}
<application
    android:name=".App"
    android:label="your_app">
    <!-- the rest of your application element -->
</application>
```

</TabItem>
</Tabs>

:::tip
Чтобы отображать одинаковое представление для каждого кастомного элемента определённого Type, передайте словарь Types и представлений вместо resolver'а. На iOS словарь имеет тип `[String: AdaptyUICustomElementBuilder]`. На Android передайте словарь в `AdaptyCustomElementsResolver.of`. Словарь требует меньше кода, чем resolver, но не позволяет [задавать условия для резервного контента](#set-conditions-for-fallback-content).

```swift showLineNumbers title="Swift"
AdaptyUI.setCustomElementsResolver([
    "lottie_animation": .init { _, id, _ in LottieElementView(animation: .named(id)) },
])
```

```kotlin showLineNumbers title="Kotlin"
val appWideViews = mapOf(
    "confetti" to AdaptyCustomElementContent.compose { LottieElement("confetti.json") },
)
AdaptyUI.setCustomElementsResolver(AdaptyCustomElementsResolver.of(appWideViews))
```
:::

Нельзя привязать резолвер к одному флоу. Чтобы отображать данные, которые ваше приложение получает только при открытии флоу, передайте эти данные в нативный код до открытия флоу. Затем прочитайте их в резолвере. Например, пейвол отображает [вес, введённый пользователем в предыдущем флоу](flutter-custom-element-interactive-chart).

## Тестирование на устройстве \{#test-on-a-device\}

Paywall Builder не может выполнять код вашего приложения, поэтому на его холсте отображается только резервный вариант. Ошибка в нативном представлении может привести к краху приложения. Перед релизом протестируйте каждый экран с кастомным элементом на устройстве iOS и на устройстве Android:

1. Чтобы видеть последнюю опубликованную версию каждого флоу, а не кешированную, зарегистрируйте устройство как [тестовое](test-devices).
2. На устройстве запустите сборку с резолвером. Откройте каждый экран с кастомным элементом и убедитесь, что нативный вид отображается и вписывается в кастомный элемент. Если вид поддерживает прокрутку или реагирует на жесты перетаскивания, проверьте их.
3. Если вместо нативного вида отображается фолбэк, найдите в консоли Xcode или в Logcat следующее предупреждение: `custom element <type>:<id> is not served by a resolver`. Затем убедитесь, что:
   - Type и ID в предупреждении совпадают с указанными в вашем коде, символ в символ.
   - В приложении есть файл, данные или разрешение, необходимые для этого вида.
   - Приложение устанавливает резолвер при запуске: в классе `AppDelegate` на iOS и в классе `Application`, указанном в `AndroidManifest.xml` на Android.

   Si предупреждение не появляется, убедитесь, что приложение использует Adapty Flutter SDK 4.4 или новее, и что [уровень логирования](sdk-installation-flutter#logging) не равен `AdaptyLogLevel.error`.
4. На Android, если кастомный элемент остаётся пустым, найдите одно из следующих предупреждений в Logcat:
   - `custom element <type>:<id> is not served by a resolver`: У кастомного элемента нет резервного содержимого, и ни один resolver не возвращает для него представление. Проверьте каждый пункт в шаге 3.
   - `content does not report its size`: У composable нет собственной высоты. Задайте кастомному элементу [**фиксированную** высоту](flow-custom-elements#add-and-configure).

   SDK записывает предупреждение о размере только для composable-элементов. Если Android `View` остаётся пустым без предупреждения, задайте кастомному элементу фиксированную высоту (**Fixed**) тоже.
5. Чтобы просмотреть резервный вариант, не возвращайте вид для данного Type и откройте экран снова.

## Примеры \{#examples\}

Каждый рецепт показывает настройку в билдере и код для вашего приложения:

- [Отображение прогресса пользователя с анимацией Lottie](flutter-custom-element-lottie-animation): Кольцо, которое заполняется по мере роста серии.
- [Интерактивный график цели по весу на пейволе](flutter-custom-element-interactive-chart): График цели по весу на пейволе, который следует за онбординг-флоу.
- [Показ ближайших мест на карте во флоу](flutter-custom-element-map): Карта фитнес-центров рядом с каждым пользователем.

Каждый рецепт содержит полный резолвер, класс `AppDelegate` и класс `App`. Чтобы использовать несколько рецептов одновременно, сохраните по одному экземпляру каждого: объедините ветки `case` резолверов, а также сторы и каналы классов `AppDelegate` и `App`.
