<SDKv4>

要为每位用户显示其可读语言的流程，请将用户语言传递给 Adapty iOS SDK 4.5 或更高版本。用户将看到流程中与其最优先语言匹配的版本。若流程不包含这些语言中的任何一种，则以默认语言显示。

在 SDK 4.0–4.4 上，您的应用会向 `getFlowConfiguration` 传递一个语言代码，SDK [精确匹配该代码](#pass-the-users-languages-to-the-sdk)。如需更新代码，请参阅 [将 Adapty iOS SDK 迁移至 v4.5](migration-to-ios-sdk-45)。

在 SDK 4.5 或更高版本上，以下三种情况遵循其他规则：

- 在自有代码中选择流程语言的应用，请[使用自定义解析器](#pick-a-flows-localization-in-your-own-code)。
- 旧版付费墙编辑工具中的付费墙，[仅按最高优先级匹配用户语言](#select-a-localization-strategy)。
- 自定义付费墙和用户引导的处理方式[与 SDK 4.4 相同](#localize-custom-paywalls-and-onboardings)。

## 将用户语言传递给 SDK \{#pass-the-users-languages-to-the-sdk\}

<Tabs groupId="ios-sdk-version" queryString>
<TabItem value="4.5" label="SDK 4.5 or later" default>

[`AdaptyUI.getFlowConfiguration`](get-pb-paywalls#fetch-the-view-configuration) 需要 `preferredLocales` 参数。请将用户的语言按优先级从高到低依次传入。您的应用可以自行决定传哪些语言，例如设备语言或应用内语言选择器中选定的语言。

```swift showLineNumbers
let flowConfiguration = try await AdaptyUI.getFlowConfiguration(
    forFlow: flow,
    preferredLocales: Locale.preferredLanguages
)
```

Three rules decide which localization users see:

- SDK 会按顺序尝试用户的语言列表，并匹配流程中第一个支持的语言。这遵循 iOS 的语言匹配规则：即 iOS 用于选择应用语言的规则。SDK 支持匹配相近的语言变体：`de-AT` 可匹配 `de`，`zh-TW` 可匹配 `zh-hant`。旧版付费墙编辑工具创建的付费墙仅使用优先级最高的用户语言。
- 大小写和分隔符不影响匹配：`pt_BR`、`pt-BR` 和 `pt-br` 匹配同一语言区域。请按 iOS 返回的原始格式传入值。
- 若列表为空，或列表中没有任何语言与流程支持的语言区域匹配，SDK 将使用默认语言区域。

传入以下三种列表之一。该列表决定 SDK 尝试语言的顺序，但无法添加流程中本不支持的语言。

| 值 | 流程显示语言 | 权衡 |
|---|---|---|
| `Locale.preferredLanguages` | 设备语言列表中第一个流程支持的语言，即便该语言不在您应用的翻译范围内 | 流程显示的语言可能与应用界面语言不同 |
| `Bundle.main.preferredLocalizations` | 应用界面所使用的语言 | 该列表只有一种语言。若流程不支持该语言，用户将看到默认语言。对于只有 `Base.lproj` 而没有英语本地化的应用，列表中可能包含 `Base`。 |
| `[selectedLanguage] + Locale.preferredLanguages` | 应用内语言选择器所选的语言，其次为设备语言 | — |

The two system lists give different results in two cases:

- 你的应用只有英语，而流程同时有法语和英语。使用 `Locale.preferredLanguages` 时，法语用户会看到法语；而使用 `Bundle.main.preferredLocalizations` 时，则会看到英语。
- 你的应用有韩语，但流程没有。某用户的语言优先级是韩语、其次是西班牙语，使用 `Locale.preferredLanguages` 时会看到西班牙语；而使用 `Bundle.main.preferredLocalizations` 时则会看到默认语言。

:::tip
不要传入 `Locale.current.identifier`。它只包含一种语言，SDK 就没有其他语言可以回退。其代码中没有文字标签：`zh_TW`，而非 `zh-Hant-TW`。使用该标识符时，旧版付费墙编辑工具的付费墙会找不到 `zh-hant` 本地化资源。
:::

大多数应用不会传入 `localizationStrategy`。不传时，SDK 默认使用 [`.auto`](#select-a-localization-strategy)，适用于流程与付费墙编辑工具构建的流程，以及旧版付费墙编辑工具构建的付费墙。

</TabItem>
<TabItem value="4.4" label="SDK 4.0–4.4">

在 [`AdaptyUI.getFlowConfiguration`](get-pb-paywalls#fetch-the-view-configuration) 的 `locale` 参数中传入一个语言区域代码。具体传入哪个代码由你的应用决定，例如设备的语言区域或应用内语言选择器中的语言。

```swift showLineNumbers
let flowConfiguration = try await AdaptyUI.getFlowConfiguration(
    forFlow: flow,
    locale: "pt-BR"
)
```

匹配是精确的。SDK 会将您传入的代码与流程的本地化代码逐字符进行比较：不会转换大小写，不会将下划线（`_`）替换为连字符（`-`），也不会回退到语言子标签。对于包含 `pt-BR` 本地化的流程，只有 `pt-BR` 能匹配：`pt-br`、`pt_BR` 和 `pt-PT` 均无法匹配。

当代码与任何本地化均不匹配时，流程会静默地以其[默认语言](add-paywall-locale-in-adapty-paywall-builder#set-the-default-locale)渲染——SDK 不会返回错误，也不会记录警告。

省略语言区域代码并不等同于请求流程的默认本地化：SDK 会固定替换为 `en`。如果一个流程的默认语言区域是 `de`，但同时包含 `en` 本地化，则仍会以 `en` 渲染；只有在没有 `en` 本地化时，才会回退到 `de`。

:::warning
请严格按照已发布流程中的语言区域代码传入：例如从 **Select languages** 字段获取的是 `pt-BR`，就传 `pt-BR`，而非 `pt-br`。对于旧版付费墙编辑工具创建的付费墙，请传入小写代码，例如 `pt-br`。

不要直接传递系统语言区域标识符。在设置为葡萄牙语（巴西）的设备上，`Locale.current.identifier` 返回 `pt_BR`，这与任何本地化都不匹配。在设置为美式英语的设备上，`Locale.current.identifier(.bcp47)` 返回 `en-US`，会错过仅包含 `en` 的流程。在传递系统语言区域标识符之前，请将其转换为流程所支持的代码。
:::

</TabItem>
</Tabs>

## 测试用户看到的本地化版本 \{#test-which-localization-a-user-sees\}

<Tabs groupId="ios-sdk-version" queryString>
<TabItem value="4.5" label="SDK 4.5 or later" default>

当流程不包含用户的任何语言时，SDK 会使用默认语言环境，不会报错也不会输出警告日志。如需确认用户看到的是哪个本地化版本，请在设备上测试该流程：

1. 在设备设置中，将测试语言移至语言列表的顶部。
2. 在您的应用中打开流程。
3. 读取 `flowConfiguration.locale`。它包含所显示本地化的代码。看板中该代码以小写形式显示：`pt-br` 对应 `pt-BR`。

如需在不更改设备设置的情况下测试某种语言，可在调试版本中传入固定的 `preferredLocales` 列表，例如 `["pt-PT"]`。

</TabItem>
<TabItem value="4.4" label="SDK 4.0–4.4">

当您传入的语言代码与流程的任何本地化版本均不匹配时，SDK 会使用默认语言，既不会抛出错误，也不会记录警告。如需确认用户实际看到的是哪个本地化版本，请在设备上测试该流程：

1. 在设备设置中，选择测试所用的语言和地区。
2. 在您的应用中打开该流程。
3. 读取 `flowConfiguration.locale` 的值，它包含当前显示的本地化版本代码。若该值与您传入的代码不同，则说明该流程没有完全匹配该代码的本地化版本。

若要在不更改设备设置的情况下测试代码，可在调试构建中传入固定的 `locale`，例如 `"pt-BR"`。

</TabItem>

当流程中某些部分仍以默认语言显示时，说明当前本地化缺少该部分的翻译。如需补全，请在 Flow & Paywall Builder 中[翻译缺失的内容行](add-paywall-locale-in-adapty-paywall-builder#manage-localizations-and-translations)。

## 选择要添加到流程中的语言区域 \{#select-which-locales-to-add-to-a-flow\}

要用最少的语言区域覆盖最多的用户，在 **Select languages** 字段中[添加语言区域](add-paywall-locale-in-adapty-paywall-builder#add-and-set-up-a-locale)时，请遵循以下三条原则：

- 添加不带区域的语言。例如，`de` 覆盖德国、奥地利和瑞士的德语使用者。
- 仅在同一语言已有翻译的情况下才添加区域区域设置，例如在已有 `fr` 的基础上再添加 `fr-ca`。
- 添加所有用户使用的语言。SDK 不会将一种语言匹配到另一种语言，例如加泰罗尼亚语不会匹配到西班牙语。加泰罗尼亚语用户会看到流程中其下一个首选语言的内容，或默认语言环境。

:::important
这些规则需要 iOS 或 [Android](android-localizations-and-locale-codes) SDK 4.5 或更高版本。使用 Adapty SDK 4.0 至 4.4 的应用只会传递一个语言区域代码。这些用户看到的同一流程本地化内容可能与使用 SDK 4.5 的用户不同。请保留这些应用所传递的所有代码，例如现有的 `zh` 或 `pt-br`。
:::

### 选择中文、西班牙语和葡萄牙语的语言代码 \{#select-codes-for-chinese-spanish-and-portuguese\}

**Select languages** 字段中，中文、西班牙语和葡萄牙语各有多个语言代码。请参照下表添加相应代码：

| 语言 | 添加 | 用户看到的内容 |
|---|---|---|
| 中文 | `zh-hans` 和 `zh-hant`，而非新建 `zh`。仅在需要单独的香港翻译时才添加 `zh-hk`。 | 中国大陆和新加坡用户看到 `zh-hans`，台湾、香港和澳门用户看到 `zh-hant`。 |
| 粤语 | `yue`，始终与 `zh-hant` 搭配使用 | 设备语言为粤语的用户看到 `yue`，设备语言为繁体中文的用户看到 `zh-hant`。若不添加 `zh-hant`，设备设置为繁体中文的用户将看到书面粤语。 |
| 西班牙语 | `es` 和 `es-419`，而非新建 `es-mx` | 西班牙用户看到 `es`，拉丁美洲和美国用户看到 `es-419`。 |
| 葡萄牙语 | `pt-br` 表示巴西葡萄牙语，`pt` 表示欧洲葡萄牙语 | 巴西用户看到 `pt-br`，葡萄牙用户看到 `pt`。 |

如果您的流程针对同一语言的多个地区变体进行了本地化，请同时提供一个不含地区信息的语言环境，以覆盖那些不在您明确支持范围内的语言变体。如果没有这样的回退机制，该语言组中的其他地区用户将随机获得某个语言环境——而您无法指定是哪一个。例如，`es-MX` 的用户可能看到 `es-ar`、`es-co` 或 `es-es`。要覆盖此类用户，请添加不含地区信息的 `es` 语言环境，或泛美洲地区的 `es-419` 语言环境。

### 从推荐的语言区域集合开始 \{#start-from-a-recommended-set-of-locales\}

如需分阶段规划翻译工作，可从以下三个集合中选择一个。每个集合均包含前一个集合的全部内容。

| 集合 | 语言区域 | 总数 |
|---|---|---|
| 最小集合 | `en`, `es`, `pt-br`, `fr`, `de`, `it`, `ru`, `ja`, `ko`, `zh-hans`, `zh-hant` | 11 |
| 扩展集合 | 最小集合，以及 `tr`, `pl`, `nl`, `sv`, `da`, `no`, `fi`, `uk`, `ar`, `he`, `hi`, `id`, `th`, `vi`, `es-419`, `pt` | 27 |
| 宽泛集合 | 扩展集合，以及 `cs`, `sk`, `hu`, `ro`, `el`, `bg`, `hr`, `sl`, `lt`, `lv`, `et`, `ca`, `kk`, `ms`, `fil`, `fa`, `ur`, `bn`, `ta`, `te`, `mr`, `fr-ca` | 49 |

在这些集合中，用户看到的语言环境如下：

- 在最小集合中，`es` 覆盖所有国家的西班牙语用户，`pt-br` 也覆盖葡萄牙的葡萄牙语用户。
- 在扩展集合中，`es-419` 和 `pt` 是额外的翻译版本。有了它们，`es` 专门服务于西班牙，`pt` 专门服务于葡萄牙。请将 `pt` 翻译为欧洲葡萄牙语。
- 加泰罗尼亚语和马来语用户只会看到各自对应的语言环境：`ca` 或 `ms`。SDK 不会向他们展示西班牙语或印度尼西亚语作为替代。

### 选择默认语言区域 \{#select-the-default-locale\}

当流程中没有用户所使用的语言时，用户将看到默认语言区域的内容。新建的流程默认只有 `en` 一种语言区域，并以其作为默认值。如需更改，请[将其他语言区域设为默认](add-paywall-locale-in-adapty-paywall-builder#set-the-default-locale)。

设置默认语言区域时，请遵守以下三条规则：

- 对于没有匹配语言区域的用户，请选择大多数用户能理解的语言。通常是英语，而不是您主要市场的语言。
- 完整翻译默认语言区域。没有匹配语言区域的用户将看到整个流程的默认语言区域内容。有匹配语言区域的用户将看到其对应语言的流程。任何未翻译的部分将以默认语言区域显示。
- 不要选择具有两种文字的语言，例如中文。使用其他文字的用户可能无法阅读默认语言区域的内容。

## 选择本地化策略 \{#select-a-localization-strategy\}

大多数应用不会传入 `localizationStrategy`，因此 SDK 默认使用 `.auto`。该策略会对来自 Flow & Paywall Builder 的流程应用 iOS 语言匹配规则，对来自旧版付费墙编辑工具的付费墙应用单语言规则。

在单语言规则下，SDK 只读取 `preferredLocales` 中优先级最高的语言。它会先尝试完整代码，再尝试更短的代码（`pt-br`，然后 `pt`），否则显示默认语言环境。旧版付费墙编辑工具创建的付费墙在此规则下仍可正常使用，即使重新发布也不受影响。若要让 SDK 遍历 `preferredLocales` 中的所有语言，请[将付费墙迁移至 Flow & Paywall Builder](convert-paywall-to-flow)，然后通过流程版位提供新的流程。

要更改 SDK 将用户语言与流程语言环境进行匹配的方式，请在 `localizationStrategy` 参数中传入以下值之一：

- `.system`：每个流程均使用 iOS 语言匹配方式，包括旧版付费墙编辑工具中的付费墙。
- `.legacy`：每个流程使用单语言规则，而不是 SDK 4.4 的精确匹配方式。对于来自 Flow & Paywall Builder 的流程，请勿传入 `.legacy`：它无法匹配带有地区或文字标记的语言环境，例如 `pt-BR`。
- `.custom(resolver:fallbackResolver:)`：[由你的代码选择本地化语言](#pick-a-flows-localization-in-your-own-code)。

### 在自己的代码中选择流程的本地化语言 \{#pick-a-flows-localization-in-your-own-code\}

iOS 语言匹配并不能覆盖所有文字脚本。例如，当设备语言列表中包含西里尔字母的阿塞拜疆语（`az-Cyrl`）但不含拉丁字母版本时，包含 `az` 的流程会以其默认语言环境显示。若要强制显示 `az`，或者按照自定义规则选择本地化语言，可以创建一个遵循 `AdaptyUICustomLocalizationResolver` 协议的类型，然后将其传入 `localizationStrategy` 参数的 `.custom(resolver:)` 值。请在包含该解析器的文件中添加 `import AdaptyUIBuilder`。

其他 Adapty SDK 会按照各自的规则匹配语言，因此同一用户在 iOS 和 Android 上可能会看到不同语言版本的流程。若要在所有平台上显示相同的语言版本，请编写一个解析器，使其返回与其他平台上的应用相同的语言区域代码。

以下规则适用于该解析器：

- 如果某个流程只有一种本地化，SDK 不会调用解析器，直接以该本地化显示流程。
- SDK 会调用 `resolve(for:from:)`，传入应用提供的列表，以及包含流程 `locales` 和 `defaultLocale` 的 `AdaptyUILocalizationSource`。`locales` 的顺序不固定。
- 若要显示某种本地化，请从 `locales` 或 `defaultLocale` 中原样返回对应的语言代码，包括大小写：应返回 `ar`，而非 `AR`。
- 如果解析器返回其他代码或 `nil`，SDK 将使用 `fallbackResolver` 中指定的策略。若未设置 `fallbackResolver`，SDK 默认使用 `.auto`。
- SDK 可能在主线程以外调用解析器。
- 请立即返回语言代码，不要在此处发起网络请求或执行其他耗时操作。SDK 会无限等待解析器的返回结果，流程只有在解析器返回后才会显示。

## Adapty 中的语言代码标准 \{#locale-code-standard-at-adapty\}

Adapty 语言代码遵循 [BCP 47 标准](https://en.wikipedia.org/wiki/IETF_language_tag)：由语言子标签和可选的文字或地区子标签组成，以连字符分隔。**Select languages** 字段中的代码均为小写形式：`en`（英语）、`pt-br`（葡萄牙语，巴西）、`zh-hans`（简体中文）和 `zh-hant`（繁体中文）。

## 本地化自定义付费墙和用户引导 \{#localize-custom-paywalls-and-onboardings\}

SDK 4.5 仅更改了流程的本地化规则。自定义付费墙和用户引导的工作方式与 SDK 4.4 相同。

### 按语言选择自定义付费墙的远程配置 \{#pick-a-custom-paywalls-remote-config-by-language\}

`getFlow` 没有 locale 参数。对于自定义付费墙，它会在 `flow.remoteConfigs` 中返回所有已配置的本地化内容。每个条目都包含一个 `locale` 语言代码和配置内容（`jsonString` 或已解析的 `dictionary`）。你需要自行编写回退逻辑，选出与用户匹配的条目：

```swift showLineNumbers
do {
    let flow = try await Adapty.getFlow(placementId: "YOUR_PLACEMENT_ID")
    let config = flow.remoteConfigs.first(where: { $0.locale == "en" })
        ?? flow.remoteConfigs.first
    // read your values from config?.dictionary
} catch {
    // handle the error
}
```

Adapty 按照 [Adapty 的语言代码标准](#locale-code-standard-at-adapty) 中描述的格式存储 `locale` 代码。SDK 不会自动将远程配置与某个语言代码进行匹配，因此具体使用哪条配置由您的应用自行决定。

### 向用户引导传递语言环境 \{#pass-a-locale-to-an-onboarding\}

<OnboardingDeprecation />

`getOnboarding` 在 SDK 4.5 中保留了其 `locale` 参数。当你向 [`getOnboarding`](get-onboardings) 传递 `locale` 时，服务器会选择对应的本地化配置：

1. 语言区域字符串将被转换为小写，所有下划线（`_`）替换为连字符（`-`）
2. Adapty 查找与完整语言区域代码完全匹配的本地化内容
3. 如果未找到匹配项，Adapty 取第一个连字符之前的子字符串（例如 `pt-br` 对应 `pt`），并查找匹配的本地化内容
4. 如果仍未找到匹配项，Adapty 返回该用户引导默认语言区域的内容

这样，`pt_BR`、`pt-BR` 和 `pt-br` 都会解析为同一个用户引导本地化内容。

## 为什么这很重要 \{#why-this-is-important\}

语言区域代码在某些场景下会起到关键作用——例如，当你需要根据应用的当前本地化语言获取对应的付费墙时。

由于语言区域代码较为复杂，且在不同平台之间可能存在差异，我们为所有支持的平台制定了一套统一的内部标准。正因如此，了解你究竟向服务器发送了什么内容以获取正确的本地化版本，以及后续会发生什么，显得尤为重要——这样你才能始终收到预期的结果。

## Adapty 中的区域代码标准 \{#locale-code-standard-at-adapty\}

在区域代码方面，Adapty 使用略经修改的 [BCP 47 标准](https://en.wikipedia.org/wiki/IETF_language_tag)：每个代码由小写子标签组成，以连字符分隔。示例：`en`（英语）、`pt-br`（葡萄牙语（巴西））、`zh`（简体中文）、`zh-hant`（繁体中文）。

## 语言区域代码匹配 \{#locale-code-matching\}

当 Adapty 收到来自客户端 SDK 的语言区域代码请求，并开始查找付费墙对应的本地化版本时，会按以下步骤处理：

1. 传入的语言区域字符串转换为小写，所有下划线（`_`）替换为连字符（`-`）
2. 查找与完整语言区域代码完全匹配的本地化版本
3. 如果未找到匹配项，则截取第一个连字符之前的子字符串（例如 `pt-br` 取 `pt`），再次查找匹配的本地化版本
4. 如果仍未找到匹配项，则返回该付费墙默认语言区域的内容

这样，发送 `'pt_BR'` 的 iOS 设备、发送 `pt-BR` 的 Android 设备，以及发送 `pt-br` 的其他设备，都会得到相同的结果。

## 实现本地化：推荐方式 \{#implementing-localizations-recommended-way\}

如果你正在考虑本地化问题，很可能已经在项目中处理过本地化字符串文件了。如果是这样，我们建议在每个本地化文件中添加一个键值对，键对应预期的 Adapty 语言代码。然后在调用 SDK 时提取该键的值，示例如下：

```swift showLineNumbers
// 1. Modify your Localizable.strings files

/*
Localizable.strings - Spanish
*/
adapty_paywalls_locale = "es";
/*
Localizable.strings - Portuguese (Brazil)
*/
adapty_paywalls_locale = "pt-br";
// 2. Extract and use the locale code
let locale = NSLocalizedString("adapty_paywalls_locale", comment: "")
// pass locale code to AdaptyUI.getViewConfiguration or Adapty.getPaywall method
```

这样，你就能完全掌控应用中每位用户所获取的本地化内容。

## 实现本地化的另一种方式 \{#implementing-localizations-the-other-way\}

你也可以不为每个本地化显式指定语言代码，同样能获得相近（但不完全相同）的效果。这种方式是从平台提供的其他对象中提取语言代码，例如：

```swift showLineNumbers
let locale = Locale.current.identifier
// pass locale code to AdaptyUI.getViewConfiguration or Adapty.getPaywall method
```

不过，我们不建议使用这种方式，原因如下：

1. 在 iOS 上，首选语言与当前区域设置并不相同。如果希望正确选取本地化内容，你需要依赖 Apple 的内置逻辑（如果你使用的是推荐的本地化字符串文件方式，该逻辑开箱即用），或者自行重新实现该逻辑。
2. 很难预测 Adapty 服务器究竟会收到什么。例如，在 iOS 上，设备可能返回类似 `ar_OM@numbers='latn'` 这样的区域标识符，并将其发送给我们的服务器。对于这个请求，你得到的不会是预期中的 `ar-om` 本地化内容，而是 `ar`，这很可能出乎意料。

Should you decide to use this approach anyway — make sure you've covered all the relevant use cases.
