## Antes de empezar \{#before-you-start\}

Necesitas:

- **Adapty Flutter SDK 4.4 o posterior**: Las versiones anteriores muestran el paywall de respaldo para cada elemento personalizado.
- **Código nativo para iOS y Android**: No es posible mostrar un widget de Flutter en un elemento personalizado. Escribe este código en Swift para iOS y en Kotlin para Android. Añade el código Swift al target `Runner` en Xcode, y el código Kotlin a la carpeta de `MainActivity.kt`. Comienza cada nuevo archivo Kotlin con la línea `package` de `MainActivity.kt`.
- **Un esquema de nombres para los elementos personalizados**: Asigna a cada vista nativa un Tipo, como `lottie_animation`. Usa solo letras minúsculas, números y guiones bajos en los Tipos. Para distinguir entre elementos personalizados del mismo Tipo, asigna a cada uno un ID, como `welcome_wave`. Los Tipos e IDs en tu código deben coincidir con los del [Flow & Paywall Builder](flow-custom-elements#add-and-configure).

Usa los mismos tipos e IDs en tu código de iOS y Android. A menos que configures una [audiencia](audience) diferente para cada plataforma, los usuarios de iOS y Android verán los mismos flows.

## Configura tu proyecto Android \{#set-up-your-android-project\}

Tu proyecto iOS no necesita configuración adicional. En tu proyecto Android, añade la librería Adapty UI. Para construir vistas nativas como composables, configura también Jetpack Compose.

### Añadir la biblioteca Adapty UI

En el archivo Gradle del módulo de tu app Android, como `android/app/build.gradle.kts`, añade `implementation("io.adapty:android-ui")` al bloque `dependencies`. No añadas una versión ni el BOM de Adapty: `adapty_flutter` establece la versión, y una versión más nueva de `android-ui` puede romper los flows.

```kotlin showLineNumbers title="android/app/build.gradle.kts"
dependencies {
    implementation("io.adapty:android-ui")
}
```

### Configurar Jetpack Compose \{#set-up-jetpack-compose\}

La plantilla de Flutter no [configura Compose](https://developer.android.com/develop/ui/compose/setup-compose-dependencies-and-compiler) en el módulo de la app. Un `View` de Android no necesita ninguna configuración de Compose. Para crear vistas nativas como composables, añade el plugin de Gradle del compilador de Compose a `android/settings.gradle.kts`, con la versión del plugin de Kotlin, `org.jetbrains.kotlin.android`:

```kotlin showLineNumbers title="android/settings.gradle.kts" {4}
plugins {
    // the other plugins of your project
    id("org.jetbrains.kotlin.android") version "2.1.0" apply false
    id("org.jetbrains.kotlin.plugin.compose") version "2.1.0" apply false
}
```

Luego aplica el plugin al módulo de la app y establece `compose = true` en el bloque `buildFeatures`:

```kotlin showLineNumbers title="android/app/build.gradle.kts" {4,8-10}
plugins {
    // the other plugins of your app module
    id("dev.flutter.flutter-gradle-plugin")
    id("org.jetbrains.kotlin.plugin.compose")
}

android {
    buildFeatures {
        compose = true
    }
}
```

Para la vista Lottie en esta página, añade también `com.airbnb.android:lottie-compose`.

## Crear vistas para elementos personalizados \{#create-views-for-custom-elements\}

Para cada Type, crea una vista nativa para iOS y para Android, o reutiliza una de tu código nativo. Las siguientes vistas del Type `lottie_animation` reproducen una animación Lottie. La vista de Android es un composable que usa la librería `com.airbnb.android:lottie-compose`:

<Tabs groupId="platform" queryString>
<TabItem value="ios" label="iOS (Swift)" default>

```swift showLineNumbers title="Swift"

struct LottieElementView: View {
    let animation: LottieAnimation?

    var body: some View {
        LottieView(animation: animation)
            .resizable()
            .looping()
    }
}
```

</TabItem>
<TabItem value="android" label="Android (Kotlin)">

```kotlin showLineNumbers title="Kotlin"

@Composable
fun LottieElement(animationFile: String) {
    val composition by rememberLottieComposition(LottieCompositionSpec.Asset(animationFile))
    LottieAnimation(
        composition = composition,
        iterations = LottieConstants.IterateForever,
    )
}
```

### Requisitos y buenas prácticas \{#requirements-and-best-practices\}

- **Tamaño**:
  - **Relleno y alineación**: Asegúrate de que la vista nativa se ajuste al contenedor que le asignaste en el Flow & Paywall Builder, menos el padding. Si la vista no ocupa toda el área, aparece por defecto en la esquina superior izquierda de esa área. Para moverla, cambia la alineación en la sección **Layout** del elemento personalizado.
  - **Altura Hug**: Si la altura del elemento personalizado está configurada como **Hug**, una vista que se estira para ocupar el espacio disponible (como un mapa o una lista lazy) se colapsará o se estirará hasta la altura de la pantalla. En su lugar, dale al elemento personalizado una altura [**Fixed**](flow-custom-elements#add-and-configure).
- **Tema**: Las vistas nativas no heredan los colores ni las fuentes de tu tema Flutter. Configúralos en el código nativo.
- **Acciones de flow**: La vista nativa no puede ejecutar acciones de flow, como la transición a la siguiente pantalla. El contexto del elemento puede enviar mensajes al flow con `sendMessage` en iOS y `send` en Android, pero están reservados para futuras funcionalidades del Flow & Paywall Builder. Mantén los botones de navegación, los botones de compra y otros botones con acciones de flow fuera del elemento personalizado.
- **Elementos seleccionables**: Mantén el elemento personalizado fuera de las tarjetas de producto y otros [elementos seleccionables](flow-selectable-elements). Cuando cambia la selección, la vista nativa puede perder su estado.
- **Gestión de navegación**: Cuando el usuario pasa a la siguiente pantalla, el SDK elimina la vista nativa de la pantalla. Detén lo que la vista haya iniciado, como sesiones de cámara, reproductores y actualizaciones de ubicación:
  - **Vista SwiftUI**: Usa la acción `onDisappear`. Para trabajo asíncrono, usa `.task`: SwiftUI lo cancela cuando la vista desaparece.
  - **Composable**: Usa el bloque `onDispose` de un `DisposableEffect`. Para trabajo asíncrono, usa `LaunchedEffect`: Compose lo cancela cuando el composable abandona la composición.
  - **`View` de Android**: Sobrescribe `onDetachedFromWindow` en tu subclase de `View`, o añade un `View.OnAttachStateChangeListener` al `View`.

  Cuando el usuario regresa, el SDK vuelve a llamar al resolver y la vista nativa se inicia sin el estado de la anterior. En Android, en un flow que abres con `present()`, una rotación hace que el SDK vuelva a llamar al resolver. En un `AdaptyUIFlowPlatformView` embebido, la vista nativa conserva su estado tras una rotación.
- **Vistas UIKit**: En iOS, envuélvelas en `UIViewRepresentable`.
- **Carruseles**: En Android, en un [carrusel](builder-containers#carousel), las vistas nativas de todas las diapositivas permanecen activas mientras la pantalla está abierta, no solo la vista de la diapositiva visible. Evita colocar previsualizaciones de cámara y reproductores con sonido en los carruseles.

## Escribe un resolver para asociar elementos y vistas personalizadas \{#write-a-resolver-to-match-custom-elements-and-views\}

Escribe un resolver para cada plataforma. El resolver recibe el Type y el ID de un elemento personalizado, y devuelve la vista nativa correspondiente.

<Tabs groupId="platform" queryString>
<TabItem value="ios" label="iOS (Swift)" default>

Para escribir un resolver, haz que un tipo implemente el protocolo `AdaptyUICustomElementsResolver` y el método `view(forType:id:context:)`.

Para el Type `lottie_animation`, el siguiente resolver devuelve `LottieElementView`. El ID indica el nombre del archivo de animación en el bundle de la app, como `welcome_wave`:

```swift showLineNumbers title="Swift"

struct CustomElementsResolver: AdaptyUICustomElementsResolver {
    func view(
        forType type: String,
        id: String,
        context: AdaptyUICustomElementContext
    ) -> AnyView? {
        switch type {
        case "lottie_animation":
            // the ID names the animation file, such as welcome_wave.json
            guard let animation = LottieAnimation.named(id) else {
                return nil // no file for this ID: show the fallback
            }
            return AnyView(LottieElementView(animation: animation))
        default:
            return nil
        }
    }
}
```

En el caso `default`, devuelve `nil`.

</TabItem>
<TabItem value="android" label="Android (Kotlin)">

Para escribir un resolver, implementa la interfaz `AdaptyCustomElementsResolver`. Su método `resolve` devuelve la vista correspondiente en una de las siguientes formas:

- **Un composable**: Devuelve `AdaptyCustomElementContent.compose`, con el composable dentro de su lambda.
- **Una `View` de Android**: Devuelve `AdaptyCustomElementContent.view`, con una función que crea la `View`. Nombra el parámetro `factory`: `AdaptyCustomElementContent.view(factory = { context, _ -> ChartView(context) })`. Sin el nombre, Kotlin pasa una trailing lambda al parámetro opcional `update`, y el código no compila.

Para el tipo `lottie_animation`, el siguiente resolver devuelve la [vista Lottie](#create-views-for-custom-elements). El ID nombra el archivo de animación en la carpeta `assets`, `android/app/src/main/assets`, como por ejemplo `welcome_wave` para `welcome_wave.json`:

```kotlin showLineNumbers title="Kotlin"

class CustomElementsResolver(context: Context) : AdaptyCustomElementsResolver {
    // the animation files in the assets folder, listed once
    private val animationFiles: Set<String> = try {
        context.assets.list("").orEmpty().toSet()
    } catch (e: IOException) {
        emptySet() // no list of files: every Lottie element shows the fallback
    }

    override fun resolve(type: String, id: String): AdaptyCustomElementContent? =
        when (type) {
            "lottie_animation" -> {
                // the ID names the animation file, such as welcome_wave.json
                val file = "$id.json"
                if (file in animationFiles) {
                    AdaptyCustomElementContent.compose { LottieElement(file) }
                } else {
                    null // no file for this ID: show the fallback
                }
            }
            else -> null
        }
}
```

Para cualquier otro Type, devuelve `null`.

</TabItem>
</Tabs>

Si [añades un elemento personalizado con un nuevo Type](flow-custom-elements#what-changes-require-an-app-release) después de publicar la app, los usuarios de la versión publicada verán su fallback.

El resolver tiene los siguientes requisitos:

- **Datos de red y reproductores**: Mantén los datos de red y los reproductores en el estado de la [vista nativa](#create-views-for-custom-elements), no en el resolver. El SDK llama al resolver muchas veces mientras la pantalla está abierta. El código del resolver se ejecuta de nuevo en cada llamada, por lo que las solicitudes de red se repiten y los reproductores vuelven a empezar. La vista nativa conserva su estado entre estas llamadas, de modo que los datos se cargan una sola vez y los reproductores siguen reproduciéndose. Crea reproductores, sesiones y solicitudes de red dentro de la vista nativa:
  - **Vista SwiftUI**: Crea reproductores, sesiones y solicitudes de red en `.task` o en un `@StateObject`, no en el valor inicial de una propiedad `@State`. Swift evalúa ese valor inicial de nuevo cada vez que el resolver crea la vista.
  - **Composable**: Crea reproductores y sesiones en `remember`, y las solicitudes de red en `LaunchedEffect`.
  - **`View` de Android**: Crea reproductores, sesiones y solicitudes de red en `onAttachedToWindow`.
- **Una vista nativa por elemento personalizado**: Algunas vistas nativas cambian mientras la pantalla está abierta, por ejemplo, cuando se cargan sus datos o cuando el usuario las toca. Implementa esta lógica en la propia vista nativa, no en el resolver. Si el resolver devuelve una vista diferente para el mismo elemento personalizado, la vista pierde su estado.
- **Una nueva `View` por cada aparición**: En Android, crea una nueva `View` en cada llamada a `factory`. El SDK llama a `factory` cada vez que aparece el elemento personalizado, por ejemplo, cuando se abre la pantalla, cuando el usuario vuelve a ella o, en un flow que abres con `present()`, después de una rotación.
- **Datos de la app**: Almacena un objeto que contenga los datos, como un `ObservableObject` o un `StateFlow` con una [racha diaria](flutter-custom-element-lottie-animation), en una propiedad del resolver. Pasa el objeto a la vista nativa y obsérvalo allí:
  - **Vista SwiftUI**: Observa un `ObservableObject` con `@ObservedObject`.
  - **Composable**: Recoge un `StateFlow` con `collectAsState`, u observa un `LiveData` con `observeAsState`.
  - **`View` de Android**: Observa el objeto en `onAttachedToWindow` y detén la observación en `onDetachedFromWindow`.

  Un valor que copias en el resolver, como el número de racha, permanece tal como estaba cuando creaste el resolver. Si tu código Dart tiene los datos, como una racha diaria, envía cada nuevo valor al código nativo a través de un [canal de plataforma](https://docs.flutter.dev/platform-integration/platform-channels), y actualiza el objeto allí.

### Establecer condiciones para el contenido de respaldo \{#set-conditions-for-fallback-content\}

<FlowCustomElementsFallbackConditions />

Para un permiso, devuelve la vista vacía solo cuando el usuario ya lo haya denegado antes de que se abra la pantalla. En Android, `ContextCompat.checkSelfPermission` devuelve el mismo valor, `PERMISSION_DENIED`, en dos casos: antes de que tu app le pida el permiso al usuario por primera vez, y después de que el usuario lo deniegue. Para distinguir ambos casos, guarda el resultado de la solicitud de permiso y lee ese resultado guardado en el resolver. Si tu app aún no ha solicitado el permiso, devuelve la vista nativa y solicita el permiso dentro de la vista. Por ejemplo, solicita acceso a la ubicación cuando aparezca una [vista de mapa](flutter-custom-element-map#3-match-the-map-to-the-custom-element) y muestra el mapa en cuanto el usuario conceda el acceso. Si devuelves la vista vacía y el usuario concede el acceso después, seguirá viendo el fallback. Un cambio de permiso no hace que el SDK vuelva a llamar al resolver. La vista nativa solo aparece después de que el SDK llame al resolver de nuevo, por ejemplo, cuando el usuario regresa a la pantalla.

## Pasa el resolver al SDK \{#pass-the-resolver-to-the-sdk\}

Configura el resolver una vez por plataforma, al iniciar la app. El SDK lo llama en cada flow, incluido un flow integrado con `AdaptyUIFlowPlatformView`. Los usuarios ven tus vistas nativas en los nuevos flows y pruebas A/B sin necesidad de publicar una nueva versión de la app. Estas vistas siguen mostrando a cada usuario sus propios datos, como una [racha diaria](flutter-custom-element-lottie-animation), porque los leen directamente de tu app.

### iOS

En `ios/Runner/AppDelegate.swift`, importa `AdaptyUI` y llama a `AdaptyUI.setCustomElementsResolver(_:)` en el método `application(_:didFinishLaunchingWithOptions:)`. Deja el resto de la clase `AppDelegate` tal como está:

```swift showLineNumbers title="ios/Runner/AppDelegate.swift"

// in application(_:didFinishLaunchingWithOptions:), before `return super.application(...)`
AdaptyUI.setCustomElementsResolver(CustomElementsResolver())
```

Si también escribes el resolver en `AppDelegate.swift`, importa también `AdaptyUIBuilder` allí.

### Android

Llama a `AdaptyUI.setCustomElementsResolver` en el método `onCreate` de tu clase `Application`. Si tu app aún no tiene una clase `Application`, crea una:

```kotlin showLineNumbers title="Kotlin"

class App : Application() {
    override fun onCreate() {
        super.onCreate()
        AdaptyUI.setCustomElementsResolver(CustomElementsResolver(this))
    }
}
```

En `android/app/src/main/AndroidManifest.xml`, indica el nombre de tu clase `Application` en el atributo `android:name` de `<application>`. La plantilla de Flutter establece este atributo como `${applicationName}`, que representa la clase base `Application`:

```xml showLineNumbers title="AndroidManifest.xml" {2}
<application
    android:name=".App"
    android:label="your_app">
    <!-- the rest of your application element -->
</application>
```

:::tip
Para mostrar la misma vista en cada elemento personalizado de un tipo, pasa un mapa de tipos y vistas en lugar de un resolver. Con un mapa, escribes menos código que con un resolver, pero no puedes [establecer condiciones para el contenido de respaldo](#set-conditions-for-fallback-content).

<Tabs groupId="platform" queryString>
<TabItem value="ios" label="iOS (Swift)" default>

El mapa es un diccionario `[String: AdaptyUICustomElementBuilder]`. Si escribes el mapa en `AppDelegate.swift`, importa también `Lottie` allí.

```swift showLineNumbers title="Swift"
AdaptyUI.setCustomElementsResolver([
    "lottie_animation": .init { _, id, _ in LottieElementView(animation: .named(id)) },
])
```

</TabItem>
<TabItem value="android" label="Android (Kotlin)">

Pasa el mapa a `AdaptyCustomElementsResolver.of`:

```kotlin showLineNumbers title="Kotlin"
val appWideViews = mapOf(
    "confetti" to AdaptyCustomElementContent.compose { LottieElement("confetti.json") },
)
AdaptyUI.setCustomElementsResolver(AdaptyCustomElementsResolver.of(appWideViews))
```

</TabItem>
</Tabs>
:::

No puedes adjuntar un resolver a un flow individual. Para mostrar datos de tu código Dart, envíalos a tu código nativo antes de que se abra el flow. Luego, lee los datos en el resolver. Por ejemplo, un paywall muestra el [peso que el usuario introdujo en un flow anterior](flutter-custom-element-interactive-chart).

## Prueba en un dispositivo \{#test-on-a-device\}

El Flow & Paywall Builder no puede ejecutar el código de tu app, por lo que su lienzo solo muestra el fallback. Un error en la vista nativa puede hacer que la app se bloquee. Antes de publicar la app, prueba cada pantalla que tenga un elemento personalizado en un dispositivo iOS y en un dispositivo Android:

1. Para ver la última versión publicada de cada flow en lugar de una versión en caché, registra el dispositivo como [dispositivo de prueba](test-devices).
2. En el dispositivo, ejecuta una compilación que incluya el resolver. Abre cada pantalla que tenga un elemento personalizado y verifica que la vista nativa aparece y se ajusta al elemento personalizado. Si la vista se desplaza o responde a gestos de arrastre, prueba también esos gestos.
3. Si aparece el fallback en lugar de la vista nativa, busca esta advertencia en la consola de Xcode o en Logcat: `custom element <type>:<id> is not served by a resolver`. Luego verifica que:
   - El Type y el ID de la advertencia coinciden exactamente, letra por letra, con los de tu código.
   - Tu app tiene el archivo, los datos o el permiso que necesita la vista.
   - Tu app configura el resolver al iniciarse: en la clase `AppDelegate` en iOS, y en la clase `Application` que `AndroidManifest.xml` define en Android.

   Si la advertencia no aparece, verifica que la app use Adapty Flutter SDK 4.4 o posterior, y que el [nivel de log](sdk-installation-flutter#logging) no sea `AdaptyLogLevel.error`.
4. En Android, si el elemento personalizado sigue vacío, busca uno de estos avisos en Logcat:
   - `custom element <type>:<id> is not served by a resolver`: El elemento personalizado no tiene contenido de respaldo y ningún resolver devuelve una vista para él. Verifica cada punto del paso 3.
   - `content does not report its size`: El composable no tiene altura propia. Asigna al elemento personalizado una altura [**Fixed**](flow-custom-elements#add-and-configure).

   El SDK solo registra la advertencia de tamaño para los composables. Si un `View` de Android permanece vacío sin ninguna advertencia, dale también una altura **Fixed** al elemento personalizado.
5. Para previsualizar el fallback, devuelve ninguna vista para el Type y vuelve a abrir la pantalla.
