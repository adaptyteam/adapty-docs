Los [flows](adapty-flow-builder) son los paywalls y onboardings que creas en el Flow & Paywall Builder. La CLI gestiona el registro del flow, su configuración del builder, la publicación y el [historial de versiones](flow-version-history). Una configuración del builder es un documento JSON de gran tamaño que normalmente genera el Flow & Paywall Builder, y la CLI no genera uno por sí sola. Para crear o editar una configuración desde el terminal, usa el [skill flow-generator](flow-generator-skill), que ejecuta estos comandos por ti. Antes de publicar, el [skill flow-audit](flow-audit-skill) comprueba si el flow está listo para producción. Los comandos `flows metrics` leen los datos de la página de [métricas del flow](flow-metrics) y requieren la versión 0.15.0 o posterior de la CLI. Los comandos `flows funnel` leen el [funnel del flow](flow-funnel) y requieren la versión 0.19.0 o posterior de la CLI. Los comandos se listan aquí como referencia.

## adapty flows list \{#adapty-flows-list\}

Lista todos los flows de una aplicación.

```bash
adapty flows list --app <app-id>
```

| Flag | Required | Description |
|---|---|---|
| `--app` | Yes | App ID (UUID) |

Acepta [flags de paginación](developer-cli-reference#global-flags).

## adapty flows get \{#adapty-flows-get\}

Obtén los detalles de un flow específico.

```bash
adapty flows get --app <app-id> <flow-id>
```

| Argumento | Descripción |
|---|---|
| `flow-id` | ID del flow (UUID) |

| Flag | Obligatorio | Descripción |
|---|---|---|
| `--app` | Sí | ID de la app (UUID) |

La respuesta contiene `id`, `name`, `status`, `published_flow_version_id` y `updated_at`. `published_flow_version_id` es el ID de la versión en producción, o `null` si el flow nunca ha sido publicado. El estado es uno de los siguientes:

| Estado | Significado |
|---|---|
| `draft` | El flow nunca ha sido publicado |
| `published` | La versión actual está activa |
| `dirty` | El flow fue publicado anteriormente y la versión actual tiene cambios sin publicar. Los usuarios siguen viendo la última versión publicada |
| `publishing` | La publicación está en curso |
| `publication_failed` | La última publicación falló. Corrige la configuración y vuelve a publicar |
| `archived` | El flow está archivado |

## adapty flows create

Crea un flow. El nuevo flow tiene un nombre y sin configuración. Para añadir una configuración, usa [`flows config update`](#adapty-flows-config-update).

```bash

```

| Flag | Obligatorio | Descripción |
|---|---|---|
| `--app` | Sí | ID de la app (UUID) |
| `--name` | Sí | Nombre del flow |

## adapty flows publish

Publica la versión actual de un flow para tus usuarios.

```bash
adapty flows publish --app <app-id> <flow-id>
```

| Argumento | Descripción |
|---|---|
| `flow-id` | ID del flow (UUID) |

| Flag | Obligatorio | Descripción |
|---|---|---|
| `--app` | Sí | ID de la app (UUID) |
| `--yes`, `-y` | No | Publica sin pedir confirmación. Obligatorio cuando la salida se redirige o se usa `--json` |

Dado que publicar cambia lo que ven tus usuarios, el comando muestra el nombre del flow y pide confirmación. Cualquier respuesta distinta de `y` cancela el comando con código de salida 1. Con `--json` o en una tubería, el comando rechaza con código de salida 2 en lugar de esperar una respuesta, así que usa `--yes` en scripts y sesiones de agentes.

La publicación es asíncrona: la respuesta devuelve `status: publishing` y el flow aún no está activo. Consulta [`flows get`](#adapty-flows-get) hasta que el estado pase a `published` o `publication_failed`. Si ocurre `publication_failed`, [`flows config get`](#adapty-flows-config-get) indica el motivo.

La publicación falla con HTTP 400 cuando el flow no tiene configuración, cuando la configuración no es publicable o cuando la versión actual ya está activa. Para validar una configuración antes de publicarla, usa [`flows config validate`](#adapty-flows-config-validate).

## adapty flows config get

Lee la configuración del builder de un flow.

```bash
adapty flows config get --app <app-id> <flow-id>
```

| Argument | Description |
|---|---|
| `flow-id` | Flow ID (UUID) |

| Flag | Required | Description |
|---|---|---|
| `--app` | Yes | App ID (UUID) |

La respuesta contiene `config`, `remote_configs`, `status` y `updated_at`. `updated_at` es una marca de tiempo en milisegundos del último cambio de configuración. Pásala a [`flows config update`](#adapty-flows-config-update) como `--expected-updated-at` para evitar sobreescribir una edición concurrente. Un flow cuya configuración nunca se ha escrito devuelve 404.

Tras un intento de publicación, la respuesta también incluye tres campos que describen cómo fue. Léelos cuando [`flows get`](#adapty-flows-get) indique `publication_failed`:

| Campo | Descripción |
|---|---|
| `publication_status` | El estado de publicación de esta versión del flow: `transforming`, `transformed`, `uploading`, `uploaded`, `published` o `failed` |
| `transform_error` | El error de transformación sin procesar: puede ser un payload JSON con los problemas o una cadena de resumen |
| `publication_error` | Un mensaje legible para una publicación fallida |

## adapty flows config update

Escribe la configuración del builder de un flow y sus Remote Configs.

```bash
adapty flows config get --app <app-id> <flow-id> --json > flow.json
adapty flows config update --app <app-id> <flow-id> --file flow.json
```

| Argumento | Descripción |
|---|---|
| `flow-id` | ID del flow (UUID) |

| Indicador | Requerido | Descripción |
|---|---|---|
| `--app` | Sí | ID de la app (UUID) |
| `--file` | En lugar de `--config`, `--config-file` y `--remote-configs` | Ruta a un archivo JSON con `config` y `remote_configs`, o `-` para leer desde stdin. La salida de `flows config get --json` funciona tal cual. Las demás claves se ignoran |
| `--config` | Sin `--file`: uno de `--config` y `--config-file` | Configuración del builder como cadena JSON |
| `--config-file` | Sin `--file`: uno de `--config` y `--config-file` | Ruta a un archivo JSON con la configuración del builder, o `-` para leer desde stdin |
| `--remote-configs` | Sin `--file` | Array JSON de entradas `{locale, data}`, donde `data` es el Remote Config como cadena. `[]` elimina todos los Remote Configs |
| `--expected-updated-at` | No | El valor `updated_at` obtenido de un `flows config get` anterior. Si la configuración cambió después de esa lectura, el comando falla en lugar de sobrescribir el cambio. Omítelo para sobrescribir incondicionalmente |

Una escritura reemplaza la configuración y toda la lista de Remote Configs. Para conservar los Remote Configs, envía el `remote_configs` de `flows config get --json`. Sin `--file`, el comando necesita tanto la configuración como `--remote-configs`: si falta alguno, sale con el código 2 y no envía ninguna solicitud. El flag `--file` y el `--remote-configs` requerido necesitan la versión 0.20.0 o posterior de la CLI.

Para escribir la primera configuración de un flow nuevo, pasa una lista vacía de Remote Configs:

```bash
adapty flows config update --app <app-id> <flow-id> --config-file config.json --remote-configs '[]'
```

Al escribir la configuración se guarda un borrador sin publicarlo. En un flow publicado, la escritura crea una nueva versión: el estado del flow pasa a `dirty`, y los usuarios siguen viendo la versión publicada hasta que ejecutes [`flows publish`](#adapty-flows-publish).

## adapty flows config validate

Comprueba si una configuración del builder es publicable, sin guardarla.

```bash
adapty flows config validate --app <app-id> <flow-id> --config-file config.json
```

| Argumento | Descripción |
|---|---|
| `flow-id` | ID del flow (UUID) |

| Flag | Requerido | Descripción |
|---|---|---|
| `--app` | Sí | ID de la app (UUID) |
| `--config` | Una de las dos | Configuración del builder como cadena JSON |
| `--config-file` | Una de las dos | Ruta a un archivo JSON con la configuración del builder, o `-` para leer desde stdin |

La respuesta contiene `valid` y una lista de `issues`. Cuando la configuración no es publicable, el comando termina con el código 1, por lo que los scripts pueden usarlo como condición de bloqueo.

## adapty flows config preview

Renderiza un archivo de configuración local en el navegador. Este comando no realiza ninguna llamada a la API y no acepta el flag `--app`.

```bash
adapty flows config preview ./config.json --screen <screen-id> --device iphone-14 --orientation portrait
```

| Argumento | Descripción |
|---|---|
| `config-file` | Ruta a un archivo JSON de configuración del builder local |

| Flag | Por defecto | Descripción |
|---|---|---|
| `--screen` | La primera pantalla del flow | ID de pantalla a renderizar |
| `--device` | `iphone-14` | Marco de dispositivo en el que renderizar |
| `--orientation` | `portrait` | `portrait` o `landscape` |

En la terminal, el comando abre la vista previa en tu navegador. Cuando se usa con pipes o con `--json`, imprime la URL en su lugar. La URL contiene toda la configuración y es larga: pásala por un pipe a una herramienta de capturas de pantalla en lugar de imprimirla. Las configuraciones de más de 32 KB aproximadamente se renderizan lentamente.

## Lista de versiones de flows de adapty \{#adapty-flows-versions-list\}

Lista las versiones de un flow, de la más reciente a la más antigua. Son las versiones del [historial de versiones](flow-version-history) en el Flow & Paywall Builder.

```bash
adapty flows versions list --app <app-id> <flow-id>
```

| Argumento | Descripción |
|---|---|
| `flow-id` | ID del flow (UUID) |

| Flag | Obligatorio | Descripción |
|---|---|---|
| `--app` | Sí | ID de la app (UUID) |
| `--search` | No | Muestra solo las versiones cuyo título contiene este texto. No distingue entre mayúsculas y minúsculas, y coincide con partes de una palabra: `friday` encuentra **Black Friday** |

Cada línea muestra el título, el estado, la fecha y el ID de una versión. El título es el nombre de la versión, o **Version N** cuando la versión no tiene nombre. El estado es uno de los siguientes:

| Estado | Significado |
|---|---|
| `draft` | La versión que estás editando. Un flow tiene un borrador o ninguno. Mientras el borrador se está publicando, su línea termina con `Publishing…`, y si la publicación falla, termina con `Publish failed` |
| `live` | La versión que ven tus usuarios |
| `previous` | Una versión anterior. Estuvo activa antes, o una versión más reciente la reemplazó antes de que se publicara |

La fecha de una versión `live` o `previous` es la fecha en que comenzó su publicación. Para el borrador y para una versión `previous` que nunca se publicó, es la fecha en que se creó la versión.

Para un flow que nunca se ha publicado, el comando imprime `History will appear after the first publish.` y la línea del borrador debajo. El [historial de versiones](flow-version-history) en el dashboard no muestra ninguna línea para ese flow. Cuando ninguna versión coincide con `--search`, el comando imprime `No versions match the search.`

El comando siempre lista todas las versiones y no acepta flags de paginación.

Con `--json`, el comando imprime `{data, meta}` de Adapty sin modificaciones, con las filas en `data`. Cada fila contiene `flow_version_id`, `version`, `name`, `title`, `state`, `is_current`, `publication_status`, `published_at`, `created_at`, `updated_at` y `last_edited_by`. `updated_at` es un timestamp en milisegundos del último cambio de contenido de la versión: pasa el `updated_at` del borrador a [`flows versions restore`](#adapty-flows-versions-restore) como `--expected-updated-at`. `last_edited_by` indica el usuario que realizó el último cambio en la versión, o es `null` cuando Adapty no conoce al usuario.

## adapty flows versions get

Lee una versión de un flow. Leer una versión no cambia nada: el borrador y la versión publicada permanecen tal cual.

El comando muestra el título, el ID, el número, el estado y la fecha de la versión, el usuario que la modificó por última vez, y su enlace de **Test on device**. El contenido completo de la versión — su configuración del builder con todos los layouts, sus Remote Configs y sus paywalls — está en la salida de `--json`, y en el archivo de `--output`.

```bash
adapty flows versions get --app <app-id> <flow-id> <version-id> --output version.json
```

| Argumento | Descripción |
|---|---|
| `flow-id` | ID del flow (UUID) |
| `version-id` | ID de versión (UUID), de [`flows versions list`](#adapty-flows-versions-list) |

| Flag | Obligatorio | Descripción |
|---|---|---|
| `--app` | Sí | ID de la app (UUID) |
| `--output` | No | Escribe el contenido completo de la versión en este archivo como JSON |
| `--yes`, `-y` | No | Reemplaza un archivo `--output` existente sin preguntar. Obligatorio con `--json` o en un pipe cuando el archivo ya existe |

Si el CLI no puede escribir el archivo `--output`, por ejemplo porque su carpeta no existe, el comando muestra `Could not write <path> (<errno>).` y sale con el código 1.

## adapty flows versions rename

Renombra una versión. Puedes renombrar el borrador, la versión en producción y versiones anteriores.

```bash
adapty flows versions rename --app <app-id> <flow-id> <version-id> --name "Black Friday"
```

| Argumento | Descripción |
|---|---|
| `flow-id` | ID del flow (UUID) |
| `version-id` | ID de la versión (UUID) |

| Flag | Requerido | Descripción |
|---|---|---|
| `--app` | Sí | ID de la app (UUID) |
| `--name` | Sí | Nuevo nombre de la versión. Pasa `--name ""` para eliminar el nombre y que la versión vuelva a mostrarse como **Version N**. Un nombre compuesto solo de espacios también lo elimina |

El comando muestra el ID de la versión y el nuevo título. Adapty elimina los espacios al inicio y al final del nombre. Dos versiones pueden tener el mismo nombre. Cambiar el nombre no modifica el contenido ni el campo `updated_at` de la versión, por lo que no entra en conflicto con un guardado posterior del borrador.

## adapty flows versions restore \{#adapty-flows-versions-restore\}

Restaura una versión como borrador del mismo flow. Esto es **Duplicate as draft** en el [historial de versiones](flow-version-history#restore-an-earlier-version). La versión restaurada no llegará a tus usuarios hasta que la [publiques](#adapty-flows-publish).

:::tip
Una restauración reemplaza el borrador actual. Para conservar el borrador, duplícalo primero en un nuevo flow con [`flows duplicate`](#adapty-flows-duplicate).
:::

```bash
adapty flows versions restore --app <app-id> <flow-id> <version-id>
```

| Argumento | Descripción |
|---|---|
| `flow-id` | ID del flow (UUID) |
| `version-id` | ID de versión (UUID) de una versión `live` o `previous` |

| Flag | Obligatorio | Descripción |
|---|---|---|
| `--app` | Sí | ID de la app (UUID) |
| `--expected-updated-at` | Con `--yes`, cuando el flow tiene un borrador | El `updated_at` del borrador, obtenido de [`flows versions list --json`](#adapty-flows-versions-list). Si el borrador cambió después de esa lectura, el comando falla en lugar de reemplazar el cambio |
| `--yes`, `-y` | No | Reemplaza el borrador sin confirmación. Obligatorio con `--json` o en un pipe cuando el flow tiene un borrador |

La instrucción primero lee las versiones del flow:

- **El flow no tiene borrador**: El comando no solicita nada. Adapty crea un nuevo borrador con el siguiente número de versión, sin nombre y con todo el contenido de la versión. La versión publicada y la versión que restauras permanecen tal como están.
- **El flow tiene un borrador**: El comando solicita `Replace the draft '<draft>' (last change <time> by <user>) with '<version>'? To keep the draft, duplicate it to a new flow first.`, luego `Apply? [y/N]`. Si respondes `y`, el borrador conserva su ID, número y nombre, y recibe el contenido de la versión. No se añade ninguna versión. Cualquier otra respuesta sale con el código 1 y no envía nada.

Con `--json`, en una tubería o sin terminal, el comando no puede hacer preguntas. Si el flow tiene un borrador, no envía nada y termina con código 6 a menos que pases `--yes`. Su mensaje plantea la pregunta y añade `To replace it, re-run with --yes --expected-updated-at <ms> (the draft's updated_at).`, con el `updated_at` del borrador en lugar de `<ms>`. Con `--yes`, pasa también `--expected-updated-at`: sin él, el comando termina con código 6 y no envía nada. En una terminal sin `--expected-updated-at`, el comando toma el `updated_at` del borrador que te muestra en la pregunta.

Después de una restauración, el comando muestra `Restored '<version>' as the draft '<draft>' (<draft-id>). Nothing is published.`

Adapty rechaza la restauración y no realiza ningún cambio en estos casos. El comando muestra el mensaje de Adapty, añade instrucciones para algunos de ellos y sale con código 4:

| Mensaje | Qué hacer |
|---|---|
| `This flow version is already the current draft.` | Elige otra versión. |
| `Flow version does not exist.` | El ID de versión no está en la lista de versiones de este flow. Obtén el ID con [`flows versions list`](#adapty-flows-versions-list). |
| `Flow version is already being published.` | Espera a que finalice la publicación y vuelve a restaurar. |
| `This flow version uses deleted products: …` | Elige una versión que no los utilice. |
| `This flow configuration was already updated by …` | Un compañero modificó el borrador después de que lo consultaste. Vuelve a listar las versiones y reintenta. |
| `Flow is deleted.` | El flow está archivado. Primero [restáuralo desde el archivo](archive-flows#restore-a-flow) en el dashboard. |

## adapty flows duplicate \{#adapty-flows-duplicate\}

Copia un flow, o una de sus versiones, a un nuevo flow. Esta opción es **Duplicate flow** en el botón de acciones del flow en la barra superior del Flow & Paywall Builder (consulta [Copiar flows](copy-flows)), y **Duplicate as new flow** en el [historial de versiones](flow-version-history#restore-an-earlier-version).

```bash
adapty flows duplicate --app <app-id> <flow-id> --version <version-id>
```

| Argumento | Descripción |
|---|---|
| `flow-id` | ID del flow (UUID) |

| Flag | Obligatorio | Descripción |
|---|---|---|
| `--app` | Sí | ID de la app (UUID) |
| `--version` | No | ID de versión (UUID) a copiar, de [`flows versions list`](#adapty-flows-versions-list). Cualquier versión es válida, incluido el borrador. Sin este flag, el comando copia el borrador o, si el flow no tiene borrador, la versión publicada |

El comando imprime `New flow '<name>' (<flow-id>), not published.`. El nuevo flow se nombra igual que el flow de origen con `_copy` al final. No está publicado y tiene un borrador con el contenido de la versión. El flow de origen, su borrador y su historial permanecen tal como están. Puedes duplicar un flow mientras está siendo publicado.

Adapty rechaza copiar una versión que utilice un producto eliminado y copiar un flow archivado. Los mensajes son los mismos que para [`flows versions restore`](#adapty-flows-versions-restore).

## adapty flows metrics list \{#adapty-flows-metrics-list\}

Muestra las métricas de por vida de varios flows, una línea por cada flow. Estos son los datos de la tabla de flows en el dashboard.

```bash
adapty flows metrics list --app <app-id> --ids <flow-id>,<flow-id>
```

| Flag | Obligatorio | Descripción |
|---|---|---|
| `--app` | Sí | ID de la app (UUID) |
| `--ids` | Sí | IDs de los flows (UUIDs). Sepáralos con comas o repite el flag |
| `--csv` | No | Imprime CSV: una fila por cada flow, con el ID del flow y las 27 métricas. No se puede usar con `--json` |

Cada línea muestra el ID del flow con sus vistas, compras, pruebas e ingresos. `--json` y `--csv` incluyen las 27 métricas de la página de [métricas de flow](flow-metrics#metrics-definitions), como `unique_profiles_views`, `net_revenue` y `conversion_rate_purchases`. Una métrica sin datos es `0`, nunca `null`. Para cada flow que nunca ha sido publicado, el comando imprime `<flow-id>: No data: the flow was never published.` debajo de la tabla. `--json` añade `note: "never_published"` a la fila de ese flow, y con `--csv` las notas van a stderr para que el CSV se mantenga limpio.

## Valores de métricas de flows de Adapty \{#adapty-flows-metrics-values\}

Lista las claves y valores de filtro de un flow: lo que acepta [`flows metrics get --filter`](#filter-the-metrics).

```bash
adapty flows metrics values --app <app-id> <flow-id>
```

| Argumento | Descripción |
|---|---|
| `flow-id` | ID del flow (UUID) |

| Flag | Requerido | Descripción |
|---|---|---|
| `--app` | Sí | ID de la app (UUID) |

Cada línea muestra una etiqueta y, entre paréntesis, el valor a pasar. Los valores están anidados tal como los filtros del dashboard los anidan:

```text
Country (country)
  Americas (Americas)
    United States (US)
  Europe (Europe)
    Germany (DE)
Store (store)
  App Store (app_store)
  Google Play (play_store)
```

El valor superior de cada grupo es la clave del filtro, y los valores más internos son los que acepta esa clave. En el ejemplo, `--filter country=US` mantiene Estados Unidos, y `--filter store=play_store` mantiene Google Play.

## adapty flows metrics get \{#adapty-flows-metrics-get\}

Muestra las métricas de un flow para un período, como el árbol de la página de [métricas de flow](flow-metrics).

```bash
adapty flows metrics get --app <app-id> <flow-id> --date-from 2026-09-01 --date-to 2026-10-21 --date-type purchase_date --based-on placement
```

| Argumento | Descripción |
|---|---|
| `flow-id` | ID del flow (UUID) |

| Flag | Requerido | Descripción |
|---|---|---|
| `--app` | Sí | ID de la app (UUID) |
| `--based-on` | Sí | Por qué se divide el primer nivel del árbol: `placement` o `audience`. Corresponden a las vistas basadas en placement y en audiencia de la página de [métricas de flow](flow-metrics#view-options-for-metrics-data) |
| `--date-type` | Sí | A qué fecha se aplica el período: `purchase_date` o `profile_install_date` para [filtrar por fecha de instalación](flow-metrics#filter-metrics-by-install-date) |
| `--date-from` | No | Primer día del período, inclusive (`YYYY-MM-DD`). Úsalo junto con `--date-to` |
| `--date-to` | No | Último día del período, inclusive (`YYYY-MM-DD`). Úsalo junto con `--date-from` |
| `--granularity` | No | Divide el período en puntos: `day`, `week`, `month`, `quarter` o `year` |
| `--filter` | No | Muestra solo los datos con estos valores de una clave de filtro. Se puede repetir. Ver [Filtrar las métricas](#filter-the-metrics) |
| `--timezone` | No | Zona horaria IANA de los puntos del período, por ejemplo `Europe/Berlin`. Sin este parámetro, Adapty usa la zona horaria de la app |
| `--depth` | No | Cuántos niveles del árbol se muestran bajo `Total`. Por defecto: `1` |
| `--csv` | No | Imprime CSV: una fila por cada nodo del árbol completo. No se puede usar con `--json` |

Para un flow que nunca se ha publicado, el comando muestra la nota `No data: the flow was never published.` encima de los números, y `--json` añade `note: "never_published"`. Con `--csv`, la nota va a stderr para que el CSV quede limpio.

Para ver los ingresos de un flow, ejecuta `adapty analytics chart --app <app-id> --chart revenue --date-from <YYYY-MM-DD> --date-to <YYYY-MM-DD> --filter flow_id=<flow-id>`. Consulta [Comandos de Analytics](developer-cli-analytics).

El CLI termina con código 2 y no envía ninguna solicitud cuando falta `--based-on` o `--date-type`, o cuando solo se proporciona un extremo del período. Adapty valida los valores de `--based-on`, `--date-type` y `--granularity`: un valor incorrecto termina con código 4, y el error lista los valores aceptados.

### Lee el resultado \{#read-the-output\}

El comando imprime una línea `Total` y, a continuación, el primer nivel del árbol. Cada línea muestra vistas, compras, trials y revenue. Con `--granularity`, los puntos del período aparecen justo debajo de su nodo:

```text
Total           views 19  purchases 7  trials 4  revenue 241.93
  Onboarding    views 10  purchases 7  trials 0  revenue 241.93
    2026-09-01  views  0  purchases 0  trials 0  revenue   0.00
    2026-10-01  views 10  purchases 0  trials 0  revenue 241.93
  Settings      views  0  purchases 0  trials 0  revenue   0.00
```

Los niveles del árbol son los niveles del dashboard: placement, audiencia, prueba A/B, variante de flow, pantalla y producto. Con `--based-on audience`, el nivel de placement se omite. Para mostrar más niveles, usa `--depth`, por ejemplo `--depth 3`.

Para el árbol completo con las 27 métricas, utiliza uno de estos flags:

- `--json` imprime la respuesta del servidor sin modificaciones.
- `--csv` imprime una fila por cada nodo, incluidos los puntos de período. Las columnas son `path` (los títulos desde `Total` hasta el nodo, separados por ` > `), `level`, `title` y luego las métricas.

### Filtrar las métricas \{#filter-the-metrics\}

Escribe cada `--filter` como `key=value`, con las claves y valores que lista [`flows metrics values`](#adapty-flows-metrics-values). Para conservar varios valores a la vez, sepáralos con comas o repite el flag con la misma clave. Los filtros con claves distintas se combinan, por lo que los datos deben cumplir todos ellos:

```bash
adapty flows metrics get --app <app-id> <flow-id> --date-from 2026-09-01 --date-to 2026-10-21 \
  --date-type purchase_date --based-on placement --filter country=US,DE --filter store=app_store
```

La CLI envía cada valor exactamente como está escrito. Para incluir una coma dentro de un valor, escribe `\,`. Un valor vacío también es un valor: `attribution_channel=` conserva los datos sin canal, que `flows metrics values` muestra como **No Data**.

## adapty flows funnel values

Lista las claves y valores de filtro de un funnel de flow: lo que acepta [`flows funnel get --filter`](#adapty-flows-funnel-get).

```bash
adapty flows funnel values --app <app-id> <flow-id>
```

| Argumento | Descripción |
|---|---|
| `flow-id` | ID del flow (UUID) |

| Flag | Obligatorio | Descripción |
|---|---|---|
| `--app` | Sí | ID de la app (UUID) |

La salida tiene el mismo formato que [`flows metrics values`](#adapty-flows-metrics-values).

## adapty flows funnel get \{#adapty-flows-funnel-get\}

Muestra la pantalla en la que los usuarios abandonan un flow: el embudo de una versión de flow, paso a paso y pantalla a pantalla, tal como aparece en la pestaña [Funnel](flow-funnel) del flow.

```bash
adapty flows funnel get --app <app-id> <flow-id> --date-from 2026-09-01 --date-to 2026-10-21 --date-type purchase_date
```

| Argumento | Descripción |
|---|---|
| `flow-id` | ID del flow (UUID) |

| Flag | Obligatorio | Descripción |
|---|---|---|
| `--app` | Sí | ID de la app (UUID) |
| `--date-from` | Sí | Primer día del período, inclusive (`YYYY-MM-DD`), en la zona `--timezone` o la zona horaria de la app |
| `--date-to` | Sí | Último día del período, inclusive (`YYYY-MM-DD`), en la zona `--timezone` o la zona horaria de la app |
| `--date-type` | Sí | A qué fecha se aplica el período: `purchase_date` o `profile_install_date` |
| `--flow-version-id` | No | ID de versión del flow (UUID) a leer. Sin él, la CLI lee la versión publicada |
| `--filter` | No | Conserva solo los usuarios con estos valores de una clave de filtro, como `key=value`. Se puede repetir. Las claves y valores provienen de [`flows funnel values`](#adapty-flows-funnel-values) y funcionan como en [Filtrar las métricas](#filter-the-metrics) |
| `--timezone` | No | Zona horaria IANA de los días, por ejemplo `Europe/Berlin`. Sin ella, Adapty usa la zona horaria de la app |
| `--csv` | No | Imprime el archivo CSV que descarga el dashboard, con la fila de totales primero. No se puede usar con `--json` |

El comando muestra la versión del flow y el período, una línea de resumen y una tabla. El resumen indica cuántos usuarios entraron al flow, cuántos lo completaron, la tasa de abandono y los ingresos. La tabla tiene una fila por cada paso, con las columnas `Step`, `Type`, `Reached`, `Completed`, `Drop rate` y `Revenue`. Un paso con más de una pantalla también tiene una fila por cada una de sus pantallas. Un valor que no aplica, como los ingresos de una pantalla de onboarding, se muestra como `—`.

When no users entered the flow in the period, the table lists the screens of the version with zeros. For every field of the answer, use `--json`.
