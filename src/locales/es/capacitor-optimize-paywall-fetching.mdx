Una obtención fiable de flows o paywalls en Capacitor hace tres cosas: renderiza rápido, devuelve la variación según la audiencia y recurre al respaldo sin problemas cuando la red es lenta. Las siguientes reglas cubren la temporización, el caché y los patrones de respaldo para conseguirlo.

:::tip
Las reglas asumen que `adapty.activate()` y `adapty.identify()` ya se han resuelto. Consulta [Orden de llamadas en el SDK de Capacitor](capacitor-sdk-call-order).
:::

## Reglas y errores comunes \{#rules-and-pitfalls\}

| Haz esto | No hagas esto | Por qué |
|---|---|---|
| Obtén el placement que vas a mostrar o precalienta la caché con [`preloadFlows`](#preload-placements) (SDK 4.3.0+). | Lanza tus propias llamadas concurrentes a `getFlow` al inicio. | Un prefetch manual en ráfaga bloquea el hilo principal y provoca una pantalla en negro. `preloadFlows` está diseñado para esto y envía el lote al SDK nativo en una sola llamada. |
| Llama a `getFlow` después de que la atribución haya tenido tiempo de resolverse — por ejemplo, 1-2 segundos después de `activate` o tras dispararse el listener `onLatestProfileLoad`. | Llames a `getFlow` al iniciar la app en `App.tsx`. | La atribución aún no ha llegado. El flow se resuelve contra la audiencia predeterminada y omite silenciosamente los segmentos y la personalización de ASA. |
| Mantén el valor predeterminado de `loadTimeoutMs` en 5000 milisegundos o establece otro valor, y configura un [paywall de respaldo](fallback-paywalls) para cada placement. | Pases a `getFlow` un `loadTimeoutMs` tan grande que nunca se dispare. | Si el timeout nunca se activa, los usuarios con mala conexión verán una pantalla en blanco hasta que la red responda — o cerrarán la app. |

Consulta [Obtener paywalls y productos personalizados](fetch-paywalls-and-products-capacitor) para la referencia de los parámetros `fetchPolicy` y `loadTimeoutMs`, y [Placements](placements) para elegir el placement adecuado.

## Precargar placements \{#preload-placements\}

:::info
`preloadFlows` y `preloadFlowsForDefaultAudience` están disponibles a partir de la versión 4.3.0 del SDK.
:::

`preloadFlows` almacena en caché el JSON del flow con antelación. Luego lo usas de la forma habitual: `getFlow` para el flow y `createFlowView` para su vista.

`fetchPolicy` decide qué capa lee primero un `getFlow` posterior, no si puede acceder a la caché o no:

- `'return_cache_data_else_load'` lee primero la copia precargada y solo va a la red cuando no hay nada en caché. `'return_cache_data_if_not_expired_else_load'` hace lo mismo mientras la copia sea más reciente que `maxAgeSeconds`.
- El valor predeterminado, `'reload_revalidating_cache_data'`, va primero a la red y recurre a la copia precargada cuando la solicitud falla o expira.

Una precarga siempre resulta beneficiosa, aunque de forma diferente según la política: con la política cache-first se elimina la petición, mientras que con la predeterminada se mantiene y se obtiene una copia en caché como respaldo. En un [dispositivo de prueba](test-devices), `getFlow` omite la caché con cualquier política y solo utiliza la copia precargada si la petición de red falla.

Úsalo cuando sepas qué placements necesitará la sesión pero no quieras mostrarlos todavía — por ejemplo, para el flow que hay detrás de un botón que el usuario aún no ha pulsado.

:::warning
Una precarga resuelve la audiencia en el momento en que se ejecuta. Si realizas una precarga antes de que lleguen los datos de atribución y luego llamas a `getFlow` con una `fetchPolicy` cache-first, el usuario verá la variante seleccionada sin atribución, lo que omite los segmentos y la personalización de ASA. Realiza la precarga después de que la atribución haya tenido oportunidad de resolverse — por ejemplo, tras dispararse el listener `onLatestProfileLoad` — o mantén la `fetchPolicy` predeterminada.
:::

```typescript showLineNumbers

try {
  await adapty.preloadFlows({
    placementIds: ['onboarding', 'main_paywall'],
    params: { loadTimeoutMs: 5000 },
  });
} catch (error) {
  // at least one placement failed to preload
}

// Later, when the user reaches the paywall:
const flow = await adapty.getFlow({
  placementId: 'main_paywall',
  params: { fetchPolicy: 'return_cache_data_else_load' },
});
```

**Parámetros:**

- `placementIds` (obligatorio): los placements que se van a precargar.
- `params.loadTimeoutMs` (opcional): el presupuesto de tiempo total para la precarga, en milisegundos. Por defecto es 5000, y los valores por debajo de 1000 se elevan a 1000. Los placements que no se carguen a tiempo se obtienen para la audiencia predeterminada.

**Comportamiento a tener en cuenta:**

- La llamada falla solo después de que se hayan intentado todos los placements, con un único `AdaptyError` que cubre todos los placements fallidos. El fallo de un placement no detiene los demás, y los placements que se cargaron correctamente permanecen en la caché.
- La precarga siempre va a la red: no tiene su propia `fetchPolicy`.
- La precarga solo calienta la caché. No devuelve contenido — para mostrarlo, debes llamar a `getFlow`.

### Qué cubre una precarga \{#what-a-preload-covers\}

Un flow llega a la pantalla en capas. Una precarga cubre la primera, exactamente igual que `getFlow`:

| Capa | Obtenida por | Precargada con un preload |
|---|---|---|
| JSON del flow — la variante seleccionada, sus IDs de producto y el Remote Config | `getFlow` | Sí |
| Diseño de UI — la estructura, el estilo y el texto de la pantalla | `createFlowView` | No |
| Imágenes, incluido el fotograma estático que reemplaza a un elemento de vídeo | `createFlowView`, en segundo plano | No |
| Productos | `createFlowView` o `getPaywallProducts` | No |
| Archivos de vídeo | El reproductor del sistema, al renderizar la pantalla | El SDK no los almacena en caché |

`createFlowView` busca el diseño en tres lugares, en este orden:

1. La caché de disco del SDK nativo, que persiste entre reinicios de la app.
2. Tu [archivo de respaldo](capacitor-use-fallback-paywalls) para SDK 4.4 o posterior, si lo descargaste después de publicar por última vez el flow.
3. Adapty, a través de la red. Esto implica una petición de ida y vuelta, incluso tras una precarga. La primera vez que la app muestra cada versión publicada del flow, el SDK nativo realiza esta solicitud y luego guarda el layout en la caché de disco.

Cuando se activa el `loadTimeoutMs` de `createFlowView`, el SDK nativo no recurre al respaldo: solicita el layout de nuevo a la API de Adapty. `loadTimeoutMs` no limita esa segunda solicitud.

### Omitir la segmentación de audiencias \{#skip-audience-segmentation\}

Para calentar la caché sin esperar la segmentación de audiencias, usa la variante de audiencia predeterminada. No requiere ningún timeout:

```typescript showLineNumbers
await adapty.preloadFlowsForDefaultAudience({ placementIds: ['main_paywall'] });
```

Un `getFlowForDefaultAudience` posterior lee la copia de la misma forma en que `getFlow` lee una copia de `preloadFlows`.

## Mostrar el contenido multimedia de la primera pantalla desde el bundle de la app \{#show-first-screen-media-from-the-app-bundle\}

Un flow descarga sus imágenes y vídeos desde Adapty. Para mostrar al instante el contenido multimedia de la primera pantalla, sírvelo directamente desde el bundle de la app. Es una buena forma de reutilizar recursos que ya tienes incluidos, como los visuales de un onboarding nativo existente.

1. En el Flow & Paywall Builder, establece un [ID de multimedia personalizado](custom-media#custom-media-id) en la imagen o el vídeo. El archivo que subas allí se usará como respaldo.
2. Añade el archivo a los proyectos nativos: el bundle de la app iOS y la carpeta `assets` de Android.
3. Cuando crees la vista del flow, pasa el archivo empaquetado para ese ID en `customAssets`:

```typescript showLineNumbers

// "welcome_video" is the custom media ID set in the Flow & Paywall Builder
const bundledAssets: Record<string, AdaptyCustomAsset> = {
  'welcome_video': {
    type: 'video',
    fileLocation: {
      ios: { fileName: 'welcome.mp4' },
      android: { relativeAssetPath: 'videos/welcome.mp4' },
    },
  },
};

const view = await createFlowView(flow, { customAssets: bundledAssets });
```

Los archivos incluidos en el bundle aumentan el tamaño de descarga de tu app, así que incluye solo los archivos multimedia que el usuario ve primero.

Una imagen incluida en el bundle aparece de inmediato, pero el SDK sigue descargando la imagen subida en segundo plano.

Los archivos multimedia que no incluyes en el bundle también aparecen enseguida: el layout del flow incorpora una copia de baja resolución de cada imagen, incluido el fotograma estático de un vídeo, y la muestra hasta que se carga el archivo completo.

Para la referencia completa de `customAssets`, consulta [Personalizar assets](capacitor-get-pb-paywalls#customize-assets).

## Optimiza para conectividad deficiente \{#tune-for-poor-connectivity\}

Para mercados con conectividad deficiente de forma constante (zonas rurales, transporte público, regiones con problemas de enrutamiento):

- Establece `fetchPolicy: 'return_cache_data_else_load'` en cada petición excepto la primera.
- Configura un [paywall de respaldo](fallback-paywalls) para cada placement en el Adapty Dashboard.
- Equilibra `loadTimeoutMs` entre velocidad y segmentación. Con un timeout más corto, los usuarios ven el respaldo antes. Con un timeout más largo, el flow con segmentación tiene más tiempo para cargarse.
- [Mantén el flow ligero](flow-size), para que su layout se descargue antes.
- No condicionar la visualización del flow a `adapty.getProfile()`. Llama a `getFlow` de forma independiente para que un perfil lento no bloquee la interfaz.
