## Antes de empezar \{#before-you-start\}

:::important
En un proyecto de Expo, los elementos personalizados solo funcionan si mantienes las carpetas `ios` y `android` en Git y no ejecutas `npx expo prebuild --clean`. De lo contrario, Expo regenera estas carpetas y elimina el código de esta página. Los proyectos nuevos de Expo no incluyen estas carpetas en Git, por lo que EAS Build las regenera en cada compilación.
:::

Necesitas:

- **Adapty React Native SDK 4.4 o posterior**: Las versiones anteriores muestran el paywall de respaldo para cada elemento personalizado.
- **Código nativo para iOS y Android**: No es posible mostrar un componente de React Native en un elemento personalizado. Escribe este código en Swift para iOS y en Kotlin para Android. Añade el código Swift al target de tu app en Xcode, y el código Kotlin a la carpeta de `MainApplication.kt`. Comienza cada nuevo archivo Kotlin con la línea `package` de `MainApplication.kt`.
- **Un esquema de nomenclatura para los elementos personalizados**: Asigna a cada vista nativa un Tipo, como `lottie_animation`. Usa solo letras minúsculas, números y guiones bajos en los Tipos. Para distinguir entre elementos personalizados del mismo Tipo, asigna a cada uno un ID, como `welcome_wave`. Los Tipos y los IDs de tu código deben coincidir con los del [Flow & Paywall Builder](flow-custom-elements#add-and-configure).

Usa los mismos tipos e IDs en tu código de iOS y Android. A menos que configures una [audiencia](audience) diferente para cada plataforma, los usuarios de iOS y Android verán los mismos flows.

## Configura tu proyecto Android \{#set-up-your-android-project\}

Tu proyecto iOS no necesita configuración adicional. En tu proyecto Android, añade la librería Adapty UI. Para construir vistas nativas como composables, configura también Jetpack Compose.

### Añadir la biblioteca Adapty UI

En `android/app/build.gradle`, añade `io.adapty:android-ui` al bloque `dependencies`, sin especificar versión. `react-native-adapty` se encarga de fijar la versión. Una versión distinta de `android-ui` puede romper los flows.

```groovy showLineNumbers title="android/app/build.gradle"
dependencies {
    implementation("io.adapty:android-ui")
}
```

La biblioteca requiere `compileSdkVersion` 35 o superior: si `android/build.gradle` tiene una versión inferior, auméntala a 35.

### Configurar Jetpack Compose \{#set-up-jetpack-compose\}

La plantilla de React Native no [configura Compose](https://developer.android.com/develop/ui/compose/setup-compose-dependencies-and-compiler) en el módulo de la app. Un `View` de Android no necesita ninguna configuración de Compose. Para construir vistas nativas como composables, configura el compilador de Compose para la versión de Kotlin de tu app, el `kotlinVersion` en `android/build.gradle`:

<Tabs groupId="kotlin-version" queryString>
<TabItem value="kotlin-2" label="Kotlin 2.0 and later" default>

Las plantillas de React Native 0.77 y posteriores usan Kotlin 2.0 o posterior. Añade el plugin Gradle del compilador de Compose a las dependencias de `buildscript`:

```groovy showLineNumbers title="android/build.gradle"
buildscript {
    dependencies {
        classpath("org.jetbrains.kotlin:compose-compiler-gradle-plugin:$kotlinVersion")
    }
}
```

Luego aplica el plugin al módulo de la app y establece `compose true` en el bloque `buildFeatures`:

```groovy showLineNumbers title="android/app/build.gradle"
apply plugin: "org.jetbrains.kotlin.plugin.compose"

android {
    buildFeatures {
        compose true
    }
}
```

</TabItem>
<TabItem value="kotlin-1-9" label="Kotlin 1.9">

Las plantillas de React Native 0.75 y 0.76 usan Kotlin 1.9. En el bloque `android`, establece `compose true` y la versión del compilador de Compose que corresponda a tu versión de Kotlin. React Native 0.75 y 0.76 compilan con Kotlin 1.9.24, que necesita Compose compiler 1.5.14. Para otras versiones de Kotlin, consulta el [mapa de compatibilidad entre Compose y Kotlin](https://developer.android.com/jetpack/androidx/releases/compose-kotlin).

```groovy showLineNumbers title="android/app/build.gradle"
android {
    buildFeatures {
        compose true
    }
    composeOptions {
        kotlinCompilerExtensionVersion "1.5.14"
    }
}
```

</TabItem>

Para la vista de Lottie en esta página, añade también `com.airbnb.android:lottie-compose`.

## Crear vistas para elementos personalizados \{#create-views-for-custom-elements\}

Para cada Type, crea una vista nativa para iOS y para Android, o reutiliza una de tu código nativo. Las siguientes vistas del Type `lottie_animation` reproducen una animación Lottie. La vista de Android es un composable que usa la librería `com.airbnb.android:lottie-compose`:

<Tabs groupId="platform" queryString>
<TabItem value="ios" label="iOS (Swift)" default>

```swift showLineNumbers title="Swift"

struct LottieElementView: View {
    let animation: LottieAnimation?

    var body: some View {
        LottieView(animation: animation)
            .resizable()
            .looping()
    }
}
```

</TabItem>
<TabItem value="android" label="Android (Kotlin)">

```kotlin showLineNumbers title="Kotlin"

@Composable
fun LottieElement(animationFile: String) {
    val composition by rememberLottieComposition(LottieCompositionSpec.Asset(animationFile))
    LottieAnimation(
        composition = composition,
        iterations = LottieConstants.IterateForever,
    )
}
```

</TabItem>
</Tabs>

### Requisitos y buenas prácticas \{#requirements-and-best-practices\}

- **Tamaño**:
  - **Relleno y alineación**: Asegúrate de que la vista nativa encaja en el contenedor que has asignado en el Flow & Paywall Builder, restando el padding. Si la vista no ocupa toda el área, aparece por defecto en la esquina superior izquierda de esa área. Para moverla, cambia la alineación en la sección **Layout** del elemento personalizado.
  - **Altura Hug**: Si la altura del elemento personalizado está configurada como **Hug**, una vista que se expande para llenar el espacio disponible (como un mapa o una lista lazy) se colapsará, o se estirará hasta la altura de la pantalla. Asigna al elemento personalizado una altura [**Fixed**](flow-custom-elements#add-and-configure) en su lugar.
- **Tema**: Las vistas nativas no heredan los estilos de tus componentes React Native. Define colores y fuentes en el código nativo.
- **Acciones de flow**: La vista nativa no puede ejecutar acciones de flow, como la transición a la siguiente pantalla. El contexto del elemento puede enviar mensajes al flow, con `sendMessage` en iOS y `send` en Android, pero están reservados para futuras capacidades del Flow & Paywall Builder. Mantén los botones de navegación, los botones de compra y otros botones con acciones de flow fuera del elemento personalizado.
- **Elementos seleccionables**: Mantén el elemento personalizado fuera de las tarjetas de producto y otros [elementos seleccionables](flow-selectable-elements). Cuando cambia la selección, la vista nativa puede perder su estado.
- **Gestión de la navegación**: Cuando el usuario avanza a la siguiente pantalla, el SDK elimina la vista nativa de la pantalla. Detén lo que la vista haya iniciado, como sesiones de cámara, reproductores y actualizaciones de ubicación:
  - **Vista SwiftUI**: Usa la acción `onDisappear`. Para trabajo asíncrono, usa `.task`: SwiftUI lo cancela cuando la vista desaparece.
  - **Composable**: Usa el bloque `onDispose` de un `DisposableEffect`. Para trabajo asíncrono, usa `LaunchedEffect`: Compose lo cancela cuando el composable abandona la composición.
  - **`View` de Android**: Sobreescribe `onDetachedFromWindow` en tu subclase de `View`, o añade un `View.OnAttachStateChangeListener` a la `View`.

  Cuando el usuario regresa, el SDK vuelve a llamar al resolver y la vista nativa se inicia sin el estado de la anterior. En Android, en un flow que abres con `present()`, una rotación hace que el SDK llame de nuevo al resolver. En un `AdaptyFlowView` embebido, la vista nativa conserva su estado tras una rotación.
- **Vistas UIKit**: En iOS, envuélvelas en `UIViewRepresentable`.
- **Carruseles**: En Android, en un [carrusel](builder-containers#carousel), las vistas nativas de todas las diapositivas permanecen activas mientras la pantalla está abierta, no solo la vista de la diapositiva visible. Evita colocar previsualizaciones de cámara y reproductores con sonido en carruseles.

## Escribe un resolver para enlazar elementos y vistas personalizadas \{#write-a-resolver-to-match-custom-elements-and-views\}

Escribe un resolver para cada plataforma. El resolver recibe el Type y el ID de un elemento personalizado y devuelve la vista nativa correspondiente.

<Tabs groupId="platform" queryString>
<TabItem value="ios" label="iOS (Swift)" default>

Para escribir un resolver, haz que un tipo se ajuste al protocolo `AdaptyUICustomElementsResolver` e implementa el método `view(forType:id:context:)`.

Para el Type `lottie_animation`, el siguiente resolver devuelve `LottieElementView`. El ID indica el nombre del archivo de animación en el bundle de la app, por ejemplo `welcome_wave`:

```swift showLineNumbers title="Swift"

struct CustomElementsResolver: AdaptyUICustomElementsResolver {
    func view(
        forType type: String,
        id: String,
        context: AdaptyUICustomElementContext
    ) -> AnyView? {
        switch type {
        case "lottie_animation":
            // the ID names the animation file, such as welcome_wave.json
            guard let animation = LottieAnimation.named(id) else {
                return nil // no file for this ID: show the fallback
            }
            return AnyView(LottieElementView(animation: animation))
        default:
            return nil
        }
    }
}
```

En el caso `default`, devuelve `nil`.

</TabItem>
<TabItem value="android" label="Android (Kotlin)">

Para escribir un resolver, implementa la interfaz `AdaptyCustomElementsResolver`. Su método `resolve` devuelve la vista correspondiente en una de las siguientes formas:

- **Un componible**: Devuelve `AdaptyCustomElementContent.compose`, con el componible dentro de su lambda.
- **Una `View` de Android**: Devuelve `AdaptyCustomElementContent.view`, con una función que crea la `View`. Nombra el parámetro `factory`: `AdaptyCustomElementContent.view(factory = { context, _ -> ChartView(context) })`. Sin el nombre, Kotlin pasa una trailing lambda al parámetro opcional `update`, y el código no compila.

Para el tipo `lottie_animation`, el siguiente resolver devuelve la [vista Lottie](#create-views-for-custom-elements). El ID nombra el archivo de animación en la carpeta `assets`, `android/app/src/main/assets`, por ejemplo, `welcome_wave` para `welcome_wave.json`:

```kotlin showLineNumbers title="Kotlin"

class CustomElementsResolver(context: Context) : AdaptyCustomElementsResolver {
    // the animation files in the assets folder, listed once
    private val animationFiles: Set<String> = try {
        context.assets.list("").orEmpty().toSet()
    } catch (e: IOException) {
        emptySet() // no list of files: every Lottie element shows the fallback
    }

    override fun resolve(type: String, id: String): AdaptyCustomElementContent? =
        when (type) {
            "lottie_animation" -> {
                // the ID names the animation file, such as welcome_wave.json
                val file = "$id.json"
                if (file in animationFiles) {
                    AdaptyCustomElementContent.compose { LottieElement(file) }
                } else {
                    null // no file for this ID: show the fallback
                }
            }
            else -> null
        }
}
```

Para cualquier otro tipo, devuelve `null`.

</TabItem>
</Tabs>

Si [añades un elemento personalizado con un nuevo tipo](flow-custom-elements#what-changes-require-an-app-release) después de lanzar la app, los usuarios de la versión publicada verán su fallback.

El resolver tiene los siguientes requisitos:

- **Datos de red y reproductores**: Mantén los datos de red y los reproductores en el estado de la [vista nativa](#create-views-for-custom-elements), no en el resolver. El SDK llama al resolver muchas veces mientras la pantalla está abierta. El código del resolver se ejecuta de nuevo en cada llamada, por lo que las peticiones de red se repiten y los reproductores empiezan desde el principio. La vista nativa conserva su estado entre estas llamadas, así que los datos se cargan una sola vez y los reproductores siguen reproduciéndose. Crea reproductores, sesiones y peticiones de red dentro de la vista nativa:
  - **Vista SwiftUI**: Crea reproductores, sesiones y peticiones de red en `.task` o en un `@StateObject`, no en el valor inicial de una propiedad `@State`. Swift evalúa ese valor inicial de nuevo cada vez que el resolver crea la vista.
  - **Composable**: Crea reproductores y sesiones en `remember`, y las peticiones de red en `LaunchedEffect`.
  - **`View` de Android**: Crea reproductores, sesiones y peticiones de red en `onAttachedToWindow`.
- **Una vista nativa por elemento personalizado**: Algunas vistas nativas cambian mientras la pantalla está abierta, por ejemplo, cuando se cargan sus datos o cuando el usuario las pulsa. Implementa esta lógica en la propia vista nativa, no en el resolver. Si el resolver devuelve una vista diferente para el mismo elemento personalizado, la vista pierde su estado.
- **Una nueva `View` por cada aparición**: En Android, crea una nueva `View` en cada llamada a `factory`. El SDK llama a `factory` cada vez que aparece el elemento personalizado, como cuando se abre la pantalla, cuando el usuario vuelve a ella o, en un flow que abres con `present()`, tras una rotación.
- **Datos de la app**: Almacena un objeto que contenga los datos, como un `ObservableObject` o un `StateFlow` con una [racha diaria](react-native-custom-element-lottie-animation), en una propiedad del resolver. Pasa el objeto a la vista nativa y obsérvalo allí:
  - **Vista SwiftUI**: Observa un `ObservableObject` con `@ObservedObject`.
  - **Composable**: Recopila un `StateFlow` con `collectAsState`, u observa un `LiveData` con `observeAsState`.
  - **`View` de Android**: Observa el objeto en `onAttachedToWindow` y detén la observación en `onDetachedFromWindow`.

  Un valor que copias en el resolver, como el número de racha, se mantiene tal como estaba cuando creaste el resolver. Si tu código JavaScript tiene los datos, como una racha diaria, envía cada nuevo valor al código nativo a través de un [Turbo Native Module](https://reactnative.dev/docs/turbo-native-modules-introduction) y actualiza el objeto allí.

### Establece condiciones para el contenido de respaldo \{#set-conditions-for-fallback-content\}

<FlowCustomElementsFallbackConditions />

Para un permiso, devuelve ninguna vista solo cuando el usuario lo haya denegado antes de que se abriera la pantalla. En Android, `ContextCompat.checkSelfPermission` devuelve el mismo valor, `PERMISSION_DENIED`, en dos casos: antes de que tu app solicite el permiso por primera vez al usuario y después de que el usuario lo deniegue. Para distinguir estos casos, guarda el resultado de la solicitud de permiso y lee el resultado guardado en el resolver. Si tu app aún no ha solicitado el permiso, devuelve la vista nativa y solicita el permiso dentro de la vista. Por ejemplo, solicita acceso a la ubicación cuando aparezca una [vista de mapa](react-native-custom-element-map#3-match-the-map-to-the-custom-element) y muestra el mapa en cuanto el usuario conceda acceso. Si devuelves ninguna vista y el usuario concede acceso después, seguirá viendo el fallback. Un cambio de permiso no hace que el SDK llame al resolver de nuevo. La vista nativa aparece solo después de que el SDK llame al resolver de nuevo, por ejemplo, cuando el usuario vuelve a la pantalla.

## Pasa el resolver al SDK \{#pass-the-resolver-to-the-sdk\}

Configura el resolver una sola vez para cada plataforma, al lanzar la app. El SDK lo llama en cada flow, incluido un flow integrado con `AdaptyFlowView`. Los usuarios ven tus vistas nativas en los nuevos flows y pruebas A/B sin necesidad de publicar una nueva versión de la app. Estas vistas siguen mostrando a cada usuario sus propios datos, como una [racha diaria](react-native-custom-element-lottie-animation), porque los leen directamente desde tu app.

### iOS

<Tabs groupId="ios-app-delegate" queryString>
<TabItem value="swift" label="AppDelegate.swift" default>

En `AppDelegate.swift`, importa `AdaptyUI` y llama a `AdaptyUI.setCustomElementsResolver(_:)` en el método `application(_:didFinishLaunchingWithOptions:)`. Las líneas resaltadas muestran qué debes añadir. Deja el resto de la clase `AppDelegate` tal como está:

```swift showLineNumbers title="ios/YourApp/AppDelegate.swift" {1,10}

@main
class AppDelegate: UIResponder, UIApplicationDelegate {
  func application(
    _ application: UIApplication,
    didFinishLaunchingWithOptions launchOptions: [UIApplication.LaunchOptionsKey: Any]? = nil
  ) -> Bool {
    AdaptyUI.setCustomElementsResolver(CustomElementsResolver())
    // the rest of your launch code
    return true
  }
}
```

Si escribes el resolver también en `AppDelegate.swift`, importa también `AdaptyUIBuilder` allí.

Si `application(_:didFinishLaunchingWithOptions:)` termina con un `true` simple, como en la plantilla de React Native 0.88, cambia `true` por `return true`.

</TabItem>
<TabItem value="objc" label="AppDelegate.mm">

Configura el resolver a través de una clase Swift, ya que `AdaptyUI.setCustomElementsResolver(_:)` solo está disponible en Swift:

1. Añade un archivo Swift con la clase a tu target de la app:

   ```swift showLineNumbers title="CustomElementsSetup.swift"
   import AdaptyUI

   @objc final class CustomElementsSetup: NSObject {
     @MainActor @objc static func register() {
       AdaptyUI.setCustomElementsResolver(CustomElementsResolver())
     }
   }
   ```

2. En `AppDelegate.mm`, importa el encabezado Swift que Xcode genera para tu target, `<YourApp>-Swift.h`. Llama a `[CustomElementsSetup register]` al inicio de `application:didFinishLaunchingWithOptions:`. En un proyecto Expo, importa `<ExpoModulesCore/ExpoModulesCore-Swift.h>` antes del encabezado de tu target.

   ```objectivec showLineNumbers title="ios/YourApp/AppDelegate.mm" {1,5}
   #import "YourApp-Swift.h"

   - (BOOL)application:(UIApplication *)application didFinishLaunchingWithOptions:(NSDictionary *)launchOptions
   {
     [CustomElementsSetup register];
     // the rest of your launch code
   }
   ```

</TabItem>
</Tabs>

### Android

En `MainApplication.kt`, importa `AdaptyUI` y llama a `AdaptyUI.setCustomElementsResolver` en el método `onCreate`. Las líneas resaltadas muestran qué añadir. Mantén el resto de la clase `MainApplication` tal como está:

```kotlin showLineNumbers title="MainApplication.kt" {1,8}

class MainApplication : Application(), ReactApplication {
  // the other members of your MainApplication class

  override fun onCreate() {
    super.onCreate()
    AdaptyUI.setCustomElementsResolver(CustomElementsResolver(this))
    // the rest of your onCreate code
  }
}
```

:::tip
Para mostrar la misma vista en cada elemento personalizado de un Type, pasa un mapa de Types y vistas en lugar de un resolver. Con un mapa, escribes menos código que con un resolver, pero no puedes [establecer condiciones para el contenido de respaldo](#set-conditions-for-fallback-content).

<Tabs groupId="platform" queryString>
<TabItem value="ios" label="iOS (Swift)" default>

El mapa es un diccionario `[String: AdaptyUICustomElementBuilder]`. Si escribes el mapa en `AppDelegate.swift`, importa también `Lottie` allí.

```swift showLineNumbers title="Swift"
AdaptyUI.setCustomElementsResolver([
    "lottie_animation": .init { _, id, _ in LottieElementView(animation: .named(id)) },
])
```

</TabItem>
<TabItem value="android" label="Android (Kotlin)">

Pasa el mapa a `AdaptyCustomElementsResolver.of`:

```kotlin showLineNumbers title="Kotlin"
val appWideViews = mapOf(
    "confetti" to AdaptyCustomElementContent.compose { LottieElement("confetti.json") },
)
AdaptyUI.setCustomElementsResolver(AdaptyCustomElementsResolver.of(appWideViews))
```

</TabItem>
</Tabs>
:::

No puedes adjuntar un resolver a un único flow. Para mostrar datos que tu app solo tiene cuando abre un flow, envía los datos a tu código nativo antes de que el flow se abra. Luego léelos en el resolver. Por ejemplo, un paywall muestra el [peso que el usuario introdujo en un flow anterior](react-native-custom-element-interactive-chart).

## Prueba en un dispositivo \{#test-on-a-device\}

El Flow & Paywall Builder no puede ejecutar el código de tu app, por lo que el canvas solo muestra el contenido de respaldo. Un error en la vista nativa puede hacer que la app se cierre inesperadamente. Antes de publicar la app, prueba cada pantalla que tenga un elemento personalizado en un dispositivo iOS y en un dispositivo Android:

1. Para ver la versión publicada más reciente de cada flow en lugar de una versión en caché, registra el dispositivo como [dispositivo de prueba](test-devices).
2. Para ver los avisos del SDK de Adapty en la consola de Xcode y en Logcat, establece el [nivel de log](sdk-installation-react-native-pure#logging) en `warn` o en un nivel más detallado.
3. En el dispositivo, ejecuta una build que incluya el resolver. Abre cada pantalla que tenga un elemento personalizado y verifica que la vista nativa aparezca y encaje correctamente en el elemento personalizado. Si la vista tiene scroll o responde a gestos de arrastre, prueba esos gestos.
4. Si aparece el fallback en lugar de la vista nativa, busca este aviso en la consola de Xcode o en Logcat: `custom element <type>:<id> is not served by a resolver`. Luego verifica que:
   - El Type y el ID del aviso coincidan exactamente con los de tu código, letra por letra.
   - Tu app tenga el archivo, los datos o el permiso que necesita la vista.
   - Tu app configure el resolver al iniciarse: en la clase `AppDelegate` en iOS y en la clase `MainApplication` en Android.

   Si la advertencia no aparece, verifica que la app utilice Adapty React Native SDK 4.4 o posterior.
5. En Android, si el elemento personalizado sigue vacío, busca uno de estos avisos en Logcat:
   - `custom element <type>:<id> is not served by a resolver`: El elemento personalizado no tiene contenido de respaldo y ningún resolver devuelve una vista para él. Verifica cada elemento del paso 4.
   - `content does not report its size`: El composable no tiene altura propia. Asigna al elemento personalizado una altura [**Fixed**](flow-custom-elements#add-and-configure).

   El SDK solo registra la advertencia de tamaño para los composables. Si una `View` de Android queda vacía sin ninguna advertencia, dale también una altura **Fixed** al elemento personalizado.
6. Para previsualizar el respaldo, no devuelvas ninguna vista para el Type y vuelve a abrir la pantalla.
