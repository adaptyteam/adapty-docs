<SDKv4>

Para mostrar a cada usuario un flow en el idioma que lee, pasa sus idiomas al SDK de iOS 4.5 o posterior. Los usuarios ven el flow en su idioma preferido que el flow tenga disponible. Un flow que no tenga ninguno de esos idiomas se muestra en su idioma predeterminado.

En SDK 4.0–4.4, tu app pasa un código de idioma a `getFlowConfiguration`, y el SDK [lo compara de forma exacta](#pass-the-users-languages-to-the-sdk). Para actualizar tu código, consulta [Migrar el SDK de iOS de Adapty a v4.5](migration-to-ios-sdk-45).

En SDK 4.5 o posterior, tres casos siguen otras reglas:

- Las apps que eligen la localización de un flow en su propio código [usan un resolver personalizado](#pick-a-flows-localization-in-your-own-code).
- Los paywalls del antiguo Paywall Builder [solo coinciden con el idioma del usuario con la máxima prioridad](#select-a-localization-strategy).
- Los paywalls personalizados y los onboardings [funcionan como en el SDK 4.4](#localize-custom-paywalls-and-onboardings).

## Pasa los idiomas del usuario al SDK \{#pass-the-users-languages-to-the-sdk\}

<Tabs groupId="ios-sdk-version" queryString>
<TabItem value="4.5" label="SDK 4.5 o posterior" default>

[`AdaptyUI.getFlowConfiguration`](get-pb-paywalls#fetch-the-view-configuration) requiere el parámetro `preferredLocales`. Pasa los idiomas del usuario en él, comenzando por el más preferido. Tu app decide qué idiomas pasar, como los idiomas del dispositivo o el idioma seleccionado en un selector dentro de la app.

```swift showLineNumbers
let flowConfiguration = try await AdaptyUI.getFlowConfiguration(
    forFlow: flow,
    preferredLocales: Locale.preferredLanguages
)
```

Tres reglas determinan qué localización ven los usuarios:

- El SDK prueba los idiomas del usuario en orden y selecciona el primero que coincida con el flow. Así es como funciona la coincidencia de idiomas en iOS: las mismas reglas que usa iOS para elegir el idioma de una app. El SDK también reconoce variantes cercanas de un idioma: `de-AT` coincide con `de`, y `zh-TW` coincide con `zh-hant`. Los paywalls del antiguo Paywall Builder solo usan el idioma con mayor prioridad del usuario.
- Las mayúsculas y los separadores no importan: `pt_BR`, `pt-BR` y `pt-br` apuntan al mismo locale. Pasa los valores tal como los devuelve iOS.
- Si la lista está vacía o ningún idioma coincide con los locales del flow, el SDK usa el locale predeterminado.

Pasa una de estas tres listas. La lista establece el orden en que el SDK prueba los idiomas, pero no puede añadir un idioma que el flow no tenga.

| Valor | El flow aparece en | Contrapartida |
|---|---|---|
| `Locale.preferredLanguages` | El primer idioma del dispositivo que tenga el flow, aunque tu app no esté traducida a ese idioma | El flow puede aparecer en un idioma distinto al de la UI de tu app |
| `Bundle.main.preferredLocalizations` | El idioma de la UI de tu app | La lista tiene un solo idioma. Si el flow no lo incluye, los usuarios ven el idioma predeterminado. En una app con `Base.lproj` y sin localización en inglés, la lista puede contener `Base`. |
| `[selectedLanguage] + Locale.preferredLanguages` | El idioma del selector de idioma de tu app, seguido de los idiomas del dispositivo | — |

Las dos listas del sistema dan resultados diferentes en dos casos:

- Tu app solo tiene inglés y el flow tiene francés e inglés. Un hablante de francés ve francés con `Locale.preferredLanguages`, y inglés con `Bundle.main.preferredLocalizations`.
- Tu app tiene coreano y el flow no. Un usuario con coreano y luego español ve español con `Locale.preferredLanguages`, y el idioma predeterminado con `Bundle.main.preferredLocalizations`.

:::tip
No uses `Locale.current.identifier`. Solo contiene un idioma, por lo que el SDK no tiene otro al que recurrir. Su código no incluye script: `zh_TW`, no `zh-Hant-TW`. Con este identificador, los paywalls del antiguo Paywall Builder no encontrarán su localización `zh-hant`.
:::

La mayoría de las apps no pasan `localizationStrategy`. Sin ello, el SDK usa [`.auto`](#select-a-localization-strategy), que es compatible con los flows del Flow & Paywall Builder y los paywalls del antiguo Paywall Builder.

</TabItem>
<TabItem value="4.4" label="SDK 4.0–4.4">

Pasa un código de idioma en el parámetro `locale` de [`AdaptyUI.getFlowConfiguration`](get-pb-paywalls#fetch-the-view-configuration). Tu app decide qué código pasar, como el idioma del dispositivo o el idioma seleccionado en un selector de tu app.

```swift showLineNumbers
let flowConfiguration = try await AdaptyUI.getFlowConfiguration(
    forFlow: flow,
    locale: "pt-BR"
)
```

La coincidencia es exacta. El SDK compara el código que introduces con los códigos de localización del flow carácter a carácter: no cambia mayúsculas ni minúsculas, no reemplaza guiones bajos (`_`) por guiones (`-`) y no recurre a la subetiqueta de idioma. Para un flow con la localización `pt-BR`, solo `pt-BR` coincide: `pt-br`, `pt_BR` y `pt-PT` no funcionan.

Cuando el código no coincide con ninguna localización, el flow se renderiza en silencio en su [idioma predeterminado](add-paywall-locale-in-adapty-paywall-builder#set-the-default-locale): el SDK no devuelve un error ni registra ninguna advertencia.

Omitir el código de configuración regional no es lo mismo que solicitar la localización predeterminada del flow: el SDK sustituye un `en` fijo. Un flow cuya configuración regional predeterminada sea `de` seguirá renderizándose en `en` si tiene una localización `en`, y solo recurrirá a `de` cuando no la tenga.

:::warning
Pasa el código de configuración regional exactamente como aparece publicado en el flow: `pt-BR`, no `pt-br`, en el campo **Select languages**. Para los paywalls del antiguo Paywall Builder, pasa los códigos en minúsculas, como `pt-br`.

No pases un identificador de configuración regional del sistema tal como está. En un dispositivo configurado en Portugués (Brasil), `Locale.current.identifier` devuelve `pt_BR`, que no coincide con ninguna localización. En un dispositivo configurado en Inglés (Estados Unidos), `Locale.current.identifier(.bcp47)` devuelve `en-US`, que no encuentra un flow que solo tenga `en`. Antes de pasar un identificador de configuración regional del sistema, conviértelo a un código que el flow tenga.
:::

</TabItem>

## Prueba qué localización ve un usuario \{#test-which-localization-a-user-sees\}

<Tabs groupId="ios-sdk-version" queryString>
<TabItem value="4.5" label="SDK 4.5 o posterior" default>

Cuando el flow no tiene ninguno de los idiomas del usuario, el SDK usa la configuración regional predeterminada sin lanzar un error ni registrar una advertencia. Para saber qué localización ve un usuario, prueba el flow en un dispositivo:

1. En los ajustes del dispositivo, mueve el idioma de prueba a la parte superior de la lista de idiomas.
2. Abre el flow en tu app.
3. Lee `flowConfiguration.locale`. Contiene el código de la localización mostrada. El dashboard muestra este código en minúsculas: `pt-br` para `pt-BR`.

Para probar un idioma sin cambiar los ajustes del dispositivo, pasa una lista fija de `preferredLocales`, como `["pt-PT"]`, en una build de depuración.

</TabItem>
<TabItem value="4.4" label="SDK 4.0–4.4">

Cuando el código que pasas no coincide con ninguna localización del flow, el SDK utiliza el idioma predeterminado sin lanzar un error ni registrar ninguna advertencia. Para saber qué localización ve un usuario, prueba el flow en un dispositivo:

1. En los ajustes del dispositivo, selecciona el idioma y la región de prueba.
2. Abre el flow en tu app.
3. Lee `flowConfiguration.locale`. Contiene el código de la localización que se está mostrando. Si difiere del código que pasaste, significa que el flow no tiene ninguna localización con ese código exacto.

Para probar el código sin cambiar la configuración del dispositivo, pasa un `locale` fijo, como `"pt-BR"`, en una build de depuración.

</TabItem>
</Tabs>

Cuando parte del flow sigue apareciendo en el idioma predeterminado, significa que la localización mostrada no tiene traducción para esa parte. Para completar los huecos, [traduce las filas que faltan](add-paywall-locale-in-adapty-paywall-builder#manage-localizations-and-translations) en el Flow & Paywall Builder.

## Selecciona los idiomas que añadirás a un flow \{#select-which-locales-to-add-to-a-flow\}

Para cubrir la mayoría de los usuarios con el menor número de idiomas posible, sigue estas tres reglas al [añadir idiomas](add-paywall-locale-in-adapty-paywall-builder#add-and-set-up-a-locale) en el campo **Select languages**:

- Añade un idioma sin región. Por ejemplo, `de` cubre a los hablantes de alemán en Alemania, Austria y Suiza.
- Solo añade una configuración regional para una segunda traducción de un idioma, como `fr-ca` además de `fr`.
- Añade todos los idiomas que lean tus usuarios. El SDK no relaciona un idioma con otro, como el catalán con el español. Los hablantes de catalán ven el siguiente idioma preferido que tenga el flow, o la configuración regional predeterminada.

:::important
Estas reglas requieren iOS o el SDK de [Android](android-localizations-and-locale-codes) 4.5 o posterior. Las apps que usen cualquier versión del SDK de Adapty entre 4.0 y 4.4 envían un único código de idioma. Sus usuarios pueden ver una localización diferente del mismo flow que los usuarios con SDK 4.5. Mantén todos los códigos que esas apps envíen, como un `zh` o `pt-br` existente.
:::

### Selecciona los códigos para chino, español y portugués \{#select-codes-for-chinese-spanish-and-portuguese\}

El campo **Select languages** tiene más de un código para chino, español y portugués. Añade los códigos de la tabla:

| Idioma | Añadir | Los usuarios ven |
|---|---|---|
| Chino | `zh-hans` y `zh-hant`, no un nuevo `zh`. Solo añade `zh-hk` para una traducción separada de Hong Kong. | `zh-hans` en China y Singapur, y `zh-hant` en Taiwán, Hong Kong y Macao. |
| Cantonés | `yue`, siempre con `zh-hant` | `yue` en dispositivos configurados en cantonés, y `zh-hant` en dispositivos configurados en chino tradicional. Sin `zh-hant`, los usuarios con dispositivos en chino tradicional ven cantonés escrito. |
| Español | `es` y `es-419`, no un nuevo `es-mx` | `es` en España, y `es-419` en Latinoamérica y Estados Unidos. |
| Portugués | `pt-br` para portugués de Brasil y `pt` para portugués de Portugal | `pt-br` en Brasil y `pt` en Portugal. |

Si tu flow está localizado en múltiples variantes regionales del mismo idioma, incluye también una variante menos específica a nivel regional, para cubrir las variedades lingüísticas que no estén entre las que admites explícitamente. Sin este respaldo, los usuarios de otras regiones ven una variante aleatoria del grupo de idiomas, y no puedes controlar cuál. Por ejemplo, un usuario con `es-MX` puede ver `es-ar`, `es-co` o `es-es`. Para cubrir a estos usuarios, añade la variante sin región `es` o la variante panamericana `es-419`.

### Comienza con un conjunto de idiomas recomendado \{#start-from-a-recommended-set-of-locales\}

Para planificar las traducciones por etapas, empieza con uno de estos tres conjuntos. Cada conjunto incluye el anterior.

| Conjunto | Idiomas | Total |
|---|---|---|
| Mínimo | `en`, `es`, `pt-br`, `fr`, `de`, `it`, `ru`, `ja`, `ko`, `zh-hans`, `zh-hant` | 11 |
| Ampliado | El conjunto mínimo y `tr`, `pl`, `nl`, `sv`, `da`, `no`, `fi`, `uk`, `ar`, `he`, `hi`, `id`, `th`, `vi`, `es-419`, `pt` | 27 |
| Amplio | El conjunto ampliado y `cs`, `sk`, `hu`, `ro`, `el`, `bg`, `hr`, `sl`, `lt`, `lv`, `et`, `ca`, `kk`, `ms`, `fil`, `fa`, `ur`, `bn`, `ta`, `te`, `mr`, `fr-ca` | 49 |

En estos conjuntos, los usuarios ven las siguientes configuraciones regionales:

- En el conjunto mínimo, `es` cubre a los hispanohablantes de todos los países, y `pt-br` también cubre a los hablantes de portugués en Portugal.
- En el conjunto extendido, `es-419` y `pt` son traducciones secundarias. Con ellas, `es` sirve a España y `pt` sirve a Portugal. Traduce `pt` al portugués europeo.
- Los hablantes de catalán y malayo solo ven su idioma en su propia configuración regional: `ca` o `ms`. El SDK no les muestra español ni indonesio en su lugar.

### Selecciona el idioma predeterminado \{#select-the-default-locale\}

Los usuarios ven el idioma predeterminado cuando el flow no tiene ninguno de sus idiomas. Un flow nuevo comienza con `en` como único idioma y como predeterminado. Para cambiarlo, [establece otro idioma como predeterminado](add-paywall-locale-in-adapty-paywall-builder#set-the-default-locale).

Sigue estas tres reglas para el idioma predeterminado:

- Para los usuarios sin un idioma coincidente, selecciona el idioma que entienda la mayoría. Generalmente es el inglés, no el idioma de tu mercado principal.
- Traduce el idioma predeterminado por completo. Los usuarios sin un idioma coincidente verán todo el flow en el idioma predeterminado. Los usuarios con un idioma coincidente verán el flow en su idioma. Cualquier parte no traducida aparece en el idioma predeterminado.
- No selecciones un idioma con dos sistemas de escritura, como el chino. Los usuarios del otro sistema puede que no puedan leer el idioma predeterminado.

## Selecciona una estrategia de localización \{#select-a-localization-strategy\}

La mayoría de las apps no pasan `localizationStrategy`, por lo que el SDK usa `.auto`. Esta estrategia aplica la coincidencia de idioma de iOS a los flows del Flow & Paywall Builder, y la regla de un único idioma a los paywalls del antiguo Paywall Builder.

Bajo la regla de idioma único, el SDK solo lee el idioma con la mayor prioridad en `preferredLocales`. Primero intenta el código completo, luego códigos más cortos (`pt-br`, después `pt`) y, si no encuentra ninguno, muestra el idioma predeterminado. Un paywall del antiguo Paywall Builder sigue funcionando con esta regla, incluso después de republicarlo. Para que el SDK pruebe todos los idiomas en `preferredLocales`, [mueve el paywall al Flow & Paywall Builder](convert-paywall-to-flow). Luego sirve el nuevo flow desde un placement de flow.

Para cambiar cómo el SDK relaciona los idiomas del usuario con los locales del flow, pasa uno de los siguientes valores en el parámetro `localizationStrategy`:

- `.system`: todos los flows usan la coincidencia de idioma de iOS, incluidos los paywalls del antiguo Paywall Builder.
- `.legacy`: todos los flows usan la regla de un solo idioma, sin la coincidencia exacta del SDK 4.4. No uses `.legacy` para flows del Flow & Paywall Builder: no detecta correctamente los locales con región o script, como `pt-BR`.
- `.custom(resolver:fallbackResolver:)`: [tu código elige la localización](#pick-a-flows-localization-in-your-own-code).

### Elige la localización de un flow en tu propio código \{#pick-a-flows-localization-in-your-own-code\}

La coincidencia de idioma de iOS no cubre todos los scripts. Por ejemplo, cuando un dispositivo lista el azerbaiyano en script cirílico (`az-Cyrl`) pero no en latín, un flow con `az` aparece en su locale predeterminado. Para mostrar `az` en su lugar, o para elegir la localización según tus propias reglas, crea un tipo que se ajuste a `AdaptyUICustomLocalizationResolver`. Luego pásalo en el valor `.custom(resolver:)` del parámetro `localizationStrategy`. Añade `import AdaptyUIBuilder` al archivo con el resolver.

Otros SDK de Adapty para otras plataformas aplican reglas distintas para hacer coincidir idiomas, por lo que el mismo usuario podría ver diferentes localizaciones de un flow en iOS y Android. Para mostrar la misma localización en todas las plataformas, escribe un resolver que devuelva el mismo código de locale que tu app en las demás plataformas.

Las siguientes reglas se aplican al resolver:

- El SDK no llama al resolver para un flow con una sola localización. El flow aparece en esa localización.
- El SDK llama a `resolve(for:from:)` con la lista que pasó tu app y un `AdaptyUILocalizationSource` con los `locales` y `defaultLocale` del flow. Los `locales` no tienen un orden fijo.
- Para mostrar una localización, devuelve un código de `locales` o `defaultLocale`, escrito exactamente igual, incluidas las mayúsculas: `ar`, no `AR`.
- Si el resolver devuelve cualquier otro código o `nil`, el SDK usa la estrategia de `fallbackResolver`. Sin `fallbackResolver`, el SDK usa `.auto`.
- El SDK puede llamar al resolver fuera del hilo principal.
- Devuelve el código de inmediato, sin peticiones de red ni otras operaciones lentas. El SDK espera al resolver sin límite de tiempo, y el flow solo aparece después de que el resolver devuelva el valor.

## Estándar de códigos de idioma en Adapty \{#locale-code-standard-at-adapty\}

Los códigos de idioma de Adapty siguen el [estándar BCP 47](https://en.wikipedia.org/wiki/IETF_language_tag): una subtiqueta de idioma y, opcionalmente, una subtiqueta de script o región, separadas por guiones. El campo **Select languages** muestra los códigos en minúsculas: `en` (inglés), `pt-br` (portugués, Brasil), `zh-hans` (chino simplificado) y `zh-hant` (chino tradicional).

## Localizar paywalls y onboardings personalizados \{#localize-custom-paywalls-and-onboardings\}

SDK 4.5 solo cambia las reglas de localización para los flows. Los paywalls y onboardings personalizados funcionan igual que en SDK 4.4.

### Seleccionar el Remote Config de un paywall personalizado por idioma \{#pick-a-custom-paywalls-remote-config-by-language\}

`getFlow` no tiene parámetro de idioma. Para un paywall personalizado, devuelve todas las localizaciones configuradas en `flow.remoteConfigs`. Cada entrada tiene un código `locale` y el contenido del config (`jsonString`, o el `dictionary` ya parseado). Elige la entrada que corresponda al usuario, con tu propia lógica de respaldo:

```swift showLineNumbers
do {
    let flow = try await Adapty.getFlow(placementId: "YOUR_PLACEMENT_ID")
    let config = flow.remoteConfigs.first(where: { $0.locale == "en" })
        ?? flow.remoteConfigs.first
    // lee tus valores desde config?.dictionary
} catch {
    // maneja el error
}
```

Adapty almacena los códigos de `locale` en el formato descrito en [Estándar de código de idioma en Adapty](#locale-code-standard-at-adapty). El SDK no compara los Remote Configs con un idioma, por lo que tu app es quien decide qué entrada aplicar.

### Pasar un idioma a un onboarding \{#pass-a-locale-to-an-onboarding\}

<OnboardingDeprecation />

`getOnboarding` mantiene su parámetro `locale` en el SDK 4.5. Cuando pasas un `locale` a [`getOnboarding`](get-onboardings), el servidor selecciona la localización:

1. La cadena de configuración regional se convierte a minúsculas y todos los guiones bajos (`_`) se reemplazan con guiones (`-`)
2. Adapty busca la localización con el código de configuración regional que coincida exactamente
3. Si no se encuentra ninguna coincidencia, Adapty toma la subcadena antes del primer guión (`pt` para `pt-br`) y busca la localización correspondiente
4. Si tampoco se encuentra ninguna coincidencia, Adapty devuelve el contenido para la configuración regional predeterminada del onboarding

De esta forma, `pt_BR`, `pt-BR` y `pt-br` se resuelven todos en la misma localización del onboarding.

## Por qué esto es importante \{#why-this-is-important\}

Hay algunos escenarios en los que los códigos de idioma entran en juego — por ejemplo, cuando intentas obtener el paywall correcto para la localización actual de tu app.

Como los códigos de idioma son complejos y pueden variar de una plataforma a otra, nos apoyamos en un estándar interno para todas las plataformas que soportamos. Sin embargo, precisamente por esa complejidad, es muy importante que entiendas exactamente qué estás enviando a nuestro servidor para obtener la localización correcta y qué ocurre después — así siempre recibirás lo que esperas.

## Estándar de códigos de idioma en Adapty \{#locale-code-standard-at-adapty\}

Para los códigos de idioma, Adapty utiliza una versión ligeramente modificada del [estándar BCP 47](https://en.wikipedia.org/wiki/IETF_language_tag): cada código está formado por subetiquetas en minúsculas separadas por guiones. Algunos ejemplos: `en` (inglés), `pt-br` (portugués (Brasil)), `zh` (chino simplificado), `zh-hant` (chino tradicional).

## Coincidencia de código de localización \{#locale-code-matching\}

Cuando Adapty recibe una llamada desde el SDK con el código de localización y comienza a buscar la localización correspondiente de un paywall, ocurre lo siguiente:

1. La cadena de localización entrante se convierte a minúsculas y todos los guiones bajos (`_`) se reemplazan por guiones (`-`)
2. A continuación, se busca la localización con el código de localización que coincida exactamente
3. Si no se encuentra ninguna coincidencia, se toma la subcadena anterior al primer guión (`pt` para `pt-br`) y se busca la localización coincidente
4. Si tampoco se encuentra ninguna coincidencia, se devuelve el contenido con la localización predeterminada del paywall

De este modo, un dispositivo iOS que envíe `'pt_BR'`, un dispositivo Android que envíe `pt-BR` y otro dispositivo que envíe `pt-br` obtendrán el mismo resultado.

## Implementar localizaciones: la forma recomendada \{#implementing-localizations-recommended-way\}

Si te estás preguntando por las localizaciones, lo más probable es que ya estés trabajando con archivos de cadenas localizadas en tu proyecto. En ese caso, te recomendamos añadir un par clave-valor con el código de idioma de Adapty correspondiente en cada uno de tus archivos para las localizaciones respectivas, y luego extraer el valor de esa clave al llamar a nuestro SDK, como se muestra aquí:

```swift showLineNumbers
// 1. Modify your Localizable.strings files

/*
Localizable.strings - Spanish
*/
adapty_paywalls_locale = "es";
/*
Localizable.strings - Portuguese (Brazil)
*/
adapty_paywalls_locale = "pt-br";
// 2. Extract and use the locale code
let locale = NSLocalizedString("adapty_paywalls_locale", comment: "")
// pass locale code to AdaptyUI.getViewConfiguration or Adapty.getPaywall method
```

Así tienes el control total sobre qué localización se obtendrá para cada usuario de tu app.

## Implementar localizaciones: la otra forma \{#implementing-localizations-the-other-way\}

Puedes obtener resultados similares (aunque no idénticos) sin definir explícitamente los códigos de idioma para cada localización. Esto implica extraer un código de idioma de otros objetos que proporciona tu plataforma, como en este ejemplo:

```swift showLineNumbers
let locale = Locale.current.identifier
// pass locale code to AdaptyUI.getViewConfiguration or Adapty.getPaywall method
```

No recomendamos este enfoque por varios motivos:

1. En iOS, los idiomas preferidos y el idioma actual no son idénticos. Si quieres que la localización se seleccione correctamente, tendrás que apoyarte en la lógica de Apple, que funciona de manera automática si usas el enfoque recomendado con archivos de cadenas localizadas, o bien recrearla tú mismo.
2. Es difícil predecir exactamente qué recibirá el servidor de Adapty. Por ejemplo, en iOS es posible obtener un código como `ar_OM@numbers='latn'` en un dispositivo y enviarlo a nuestro servidor. Para esa llamada no obtendrás la localización `ar-om` que buscabas, sino `ar`, lo cual probablemente no es lo que esperabas.

Should you decide to use this approach anyway — make sure you've covered all the relevant use cases.

</SDKv3>
