## なぜこれが重要なのか \{#why-this-is-important\}

ロケールコードは、Adapty がフローやオンボーディングのローカライズを選択する際、およびカスタムペイウォール向けにリモートコンフィグを読み取る際に使用されます。

ロケールコードはプラットフォームによって異なる複雑な仕様を持つため、Adapty はサポートするすべてのプラットフォームで一つの内部標準に依存しています。この標準を理解することで、ユーザーが受け取るローカライズを予測できます。

## Adapty におけるロケールコードの標準 \{#locale-code-standard-at-adapty\}

Adapty のロケールコードは [BCP 47 標準](https://en.wikipedia.org/wiki/IETF_language_tag) に従います。言語サブタグの後に、オプションでスクリプトまたは地域サブタグをハイフンで区切って続けます。コードが表示される場所によって、文字の大文字・小文字が変わります：

- **Select languages** フィールドでは、すべてのコードが小文字で表示されます：`pt-br`、`zh-hant`。
- フロー＆ペイウォールビルダーで公開されたフローのコードは、地域部分が大文字、スクリプト部分が先頭大文字になります：`pt-BR`、`zh-Hant`。
- 旧ペイウォールビルダーのペイウォールでは、すべてのコードが小文字のまま維持されます：`pt-br`、`zh-hant`。

`en`、`pt`、`es-419` などのコードはどこでも同じように見えます。

## ロケールコードのマッチング \{#locale-code-matching\}

SDK v4 では、フローとオンボーディングのロケールコードのマッチング方法が異なります。フローはデバイス上の SDK によってローカライズされ、オンボーディングは Adapty サーバーによってローカライズされます。

### フローとペイウォール \{#flows-and-paywalls\}

Adapty がレンダリングするペイウォールは SDK v4 ではフローとして配信されるため、以下のルールは両方に適用されます。

マッチングは完全一致です。SDK は渡されたコードをフローのローカライゼーションコードと1文字ずつ比較します。大文字・小文字の変換、アンダースコア（`_`）とハイフン（`-`）の置換、言語サブタグへのフォールバックは一切行われません。`pt-BR` のローカライゼーションを持つフローにマッチするのは `pt-BR` だけです。`pt-br`、`pt_BR`、`pt-PT` はいずれもマッチしません。

コードがローカライゼーションに一致しない場合、フローは[デフォルトロケール](add-paywall-locale-in-adapty-paywall-builder#set-the-default-locale)で静かにレンダリングされます — SDKはエラーを返さず、警告もログに記録しません。

コードが一致する場合、Adaptyは該当するローカライゼーションをデフォルトのものとマージします。一致したローカライゼーションに定義されていない文字列やアセットは、デフォルトのローカライゼーションから取得されます。

ロケールコードを省略することは、フローのデフォルトローカライゼーションを要求することと同じではありません。SDK は固定の `en` を代わりに使用します。デフォルトロケールが `de` のフローは、`en` ローカライゼーションが存在する場合は `en` で表示され、存在しない場合のみ `de` にフォールバックします。

:::warning
ロケールコードは、公開済みフローの **Select languages** フィールドに表示されている形式のまま正確に渡してください（例：`pt-br` ではなく `pt-BR`）。旧ペイウォールビルダーのペイウォールの場合は、`pt-br` のように小文字のコードを渡してください。

システムのロケール識別子をそのまま渡さないでください。英語（米国）に設定されたデバイスでは、`navigator.language` は `en-US` を返しますが、`en` のみを持つフローにはマッチしません。システムのロケール識別子を渡す前に、フローが持つコードに変換してください。
:::

### オンボーディング \{#onboardings\}

オンボーディングはサーバー側でローカライズされており、サーバーのルールは他のフォーマットにも対応しています。[`getOnboarding`](capacitor-get-onboardings) に `locale` を渡すと、次の順序で処理されます：

1. ロケール文字列が小文字に変換され、アンダースコア（`_`）がハイフン（`-`）に置き換えられます
2. Adapty は完全に一致するロケールコードのローカライズを検索します
3. 一致するものが見つからない場合、Adapty は最初のハイフンより前の部分文字列（`pt-br` であれば `pt`）を取り出し、一致するローカライズを検索します
4. それでも一致するものが見つからない場合、Adapty はオンボーディングのデフォルトロケールのコンテンツを返します

このようにして、`pt_BR`、`pt-BR`、`pt-br` はすべて同じオンボーディングのローカライズに解決されます。

## ローカライゼーションの実装 \{#implementing-localizations\}

SDK v4 では、フローを取得する際にロケールコードを渡す必要はありません。フロービューが構築される際に SDK がすべてのローカライゼーションを読み込み、そのうちの1つを適用します。

- **ビルダーで作成したフロー**: アプリ側でどのロケールコードを渡すかを決定します（デバイスのロケールやアプリ内の言語ピッカーで選択した言語など）。`createFlowView` の `locale` オプションとして渡してください。省略可能です — 省略した場合、フローは `en` でレンダリングされます。ただし、フローに `en` のローカライゼーションがない場合は[デフォルトロケール](add-paywall-locale-in-adapty-paywall-builder#set-the-default-locale)でレンダリングされます。

  ```typescript showLineNumbers
  import { createFlowView } from '@adapty/capacitor';

  const view = await createFlowView(flow, { locale: 'es' });
  ```

  `view.locale` は、ビューの構築に使用されたローカライゼーションを報告します。`locale` オプションと `view.locale` の両方とも、Capacitor SDK 4.1 以降が必要です。それより古いバージョンでは `view.locale` は `undefined` になります。[`onAppeared` ハンドラー](capacitor-handling-events#the-view-argument) も同じ値を報告します。
- **カスタム（リモートコンフィグ）ペイウォール**: `getFlow` は設定されたすべてのローカライゼーションを `flow.remoteConfigs` に返します。各エントリには `lang` コードと `data` オブジェクトがあります。ユーザーに合ったエントリを独自のフォールバックロジックで選択してください。

```typescript showLineNumbers

const flow = await adapty.getFlow({ placementId: 'placement_id' });
const config = flow.remoteConfigs?.find((c) => c.lang === 'en') ?? flow.remoteConfigs?.[0];
// read your values from config?.data
```

Adapty は `lang` コードを [Adapty のロケールコード標準](#locale-code-standard-at-adapty) に記載された形式で保存します。SDK はリモートコンフィグをロケールと照合しないため、どのエントリを適用するかはアプリ側で決定してください。

## これが重要な理由 \{#why-this-is-important\}

ロケールコードが関係するシナリオはいくつかあります。たとえば、アプリの現在のローカライゼーションに合った正しいペイウォールを取得しようとする場合などです。

ロケールコードはプラットフォームによって異なり複雑なため、Adapty ではサポートするすべてのプラットフォームに対して内部標準を設けています。ただし、コードが複雑である以上、サーバーに何を送信しているのか、その後どのような処理が行われるのかを正確に把握することが非常に重要です。そうすることで、期待通りのローカライゼーションを常に受け取ることができます。

## Adaptyのロケールコード標準 \{#locale-code-standard-at-adapty\}

ロケールコードには、Adaptyは少し修正した [BCP 47標準](https://en.wikipedia.org/wiki/IETF_language_tag) を使用しています。各コードはハイフンで区切られた小文字のサブタグで構成されています。例: `en`（英語）、`pt-br`（ポルトガル語（ブラジル））、`zh`（簡体字中国語）、`zh-hant`（繁体字中国語）。

## ロケールコードのマッチング \{#locale-code-matching\}

Adaptyがクライアント側のSDKからロケールコードを含むリクエストを受け取り、ペイウォールの対応するローカライズを検索する際、以下の処理が行われます：

1. 受信したロケール文字列を小文字に変換し、アンダースコア（`_`）をすべてハイフン（`-`）に置き換えます
2. 完全に一致するロケールコードのローカライズを検索します
3. 一致するものが見つからない場合、最初のハイフンより前の部分文字列（`pt-br` の場合は `pt`）を取得し、一致するローカライズを検索します
4. それでも一致するものが見つからない場合、ペイウォールのデフォルトロケールのコンテンツを返します

このようにすることで、`'pt_BR'` を送信した iOS デバイス、`pt-BR` を送信した Android デバイス、`pt-br` を送信した別のデバイスが、すべて同じ結果を受け取れます。

## ローカライゼーションの実装：推奨方法 \{#implementing-localizations-recommended-way\}

ローカライゼーションについて調べているということは、すでにプロジェクト内でローカライズされた文字列ファイルを扱っているはずです。その場合は、各ファイルに対応するローカライゼーション用の Adapty ロケールコードをキーと値のペアとして追加することをおすすめします。そして、SDK を呼び出す際にそのキーの値を取り出して使用します。例を示します：

```javascript showLineNumbers
// 1. Modify your localization files (e.g., using react-i18next)

/*
en.json
*/
{
  "adapty_paywalls_locale": "en"
}

/*
es.json
*/
{
  "adapty_paywalls_locale": "es"
}

/*
pt-BR.json
*/
{
  "adapty_paywalls_locale": "pt-br"
}

// 2. Extract and use the locale code

const MyComponent = () => {
  const { t } = useTranslation();
  
  const fetchPaywall = async () => {
    const locale = t('adapty_paywalls_locale');
    // pass locale code to adapty.getPaywall or adapty.getPaywallForDefaultAudience method
    const paywall = await adapty.getPaywallForDefaultAudience('placement_id', locale);
  };
};
```

That way you can ensure you're in full control of what localization will be retrieved for every user of your app.

## ローカライゼーションの実装：別の方法 \{#implementing-localizations-the-other-way\}

すべてのローカライゼーションにロケールコードを明示的に定義しなくても、同様の（ただし完全に同一ではない）結果を得ることができます。これは、プラットフォームが提供する他のオブジェクトからロケールコードを取得する方法です。例えば次のようにします：

```javascript showLineNumbers

const getLocaleCode = () => {
  if (Capacitor.getPlatform() === 'ios') {
    return navigator.language || 'en';
  } else {
    return navigator.language || 'en';
  }
};

const fetchPaywall = async () => {
  const locale = getLocaleCode();
  // pass locale code to adapty.getPaywall or adapty.getPaywallForDefaultAudience method
  const paywall = await adapty.getPaywallForDefaultAudience('placement_id', locale);
};
```

この方法はいくつかの理由からお勧めしません：

1. iOSでは、優先言語と現在のロケールは必ずしも同一ではありません。ローカライゼーションが正しく選択されるようにするには、ローカライズされた文字列ファイルを使用する推奨アプローチを採用してAppleのロジックに任せるか、自分でそれを再現する必要があります。
2. Adaptyのサーバーが実際に何を受け取るかを予測するのは難しい場合があります。たとえばiOSでは、デバイスから `ar_OM@numbers='latn'` のようなロケールを取得してサーバーに送信することがあります。この場合、期待していた `ar-om` ローカライゼーションではなく、`ar` が返されることになり、意図しない結果になる可能性があります。

そのアプローチを使用する場合は、関連するすべてのユースケースを確実にカバーしてください。
