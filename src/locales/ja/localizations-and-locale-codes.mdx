<SDKv4>

各ユーザーに適切な言語でフローを表示するには、ユーザーの言語をAdapty iOS SDK 4.5以降に渡してください。ユーザーには、フローが対応している中で最も優先度の高い言語でフローが表示されます。これらの言語がいずれもフローに含まれていない場合は、デフォルトロケールで表示されます。

SDK 4.0〜4.4では、アプリは1つのロケールコードを `getFlowConfiguration` に渡し、SDKは[完全一致で照合します](#pass-the-users-languages-to-the-sdk)。コードを更新するには、[Adapty iOS SDK v4.5への移行](migration-to-ios-sdk-45)をご覧ください。

SDK 4.5以降では、次の3つのケースが異なるルールに従います：

- 独自のコードでフローのローカライゼーションを選択するアプリは、[カスタムリゾルバーを使用します](#pick-a-flows-localization-in-your-own-code)。
- 旧ペイウォールビルダーのペイウォールは、[最優先でユーザーの言語のみを照合します](#select-a-localization-strategy)。
- カスタムペイウォールとオンボーディングは、[SDK 4.4 と同様に動作します](#localize-custom-paywalls-and-onboardings)。

## ユーザーの言語をSDKに渡す \{#pass-the-users-languages-to-the-sdk\}

<Tabs groupId="ios-sdk-version" queryString>
<TabItem value="4.5" label="SDK 4.5 or later" default>

[`AdaptyUI.getFlowConfiguration`](get-pb-paywalls#fetch-the-view-configuration) には `preferredLocales` パラメータが必要です。ユーザーの言語を優先度の高い順に渡してください。デバイスの言語やアプリ内の言語ピッカーで選択された言語など、どの言語を渡すかはアプリ側で決定します。

```swift showLineNumbers
let flowConfiguration = try await AdaptyUI.getFlowConfiguration(
    forFlow: flow,
    preferredLocales: Locale.preferredLanguages
)
```

3つのルールによって、ユーザーが見るローカライズが決まります：

- SDKはユーザーの言語を順番に試し、フローが持つ最初の言語に一致させます。これはiOSの言語マッチングです。つまり、iOSがアプリの言語を選択するために使用するルールです。SDKは言語の近いバリアントにも一致します: `de-AT`は`de`に、`zh-TW`は`zh-hant`に一致します。旧ペイウォールビルダーのペイウォールは、最も優先度の高いユーザーの言語のみを使用します。
- 大文字・小文字とセパレーターは関係ありません: `pt_BR`、`pt-BR`、`pt-br`はすべて同じロケールに一致します。iOSが返す値をそのまま渡してください。
- 空のリスト、またはフローのどのロケールにも一致しないリストの場合、SDKはデフォルトロケールを使用します。

SDKが言語を試みる順序を設定するリストを3種類から1つ渡します。ただし、フローに存在しない言語を追加することはできません。

| 値 | フローが表示される言語 | トレードオフ |
|---|---|---|
| `Locale.preferredLanguages` | デバイスの優先言語の中でフローが対応している最初の言語（アプリが翻訳されていない言語でも対象） | フローがアプリのUIとは異なる言語で表示される可能性がある |
| `Bundle.main.preferredLocalizations` | アプリのUIの言語 | リストには言語が1つしか含まれない。フローがその言語に対応していない場合、ユーザーにはデフォルトのロケールが表示される。`Base.lproj` を持ち、英語のローカライズがないアプリでは、リストに `Base` が含まれる場合がある。 |
| `[selectedLanguage] + Locale.preferredLanguages` | アプリ内の言語ピッカーで選択した言語、次にデバイスの言語 | — |

The two system lists give different results in two cases:

- Your app has only English, and the flow has French and English. A French speaker sees French with `Locale.preferredLanguages`, and English with `Bundle.main.preferredLocalizations`.
- Your app has Korean, and the flow doesn't. A user with Korean, then Spanish, sees Spanish with `Locale.preferredLanguages`, and the default locale with `Bundle.main.preferredLocalizations`.

:::tip
`Locale.current.identifier` は渡さないでください。これには1つの言語しか含まれないため、SDKが他の言語を試すことができません。またそのコードにはスクリプトがありません（`zh-Hant-TW` ではなく `zh_TW`）。この識別子を使用すると、旧ペイウォールビルダーのペイウォールで `zh-hant` のローカライズが適用されません。
:::

ほとんどのアプリでは `localizationStrategy` を渡しません。指定しない場合、SDKは [`.auto`](#select-a-localization-strategy) を使用します。これはFlow & ペイウォールビルダーのフローや旧ペイウォールビルダーのペイウォールに適しています。

</TabItem>
<TabItem value="4.4" label="SDK 4.0–4.4">

[`AdaptyUI.getFlowConfiguration`](get-pb-paywalls#fetch-the-view-configuration) の `locale` パラメータに、ロケールコードを1つ渡します。デバイスのロケールやアプリ内のピッカーで選択した言語など、どのコードを渡すかはアプリ側で決定します。

```swift showLineNumbers
let flowConfiguration = try await AdaptyUI.getFlowConfiguration(
    forFlow: flow,
    locale: "pt-BR"
)
```

一致は完全一致です。SDKは渡されたコードとフローのローカリゼーションコードを1文字ずつ比較します。大文字・小文字の変換は行われず、アンダースコア（`_`）とハイフン（`-`）の置換も行われず、言語サブタグへのフォールバックもありません。`pt-BR` のローカリゼーションを持つフローの場合、`pt-BR` のみが一致します。`pt-br`、`pt_BR`、`pt-PT` はいずれも一致しません。

コードがどのローカリゼーションにも一致しない場合、フローは[デフォルトロケール](add-paywall-locale-in-adapty-paywall-builder#set-the-default-locale)で静かにレンダリングされます。SDKはエラーを返さず、警告もログに記録しません。

ロケールコードを省略することは、フローのデフォルトローカライゼーションを要求することとは異なります。省略した場合、SDK は固定値として `en` を使用します。デフォルトロケールが `de` のフローでも、`en` のローカライゼーションが存在する場合は `en` で表示され、`en` が存在しない場合にのみ `de` にフォールバックします。

:::warning
ロケールコードは、公開済みフローに設定されている表記を正確に指定してください。**Select languages** フィールドには `pt-BR` と表示されているため、`pt-br` ではなく `pt-BR` を渡してください。旧ペイウォールビルダーのペイウォールの場合は、`pt-br` のように小文字のコードを渡してください。

システムのロケール識別子をそのまま渡さないでください。ポルトガル語（ブラジル）に設定されたデバイスでは、`Locale.current.identifier` は `pt_BR` を返しますが、これはどのローカライズにも一致しません。英語（米国）に設定されたデバイスでは、`Locale.current.identifier(.bcp47)` は `en-US` を返しますが、`en` のみを持つフローを見逃してしまいます。システムのロケール識別子を渡す前に、フローが持つコードに変換してください。
:::

</TabItem>
</Tabs>

## ユーザーが表示するローカライズのテスト \{#test-which-localization-a-user-sees\}

<Tabs groupId="ios-sdk-version" queryString>
<TabItem value="4.5" label="SDK 4.5 or later" default>

フローにユーザーの言語が含まれていない場合、SDKはエラーや警告を出さずにデフォルトのロケールを使用します。ユーザーが表示するローカライズを確認するには、デバイスでフローをテストしてください：

1. デバイスの設定で、テストしたい言語を言語リストの先頭に移動します。
2. アプリでフローを開きます。
3. `flowConfiguration.locale` を確認します。これには表示されているローカライゼーションのコードが含まれています。ダッシュボードではこのコードが小文字で表示されます（例：`pt-BR` は `pt-br` と表示）。

デバイスの設定を変更せずに言語をテストするには、デバッグビルドで `preferredLocales` に `["pt-PT"]` のような固定リストを渡してください。

</TabItem>
<TabItem value="4.4" label="SDK 4.0–4.4">

コードがフローのどのローカライズとも一致しない場合、SDKはエラーを発生させたり警告をログに記録したりせず、デフォルトのロケールを使用します。ユーザーがどのローカライズを見ているかを確認するには、デバイスでフローをテストしてください：

1. デバイスの設定でテスト言語とリージョンを選択します。
2. アプリでフローを開きます。
3. `flowConfiguration.locale` を読み取ります。これには表示されているローカライズのコードが含まれています。渡したコードと異なる場合、そのコードに対応するローカライズがフローに存在しません。

デバッグビルドでデバイス設定を変更せずにコードをテストするには、`"pt-BR"` などの固定 `locale` を渡してください。

</TabItem>
</Tabs>

フローの一部がデフォルトのロケールで表示される場合、その部分の翻訳がローカライズに含まれていません。不足している箇所を補うには、Flow & Paywall Builder で[不足している行を翻訳](add-paywall-locale-in-adapty-paywall-builder#manage-localizations-and-translations)してください。

## フローに追加するロケールの選択 \{#select-which-locales-to-add-to-a-flow\}

ユーザーの大多数をできるだけ少ないロケールでカバーするには、**Select languages** フィールドで[ロケールを追加する](add-paywall-locale-in-adapty-paywall-builder#add-and-set-up-a-locale)際に次の3つのルールに従ってください：

- 地域なしで言語を追加します。例えば、`de` はドイツ、オーストリア、スイスのドイツ語話者をカバーします。
- 同じ言語の2つ目の翻訳がある場合にのみ、地域ロケールを追加します。例えば、`fr` に加えて `fr-ca` を追加するなど。
- ユーザーが読む言語をすべて追加します。SDKはカタルーニャ語をスペイン語に対応させるといった、言語間のマッチングは行いません。カタルーニャ語話者には、フローが持つ次の優先言語、またはデフォルトロケールが表示されます。

:::important
これらのルールは iOS または [Android](android-localizations-and-locale-codes) SDK 4.5 以降が必要です。Adapty SDK 4.0〜4.4 を使用しているアプリはロケールコードを1つだけ渡します。そのため、これらのユーザーは SDK 4.5 のユーザーとは異なるローカライゼーションのフローを表示することがあります。該当アプリが渡している既存のコード（例：`zh` や `pt-br`）はそのまま維持してください。
:::

### 中国語、スペイン語、ポルトガル語のコードを選択する \{#select-codes-for-chinese-spanish-and-portuguese\}

**Select languages** フィールドには、中国語、スペイン語、ポルトガル語に対して複数のコードが用意されています。以下の表からコードを追加してください：

| 言語 | 追加 | ユーザーに表示される内容 |
|---|---|---|
| 中国語 | 新しい `zh` は追加せず、`zh-hans` と `zh-hant` を追加する。香港向けに別途翻訳が必要な場合のみ `zh-hk` を追加する。 | 中国とシンガポールでは `zh-hans`、台湾・香港・マカオでは `zh-hant` が表示される。 |
| 広東語 | `yue` は常に `zh-hant` と併用する。 | 広東語設定のデバイスでは `yue`、繁体字中国語設定のデバイスでは `zh-hant` が表示される。`zh-hant` がない場合、繁体字中国語設定のユーザーには書き言葉の広東語が表示される。 |
| スペイン語 | 新しい `es-mx` は追加せず、`es` と `es-419` を追加する。 | スペインでは `es`、ラテンアメリカおよびアメリカ合衆国では `es-419` が表示される。 |
| ポルトガル語 | ブラジルポルトガル語には `pt-br`、ヨーロッパポルトガル語には `pt` を追加する。 | ブラジルでは `pt-br`、ポルトガルでは `pt` が表示される。 |

フローが同じ言語の複数の地域バリアントにローカライズされている場合は、より地域を限定しないロケールも提供してください。これにより、明示的にサポートしていない言語バリエーションを持つユーザーをカバーできます。このようなフォールバックがない場合、その言語グループに属する他の地域のユーザーにはランダムなロケールが表示され、どれが表示されるかを制御できません。たとえば、`es-MX` のユーザーには `es-ar`、`es-co`、`es-es` のいずれかが表示される可能性があります。このようなユーザーをターゲットにするには、地域を含まない `es` ロケール、またはパンアメリカン向けの `es-419` ロケールを追加してください。

### 推奨ロケールセットから始める \{#start-from-a-recommended-set-of-locales\}

翻訳を段階的に進める場合は、以下の3つのセットのいずれかから始めてください。各セットは前のセットを含みます。

| セット | ロケール | 合計 |
|---|---|---|
| 最小 | `en`, `es`, `pt-br`, `fr`, `de`, `it`, `ru`, `ja`, `ko`, `zh-hans`, `zh-hant` | 11 |
| 拡張 | 最小セットに加え `tr`, `pl`, `nl`, `sv`, `da`, `no`, `fi`, `uk`, `ar`, `he`, `hi`, `id`, `th`, `vi`, `es-419`, `pt` | 27 |
| 広範 | 拡張セットに加え `cs`, `sk`, `hu`, `ro`, `el`, `bg`, `hr`, `sl`, `lt`, `lv`, `et`, `ca`, `kk`, `ms`, `fil`, `fa`, `ur`, `bn`, `ta`, `te`, `mr`, `fr-ca` | 49 |

これらのセットでは、ユーザーに以下のロケールが表示されます：

- 最小セットでは、`es` がすべての国のスペイン語話者をカバーし、`pt-br` がポルトガルのポルトガル語話者もカバーします。
- 拡張セットでは、`es-419` と `pt` が2番目の翻訳です。これにより、`es` はスペインに対応し、`pt` はポルトガルに対応します。`pt` はヨーロッパポルトガル語に翻訳してください。
- カタルーニャ語とマレー語の話者は、それぞれ固有のロケール（`ca` または `ms`）でのみその言語を表示します。SDK はスペイン語やインドネシア語の代わりに表示することはありません。

### デフォルトロケールを選択する \{#select-the-default-locale\}

フローにユーザーの言語が含まれていない場合、ユーザーにはデフォルトロケールが表示されます。新しいフローは `en` のみのロケールとデフォルトとして開始されます。変更するには、[別のロケールをデフォルトとして設定](add-paywall-locale-in-adapty-paywall-builder#set-the-default-locale)してください。

デフォルトロケールについては、次の3つのルールに従ってください：

- 一致するロケールのないユーザーには、ほとんどのユーザーが理解できる言語を選択してください。通常、それはあなたのメイン市場の言語ではなく、英語です。
- デフォルトロケールは完全に翻訳してください。一致するロケールのないユーザーはフロー全体をデフォルトロケールで表示します。一致するロケールのあるユーザーはその言語でフローを表示します。翻訳されていない部分はデフォルトロケールで表示されます。
- 中国語のように2つの文字体系を持つ言語は選択しないでください。もう一方の文字体系のユーザーはデフォルトロケールを読めない場合があります。

## ローカライゼーション戦略を選択する \{#select-a-localization-strategy\}

ほとんどのアプリは `localizationStrategy` を指定しないため、SDK は `.auto` を使用します。この戦略では、フロー＆ペイウォールビルダーで作成したフローに対しては iOS の言語マッチングを適用し、旧ペイウォールビルダーで作成したペイウォールに対しては単一言語ルールを適用します。

単一言語ルールでは、SDKは`preferredLocales`の中で最も優先度の高い言語のみを読み込みます。フルコード、次に短いコード（`pt-br`、次に`pt`）の順に試し、一致しない場合はデフォルトのロケールを表示します。旧ペイウォールビルダーで作成したペイウォールは、再公開後もこのルールで引き続き動作します。SDKに`preferredLocales`のすべての言語を試させるには、[ペイウォールをFlow & Paywall Builderに移行](convert-paywall-to-flow)してください。その後、フロープレースメントから新しいフローを配信します。

SDKがユーザーの言語とフローのロケールをマッチングする方法を変更するには、`localizationStrategy` パラメータに以下のいずれかの値を渡してください：

- `.system`：すべてのフローでiOSの言語マッチングを使用します（旧ペイウォールビルダーのペイウォールも含む）。
- `.legacy`：すべてのフローでSDK 4.4の完全マッチングではなく、単一言語ルールを使用します。フロー＆ペイウォールビルダーのフローに`.legacy`を渡さないでください：`pt-BR`のようにリージョンやスクリプトが含まれるロケールと一致しません。
- `.custom(resolver:fallbackResolver:)`：[ローカライゼーションをコードで選択する](#pick-a-flows-localization-in-your-own-code)。

### 独自のコードでフローのローカリゼーションを選択する \{#pick-a-flows-localization-in-your-own-code\}

iOSの言語マッチングはすべてのスクリプトをカバーしているわけではありません。たとえば、デバイスがキリル文字のアゼルバイジャン語（`az-Cyrl`）をリストしていてもラテン文字でない場合、`az` を持つフローはデフォルトロケールで表示されます。代わりに `az` を表示したい場合、または独自のルールでローカリゼーションを選択したい場合は、`AdaptyUICustomLocalizationResolver` に準拠した型を作成します。そして、`localizationStrategy` パラメータの `.custom(resolver:)` 値に渡します。リゾルバーを含むファイルに `import AdaptyUIBuilder` を追加してください。

他のAdapty SDKは異なるルールで言語を照合するため、同じユーザーがiOSとAndroidで異なるフローのローカライズを見る場合があります。すべてのプラットフォームで同じローカライズを表示するには、他のプラットフォームのアプリと同じロケールコードを返すリゾルバーを作成してください。

リゾルバーには以下のルールが適用されます。

- ローカライズが1つのフローでは、SDKはリゾルバーを呼び出しません。そのローカライズでフローが表示されます。
- SDKは、アプリが渡したリストと、フローの`locales`および`defaultLocale`を持つ`AdaptyUILocalizationSource`を使って`resolve(for:from:)`を呼び出します。`locales`は順不同で渡されます。
- ローカライズを表示するには、`locales`または`defaultLocale`に含まれるコードを、大文字・小文字も含めて完全に一致する形で返します（例：`AR`ではなく`ar`）。
- リゾルバーが他のコードや`nil`を返した場合、SDKは`fallbackResolver`の戦略を使用します。`fallbackResolver`がない場合は`.auto`が使われます。
- SDKはメインスレッド以外からリゾルバーを呼び出す場合があります。
- ネットワークリクエストや重い処理を行わず、コードをすぐに返してください。SDKはタイムアウトなしでリゾルバーの返答を待つため、リゾルバーが返すまでフローは表示されません。

## Adaptyにおけるロケールコードの標準 \{#locale-code-standard-at-adapty\}

Adaptyのロケールコードは[BCP 47標準](https://en.wikipedia.org/wiki/IETF_language_tag)に従っています。言語サブタグの後に、任意のスクリプトまたは地域サブタグをハイフンで区切って続ける形式です。**Select languages**フィールドではコードが小文字で表示されます（例：`en`（英語）、`pt-br`（ポルトガル語、ブラジル）、`zh-hans`（簡体字中国語）、`zh-hant`（繁体字中国語））。

## カスタムペイウォールとオンボーディングのローカライズ \{#localize-custom-paywalls-and-onboardings\}

SDK 4.5 はフローのローカライズルールのみを変更します。カスタムペイウォールとオンボーディングは SDK 4.4 と同様に動作します。

### カスタムペイウォールのリモートコンフィグを言語で選択する \{#pick-a-custom-paywalls-remote-config-by-language\}

`getFlow` にはロケールパラメーターがありません。カスタムペイウォールの場合、`flow.remoteConfigs` にすべてのローカライズ設定が返されます。各エントリには `locale` コードとコンフィグの内容（`jsonString`、またはパース済みの `dictionary`）が含まれています。ユーザーに合ったエントリをフォールバックロジックとともに選択してください。

```swift showLineNumbers
do {
    let flow = try await Adapty.getFlow(placementId: "YOUR_PLACEMENT_ID")
    let config = flow.remoteConfigs.first(where: { $0.locale == "en" })
        ?? flow.remoteConfigs.first
    // read your values from config?.dictionary
} catch {
    // handle the error
}
```

Adapty は `locale` コードを [Adaptyのロケールコード標準](#locale-code-standard-at-adapty) で説明されている形式で保存しています。SDK はリモートコンフィグをロケールに対して自動的にマッチングしないため、どのエントリを適用するかはアプリ側で決定します。

### オンボーディングにロケールを渡す \{#pass-a-locale-to-an-onboarding\}

<OnboardingDeprecation />

`getOnboarding` は SDK 4.5 でも `locale` パラメータを保持しています。[`getOnboarding`](get-onboardings) に `locale` を渡すと、サーバーがローカライズを選択します：

1. ロケール文字列は小文字に変換され、すべてのアンダースコア（`_`）はハイフン（`-`）に置き換えられます
2. Adapty は完全に一致するロケールコードのローカライゼーションを検索します
3. 一致するものが見つからない場合、Adapty は最初のハイフンより前の部分文字列（`pt-br` の場合は `pt`）を取得し、一致するローカライゼーションを検索します
4. それでも一致するものが見つからない場合、Adapty はオンボーディングのデフォルトロケールのコンテンツを返します

このようにして、`pt_BR`、`pt-BR`、`pt-br` はすべて同じオンボーディングのローカライゼーションに解決されます。

## これが重要な理由 \{#why-this-is-important\}

ロケールコードが関係するシナリオはいくつかあります。たとえば、アプリの現在のローカライゼーションに合った正しいペイウォールを取得しようとする場合などです。

ロケールコードはプラットフォームによって異なり複雑なため、Adapty がサポートするすべてのプラットフォームで内部標準に依存しています。ただし、コードが複雑であるため、サーバーに送信している内容と、その後の処理を正確に把握しておくことが非常に重要です。そうすることで、常に期待通りの結果を受け取ることができます。

## Adapty でのロケールコード規格 \{#locale-code-standard-at-adapty\}

ロケールコードには、Adapty は [BCP 47 標準](https://en.wikipedia.org/wiki/IETF_language_tag) を少し改変したものを採用しています。各コードは小文字のサブタグをハイフンで区切って構成されます。例: `en`（英語）、`pt-br`（ポルトガル語（ブラジル））、`zh`（簡体字中国語）、`zh-hant`（繁体字中国語）。

## ロケールコードのマッチング \{#locale-code-matching\}

Adapty がクライアントサイド SDK からロケールコードを含む呼び出しを受け取り、対応するペイウォールのローカライズを検索する際、以下の処理が行われます：

1. 受け取ったロケール文字列を小文字に変換し、アンダースコア（`_`）をすべてハイフン（`-`）に置き換えます
2. 完全一致するロケールコードのローカライズを検索します
3. 一致するものが見つからない場合、最初のハイフンより前の部分文字列（`pt-br` なら `pt`）を取り出し、一致するローカライズを検索します
4. それでも一致するものが見つからない場合、ペイウォールのデフォルトロケールのコンテンツを返します

これにより、`'pt_BR'`を送信したiOSデバイス、`pt-BR`を送信したAndroidデバイス、`pt-br`を送信した別のデバイスは、すべて同じ結果を受け取ります。

## ローカライゼーションの実装：推奨方法 \{#implementing-localizations-recommended-way\}

ローカライゼーションについて検討しているなら、すでにプロジェクト内のローカライズされた文字列ファイルを扱っているでしょう。その場合、各ローカライゼーションに対応するファイルに、意図したAdaptyロケールコードをキーと値のペアとして配置することをお勧めします。そして、次のようにSDKを呼び出す際にそのキーの値を取得します：

```swift showLineNumbers
// 1. Modify your Localizable.strings files

/*
Localizable.strings - Spanish
*/
adapty_paywalls_locale = "es";
/*
Localizable.strings - Portuguese (Brazil)
*/
adapty_paywalls_locale = "pt-br";
// 2. Extract and use the locale code
let locale = NSLocalizedString("adapty_paywalls_locale", comment: "")
// pass locale code to AdaptyUI.getViewConfiguration or Adapty.getPaywall method
```

これにより、アプリのすべてのユーザーに対してどのローカライゼーションが取得されるかを完全にコントロールできます。

## ローカライゼーションの実装：別の方法 \{#implementing-localizations-the-other-way\}

ロケールコードをすべてのローカライゼーションに明示的に定義しなくても、類似した（ただし同一ではない）結果を得ることができます。その場合、プラットフォームが提供する他のオブジェクトからロケールコードを抽出することになります。例：

```swift showLineNumbers
let locale = Locale.current.identifier
// pass locale code to AdaptyUI.getViewConfiguration or Adapty.getPaywall method
```

いくつかの理由から、このアプローチは推奨しません：

1. iOSでは、優先言語と現在のロケールは同一ではありません。ローカライゼーションを正しく選択したい場合、Appleのロジックに依存するか（ローカライズされた文字列ファイルを使用する推奨アプローチでは自動的に機能します）、それを再現する必要があります。
2. Adaptyのサーバーが何を受け取るかを予測するのが難しいです。たとえばiOSでは、デバイスから`ar_OM@numbers='latn'`のようなロケールを取得してサーバーに送信することがあります。この場合、期待していた`ar-om`ローカライゼーションではなく、`ar`が返ってくる可能性があり、意図しない結果になることがあります。

Should you decide to use this approach anyway — make sure you've covered all the relevant use cases.
