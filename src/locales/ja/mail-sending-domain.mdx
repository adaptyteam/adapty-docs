Adapty Mail はキャンペーンを共有アドレスではなく独自ドメインから送信するため、送信者のレピュテーションを自分で管理できます。起動するには認証済みドメインが1つあれば十分で、プロジェクトには最大5つまで登録できます。

最小手順でドメインを認証するには、[Adapty Mail を始める](mail-get-started#4-set-up-your-sending-domain)ガイドを参照してください。この記事はセットアップ、認証、ウォームアップ、複数ドメインからの送信を含む完全なリファレンスです。

## 要件と制限 \{#requirements-and-limitations\}

- **ルートドメイン**: ルートドメインを入力してください。トップレベルドメインのサフィックスが必要です（`yourapp.com`）。Adapty Mail はサブドメイン（`app.yourapp.com`）や第2レベルのサフィックスを含むドメイン（`yourapp.co.uk`、`yourapp.com.br`）は受け付けません。
- **ASCII のみ**: Punycode および国際化ドメイン名はサポートされていません。
- **有効な NS レコード**: ドメインが解決できる必要があります。Adapty Mail はセットアップ時に DNS ルックアップを実行し、有効な NS レコードのないドメインは拒否します。
- **1 プロジェクトにつき 1 ドメイン**: ドメインを複数のプロジェクトで共有することはできません。自分のものか他者のものかを問わず、すでにいずれかのプロジェクトに登録されているドメインはセットアップが失敗します。
- **ブランドに合ったドメイン名**: ドメイン名はアプリとして認識できるものである必要があります。「Yourapp」というアプリに対して `yourapp.com` は問題ありませんが、無関係な `anotherapp.com` は通りません。Adapty は [ブランド](mail-brand) のアプリ名、説明、タグラインを参照します。ブランドが設定されていないプロジェクトはこのチェックをスキップします。
- **信頼性の高いドメイン**: [Blacklist Master](https://www.blacklistmaster.com/) でスパムブラックリストに掲載されていると報告されたドメインは、Adapty Mail が拒否します。
- **1 プロジェクトあたり最大 5 つの送信サブドメイン**: 同じルートドメインを 2 つ使用する場合も含め、各送信サブドメインはこの上限にカウントされます。それぞれが個別に検証とウォームアップを行います。
- **削除は元に戻せません**: 送信は即時停止され、ドメインの検証状況、DNS レコード、ウォームアップメールボックスはすべて削除されます。ドメインを再追加することは可能ですが、新しいレコードで最初から検証をやり直す必要があります。同じ送信サブドメインで再追加した場合、過去 30 日間のキャンペーンメールは引き続き[配信スコア](mail-domain-health)に反映され、1 日の送信上限も引き継がれます。自身の DNS レコードはそのまま残るため、手動で削除してください。

## 1. ドメインを追加する \{#1-add-the-domain\}

Adapty Mail で **Settings** > **DNS** を開き、**Email domains** セクションに移動します。

1. **Domain** フィールドに、ルートドメインを入力します（例：`yourapp.com`）。
2. **Sending subdomain** フィールドに、メール送信に使用するサブドメインを指定します。空のままにすると `mail` が使用されます。フィールド下のヒントにはホスト名のプレビューが表示されます：*Emails will be sent from mail.yourapp.com*。
3. **Link subdomain** フィールドに、メール内のリンクや画像に使用する*別のサブドメイン*を指定します。空のままにすると `go` が使用されます。こちらもホスト名が表示されます：*Links and images in emails will be served from go.yourapp.com*。
4. **Add domain** をクリックします。Adapty Mail が入力内容を検証し、ドメインをプロジェクトに追加して、そのドメインに必要なすべての DNS レコードをカードで表示します。

   <ZoomImage id="mail-email-domains.webp" width="500px" alt="ドメイン、送信サブドメイン、リンクサブドメインのフィールドを含むドメイン追加フォーム" />

5. 必要に応じて、[ドメインを追加する](#multiple-domains)と1日に送信できるメール数を増やせます。

### カスタムサブドメインを使用する \{#use-custom-subdomains\}

送信プレフィックスはすべての受信者が目にする送信元アドレスに表示され、リンクプレフィックスはクリックされるすべてのリンクに含まれます。多くのプロジェクトではデフォルト設定をそのまま使用しますが、独自の値を入力する場合、両フィールドとも同じルールに従います。

- 小文字、数字、ハイフンを使用し、先頭と末尾にハイフンを付けないこと。最大63文字。
- `www`、`smtp`、`admin`、`api`、`mx`、`dkim` は予約済みです。
- 不適切なラベルや有名ブランドを模倣するラベル（例：`paypal`）は拒否されます。`news`、`offers`、`hello` のような一般的なマーケティング用語は使用できます。
- リンクプレフィックスは、プロジェクト内の送信プレフィックスと一致させることはできません。
- 送信サブドメインごとに専用のリンクサブドメインが必要です。同じルートドメインの2つ目の送信サブドメインを追加する場合は、`go` 以外のリンクプレフィックスを入力してください。
- どちらも、ドメインを追加した後は変更できません。同じルートドメインの別のホストから送信するには、別の送信サブドメインを指定してドメインを再度追加してください。

## 2. DNSレコードを追加する \{#add-the-dns-records\}

カードに表示されているすべてのレコードを、そのままDNSに追加してください。一括で転送するには、**Export**をクリックして**CSV**、**GoDaddy zone file**、**Cloudflare zone file**、**Route 53 zone file**のいずれかを選択します。

:::warning
**Cloudflareでは、すべてのCNAMEをDNS onlyに設定する必要があります** — プロキシ設定のレコードはCloudflareのアドレスに解決され、認証が通りません。**Cloudflare zone file**でエクスポートすると、自動的にそのように設定されます。
:::

:::tip
[Adapty Mail MCPサーバー](mail-mcp)に接続されたAIアシスタントがこれらのレコードを読み取り、DNSプロバイダーでの公開手順を案内し、認証を再実行することができます。
:::

最初の3つのセクションは必須です — レコードが解決されるまでセットアップは完了しません。ルートドメインのDMARCレコードはオプションです。

| セクション | ホスト | 役割 |
| --- | --- | --- |
| **送信インフラ** | 送信サブドメイン | キャンペーンに署名し、バウンスを Adapty Mail にルーティングします |
| **ウォームアップメールボックス** | 送信サブドメイン | [ウォームアップ](#warm-up-and-daily-limits)中に送信者レピュテーションを構築するメールボックスを運用します |
| **メディア & リダイレクト** | リンクサブドメイン | メール内の画像とトラッキングリンクを独自ドメインから配信します |
| **DMARC ポリシー**（任意） | ルートドメイン | 認証に失敗したメールをどう扱うかを受信プロバイダーに伝えます |

ルートドメインにビジネスメール用の SPF レコードや DMARC レコードがすでに設定されている場合でも、そのまま変更不要です — 必要なレコードはすべてサブドメインに設定します。

<Details>
<summary>DNS レコードリファレンス</summary>

**DKIM — CNAME レコード 3 件。** メールが転送中に改ざんされていないことを証明する暗号署名です。

| フィールド | 形式                              |
| ----- | ----------------------------------- |
| Type  | CNAME                               |
| Name  | `{token}._domainkey.mail.yourapp.com` |
| Value | `{token}.dkim.amazonses.com`        |

**MAIL FROM — MX レコード 1 件。** バウンスを処理します。

| フィールド | フォーマット                                             |
| ---------- | -------------------------------------------------------- |
| Type       | MX                                                       |
| Name       | `hello.mail.yourapp.com`                                 |
| Priority   | `10`                                                     |
| Value      | `feedback-smtp.{region}.amazonses.com`                   |

**MAIL FROM — 1 TXT レコード。** Adapty があなたの代わりにメールを送信することを承認します。

| フィールド | フォーマット                                 |
| ---------- | -------------------------------------- |
| Type  | TXT                                    |
| Name  | `hello.mail.yourapp.com`               |
| Value | `"v=spf1 include:amazonses.com ~all"`  |

**DMARC — ルートドメインに 1 つの TXT レコード。** 任意ですが、推奨されます。

| フィールド | フォーマット                |
| ---------- | --------------------- |
| Type  | TXT                   |
| Name  | `_dmarc.yourapp.com`  |
| Value | `v=DMARC1; p=reject`  |

メールウォームアップメールボックスと `go.yourapp.com` レコードは同じ形式に従っており、名前と値はAdapty Mailが使用するメールおよびホスティングプロバイダーによって発行されます。トークン、リージョン、ホスト名、所有権の値はすべてセットアップ時に生成されます。これらはドメインカードまたはエクスポートからコピーしてください。このリファレンスからは絶対にコピーしないでください。

## 3. レコードを確認する \{#verify-the-records\}

<ZoomImage id="email-domains.webp" width="700px" alt="Expanded domain card showing DNS record groups and verification progress" />

 DNS の伝播には通常数分かかりますが、まれに最大 48 時間かかる場合があります。レコードの検証は、Adapty Mail が定期的に DNS をポーリングし、レコードが見つかるか 7 日間が経過するまで自動的に行われます。カードの **Check** をクリックするとオンデマンドで確認を実行できます（10 秒のクールダウンあり）。自動チェックが停止した場合は、再起動することもできます。

A レコードは、DNS に存在し、Adapty Mail から提供された値と一致し、プロバイダーによって確認された場合に検証済みとなります。未検証のレコードには、どの条件が満たされていないかを示すチップが表示されます:

| チップ | 意味 |
| --- | --- |
| **Missing** | DNSにレコードが存在しません。カードに表示された内容をそのまま追加してください。 |
| **Wrong value** | レコードは存在しますが、値が異なります。一致するように更新してください。 |
| **Differs from suggested** | ルートドメインにすでに別の値のDMARCレコードがあります。Adapty Mailの提案は必須ではありません。必要な場合のみ置き換えてください。 |
| **Provider check failed** | プロバイダーがレコードを拒否しました。値を確認してから **Check** をクリックしてください。 |
| **Awaiting provider** | DNSにレコードは正しく設定されていますが、プロバイダーがまだ確認していません。**Check** をクリックして更新してください。 |

Adapty Mail は、検証済みレコードの有効性を定期的にチェックする機能を持っていません。**Check** をクリックするか、**Settings** > **DNS** を開いて手動でチェックをトリガーしてください。

メールを送信する予定がある間は、レコードを削除しないでください。DKIM レコードが消えると、Amazon SES はグレース期間の後にメールへの署名を停止し、ドメインを最初から再検証する必要があります。

## 4. 送信者名と返信先アドレスを設定する \{#set-the-sender-name-and-reply-to-address\}

ドメインが認証されると、そのカードに **Email sender name** フィールドが表示されます。Adapty Mail はプロジェクト名をそこに自動入力し、送信サブドメインの `hello@` から送信します。そのため、フィールドのヒントには差出人の全表示（*Your Company &lt;hello@mail.yourapp.com&gt;*）が示されます。この名前はドメインごとに設定するもので、2 つのドメインから送信するプロジェクトには 2 つの設定が必要です。名前には `+`、`{`、`}` を含めることはできません。

受信者からの返信を受け取るには、同じドメインカードの **Reply-to address** フィールドにアドレスを入力し（例：`support@yourapp.com`）、**Save** をクリックします。`hello@` アドレスはドメインの[ウォームアップメールボックス](#warm-up-and-daily-limits)であり、誰も確認していないため、返信先アドレスが設定されていないメールへの返信は誰にも届きません。返信先アドレスはどのドメインでも使用でき、DNS レコードの設定は不要です。保存後に送信されるメールにのみ適用されます。送信者名と同様に、ドメインごとに設定します。

## ウォームアップとデイリー上限 \{#warm-up-and-daily-limits\}

Gmail や Yahoo などのメールプロバイダーに対して、新しいドメインにはまだ実績がありません。そのため、新規ドメインから一度に大量のメールを送信すると、スパムに分類されるリスクがあります。Adapty Mail は、同時並行で動作する2つの方法によって、すべてのドメインを自動的にウォームアップします。どちらも設定は不要です。

- **ウォームアップメールボックス**: DNS が確認されると、Adapty Mail は送信サブドメインにメールボックスを作成します。このメールボックスは、主要プロバイダーのテスト用メールボックスと通常の会話メールをやり取りします。この双方向のメールにより、プロバイダーはそのドメインが通常のメールを送信していることを認識し、ドメインの評判が構築されます。ドメインカードには、メールボックスが現在どのフェーズにあるかが表示されます。[**Warmup mailbox** レコード](#2-add-the-dns-records)が確認されるまで、ウォームアップは開始されません。
- **1 日の送信制限**: キャンペーンの送信量は、ウォームアップメールボックスとは別に、メールボックスプロバイダーのグループごとに 20 段階のティアで管理されます。この制限により、新しいドメインがスパムとしてフラグされるような送信量を超えないよう抑制され、送信するにつれて上限が引き上げられていきます。

### ティアの仕組み \{#how-tiers-work\}

ドメインのウォームアップは、メールボックスプロバイダーのグループ（**Google**、**Microsoft**、**Yahoo**、**iCloud**、**Other**）ごとに個別に行われます。各グループは**Tier 1**（1日100通）から始まるため、新しいドメインはGmailアドレスに1日100通、iCloudアドレスにさらに100通のメールを送信できます。各グループがカバーするメールボックスドメインを確認するには、[**Send tiers**カード](mail-domain-health#send-tiers-daily-email-caps)でグループ名にカーソルを合わせてください。

毎日、UTC 午前0時を少し過ぎた頃に、Adapty Mail は各グループのティアを見直します。このレビューでは、現在のティアに属している直近3日間のマーケティングメールとダブルオプトイン確認リクエストの開封率を読み取ります。新しいティアは、レビューの翌日全体に適用されます。

| グループ | 開封率がこの値以上でティアアップ | 開封率がこの値未満でティアダウン |
| --- | --- | --- |
| Google、Microsoft、Yahoo | 15% | 5% |
| iCloud | 40% | 20% |
| その他 | 使用しない | 使用しない |

グループがティアアップするには、上記に加えて以下の条件も必要です：

- **判断に十分なメール数**: 対象期間中にそのグループへ200通以上のメールが配信されていること。それ未満の場合、グループは現在のティアに留まります。
- **1日の上限に達していること**: レビューの前日に1日の送信上限に到達していること。送信済みと保留済みの両方がカウントされ、各メールは1回のみ計上されます。

**Other** グループは1日の上限のみで昇格し、降格はありません。2つの開封率の間にある場合、どれだけ日数が経過してもグループは現在のティアに留まります。1ティア降格の場合、当日の開封数がまだ集計中のため、レビューでは最新の1日分が除外されます。

Google、Yahoo、iCloud では、3日間のオープン率に反映される前に開封数の低下を検知できるよう、直近の1日と直前の3日間を比較するレビューも行われます。どちらのオープン率も、メールが配信された当日に届いた開封のみをカウントします。

- **3日間レートの80%未満**: グループは現在のティアを維持します。
- **3日間レートの50%未満**: グループは一度に2ティア降格するか、ティア2からティア1に降格します。

このレビューによる比較は、各側に少なくとも200件の配信済みメールがあり、かつ直前の3日間が上位ティアに移動するためのオープン率を達成していた場合にのみ行われます。

1日の許容量は時間帯にわたって分散されます。1時間あたり、グループは1日の上限のおよそ16分の1を送信し、ある時間帯に保留されたメールは後の時間帯に送信されます。トランザクションメールは上限の2倍まで使用でき、フローの最初のメールとダブルオプトイン確認リクエストは20%多く送信できるため、上限が不足しているときは他のメールよりも先に送信される余裕があります。これらの最初のメールと確認リクエストを合わせて上限の最大60%を使用するため、各フローの後続メールにも余裕が残ります。最上位ティアを超えると、グループに1日の上限はありません。

| ---- | ----------- |
| 1    | 100         |
| 2    | 200         |
| 3    | 300         |
| 4    | 500         |
| 5    | 750         |
| 6    | 1,000       |
| 7    | 1,500       |
| 8    | 2,500       |
| 9    | 3,500       |
| 10   | 5,000       |
| 11   | 7,000       |
| 12   | 9,000       |
| 13   | 12,000      |

### オーディエンスサイズが配信開始に与える影響 \{#impact-on-launch-by-audience-size\}

| オーディエンスサイズ | 配信開始時の効果                         |
| -------------------- | ---------------------------------------- |
| 100人未満            | 1日目にオーディエンス全員に配信される    |
| 100〜2,000人         | 配信が数日間にわたって分散される         |
| 2,000人以上          | 配信が1〜2週間にわたって分散される       |

:::tip
DNS認証が完了したらすぐに最初のキャンペーンを開始しましょう。送信を早く始めるほど、ドメインのティアが早く上がり、1日あたりの最大配信数に早く到達できます。
:::

## 配信到達性 \{#deliverability\}

:::link
メイン記事：[ドメインの健全性を監視する](mail-domain-health)
:::

**Settings** > **DNS** の各ドメインには、100点満点の**配信到達性スコア**が表示されます。**Details** をクリックすると詳細を確認できます — セットアップはドメインが設定されているかどうかを示しますが、これはメールが実際に届いているかどうかを示します。

スコアは、ハードバウンス率、苦情率、ウォームアップメールボックスの受信トレイ到達率という3つのシグナルを組み合わせたものです。ハードバウンス率は2%で警告、5%で危険とみなされます。苦情はバウンスよりもはるかに重く扱われます。送信数の0.1%で警告、0.5%で危険です。苦情が1件届くと、その受信者は直ちに[配信停止](mail-suppression#delivery-failed-or-the-recipient-marked-it-as-spam)されます。

## 複数のドメイン \{#multiple-domains\}

ドメインのウォームアップが完了するまで、Adaptyは各ドメインが1日に送信できるメール数を[制限](#warm-up-and-daily-limits)します。そのため、複数のドメインを使用することで、メール送信容量を増やすことができます。

Adaptyがどのドメインからメールを送信するかは、以下のロジックに従って決定されます。

- **1つのキャンペーンにつき、受信者1人に対してドメインは1つ**: キャンペーンの一貫性を保つため、Adapty Mail は同じ受信者には常に同じメールアドレスからメールを送信します。そのドメインを削除するか送信を停止した場合、Adapty Mail は次のメールを開封率に基づいて選ばれた別のドメインから送信します。
- **開封率の高いドメインを優先**: メールごとに、Adapty Mail は前日の受信者のメールボックスプロバイダーグループにおける各ドメインの開封率を比較します。最高開封率の80%以上を達成しているドメインがメール送信を分担し、1日の送信上限に余裕があるドメインほど多くのメールを担当します。それ以外のドメインは、自分より上位のすべてのドメインが上限を超えた場合にのみメールを送信します。
- **新しいドメインにも配分あり**: そのグループへの配信数がその日200通未満のドメインは、ウォームアップできるよう最高開封率ドメインの扱いとなります。**Other** グループについては、すべてのドメインが1日の送信上限の残量に応じてメールを分担します。

すべてのドメインが受信者のメールボックスプロバイダーに対するリミットを超えた場合、Adapty Mail はメールの送信を遅延させます — その後の受信者側の挙動については [スロットル](mail-suppression#throttle-temporary-delays-and-cancellations) をご覧ください。

## 送信の停止と再開 \{#stop-and-resume-sending\}

ドメインを再認証せずに一時停止するには、そのカードの **Stop sending** をクリックします。カードに **Sending off** と表示され、Adapty Mail は送信先を選ぶ際にそのドメインをスキップします。**Resume sending** をクリックすると元に戻ります。

## トラブルシューティング \{#troubleshooting\}

| 問題                                                                          | 解決策                                                                                                                  |
| ------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------- |
| "Enter a valid domain (e.g. example.com)" | 入力内容を確認してください。トップレベルサフィックス付きのルートドメイン（`yourapp.com`）、ASCIIのみ、先頭および末尾にハイフンなし。`yourapp.co.uk` のようなセカンドレベルサフィックスは拒否されます。 |
| "Domain does not have valid DNS records" | ルートドメイン自体が解決できる必要があります。再試行前にNSレコードが有効であることを確認してください。 |
| "Domain is already registered to another project"                              | 別のドメインを選択するか、登録が誤りだと思われる場合はサポートにお問い合わせください。                                  |
| "This subdomain cannot be used" | そのラベルは予約済みか、スクリーニングで拒否されました。別のものを選択してください — [カスタムサブドメインを使用する](#use-custom-subdomains)を参照。 |
| "This link subdomain cannot be used" | リンクサブドメインは送信サブドメインと同じルールに従います。プロジェクト内の送信サブドメインや、他の送信サブドメインがすでに使用しているリンクサブドメインと一致することはできません — [カスタムサブドメインを使用する](#use-custom-subdomains)を参照。 |
| "Please wait before checking again"                                            | 手動確認の間隔は10秒空けてください。バックグラウンドでは自動ポーリングが継続されます。                                      |
| レコードが未確認のまま                                                        | 末尾のドット、正しいCNAMEターゲット、レコードごとの値が1つであるかなど、完全に一致していることを確認してください。DNSの伝播には最大48時間かかる場合があります。 |
| CloudflareでCNAMEが未確認のまま                                           | レコードが **Proxied** になっています。各レコードを **DNS only** に切り替えてから **Check** をクリックしてください。                                        |
| ウォームアップが開始されない                                                         | ウォームアップメールボックスのMX、DKIM、SPFレコードがまだ確認されていません。追加または修正してから **Check** をクリックしてください。             |
| リンクサブドメインのレコードが確認できない | カードにホスト下の理由が表示されます。CNAMEとTXTレコードを確認してから **Check** をクリックしてください — このホストが有効になるまでドメインは完全にセットアップされません。 |
| "Cannot delete: some identities are verified"                                  | このドメインは自動ウォームアップ前にセットアップされており、ダッシュボードから削除できません。サポートにお問い合わせください。                    |
| メールがスパムに入る                                                           | DMARCレコードが公開されていることを確認してください。新しいドメインはウォームアップ期間が必要です — [ウォームアップと日次制限](#warm-up-and-daily-limits)を確認してください。主要プロバイダーでウォームアップメールボックスからのメールがどのフォルダーに届くかを確認するには、配信可能性ページの [**Inbox placement** カード](mail-domain-health#inbox-placement)をご覧ください。 |
| 受信者からの返信が届かない | 返信先アドレスが設定されていない場合、返信は誰も読まない `hello@` メールボックスに届きます。ドメインカードで[返信先アドレスを設定](#4-set-the-sender-name-and-reply-to-address)してください。設定前に送信されたメールには古いアドレスが使用されます。 |
| 高いバウンス率 | オーディエンスリストに有効なオプトイン済みのアドレスのみが含まれていることを確認してください。[メールが停止する理由](mail-suppression)では、バウンスしたアドレスに何が起きるかを説明しています。最もバウンスが多い理由を確認するには、配信可能性ページの [**Bounces** カード](mail-domain-health#bounces)をご確認ください。 |
| 高いクレーム率 | スパム報告を送信数の0.1%未満に抑えてください。クレームはバウンスよりもはるかに重く、受信者は即座に抑制されます。過去30日間のクレーム率を確認するには、[配信可能性ページ](mail-domain-health#deliverability-score)を開いてください。 |
