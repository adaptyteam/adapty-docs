<SDKv4>

各ユーザーが読める言語でフローを表示するには、Adapty Android SDK 4.5以降にユーザーの言語を渡してください。ユーザーはフローが対応している言語の中で、最も優先度の高い言語でフローを表示します。該当する言語がフローにない場合は、デフォルトのロケールで表示されます。

SDK 4.0〜4.4では、アプリは1つのロケールコードを`getFlowConfiguration`に渡し、SDKは[完全一致](#pass-the-users-languages-to-the-sdk)でマッチングします。コードを更新するには、[Adapty Android SDK v4.5への移行](migration-to-android-sdk-45)をご覧ください。

SDK 4.5以降では、3つのケースが異なるルールに従います：

- 独自のコードでフローのローカライゼーションを選択するアプリは、[カスタムリゾルバーを使用](#pick-a-flows-localization-in-your-own-code)します。
- 旧ペイウォールビルダーのペイウォールは、[最優先でユーザーの言語に一致する](#select-a-localization-strategy)のみです。
- カスタムペイウォールとオンボーディングは、[SDK 4.4 と同様に動作](#localize-custom-paywalls-and-onboardings)します。

## ユーザーの言語をSDKに渡す \{#pass-the-users-languages-to-the-sdk\}

<Tabs groupId="android-sdk-version" queryString>
<TabItem value="4.5" label="SDK 4.5 or later" default>

[`AdaptyUI.getFlowConfiguration`](android-get-pb-paywalls#fetch-the-view-configuration) には `preferredLocales` パラメーターが必要です。ユーザーの言語を優先度の高い順に渡してください。デバイスの言語やアプリ内のピッカーで選択した言語など、どの言語を渡すかはアプリ側で決定します。

<Tabs groupId="current-os" queryString>
<TabItem value="kotlin" label="Kotlin" default>

```kotlin showLineNumbers
val preferredLocales = LocaleListCompat.getAdjustedDefault().toLanguageTags().split(",")

AdaptyUI.getFlowConfiguration(flow, preferredLocales) { result ->
    // handle the result
}
```

</TabItem>
<TabItem value="java" label="Java">

```java showLineNumbers
List<String> preferredLocales =
    Arrays.asList(LocaleListCompat.getAdjustedDefault().toLanguageTags().split(","));

AdaptyUI.getFlowConfiguration(flow, preferredLocales, result -> {
    // handle the result
});
```

</TabItem>
</Tabs>

ユーザーに表示されるローカライズは、次の3つのルールによって決まります：

- SDKはユーザーの言語を順番に試し、フローが持つ最初の一致を選択します。これはAndroidリソースマッチングです。つまり、Androidがアプリの翻訳を選択するために使用するルールです。SDKは言語の近いバリアントもマッチングします：`de-AT`は`de`にマッチし、`zh-TW`は`zh-hant`にマッチします。Android 6以前では、SDKはユーザーの言語とスクリプトに一致するフローの最初のローカライズを、リージョンに関わらず選択します。旧ペイウォールビルダーのペイウォールは、最優先のユーザー言語のみを使用します。
- 大文字・小文字や区切り文字は関係ありません：`pt_BR`、`pt-BR`、`pt-br`はすべて同じロケールにマッチします。Androidが返す値をそのまま渡してください。
- 空のリスト、またはフローのどのロケールにもマッチしないリストの場合、SDKはデフォルトのロケールを使用します。

3つのリストのいずれかを渡します。このリストはSDKが言語を試みる順序を設定しますが、フローに存在しない言語を追加することはできません。

| 値 | フローが表示される言語 | トレードオフ |
|---|---|---|
| `LocaleListCompat.getAdjustedDefault()` | Androidの設定またはアプリ内でユーザーが選択した言語。選択がない場合は、フローが対応している最初のデバイス言語 | Android 13未満では、`AppCompatDelegate.setApplicationLocales`でアプリが設定した言語は、最初の`AppCompatActivity`が作成された後にのみ適用されます。`Application.onCreate`ではなく、その後にリストを読み取ってください。 |
| `LocaleManagerCompat.getSystemLocales(context)` | ユーザーがアプリ用に別の言語を選択していても、フローが対応している最初のデバイス言語 | フローがアプリのUIとは異なる言語で表示される可能性があります |
| `selectedLanguage`、次に`LocaleListCompat.getAdjustedDefault()` | アプリ内の言語ピッカーで選択した言語、次にデバイスの言語 | — |

リストを渡すには、ロケールコードに変換します：

```kotlin showLineNumbers
// The language selected for your app, then the device languages
val appLocales = LocaleListCompat.getAdjustedDefault().toLanguageTags().split(",")

// The device languages
val deviceLocales = LocaleManagerCompat.getSystemLocales(context).toLanguageTags().split(",")

// The language from the language picker in your app, then the other languages
val pickerLocales = listOf(selectedLanguage) + appLocales
```

最初の2つのリストは、ユーザーがアプリの言語を選択した場合に異なる結果を返します。たとえば、デバイスの言語が英語に設定されている状態で、ユーザーがアプリの言語としてスペイン語を選択した場合、`getAdjustedDefault()` ではスペイン語が、`getSystemLocales()` では英語が表示されます。

`AppCompatDelegate.setApplicationLocales` を使って言語を保存する言語ピッカーを使用している場合、3番目のリストは不要です。このようなピッカーでは、最初のリストの先頭が選択した言語になります。

:::tip
`Locale.getDefault().toLanguageTag()` 単独では渡さないでください。これは1つの言語しか含まないため、SDKが代替言語を試す手段がなくなります。
:::

ほとんどのアプリでは `localizationStrategy` を渡しません。指定しない場合、SDK は [`AdaptyUiLocalizationStrategy.Auto`](#select-a-localization-strategy) を使用します。これは Flow & ペイウォールビルダーのフローや旧ペイウォールビルダーのペイウォールに適しています。

</TabItem>
<TabItem value="4.4" label="SDK 4.0–4.4">

[`AdaptyUI.getFlowConfiguration`](android-get-pb-paywalls#fetch-the-view-configuration) の `locale` パラメータにロケールコードを1つ渡します。デバイスのロケールやアプリ内の言語選択画面で選ばれた言語など、どのコードを渡すかはアプリ側で決定します。

```kotlin showLineNumbers
AdaptyUI.getFlowConfiguration(flow, locale = "pt-BR") { result ->
    // handle the result
}
```

マッチングは完全一致です。SDKは渡されたコードとフローのローカライゼーションコードを1文字ずつ比較します。大文字・小文字の変換、アンダースコア（`_`）とハイフン（`-`）の置き換え、言語サブタグへのフォールバックはいずれも行いません。`pt-BR` ローカライゼーションを持つフローに対して一致するのは `pt-BR` のみで、`pt-br`、`pt_BR`、`pt-PT` はいずれもマッチしません。

コードがどのローカライズにも一致しない場合、フローは[デフォルトロケール](add-paywall-locale-in-adapty-paywall-builder#set-the-default-locale)で静かにレンダリングされます — SDK はエラーを返さず、警告もログに出力しません。

ロケールコードを省略することは、フローのデフォルトローカライズを要求することとは異なります。SDK は固定値の `en` を代用します。デフォルトロケールが `de` のフローでも、`en` のローカライズがあれば `en` でレンダリングされ、`en` がない場合にのみ `de` にフォールバックします。これは Android SDK 4.0.1 以降に適用されます — 4.0.0 ではコードを省略するとフローのデフォルトローカライズでレンダリングされます。

:::warning
公開済みフローに設定されているロケールコードを正確に渡してください：**Select languages** フィールドには `pt-BR` のように記述し、`pt-br` のように小文字で渡さないでください。旧ペイウォールビルダーのペイウォールでは、`pt-br` のように小文字のコードを渡してください。
:::

システムのロケール識別子をそのまま渡さないでください。ポルトガル語（ブラジル）に設定されたデバイスでは、`Locale.getDefault().toString()` が `pt_BR` を返しますが、これはどのローカライズとも一致しません。英語（米国）に設定されたデバイスでは、`Locale.getDefault().toLanguageTag()` が `en-US` を返しますが、`en` のみのフローは見つかりません。システムのロケール識別子を渡す前に、フローが持つコードに変換してください。
:::

</TabItem>
</Tabs>

## ユーザーに表示されるローカライズのテスト \{#test-which-localization-a-user-sees\}

<Tabs groupId="android-sdk-version" queryString>
<TabItem value="4.5" label="SDK 4.5 or later" default>

フローにユーザーの言語が1つも含まれていない場合、SDKはエラーを発生させずにデフォルトのロケールを使用します。ユーザーに表示されるローカライズを確認するには、デバイスでフローをテストしてください：

1. [ログレベル](sdk-installation-android#logging)を`AdaptyLogLevel.VERBOSE`に設定します。
2. デバイスの設定で、テストしたい言語を言語リストの先頭に移動します。
3. アプリでフローを開きます。
4. Logcatで`getFlowConfiguration: preferredLocales`を含む行を見つけます。その行の末尾には、`strategy = Auto -> pt-BR`のように表示されているローカライズのコードが記載されています。ダッシュボードでは、このコードは小文字で表示されます（例：`pt-BR`に対して`pt-br`）。

デバイスの設定を変更せずに言語をテストするには、デバッグビルドで`listOf("pt-PT")`のような固定の`preferredLocales`リストを渡してください。

</TabItem>
<TabItem value="4.4" label="SDK 4.0–4.4">

渡したコードがフローのどのローカライズとも一致しない場合、SDKはエラーや警告を出力せずにデフォルトロケールを使用します。ユーザーがどのローカライズを見ているかを確認するには、デバイスでフローをテストしてください：

1. デバイスの設定で、テスト用の言語と地域を選択します。
2. アプリでフローを開きます。
3. デバイス上のフローと、Flow & Paywall Builderのローカライズを比較します。フローがデフォルトロケールを表示している場合、渡したコードと完全に一致するローカライズがフローに存在しないことを意味します。

デバイス設定を変更せずにコードをテストするには、デバッグビルドで `"pt-BR"` のような固定の `locale` を渡します。

</TabItem>
</Tabs>

フローの一部がデフォルトのロケールで表示される場合、その部分の翻訳がローカライゼーションに含まれていません。不足部分を補うには、Flow & Paywall Builder で[不足している行を翻訳](add-paywall-locale-in-adapty-paywall-builder#manage-localizations-and-translations)してください。

## フローに追加するロケールの選択 \{#select-which-locales-to-add-to-a-flow\}

ユーザーの大半をカバーするために最小限のロケールを追加するには、**Select languages** フィールドで[ロケールを追加する](add-paywall-locale-in-adapty-paywall-builder#add-and-set-up-a-locale)際に次の3つのルールに従ってください。

- 地域なしで言語を追加します。例えば、`de` はドイツ、オーストリア、スイスのドイツ語話者をカバーします。
- 同じ言語の2つ目の翻訳がある場合にのみ、地域ロケールを追加します。例えば、`fr` に加えて `fr-ca` を追加するなどです。
- ユーザーが読むすべての言語を追加します。SDK はカタロニア語をスペイン語に対応させるといった、言語間のマッチングを行いません。カタロニア語話者には、フローが持つ次の優先言語か、デフォルトのロケールが表示されます。

:::important
このルールは Android または iOS SDK 4.5 以降が必要です。Adapty SDK 4.0〜4.4 を使用しているアプリはロケールコードを1つだけ渡します。そのため、これらのユーザーは SDK 4.5 のユーザーとは異なるローカリゼーションの同じフローを表示する場合があります。これらのアプリが渡す既存のコード（`zh` や `pt-br` など）はすべて保持してください。
:::

### 中国語、スペイン語、ポルトガル語のコードを選択する \{#select-codes-for-chinese-spanish-and-portuguese\}

**Select languages** フィールドには、中国語、スペイン語、ポルトガル語に対して複数のコードが用意されています。以下のテーブルからコードを追加してください。

| 言語 | 追加 | ユーザーに表示される内容 |
|---|---|---|
| 中国語 | 新たに `zh` を追加するのではなく、`zh-hans` と `zh-hant` を追加してください。香港向けの別翻訳が必要な場合のみ `zh-hk` を追加してください。 | 中国とシンガポールでは `zh-hans`、台湾・香港・マカオでは `zh-hant` が表示されます。 |
| 広東語 | `yue`（常に `zh-hant` と併用） | 広東語に設定されたデバイスでは `yue` が、繁体字中国語に設定されたデバイスでは `zh-hant` が表示されます。広東語に設定されたデバイスに `zh-hant` は表示されず、繁体字中国語に設定されたデバイスに `yue` は表示されません。 |
| スペイン語 | 新たに `es-mx` を追加するのではなく、`es` と `es-419` を追加してください。 | スペインでは `es`、ラテンアメリカおよびアメリカ合衆国では `es-419` が表示されます。 |
| ポルトガル語 | ブラジルポルトガル語には `pt-br`、ヨーロッパポルトガル語には `pt` を追加してください。 | ブラジルでは `pt-br`、ポルトガルでは `pt` が表示されます。 |

フローに `es-ar` や `es-co` のような同一言語の地域バリアントが複数ある場合は、`es-419` も追加してください。これにより、メキシコなどの他のラテンアメリカ諸国のユーザーには `es-419` が表示されます。

### 推奨ロケールセットから始める \{#start-from-a-recommended-set-of-locales\}

翻訳を段階的に進めるには、3つのセットのいずれかから始めてください。各セットは前のセットを含んでいます。

| セット | ロケール | 合計 |
|---|---|---|
| 最小 | `en`, `es`, `pt-br`, `fr`, `de`, `it`, `ru`, `ja`, `ko`, `zh-hans`, `zh-hant` | 11 |
| 拡張 | 最小セットに加え `tr`, `pl`, `nl`, `sv`, `da`, `no`, `fi`, `uk`, `ar`, `he`, `hi`, `id`, `th`, `vi`, `es-419`, `pt` | 27 |
| 広範 | 拡張セットに加え `cs`, `sk`, `hu`, `ro`, `el`, `bg`, `hr`, `sl`, `lt`, `lv`, `et`, `ca`, `kk`, `ms`, `fil`, `fa`, `ur`, `bn`, `ta`, `te`, `mr`, `fr-ca` | 49 |

これらのセットでは、ユーザーに以下のロケールが表示されます：

- 最小セットでは、`es` がすべての国のスペイン語話者をカバーし、`pt-br` がポルトガルのポルトガル語話者もカバーします。
- 拡張セットでは、`es-419` と `pt` が2番目の翻訳です。これらにより、`es` はスペインに対応し、`pt` はポルトガルに対応します。`pt` はヨーロッパ・ポルトガル語に翻訳してください。
- カタルーニャ語とマレー語の話者は、それぞれのロケール（`ca` または `ms`）でのみ言語を確認できます。SDKはスペイン語やインドネシア語の代わりに表示することはありません。

### デフォルトロケールの選択 \{#select-the-default-locale\}

フローにユーザーの言語が含まれていない場合、ユーザーにはデフォルトロケールが表示されます。新しいフローは `en` を唯一のロケールおよびデフォルトとして開始します。変更するには、[別のロケールをデフォルトとして設定](add-paywall-locale-in-adapty-paywall-builder#set-the-default-locale)してください。

デフォルトロケールには次の3つのルールに従ってください：

- 一致するロケールがないユーザーに対しては、多くのユーザーが理解できる言語を選択してください。通常は、メインマーケットの言語ではなく英語が適切です。
- デフォルトのロケールは完全に翻訳してください。一致するロケールがないユーザーは、フロー全体をデフォルトのロケールで表示します。一致するロケールがあるユーザーは、自分の言語でフローを表示します。未翻訳の部分はデフォルトのロケールで表示されます。
- 中国語のように2種類の文字体系を持つ言語は選択しないでください。もう一方の文字体系のユーザーはデフォルトのロケールを読めない可能性があります。

## ローカリゼーション戦略を選択する \{#select-a-localization-strategy\}

ほとんどのアプリは `localizationStrategy` を指定しないため、SDK は `AdaptyUiLocalizationStrategy.Auto` を使用します。この戦略は、Flow & Paywall Builder のフローには Android のリソースマッチングを適用し、旧ペイウォールビルダーのペイウォールには単一言語ルールを適用します。

`preferredLocales` の単一言語ルールでは、SDKは最も優先度の高い言語のみを読み取ります。フルコード、次に短いコード（`pt-br`、次に`pt`）の順に試し、一致しない場合はデフォルトのロケールを表示します。旧ペイウォールビルダーのペイウォールは、再公開後もこのルールで引き続き動作します。SDKが`preferredLocales`のすべての言語を試すようにするには、[ペイウォールをFlow & Paywall Builderに移行](convert-paywall-to-flow)してください。その後、フロープレースメントから新しいフローを配信します。

SDKがユーザーの言語とフローのロケールをどのように照合するかを変更するには、`localizationStrategy` パラメータに次のいずれかの値を渡します。

- `AdaptyUiLocalizationStrategy.System`: すべてのフローがAndroidリソースマッチングを使用し、旧ペイウォールビルダーのペイウォールも含まれます。
- `AdaptyUiLocalizationStrategy.Legacy`: すべてのフローが単一言語ルールを使用し、SDK 4.4の完全マッチングは行われません。フロー＆ペイウォールビルダーのフローに`Legacy`を渡さないでください。`pt-BR`のようなリージョンやスクリプトを含むロケールが正しく処理されません。
- `AdaptyUiLocalizationStrategy.Custom(resolver, fallbackResolver)`: [ローカライズをコードで選択する](#pick-a-flows-localization-in-your-own-code)。

### 独自のコードでフローのローカライゼーションを選択する \{#pick-a-flows-localization-in-your-own-code\}

Android のリソースマッチングはすべてのスクリプトに対応しているわけではありません。たとえば、デバイスがキリル文字のアゼルバイジャン語（`az-Cyrl`）を設定しているが、ラテン文字のアゼルバイジャン語が設定されていない場合、`az` を持つフローはデフォルトロケールで表示されます。代わりに `az` を表示したい場合や、独自のルールでローカライゼーションを選択したい場合は、`AdaptyUiCustomLocalizationResolver` を実装してください。その後、`localizationStrategy` パラメーターの `AdaptyUiLocalizationStrategy.Custom` に渡します。

他のAdapty SDKは異なるルールで言語を照合するため、同じユーザーがAndroidとiOSで異なるフローのローカライズを見る可能性があります。すべてのプラットフォームで同じローカライズを表示するには、他のプラットフォームのアプリと同じロケールコードを返すリゾルバーを作成してください。

リゾルバーには以下のルールが適用されます。

- SDKは、ローカライゼーションが1つのフローに対してリゾルバーを呼び出しません。フローはそのローカライゼーションで表示されます。
- SDKは、アプリが渡したリスト、フローの`locales`と`defaultLocale`を持つ`AdaptyUiLocalizationSource`、および`callback`を引数に`resolve`を呼び出します。`locales`はフローのローカライゼーションの順序で渡されます。
- ローカライゼーションを表示するには、`locales`または`defaultLocale`のコードを`callback`に渡します。スペルは大文字・小文字を含めて完全に一致させてください（例：`AR`ではなく`ar`）。
- `callback`がそれ以外のコードや`null`を受け取った場合、SDKは`fallbackResolver`のリゾルバーを使用します。`fallbackResolver`がない場合、SDKは`AdaptyUiLocalizationResolver.Auto`を使用します。
- SDKはメインスレッドで`resolve`を呼び出します。`callback`はどのスレッドからでも1回だけ呼び出してください。
- `callback`はすぐに呼び出してください。ネットワークリクエストやその他の重い処理は行わないでください。SDKはタイムアウトなしで`callback`を待ち続けるため、あなたのコードが`callback`を呼び出すまでフローは表示されません。

## Adaptyにおけるロケールコードの標準 \{#locale-code-standard-at-adapty\}

Adaptyのロケールコードは[BCP 47標準](https://en.wikipedia.org/wiki/IETF_language_tag)に従っています。言語サブタグの後にオプションのスクリプトまたは地域サブタグをハイフンで区切ります。**Select languages**フィールドには小文字でコードが表示されます：`en`（英語）、`pt-br`（ポルトガル語、ブラジル）、`zh-hans`（簡体字中国語）、`zh-hant`（繁体字中国語）。

## カスタムペイウォールとオンボーディングのローカライズ \{#localize-custom-paywalls-and-onboardings\}

SDK 4.5 はフローのローカライズルールのみを変更します。カスタムペイウォールとオンボーディングは SDK 4.4 と同様に動作します。

### カスタムペイウォールのリモートコンフィグを言語で選択する \{#pick-a-custom-paywalls-remote-config-by-language\}

`getFlow` にはロケールパラメーターがありません。カスタムペイウォールの場合、`flow.remoteConfigs` に設定済みのすべてのローカライゼーションが返されます。各エントリには `locale` コードとコンフィグの内容（`jsonString`、またはパース済みの `dataMap`）が含まれます。ユーザーに合ったエントリを選び、独自のフォールバックを実装してください：

```kotlin showLineNumbers
Adapty.getFlow("YOUR_PLACEMENT_ID") { result ->
    when (result) {
        is AdaptyResult.Success -> {
            val flow = result.value
            val config = flow.remoteConfigs.firstOrNull { it.locale == "en" }
                ?: flow.remoteConfigs.firstOrNull()
            // read your values from config?.dataMap
        }
        is AdaptyResult.Error -> {
            // handle the error
        }
    }
}
```

Adaptyは、[AdaptyでのロケールコードのStandard](#locale-code-standard-at-adapty)に記載されている形式で`locale`コードを保存します。SDKはリモートコンフィグをロケールと照合しないため、どのエントリを適用するかはアプリ側で決定します。

### オンボーディングにロケールを渡す \{#pass-a-locale-to-an-onboarding\}

<OnboardingDeprecation />

SDK 4.5 では、`getOnboarding` の `locale` パラメータが引き続き利用できます。[`getOnboarding`](android-get-onboardings) に `locale` を渡すと、サーバーがローカライズを選択します。

1. ロケール文字列は小文字に変換され、アンダースコア（`_`）はハイフン（`-`）に置き換えられます
2. Adapty は完全に一致するロケールコードのローカライゼーションを検索します
3. 一致するものが見つからない場合、Adapty は最初のハイフンより前の部分文字列（`pt-br` の場合は `pt`）を取得し、一致するローカライゼーションを検索します
4. それでも一致するものが見つからない場合、Adapty はオンボーディングのデフォルトロケールのコンテンツを返します

これにより、`pt_BR`、`pt-BR`、`pt-br` はすべて同じオンボーディングのローカライゼーションに解決されます。

## これが重要な理由 \{#why-this-is-important\}

ロケールコードが関係するシナリオはいくつかあります。たとえば、アプリの現在のローカライゼーションに合った正しいペイウォールを取得しようとする場合などです。

ロケールコードはプラットフォームによって異なり複雑なため、Adapty がサポートするすべてのプラットフォームで統一した内部標準を採用しています。ただし、コードが複雑であるがゆえに、サーバーに何を送信して正しいローカライゼーションを取得しているのか、その後どのような処理が行われるのかをしっかり理解しておくことが大切です。そうすることで、常に期待通りの結果を受け取ることができます。

## Adapty でのロケールコード標準 \{#locale-code-standard-at-adapty\}

ロケールコードには、Adapty は [BCP 47 標準](https://en.wikipedia.org/wiki/IETF_language_tag) をわずかに修正したものを使用しています。各コードは小文字のサブタグをハイフンで区切って構成されます。例: `en`（英語）、`pt-br`（ポルトガル語（ブラジル））、`zh`（簡体字中国語）、`zh-hant`（繁体字中国語）。

## ロケールコードのマッチング \{#locale-code-matching\}

Adapty がクライアントサイド SDK からロケールコードを受け取り、ペイウォールの対応するローカライズを検索する際、以下の処理が行われます。

1. 受信したロケール文字列が小文字に変換され、アンダースコア（`_`）がすべてハイフン（`-`）に置き換えられます
2. 完全に一致するロケールコードのローカライズを検索します
3. 一致するものが見つからない場合、最初のハイフンより前の部分文字列（`pt-br` の場合は `pt`）を取り出して、一致するローカライズを検索します
4. それでも一致するものが見つからない場合、ペイウォールのデフォルトロケールのコンテンツを返します

これにより、`'pt_BR'` を送信した iOS デバイス、`pt-BR` を送信した Android デバイス、`pt-br` を送信した別のデバイスはすべて同じ結果を受け取ります。

## ローカライゼーションの実装：推奨方法 \{#implementing-localizations-recommended-way\}

ローカライゼーションについて検討している場合、すでにプロジェクト内でローカライズされた文字列ファイルを扱っている可能性が高いです。その場合、各ローカライゼーションに対応するファイルに、意図した Adapty のロケールコードをキーと値のペアで設定しておくことをお勧めします。そして、SDK を呼び出す際にそのキーの値を取得します：

```kotlin showLineNumbers
// 1. Modify your strings.xml files

/*
strings.xml - Spanish
*/
<string name="adapty_paywalls_locale">es</string>

/*
strings.xml - Portuguese (Brazil)
*/
<string name="adapty_paywalls_locale">pt-br</string>

// 2. Extract and use the locale code

val localeCode = context.getString(R.string.adapty_paywalls_locale)
// pass locale code to AdaptyUI.getViewConfiguration or Adapty.getPaywall method
```

この方法により、アプリのすべてのユーザーに対してどのローカライゼーションが取得されるかを完全にコントロールできます。

## ローカライゼーションの実装：別の方法 \{#implementing-localizations-the-other-way\}

すべてのローカライゼーションに対してロケールコードを明示的に定義しなくても、似た結果（ただし完全に同一ではありません）を得ることができます。それは、プラットフォームが提供する他のオブジェクトからロケールコードを抽出する方法です：

```kotlin showLineNumbers
val locale = if (Build.VERSION.SDK_INT >= Build.VERSION_CODES.N)
    context.resources.configuration.locales[0]
else
    context.resources.configuration.locale

val localeCode = locale.toLanguageTag()
// pass locale code to AdaptyUI.getViewConfiguration or Adapty.getPaywall method
```

この方法は、Adaptyのサーバーが実際に何を受け取るかを予測しにくいため、推奨しません。

それでもこの方法を使用する場合は、関連するすべてのユースケースをカバーしていることを確認してください。
